## 统一基线与读表方法

### 主基线固定什么，Env 方案增加什么

从现在起，Env 调度实验统一使用以下主基线。它仍可经过 EnvRouter 管理资源，基线与改进的区别在调度策略，不等同于关闭 Router。

| 项目 | 统一主基线：静态环境池＋episode |
|---|---|
| 源码 | 与实验组使用同一次冻结实现，记录提交和补丁，不默认使用历史旧分支 |
| 卡的分工 | 开始前划定训练、推理、环境 GPU，运行期间不因排队而改变角色 |
| 环境放置 | 按固定卡序检查容量，一张卡可接纳则放入，满了尝试下一张，全部不满足则等待 |
| 持卡时间 | 会话获准进入环境后，一直保留 GPU 预算，直到会话结束并清理 |
| 等模型回复时 | 继续保留 GPU 预算，不能让等待者复用这份预约 |
| 推理卡 | 不供环境共享，不为环境主动休眠 vLLM，也不自动调整分卡 |
| 公平对照 | 固定总 GPU、模型、数据、任务、共同安全预算和时间上限，额外改变的条件单列 |

下面用同一个 A、B 例子看清“留着 GPU”和“正在计算”的区别。这里假设只剩一个可用名额，A 中间暂停，B 在暂停开始时到达。

[![固定环境池的设备角色，以及同一A、B任务在episode与command下的持卡时间线](partition-episode-baseline.png)](partition-episode-baseline.svg)

图中 episode 把 A 暂停时的名额也留住，B 到第 70 秒才能开始。command 允许 B 利用 A 的暂停期，A 回来时 B 已完成，因此整批第 70 秒结束。**这些时间是教学假设，省略交接成本，用于解释持卡方式，不是本项目的实测收益。** 真实命令可能持续更久，也可能因共享而变慢，后续实验正是在检查这些代价。

本文将不同策略明确分开，避免都简称“动态组”：

| 本文名称 | 相对主基线改变了什么 | 在本文中的作用 |
|---|---|---|
| **Episode 静态池** | 无 | 以后统一的主基线，实测见实验九 |
| **Command 静态池** | 每条 GPU 命令物理归还后释放预算，下一条重新准入 | 历史对照组，也是区分持卡粒度收益的消融组 |
| **Command＋常驻余量共享** | 独立环境卡都不满足时，再尝试显式绑定的推理卡余量 | vLLM 保留在原卡，环境与其共用安全余量 |
| **Command＋整卡借用＋共享** | 推理持续低负载时，排空一个副本，再使其休眠并借出卡 | 保留至少一个副本服务，之后可恢复，本次完整训练未触发恢复 |

“消融”就是只加入一部分能力来区分收益来自哪里。例如 command 静态池对比主基线，主要检验逐命令归还是否有价值。共享组再对比 command 静态池，才检验使用推理卡余量的增量。历史 episode 补测还改变了会话选卡顺序，不能当作严格只改一个变量的证据。

下面这张已有设备图补充后两种策略的差别。图中的四张卡不含另外固定的两张训练卡。

[![常驻余量共享、休眠后借整卡、启动即静态分卡的区别](partition-strategy-distinction.png)](partition-strategy-distinction.svg)

常驻共享没有把两个 vLLM 搬到一张卡。整卡借用也只是先让一个副本不再接新请求，等原请求结束后休眠，把后续请求交给剩余副本。**这些实验没有迁移正在生成的请求及其 KV cache，也没有借用两张训练卡。** KV cache 是推理过程中保存已处理 token 的注意力状态，活动请求迁移还需要搬走它和请求进度。

### 训练步数、任务数量与计时边界

完整训练使用一个有界 PostTrain 任务：策略模型先选择学习率，环境执行模型适配，再问策略模型如何检查，环境独立评分，最后让策略模型总结。执行顺序为：

**请求①选学习率 → GPU 命令①适配 → 请求②解释检查 → GPU 命令②评分 → 请求③总结 → 轨迹与奖励返回。**

策略模型为 Qwen2.5-3B-Instruct，环境适配 Qwen3-4B-Base 的最终归一化参数。评分是四条私有 GSM8K 样本上答案的似然分数，由平均负对数似然换算，和执行快慢无关。命令集合受控，真实生成可改变学习率和 token 数，因此这不是完整 Science 自由工具调用 benchmark，也不是 GSM8K 准确率实验。

一个题目组对同一个任务采样两条轨迹，一个训练 step 消费若干完整题目组。比例是**本任务特有**的：

| 实验工作量，每个对照组分别计数 | PSRL 策略训练 step | 每步题目组 | 累计完整轨迹 | 累计 GPU 命令 | 累计模型请求 | 工具内部更新 |
|---|---:|---:|---:|---:|---:|---:|
| 实验三 | 6 | 4 | 6×4×2＝48 | 48×2＝96 | 48×3＝144 | 26880 |
| 实验四至七的完整训练组 | 4 | 6 | 4×6×2＝48 | 48×2＝96 | 48×3＝144 | 25088 |
| 实验八，以及实验九的计划量 | 2 | 6 | 2×6×2＝24 | 24×2＝48 | 24×3＝72 | 12544 |

这是累计工作量，48 条轨迹并不意味着同时运行 48 条命令。工具内部几百次参数更新，也不能和 PSRL 对策略模型的 step 相加。六步与四步虽然轨迹数相同，批次和长任务比例不同，不能直接按训练秒数比较。

PSRL 可以一边收集后续轨迹，一边训练前一批。这里允许滞后一个策略版本，最多有两批在途。某个 episode 做完是把结果交给队列，**不表示立刻单独训练它**。训练器拿到满足批次和版本条件的题目组后才训练，再把新权重发给推理副本。SMG 是模型请求网关，负责把请求送到可用副本。它不是环境 GPU 的调度器。EnvRouter 负责后者。

全文区分两种时间：**训练时间**是训练器各 step 时间的累计，包含等待轨迹、参数计算等阶段；**完整作业时间**是该组启动到物理资源清理完成，还包括初始化和尾部成本。组件实验没有训练器，只报告初始化后的整批任务时间，不能当作完整训练收益。P95 表示 95% 的已统计请求延迟不超过该值。

## 实验一：低推理负载时借出整张卡

**问题：环境池已满，推理还有空闲副本，减少一个推理副本能否让同一批任务更早完成？** 这轮先验证机制，不经过 SMG 和策略优化器。

两组使用四张 H20，初始两张环境卡、两张推理卡，无 MPS。每张环境卡最多两条命令，每条预约 16 GiB，控制器环境卡预算 64 GiB。静态组逐卡检查，全部不满足就等待。借卡组保留同样限制，环境积压时最多休眠一个已排空的推理副本，至少保留另一个服务。

每组完成六份相同 PostTrain 工作负载，共六条适配命令、六条评分命令。每份适配用两个公开样本交替执行 448 次更新，评分使用四个私有样本。推理另有 12 个固定输出 512 token 的请求，分三批，每批四个，相隔十秒。每副本最多四个在途请求，这是实验配置，不是硬件饱和点。

| 初始化后同一批任务的指标 | Command 静态池 | 排空休眠后借卡 |
|---|---:|---:|
| 整批完成，包含恢复推理副本 | 344.32 秒 | 271.04 秒 |
| 环境命令平均排队 | 39.47 秒 | 1.66 秒 |
| 模型请求平均延迟 | 6.420 秒 | 6.337 秒 |
| 模型请求最大延迟 | 6.491 秒 | 6.546 秒 |
| 在借出卡上完成的环境命令 | 0 | 4 |
| 休眠和唤醒调用累计，不含等命令归还 | 0 | 3.47 秒 |

静态组前四条适配先运行，第五、第六条各等约 136 秒。借卡组把一个副本排空并休眠，卡上占用从约 24.3 GiB 降到 0.60 GiB，让这两条命令约等 8.6 秒就能开始。请求实际路由从两副本各六条，变为两条与十条，剩余副本接住了本轮低负载。

整批提前 21.28%，来自少排队和准备阶段重叠，单条命令没有普遍加速。共享文件读取、CPU 或主存可能竞争，评分准备变长，主要评分计算仍只有约 0.5～0.8 秒。本次发生两次借还，全部代价已计入整批时间。

两组适配权重哈希、逐请求 token 和评分一致，评分均为 0.4371073645。**它证明低负载下借还可行，不能证明休眠优于直接使用常驻余量。** 推理请求在约第 26 秒已经结束，没有覆盖后期突发。

两副本共同初始化 321.68 秒，只做一次，不在上表内。修复后整个研究进程共 969.57 秒，不能把 21.28% 称为两次独立冷启动的完整作业收益。首次运行因成功命令 stderr 为 None 导致日志写入失败，550 秒失败成本另存，未纳入成绩。修复后两组各一次，17 项 CPU 回归通过，最终容器和 GPU 均释放。

证据：[本轮摘要](elastic-partition-evidence.json)、[完整请求与借还记录](../env-service-verification/results/elastic-partition-20261118-02/run/evidence.json)、[首次失败](../env-service-verification/results/elastic-partition-20261118-01/run/evidence.json)。下一轮增加真实任务反馈和推理突发，检验恢复代价。

## 实验二：借卡期间突然来了推理请求

**问题：B 环境命令占着借来的卡时，推理 A 再次需要这张卡，会等多久？常驻共享是否更合适？** 三组分别为 command 静态池、常驻共享、排空休眠借卡，均先尝试独立环境卡。

每组五份任务，按三次模型请求、两条 GPU 命令的顺序完成。四份适配 448 次，一份 1792 次。模型请求固定生成 512 token，并在第 55 秒同时增加 64 个突发请求。因此每组共 10 条 GPU 命令、15＋64＝79 次请求，没有 PSRL 策略训练 step。

先在单副本测并发 1、2、4、8、16，整批生成约 6.1 秒，吞吐从 83.4 增至 1317.9 token/s。16 已是软件 `max_num_seqs` 上限，曲线仍接近线性，因此只把 16 当共同已测请求上限，没有声称找到 SM 饱和点。

| 同轮指标 | Command 静态池 | 常驻余量共享 | 休眠后借卡 |
|---|---:|---:|---:|
| 整批完成并恢复模型 | 343.79 秒 | 292.79 秒 | 291.81 秒 |
| 环境平均排队 | 23.67 秒 | 约 0 秒 | 0.64 秒 |
| 突发请求平均延迟 | 9.65 秒 | 9.97 秒 | 19.86 秒 |
| 突发请求 P95 | 13.09 秒 | 13.84 秒 | 31.39 秒 |

| 禁止新环境准入后，等到卡恢复 | 无 | 无 | 两次 130.67、107.42 秒 |

共享和休眠整批只差约一秒，单次测量不足以支持休眠更优。休眠让剩余副本承担突发，主要多出的是请求排队。几次休眠唤醒调用合计只有 5.16 秒，但把卡真正取回要等约 131 或 107 秒，**控制调用很快不意味着借出去能很快收回。** 保留的副本仍在处理请求，所以也不能给每条请求都加上 131 秒。

阶段记录还发现：这次突发碰到的是环境模型准备期，共享卡上的适配主要计算约在第 106.9～128.3 秒，评分计算约在第 238.2～238.7 秒，均没有与已准入推理请求的服务区间重叠。它覆盖了显存共存与容量减少，尚不能说明持续的 SM 计算竞争是否可接受。

两组按任务对齐的产物和评分一致。初始化共 672.39 秒，整场研究含初始化清理 1641.12 秒，与各组表内时间分开。18 项回归通过，四卡和容器释放。预算为单组 540 秒、外层 2160 秒、一次尝试。

## 实验三：把余量共享接入六步真实训练

### 实际对照：只增加推理卡余量，不休眠副本

**问题：环境少排队的收益，进入真实采样、策略训练和权重发布后，还能保留多少？** 两组总预算均为六张 GPU，固定两张训练、两张推理、两张环境。每张独立环境卡最多两条活动命令，共享组每张推理卡最多两条，额外保留经检查的 8 GiB 模型余量。每条环境命令申报 16 GiB，vLLM 显存比例 0.45，每副本请求上限 16，direct 执行、不开 MPS。

换卡发生在两条独立命令之间，容器、文件、CPU 和主存留在原节点，下一条进程获得另一张 GPU。运行中的 CUDA 进程和 KV 状态没有迁移。普通命令退出后，下一条仍要启动进程、加载模型，episode 保留预算也不会自动保住已经退出的模型。

### 为什么一次权重同步会等约五十秒

采样产生一个批次后，训练器开始更新并发布新权重。协调器先暂停 SMG 分派，再让推理副本进入同步。如果某张推理卡正被环境命令占用，原协议要等它物理归还才能继续。因此一个环境命令即使已经结束主要计算，准备和清理阶段也可能延后下一轮推理。

第 3 步两副本分别等约 50.109、50.103 秒。它们并行等待，整段约五十秒，不能加成一百秒。阻塞它们的评分命令完整调用 80.87 秒，主要计算只有 0.54 秒，且在获准后 47.71 秒才开始。之后一次同步等待达到 125.43 秒，另一副本早约 23 秒准备好仍得等全局网关恢复。

这解释了“整批训练更快，但部分模型请求更慢”可以同时成立：环境更快提供足够轨迹开训，而权重发布时的共享归还又拉长了某些请求等待。后续实验六专门检验能否缩短这类同步等待。

<summary>补充：Roofline 在这一轮做了什么，预测器验证到哪里</summary>

Roofline 用“算得多快”和“数据搬得多快”给执行时间提供参考边界。在空闲 H20 上，BF16 矩阵乘测得约 138.16 TFLOP/s，大数组加法测得约 3.55 TB/s，两者相除约 38.90 FLOP/byte。这是两种微基准的比值，不是所有算子的固定效率，也不能直接推导环境最优并发。

加入 KV 读取量后，Qwen2.5-3B 的近似平衡候选随上下文改变：128、384、2048、2304 token 分别约为 40、42、63、68 个请求。候选仅用于优先测哪些点，显存、注意力和软件开销仍会限制速度。8192 token 的理论示例在简化公式下没有有限平衡点，且超过本引擎 2560 上下文上限，没有实测。

为贴近实际，使用“固定成本＋计算/带宽参考成本的校正＋KV 读取参考成本的校正”这三个非负参数拟合平均每个解码 token 的时间。用已有 vLLM 曲线七个配置拟合，另外六个完整配置留出，不重新运行推理。留出平均相对绝对误差为 2.20%、最大 8.15%，直接套理想参考时间误差为 80.07%。只用短输入预测长输入，误差变为 11.60%。

## 实验六：权重同步能否提前完成

### 先测拷贝，再测真实权重同步

**问题：环境命令尚未归还时，vLLM 能否先接收新权重，减少网关暂停？** 这里研究的是同步等待，和增加环境卡数量是不同问题。

先做单卡 CUDA 微实验：一个进程运行 8192 阶 FP16 矩阵乘，持续约 4.0269 秒，另一进程晚约 0.1001 秒开始，将 32 份 64 MiB 固定主存数据复制到 GPU，共 2 GiB，约 0.0423 秒完成并通过内容检查。没有 MPS。它证明该条件下拷贝可与另一进程计算重叠，没有接入 vLLM 或训练，不能单独证明完整训练提速。证据：[微实验](../env-service-verification/results/sync-followup-20261119/cuda-copy.json)、[脚本](../env-service-verification/scripts/weight_copy_overlap.py)。

随后在冻结实验路径中允许常驻共享卡上仍有环境租约时，提前执行 NIXL 权重拉取。NIXL 是这里传输新参数的通信组件。同步期间冻结新的共享准入，原命令继续，休眠和唤醒仍须等物理归还。这项门禁改动不等于可以随意覆盖正在被推理读取的权重，也不能绕过整卡角色转换。

### 四步结果：控制等待减少，训练收益尚未证明

两组都为 2＋2 常驻共享、独立卡上限四、共享上限二、模型额外余量 16 GiB。对照只改变是否允许同步提前。余量已不同于实验四的 8 GiB，所以不能把跨轮全部变化归给同步。

| 指标 | 同步等待环境归还 | 允许同步提前 |
|---|---:|---:|
| 四步训练累计 | 969.96 秒 | 1014.76 秒 |
| 初始化 | 780.96 秒 | 669.98 秒 |
| 启动至物理清理 | 1763.41 秒 | 1693.75 秒 |
| 模型请求 P95 | 35.34 秒 | 17.34 秒 |
| 最长模型控制等待 | 32.0094 秒 | 约 0.000018 秒 |

[![同步提前的结果：分别看初始化、训练和模型请求尾延迟](sync-overlap-results.png)](sync-overlap-results.svg)

观察上控制等待几乎消失，训练却多 4.62%，完整作业少 3.95% 主要来自初始化差异。允许同步的那组还观察到一个归属未核实的 GPU 进程，占用约 25～28 GiB，涉及六卡的一段窗口。这不是预设压力注入，也没有证据确认它属于谁。因此不能把训练变慢归因于同步改动，也不能据此声称改动加速训练。

[![真实权重拉取在环境租约归还前完成，但发生于其准备阶段](sync-overlap-timeline.png)](sync-overlap-timeline.svg)

三次真实权重拉取约 0.262 秒，在环境归还前约 21.23／60.86／59.79 秒完成。不过阶段审计说明它们发生在准备期，环境主要计算并未同时发生。由于当时没有联合采集两种时钟偏移，阶段推断保留约 9.33 秒的不确定区间，不能伪造精确计算重叠。

**结论是“可以越过尚未归还的环境租约完成真实同步”，不是“权重同步与环境密集计算并行且无损”。** 工具适配参数相同条件下哈希和评分一致，但没有逐位核对策略权重内容，部分同步附近策略梯度为零，验证边界保留。

证据：[两组完整分析](../env-service-verification/results/sync-overlap-20261122/analysis.json)、[重叠阶段与产物审计](../env-service-verification/results/sync-overlap-20261122/mechanism-audit.json)、[完成与物理释放](../env-service-verification/results/sync-overlap-20261122/status.json)。下一轮在共同冻结同步实现上比较静态和共享，避免把同步差异混入共享收益。

## 实验七：在三环境卡上比较共享和增加并发

### 同窗口四步：共享略胜原静态，增加静态并发更快

**问题：选择更合适的 3＋1 后，共享还有多少增量？如果静态每卡再多放一条呢？** 三组固定两训练、三环境、一推理，同任务、同冻结同步原型，均为 command。共享组模型余量为 16 GiB，共享上限二。静态组不允许环境进入推理卡。

| 同轮方案 | 独立卡命令上限 | 四步训练累计 | 启动至物理清理 |
|---|---:|---:|---:|
| Command 静态池 | 每卡 4 条 | 1036.81 秒 | 1782.38 秒 |
| Command＋常驻共享 | 每卡 4 条 | 965.42 秒 | 1777.98 秒 |
| Command 静态池，提高并发 | 每卡 5 条 | **898.98 秒** | **1633.11 秒** |

[![相同3＋1布局下，静态上限四与共享的训练及完整作业计时](three-env-resident-pair.png)](three-env-resident-pair.svg)

共享比同上限静态少 `1036.81−965.42＝71.39` 秒，占原训练时间 6.89%。共享初始化多 64.20 秒，完整作业仅少 4.40 秒，约 0.25%。推理卡实际执行九条环境命令，最大同时只有一条，共享上限二不能写成达到二并发。

再把静态独立卡上限提高到五，训练变为 898.98 秒，比原静态少 13.29%，比共享少 66.44 秒。换成以较快的静态上限五为分母，共享慢 `66.44÷898.98≈7.39%`。**现有证据不支持“共享已超过调优的静态池”。** 上限五仍受 90 GiB 卡预算、每条 16 GiB 预约及实时占用限制，名额不是硬保证。

三组均完成四步、48 轨迹、96 命令、144 请求、25088 次工具更新且物理释放。前三列数字是顺序单次观察，模型动作和生成 token 不同，没有置信区间。静态与共享生成 token 为 47829／47666，相同工具更新次数和学习率条件下产物哈希一致。权重拉取与活动租约重叠三次，仍在环境准备期，不能扩大为主要计算并行已验证。

整卡组训练少 `569.87−512.58≈57.29` 秒，即 10.05%，完整作业却多约 173 秒，即 12.98%。常驻共享训练比静态慢 7.22%。所以本轮支持整卡策略存在训练阶段潜力，**没有证明完整作业比 command 静态更快**。Episode 主基线另见实验九的成功补测，不能混淆参照对象。

机制验收确实观察到：副本 0 排空并休眠，GPU2 借给环境，最多同时有五条环境命令。另一个副本继续服务，SMG 观察到策略版本 0、1，保留副本的常驻余量也被使用。模型请求 P95 从静态的 12.30 秒变为整卡组 14.61 秒。推理负载未回升，没有触发恢复，因此不声称完整训练借还往返已验证。

三组两步策略梯度均为零，原因是每个题目组内奖励相同。它们证明真实采样、训练调用和版本通路完成，没有证明这两步改变了策略权重或改善学习效果。三组生成 token 为 24222／24162／24283，动作也可能不同。异步预取使静态两步分别约 546.80 秒和 23.06 秒，只看第二步会误读吞吐，应比较累计。

### 初始化多约233秒，发生在什么位置

近期不同启动失败的阶段、11月19日48个worker预启动阻塞、11月23日三次注册超时及11月24日依赖导入栈，已集中到[Ray启动分诊](../../psrl/psrl-run-guide/03-启动排障_单机与多机故障复盘.md#近期env实验ray启动失败与导入阻塞)。本节继续维护该次实验的时间对账，不把所有初始化差异算成同一根因。

额外初始化不能全部归给整卡策略。成功的训练主控进程启动前，静态组用了 169.93 秒、整卡组 342.45 秒，差 172.52 秒，**此时 EnvRouter 和整卡控制器尚未建立**。

[![两组初始化里程碑，以及三次Ray进程注册超时的位置](live-partition-startup.png)](live-partition-startup.svg)

Ray 是启动训练和推理进程的运行底座，TaskRunner 是继续创建各组件的主控进程。整卡组先启动三个 worker，各约三十秒后因未及时注册被放弃，第四个才成为成功主控。日志能确认约九十秒花在失败尝试上，但尚未查清加载慢或挂起的根因，也不能承诺修复会恰好节省九十秒。首段其余约八十二秒，以及后续组件初始化差异，还缺细粒度证据。

可以用总账复算：初始化增加 `978.98−746.21≈232.77` 秒，训练减少约 57.29 秒，其余与清理减少约 2.48 秒，合计多 `232.77−57.29−2.48＝173.00` 秒。尾项是总耗时减去前两项的剩余量，包含计时边界差异，不是独立测得的纯容器清理成本。

2026-11-24 补测增加了启动分段和本任务进程栈采样：Ray 建立约 8.14 秒，依赖导入预检约 99.26 秒，配置预检约 41.65 秒。一次配置预检采样看到 Transformers 递归扫描模型包目录；一次 Ray worker 采样看到它在加载 requests 的字符编码依赖时等待文件元数据查询。这支持“共享文件系统上的 Python 包加载是启动成本之一”，但尚未复现历史三次注册失败的完整因果链，不能把它们全部归为同一个原因。

维护中的代码现在做了三件事：记录资源预检、Ray 建立、依赖预检、配置预检和 driver 启动的边界；把 `main_ppo` 顶层的策略、模型和训练辅助依赖延后到真正执行训练时导入，使 `--cfg job` 配置检查跳过这些工作；把本实验独立 Ray 的 worker 注册期限从 30 秒改为 90 秒，避免正常但较慢的启动过早被放弃。后一个改动提高容忍度，遇到真正挂死的进程也会等得更久，因此仍保留 1200 秒总初始化期限，不改共享 Ray 集群。

CPU 对照使用旧入口与新入口打印同一份真实配置，分别用 **96.59 秒和 37.72 秒**，解析后的配置完全一致，单次少 58.87 秒。Hydra 查找 veRL 配置时仍会间接加载部分依赖（包括 torch、tokenizer 和 TransferQueue），这里没有声称完全去掉所有重库。该结果观察到配置预检成本下降，顺序测量仍可能受文件缓存影响，不等于已证明完整训练初始化能稳定缩短同样多的时间。

### 借卡本身也要等，但属于训练阶段

整卡借用在首条轨迹开始后约第 313.81 秒才发起，约 71.08 秒后完成，其中模型控制门禁等待约 67.68 秒。这些代价已经进入 512.58 秒训练时间，不能再加到初始化，也不等于所有 GPU 都暂停了 71 秒。

借卡决定时，GPU2 上已有一条评分命令，约 67.69 秒后才归还；GPU3 上另一条评分也约 67.72 秒后才结束，因此简单改借另一副本也不会明显变快。当前进入排空状态后已经禁止新的共享命令，旧命令自然完成。低负载观察期是否提前保留一张候选卡是待研究策略，本轮没有抢占或取消运行中命令。

“提前准备”具体是：低负载观察刚开始时，先选一张候选卡，暂缓往它追加新环境命令，旧命令继续、vLLM 继续服务；观察期结束且条件仍成立，再暂停该副本的新模型请求、排空、休眠借卡。若负载回升则取消候选状态。这样有机会避免观察期末刚进来的长命令挡住整卡切换，也可能让本可立即运行的命令白等，因此不能默认一定更快。带同一组 B、C、D 命令的完整时间线和反例见[提前准备借卡具体改变哪一步](../knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md#提前准备借卡具体改变哪一步)。本次只解释该提案，没有把它接入控制器或计入收益。用户随后提出更直接的[模型排空与环境命令并行](../knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md#借卡时能否一边排空模型请求一边运行环境命令)：区分模型服务退场与环境命令归还，在已有余量内继续准入，确认模型释放后才扩大预算；此路径已在工作区实现为默认关闭的可选行为，新的配对验证见下节。

证据：[冻结协议](../env-service-verification/results/live-partition-20261123/protocol.json)、[完整分析](../env-service-verification/results/live-partition-20261123/analysis.json)、[借卡机制验收](../env-service-verification/results/live-partition-20261123/mechanism-verdict.json)、[启动和门禁审计](../env-service-verification/results/live-partition-20261123/startup-audit.json)、[最终状态](../env-service-verification/results/live-partition-20261123/status.json)。静态组完成后外层监督器曾错误导入共享 PSRL 而停止，核验后只补续未启动的两组，原始记录保存在[恢复审计](../env-service-verification/results/live-partition-20261123/recovery/audit.json)。

本轮预算为每组 2700 秒、初始化 1200 秒、一次尝试。60 项相关 CPU 回归通过，张量回读指定冻结实验的隔离依赖后三项通过。三组均已确认物理释放。源码已接入整卡控制正式路径，默认关闭，恢复保护有 CPU 覆盖，但完整训练实机恢复仍缺证据。

## 实验九：补测统一的episode静态基线

### 怎么补测，为什么它和历史command组不同

**问题：按现在确定的 episode 主基线，同样两步任务会表现怎样？** 复制实验八静态组的冻结代码和十二行数据，只使用两张独立环境卡，会话预约 16 GiB、每卡预算 90 GiB，最多五个同类预约，仍检查实际占用和主机资源。

Episode 在第一次模型回复后申请环境，获准后预算贯穿容器建立、适配、后续模型回复、评分、总结，直到清理才释放。首次模型请求发生在环境创建之前，与历史 command 组沿用同一边界。静态池不共享推理卡，也不收缩副本。

该补测还按指定协议把同一层级的会话选卡改成 first-fit，即先填当前可放的卡，再看下一张。补丁只有 runner、agent、账本三份，另增加持有模式记录，快照哈希执行期间未变。因此它符合本次主基线的放置协议，但**与旧 command 组不只改变持卡粒度**，全部差异不能仅归给 command。

### 1200秒补测：相同工作量已完成

本任务一个 **PSRL 训练 step** 消费 6 个题目组，每组采样 2 条完整轨迹。一条轨迹包含模型提出适配动作、环境 GPU 适配、模型提出检查动作、环境 GPU 评分、模型总结，即 2 条 GPU 命令和 3 次模型请求。因此两步累计是 `2×6×2＝24` 条轨迹、`24×2＝48` 条 GPU 命令、`24×3＝72` 次模型请求。这是累计工作量，不是同时运行 24 个 GPU 进程；环境适配程序内部的 12544 次参数更新也不是 PSRL 的 12544 个训练 step。

## 目前相对主基线能下什么结论

回到统一的 **episode 静态环境池**，当前结论要把能力、完成性和速度分开：

| 要回答的事 | 当前已有证据 | 结论到哪里 |
|---|---|---|
| 能否把环境 GPU 在命令之间归还 | Command 路径有完整真实训练；episode 补测确认全程保留 | 能，仍保留容器、文件及 CPU/主存会话资源 |
| 是否能让这份有界任务更容易完成 | 同 720 秒轨迹上限，Command 静态池完成，Episode 完成了 20／24 轨迹 | 本轮观察受到选卡顺序和运行波动影响 |
| 相对主基线能快多少 | Episode、command 静态和多组整卡方案均完成相同两步 | Command 静态用时少 14.77%。完成重叠交接的补跑少 38.39%，含启动变化。不同次运行的绝对耗时见[实验总览](01-实验总览_调度收益与证据范围.md#完整两步主基线对照) |

| 是否已胜过调优静态池 | 3＋1 command 静态上限五比上限四共享更快 | 尚未证明，不能把保守静态配置当最优参考 |
| 整卡动态分配是否跑通 | 主动查询后的等待组和重叠组都借出 GPU2，旧命令仍在时重叠组即可完成交接 | 整卡交接 98.11→5.19 秒，已观察到新环境命令进入，重叠补跑实现 3.62 秒交接并完整完成两步 |
| 预测器是否能自动选最优并发 | 解码配置留出平均误差 2.20%，整体训练预测却低估约 27%～29% | 离线筛选有用，在线联合控制器尚未接入 |

完整 episode 工作量现已补齐，接下来的证据缺口是共同冻结放置协议、共同期限和启动修复之后的同窗口配对，而不是继续延长这一组任务。再逐层加入共享、整卡借用，才能分离持卡粒度、额外容量和角色调整的贡献。本次有界补测已结束，不再为补正文追加训练。

性能研究仍有空间，但更有价值的目标是**让依赖同一训练批次的工作更早完成，同时少阻塞权重发布和后续推理**。前面已测到的现象是：未来批次适配能挡住当前批次评分，长时间的环境准备也能阻塞很短的权重传输。两者都说明只按显存和命令数放置还不够。不过这些是下一步待验证方向，本报告没有把它们记成已实现收益。

机制细节回到[共享与容量主文档](../knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md)，整体调用关系看[Env 架构现状](../knowledge/01-架构与执行/01-Env架构_现状与完整执行流程.md)，批次和版本机制看[PSRL 异步训推协作](../../psrl/推理与训练/03-训推协作_异步流水线与版本协调.md)。这些文档解释现状，历史实验始终以本轮冻结证据为准。
