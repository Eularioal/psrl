# Env 实现、实测收益与后续规划

> **核心结论，截至 2026-10-27**：Env 已具备 science / Harbor 路径的资源准入、跨任务 GPU 命令排队、统一作业执行和归属清理能力。在一次人工高显存压力的真实 PSRL science 三步训练对照中，OOM 尝试从 18 次降到 0 次，训练步骤累计耗时减少 **54.24%**，含初始化和清理的总时间减少 **27.59%**。收益来自减少失败重试，不是 CUDA 计算本身加速。
>
> 低压力下尚未证明稳定提速。可选 eBPF 进程归属后端已通过双 Docker 容器真实 CUDA 验证，新的故障恢复、逐卡预算和辅助容器限制已通过 CPU 回归，但尚未合并成一版完成原生 science GPU 任务的端到端验收。下一阶段优先完成这一闭环，再做通用接入、调度优化和自动策略选择。

本文是可单独转发的项目状态说明。背景、架构图、实验条件、结果数据和后续规划均直接写在本文中，不需要其他文件或图片。状态截止到 2026-10-27 本次汇总核验的范围，其他并行开发中的改动不自动纳入。性能数字来自明确版本的实验，不能当作全部新改动的性能结论。最新实现包含尚未提交的开发内容，**实现与验证完成不等于已经发布部署**。

## 项目定位与完整执行链

PSRL 训练需要不断收集模型做题的过程：模型生成操作，环境执行操作，评分器检查结果，训练器使用这些轨迹更新模型。一次从开始到评分的完整尝试叫 **episode**，采集到的一条交互轨迹称为 **rollout**。同一道题采样四条 rollout，通常对应四个独立的环境会话，不等于在同一个容器里同时执行四条 GPU 命令。

Env 要解决的是：任务增多以后，谁能在哪台机器启动、允许占用多少资源、什么时候可以交给下一条任务，以及任务异常后如何确认资源已经收回。否则，即使模型正常生成，环境显存不足或资源残留也会拖慢训练数据供给。

以下为当前 science / Harbor 主路径。Harbor 是实际组织任务环境、命令执行和评分的运行器。图中的分支有各自的接入和验收边界，不能理解成任意配置都能同时使用。

```text
[1] PSRL Trainer / AgentLoopManager
    读取任务需求，按组内 rollout 数选择有容量的健康 worker
                       ↓
[2] science runner / EnvServiceClient
    请求一次任务会话的资源租约
                       ↓
[3] EnvRouter + Ledger 资源账本
    unit 节点资源池：CPU、主存、会话槽位、GPU 预算
    决策：允许 / 等待 / 拒绝，异常资源先确认清理
                       ↓
[4] Harbor + ManagedDockerEnvironment
    启动并标记主容器、评分环境和 sidecar 辅助容器
                       ↓
[5] 统一 GPU 作业后端
    episode：会话期间保留 GPU 预算
    command：每条显式 GPU 命令申请，容量不足排队
                       ↓
[6] 节点服务：设备授权 → Docker 执行 CUDA → 任务遥测
    身份来自 procfs 或可选 eBPF，GPU 数据来自 NVML
                       ↓
[7] 命令归还确认 → 其他任务获准
    原容器可以继续 CPU 工作或等待模型
    评分、会话结束 → 按归属清理全部相关资源

独立分支 [8]：vLLM 推理副本 sleep → 容器借卡
              → 确认归还 → vLLM wake
              当前不与 command 配额模式组合
```

图例：各部分的职责、输入和输出。

| 编号 | 职责与数据流 |
|---|---|
| 1 | 任务派发器读取任务需求和同题采样条数，选择执行进程所在的节点。这一步是放置建议，还不是最终资源授权 |
| 2 | science 运行器将任务的 CPU、主存和 GPU 需求提交给资源服务，请求一次会话的资源租约 |
| 3 | EnvRouter 检查节点健康和遗留资源清理状态，账本核对容量，返回允许、等待或拒绝 |
| 4 | Harbor 创建执行与评分环境。容器附带所属租约标签，CPU 和主存限制覆盖主服务与辅助服务 |
| 5 | 统一后端管理执行、等待、超时和取消。命令模式还需在每次 GPU 工作前申请阶段预算 |
| 6 | 节点服务核对容器归属并授予设备权限，命令实际执行，同时记录属于本任务的 GPU 活动 |
| 7 | 命令结束后确认 GPU 物理资源归还，释放阶段预算。整个会话结束后清理容器并释放其余资源 |
| 8 | 独立借卡分支协调模型休眠、容器使用、确认归还、模型唤醒，不能跳过任何交接确认 |

**unit** 是配置中声明的本节点资源池。**lease，租约**是一次任务获准使用资源的凭证。两者都是调度状态，租约归零本身不能证明真实进程或显存已经消失。**NVML** 是 NVIDIA 提供的 GPU 管理查询接口，用于读取显存和 GPU 进程数据。

**CUDA** 是程序使用 NVIDIA GPU 执行计算的接口与运行环境。**vLLM** 是模型推理服务，负责生成下一步操作。**verifier** 是任务评分器，**sidecar** 是伴随主容器运行的辅助容器，例如提供网络控制的服务。它们虽然不直接负责模型做题，也会消耗资源，因此不能在预算和清理中漏掉。

这里的“统一 GPU 作业后端”只指 episode 与 command 共用执行、等待、取消和收尾接口，不代表已有 EnvWorker 路径与 Harbor 路径已经全面统一。

## 当前实现与验证程度

“已实现”表示能在当前源码中找到对应逻辑。“CPU 回归”验证控制逻辑，不代表已经经过真实 Docker、GPU 或分布式故障验收。各行证据可以有重叠，不能把测试数量相加当作独立验证规模。

| 能力 | 当前实现 | 已有证据与边界 |
|---|---|---|
| 会话资源准入与放置 | 按 unit 管理 CPU、主存、GPU 和会话槽位，派发考虑任务需求 | 已有真实 science / Docker / 训练运行。最新按整组需求和健康状态派发的修改，主要通过 CPU 回归 |
| 命令阶段 GPU 复用 | 不同容器的命令容量足够可重叠，容量不足排队。会话仍保留文件与主机资源 | 有真实容器并发和高压力训练证据。同容器当前仍串行 |
| episode / command 统一后端 | 两种持有范围共用执行、超时、等待、取消和收尾 | 已有组件验收。持有范围由启动配置选定，不会根据模型等待时间自动切换 |
| 显存预约记账 | 实测占用加尚未兑现的预约，可信归属用于避免重复计费 | CPU 反例及修复后高压力三步训练通过。预算不是显存硬隔离 |
| 启动与控制路径优化 | 节点异步预热，复用 NVML 连接，减少重复 Docker 查询，将同步准备移出事件循环 | 有固定 OFF 的低负载配对结果。短作业仍需计入服务初始化 |
| 生命周期与回收 | 作业状态、心跳、超时、按标签清理，归还确认前不释放不确定的 GPU 使用权 | 有真实容器清理证据。控制器重启重建和网络分区恢复尚未闭环 |
| 可信任务 GPU 归属 | procfs / eBPF 可选后端，按进程身份归属过滤 GPU 数据 | eBPF 已通过两个真实 CUDA 容器的独立记账和退出失效验证，尚未完成原生 science 严格评分验收 |
| 逐卡需求与容器集合预算 | 每张 GPU 单独检查。主容器、独立 verifier 和 sidecar 纳入 CPU / 主存预算与限制 | 新实现通过 CPU 控制逻辑及 Harbor 配置序列化回归，尚未完成真实多卡与全部容器限额验收 |
| 迁移暂停恢复与健康派发 | 迁移异常只释放自己的暂停持有者，故障节点停止新派发，恢复和重试有界 | 新实现通过 CPU 故障注入，尚未完成真实网关失联或节点故障实验 |
| vLLM 与容器同卡交接 | 显式绑定完整推理副本，sleep 后借出，确认归还后 wake | 已有两轮真实 Docker CUDA / vLLM 组件交接。未覆盖完整训练侧权重传输与路由 |

这些能力处于不同验收阶段。例如，逐卡预算已能拒绝“两张卡总量够、但一张卡放不下”的申请，辅助容器也已纳入预算，相关控制逻辑通过 CPU 回归。但这些新修改与 eBPF 后端并不属于下文三步训练使用的冻结代码，不能将下文提速归因于它们。

## Results：已经拿到的收益

**OFF 和 ON 的含义。** OFF 是固定历史版本的任务执行路径，ON 是启用 EnvRouter 的对应实验版本。下表 OFF 固定为提交 `0eeead861ffafed6bf31c962d259fd847775dcf9`，保持静态 GPU 映射与进程内 episode 信号量，没有添加整卡锁。信号量在这里用于限制单个进程允许同时运行的会话数量，它不是按整机显存动态准入的账本。

为使两组在相同环境运行，实验使用了必要的设备参数传递、Ray 节点地址、HTTP 调用和依赖兼容修复，并移除会影响其他任务的全局镜像清理。这些运行修复没有把 OFF 改成整卡串行，也没有给它加入 ON 的显存调度。当前代码仅关闭 Env Service 不能替代这个固定基线。

| 场景与版本 | 实测结果 | 可以支持的结论 |
|---|---|---|
| 高压力真实训练，2026-10-26。ON 为 `b52a82d` 加显存准入修复，每组 3 步、12 条接受轨迹 | 训练步骤累计 **1100.80 → 503.69 秒**，减少 **54.24%**。含初始化和清理 **1954.11 → 1415.01 秒**，减少 **27.59%**。OOM 尝试 **18 → 0** | 这组压力条件下，减少过量准入和失败补采带来了可观的完成时间收益 |
| 低压力真实训练，2026-10-26。ON 为 `b52a82d`，尚未加入上述显存准入修复，每组 1 步、4 条接受轨迹 | 单步 **141.47 → 145.98 秒**，ON 多约 **3.19%**。采样等待 **115.11 → 115.28 秒**。双方四路成功 CUDA 分配并发，无 OOM | 低压力下可以并行，未看到稳定加速。单步差异主要在更新阶段，不能全算 Router 开销，也不能替代修复后低压力验收 |
| 低负载容器组件配对，2026-10-20。ON 为 `37a06ea` 加同步准备优化，两对 OFF/ON | 工作阶段合计 **171.68 → 160.84 秒**，减少 **6.31%**。含初始化和驱动收尾 **213.96 → 217.15 秒**，增加 **1.49%** | 控制开销已接近 OFF，但两对差异方向不同，不能宣称低负载稳定提速。这不是完整训练 |

**高压力三步训练的完整条件。** 模型为 Qwen3.5-4B，任务为两个 LAPS 科学程序修复题，分别属于 coef / subtle 的 `l17k1` 实例。每题采样两条轨迹，每步接受四条，共三步、十二条。每条最多两轮模型交互，回复长度上限为 4096 token。token 是模型处理文本的基本片段，轨迹数量相同不保证 token 数相同。

训练与推理使用三张卡，环境另用一张 H20，环境卡可见容量约 95.58 GiB。环境卡持续**人工注入 70 GiB 常驻占用**，双方每条轨迹均加入 **14 GiB、15 秒的受控 CUDA 阶段**，ON 按 15 GiB 需求和 90 GiB unit 预算准入。GiB 是按 1024 换算的容量单位。原生 LAPS 修复题主要运行 CPU 程序，不能把这说成原生 science 自然产生的 GPU 压力，也不能称为模型与环境同卡借还实验。

两组采用相同的显存不足重试规则，以相同数量的接受轨迹为完成目标。每组初始化上限 900 秒，从开始采样起的训练阶段上限 1440 秒，两组均在预算内完成，退出码为零。全部训练进程、压力进程和所属容器已结束，物理显存释放经过核验。下面直接列出逐步结果：

三步训练中，OFF 共尝试 30 条才获得 12 条接受轨迹，ON 只尝试 12 条。两组成功 CUDA 阶段的并发峰值都为一，ON 观测到四个会话存活、一个 GPU 命令运行、三个等待。**这证明的是在该压力场景减少失败工作，而不是把同时成功运行的 GPU 命令从一条变成四条。**

ON 的初始化比 OFF 多 52.37 秒，但三步训练累计少 597.11 秒，最终全程少约九分钟。初始化包含压力准备、Ray 和模型启动，不能把这 52.37 秒都认作 EnvRouter 自身开销。训练步骤与初始化的计时边界不同，也不能将二者机械相加当作完整耗时分解。

这些数字还有三项必要限制：

1. 双方接受轨迹数相同，但有效回复 token 为 7166 / 8852，不是逐 token 相同的工作量。双方 `reward_repair` 和 `grad_norm` 均为零，不能据此声称学习效果、任务修复率或模型质量提高。
2. 三步对照仅一次 OFF → ON 顺序运行，没有重复统计，不能排除缓存、共享 CPU / 存储和模型生成差异，更不能给出普遍适用的加速倍数。
3. 该轮没有启用后来完成的 eBPF 后端，使用缺少可信归属时的保守记账路径。因此训练收益不能归因于 eBPF，也不是当前全部可靠性改动的联合性能验收。

**低压力训练条件与结果。** 同样使用 Qwen3.5-4B 和上述两题，每题两条轨迹，但只运行一步。不注入 70 GiB 常驻占用，每条轨迹仍执行 14 GiB、15 秒 CUDA 阶段，因此环境卡有足够容量让四条命令重叠。ON 是尚未加入本轮显存预约修复的 `b52a82d`，这组结果不能替代修复后版本的低压力验收。

**低负载组件配对条件与结果。** 另一组实验不包含模型生成或训练，仅运行真实 science 运行器、Harbor、Docker 和 CUDA。每次八个任务、四并发，每任务两条 GPU 命令，每条分配 1 GiB 并持有两秒，中间有八秒 CPU 等待。ON 每条申报 2 GiB，unit 预算 80 GiB，允许在相同准备窗口内预热节点服务。采用 OFF → ON → ON → OFF 顺序，两对共 32 个任务、64 条 GPU 命令，均成功且无重试。

| 计时范围 | OFF | ON | 观察 |
|---|---:|---:|---|
| 第一对任务工作阶段 | 89.46 秒 | 77.83 秒 | ON 更快 |
| 第二对任务工作阶段 | 82.23 秒 | 83.02 秒 | ON 略慢 |
| 两对工作阶段合计 | 171.68 秒 | 160.84 秒 | ON 少 6.31% |
| 两对含初始化和驱动收尾合计 | 213.96 秒 | 217.15 秒 | ON 多 1.49% |

工作阶段从任务开始到结果收集，含任务容器生命周期。最后一行还包括服务初始化和驱动收尾，但不包括 Python 导入前的进程启动及驱动结束后的独立物理释放复核。两对差异方向不一致、样本很少，不能把 6.31% 当作稳定提速，也不能把组件结果称作完整训练结果。只看工作阶段会隐藏短任务的初始化成本。

**另两类收益目前是功能收益，不能换算为训练提速。**

- 进程归属：两个容器内部都出现 PID 8、同名程序时，eBPF 后端仍分别记到各自约 380 MiB GPU 进程显存。每个 CUDA 子进程显式分配 64 MiB，进程总显存还包含运行时开销，小内核均返回预期值 42。结束 A 后，A 的记录失效，B 继续运行。两者最终释放，GPU 无计算进程。这解决了当前部署缺少宿主 procfs 挂载时的记账障碍。验证调用真实节点授权、遥测、归还接口，但终止由验证脚本控制，不是完整 Agent 工具取消链路验收，也未启动训练。
- 同卡交接：一张 H20、Qwen2.5-3B-Instruct 模型，执行两轮受控 Docker CUDA 与 vLLM 交接，容器文件保留，模型恢复后可以生成，每次最多 16 token。没有包含完整训练侧 NIXL 权重传输与 SMG 模型请求路由。前者负责跨进程传递模型数据并登记传输内存，后者负责把模型请求分配给推理实例。因此当前只能声称受控组件交接可行，尚无完整训练吞吐收益结论。

| 功能验证的阶段 | 实际观测 | 能说明什么 |
|---|---|---|
| eBPF 双容器同时计算 | 各自归属 380 MiB，容器内 PID 都是 8 | 身份不依赖容器内 PID 或程序名唯一 |
| eBPF 验证结束 A 后 | A 身份失效，B 仍归属 380 MiB | 能区分两个容器，A 退出未影响 B |
| eBPF 验证清理结束 | 无 GPU 计算进程、无本次容器，采集器关闭 | 本次资源回收经过核实 |
| 借卡验证初始模型阶段 | GPU 显存 7209 MiB | 模型处于可生成状态 |
| 模型休眠后 | GPU 显存 593 MiB | 释放了大部分显存，但不是零占用 |
| 容器 CUDA 阶段 | GPU 显存 978 MiB，两次内核均返回 42 | Docker 使用了同一张物理 GPU |
| 归还并恢复模型 | GPU 显存 7191 MiB，两轮恢复后生成成功 | 本次受控交接可以反复进行 |
| 借卡验证清理结束 | 独立复查显存 0 MiB，无本次 GPU 进程和容器 | 本次物理资源已释放 |

## 为什么高压力下排队反而更快

可以沿真实配置做一个可手算的说明。以下加法省略驱动和 CUDA 上下文开销，是机制解释，不是逐次遥测值。

环境资源池预算 90 GiB，外部已经占 70 GiB，A、B 各申请 15 GiB。A 获准后，CUDA 进程可能还没来得及分配显存，此时查询 GPU 仍只看见约 70 GiB。如果只看物理占用，就容易再把 B 放进去。

当前公式是：

```text
用于准入的占用 = 当前实际显存
               + 每个已获准任务尚未兑现的预约

尚未兑现的预约 = max(申报预算 - 可信识别到的本任务当前占用, 0)

A 尚未实际分配时：70 + A 的 15 + B 的 15 = 100 GiB
100 > 90，所以 B 等待
A 完成并确认归还后：70 + B 的 15 = 85 GiB，B 可以进入
```

这个公式已用于当前准入实现，目的在于把“已经答应但还没分配”的显存也算进去。有可信任务归属时，从预约中扣除已经兑现的部分，避免同一份显存算两次。归属不可信时不给抵扣，可能保守地减少并发，但不能凭总显存增长猜测它属于哪条任务。

这也说明了 command 模式的价值：A 的 GPU 命令结束后，A 的容器还可以等待模型生成下一条指令，B 已经使用刚归还的 GPU 预算。容器生命周期与 GPU 预算持有时间被分开，CPU 状态和文件不必一起销毁。

不过，程序正在 GPU 上保存的模型、仿真状态或 CUDA 上下文不会因为“等待模型”自动搬走。episode 模式适合需要保留这类状态的任务。若要等待时卸载、下次恢复，必须由任务提供可执行的保存和恢复方法，并衡量切换成本。目前没有通用自动卸载机制。

## 仍然存在的边界

| 边界 | 对使用者意味着什么 |
|---|---|
| 显式接入 GPU 命令 | command 只管理走受控 GPU 接口的工作，不能自动识别任意 shell 命令或接入所有新任务 |
| 同容器 GPU 作业串行 | 已有 start / status / wait / cancel 作业接口，但本地执行锁及每租约单条活动命令约束仍在。异步提交不等于同容器并行 |
| 模式为启动配置 | `gpu_reservation` 当前由 unit 配置选择，不是仅靠 task.toml，也没有运行中自动选择 episode / command |
| 显存预算不是硬隔离 | 能阻止已知超额申请，无法强制任意 CUDA 程序不超申报，也不能阻止外部进程在准入后继续增长 |
| 多卡抵扣仍保守 | 已有逐卡预算与需求，但任务归属当前提供总量，不能拿总量猜各卡实际分布并抵扣 |
| 故障恢复尚未完整 | 没有持久化账本重建、跨 Router 全局唯一设备所有权、完整网络分区恢复，也没有运行中整条 episode 清理后跨 worker 重放协议 |
| 部署有条件 | command 依赖可写 cgroup v1 设备控制，即 Linux 按进程组限制设备访问的机制。eBPF 需要内核追踪权限和对应工具，当前不是任意节点即插即用，也未验收 cgroup v2 |
| 借卡分支独立 | vLLM 借卡绑定完整副本，当前限制每 unit 一个会话，不能与 command 配额模式任意组合 |
| 评分与调度不同 | 原生 GPU 任务严格评分需要可信任务活动归属。整卡繁忙不等于本任务在计算，旧 Gate B 回复节流不能提供这种证明 |

procfs 是 Linux 用文件形式暴露进程信息的接口。当前平台登录环境本身可能处在容器中，其 `/proc` 不一定能对应 GPU 驱动报告的宿主进程号。eBPF 是在 Linux 内核中运行受检查的小程序，这里用于登记进程身份及任务归属，GPU 数值仍来自 NVML。它绕开的是宿主 procfs 挂载需求，不是取消所有权限和部署要求。

两种身份方案的区别可以理解为“查进程档案”和“在内核中登记”。procfs 按宿主进程号查询出生时间与资源组。eBPF 则在节点确认容器归属后，登记这次命令对应的资源组和注册号，通过内核事件维护真实宿主进程号与出生时间。进程退出时使旧记录失效，避免进程号被重新使用后认错任务。身份采集失败时不抵扣未知占用，不能把采不到数据当作显存为零。

旧 Gate B 会根据 GPU 活动推迟给模型的回复，属于软节流，达到等待上限仍可能放行。它既不等同于当前 command 的容量准入，也不能保证评分采样期间的独占或归属正确。

## 未来规划与验收标准

以下是**建议的推进顺序，不是已实现能力或排期承诺**。先让最新能力在一个真实任务闭环，再扩大可接入任务范围。自动选择 episode / command 需要资源画像和安全释放边界，适合放在这些基础之后。

| 优先级 | 工作内容 | 完成时应拿到的证据 |
|---|---|---|
| P0：原生任务与最新版本闭环 | 选一个原生 science GPU 任务，将显式 GPU 执行、可信归属、任务评分、取消和清理串起来。冻结包含最新修复的代码版本 | Docker 内真实 CUDA 工作得到本任务的活动证据。CPU 假工作不能借用别人的 GPU 活动通过严格评分。取消或正常结束后核实进程、容器及显存释放 |
| P0：补齐新修复实机验收 | 小规模核验逐卡预算、主容器 / verifier / sidecar 限额、节点失效停止派发和恢复清理 | 真实两卡中单卡放不下时拒绝或等待。全部容器限制与账本一致。故障下有界结束，不遗留全局暂停，不在清理未完成时放行 |
| P1：当前版本低压力基准 | 用相同成功工作量、固定 OFF 和冻结 ON，做少量顺序平衡对照 | 同时记录冷启动、工作阶段、总时间、等待、OOM 和有效 token，明确额外开销及适用负载。达到预设结论后停止，不自动拉长训练 |
| P1：通用任务接入与可观测性 | 把 GPU 阶段边界、峰值预算、作业生命周期、归属与清理做成明确适配契约，统一关键指标 | 新任务主要补资源声明和 GPU 执行适配，不需要复制 science 专用脚本。日志能区分准备慢、排队慢、执行慢和清理慢 |
| P1：服务故障恢复 | 持久化或可重建的租约、跨控制器设备所有权、清理确认后再调度 | 控制器退出重启或通信中断不会重复授权，不会把遗留工作当作已释放 |
| P2：提高剩余容量利用率 | 改善 FIFO，即先进先出队列中大任务挡住后续小任务的情况。允许能放下的小任务使用余量，并限制大任务的等待时间，完善多卡逐任务归属 | 在相同混合负载下减少空闲和等待，同时大任务有等待上界。不能只报告小任务变快 |
| P2：同容器多作业并发 | 按作业建立独立预算和进程归属，设备权限按活动作业生命周期管理 | 容量够时 A/B 重叠，不够时 C 等待。取消 A 不杀 B、不撤掉 B 所需权限，不错误归还 B 的预算 |
| P3：自动持有和卸载策略 | 基于任务能力、峰值、等待时长及释放恢复成本选择持续占用、command 或协作式卸载 | 比较释放加恢复成本与可利用等待窗口，只在有安全恢复方法且净收益为正时切换。不能通过检测“模型在生成”就强制撤走 CUDA 状态 |
| P3：完整训推与环境共享 | 将受控借卡接入完整训练的模型请求路由、权重有效性与传输登记，再评估和 command 的组合 | 模型正确恢复，容器物理归还后才唤醒，测量交接总成本和完整训练收益，避免只证明裸 sleep / wake 可调用 |

本阶段不把运行中活容器跨机迁移、任意 CUDA 程序强制抢占或最优调度器作为已有承诺。它们需要额外的任务恢复协议或系统支持。

## 完整生命周期与独立可运行演示

| 步骤 | 图中编号 | 输入与状态变化 |
|---|---|---|
| 1. 放置 | 1 → 2 | 按实际组大小读取需求和健康容量，选择 worker。此时尚未取得最终执行许可 |
| 2. 会话准入 | 2 → 3 | 提交资源需求，等待节点探活和清理确认后返回允许、等待或拒绝 |
| 3. 容器创建 | 3 → 4 | 运行器将租约配置交给 Harbor，在最终容器集合施加标签和限制 |
| 4. GPU 工作 | 4 → 5 → 6 | 统一后端选择持有策略。command 经命令排队和预算检查，节点授权后才执行 |
| 5. 并行收尾 | 6 → 7 | 等待撤权和归还确认。采用后台归还时，CPU / 模型规划可继续，下一条 GPU 工作仍必须服从归还状态 |
| 6. 结束与异常 | 7 → 3 | 评分后释放会话，异常进入按归属清理。待清理资源不能因为租约计时到期就直接重新使用 |
| 独立分支 | 8 | 借卡状态机在模型和环境阶段交替，不能将其伪装成 command 路径里的一个无条件步骤 |

下面的演示直接包含全部代码，安装 Python 3 的机器即可运行，不需要 PSRL 仓库、其他脚本、Docker 或 GPU。复制整个命令块到终端执行即可。

**这是教学模拟，不是生产调度器。** 它用简化账本模拟图中 3、5、7 的申请、等待和确认归还，假设外部占用一直为 70 GiB，已获准任务还没实际分配。实际系统还需检查进程身份、设备权限、节点健康、并发请求和真实释放状态。脚本最后还用本文表格中的数值生成上面的文本条形图，图表数据无需外部文件。

```bash
python3 - <<'PY'
capacity = 90
measured = 70
reservations = {}

def request(name, amount):
    # 图中 3、5：把已承诺但尚未分配的额度计入准入。
    projected = measured + sum(reservations.values()) + amount
    allowed = projected <= capacity
    if allowed:
        reservations[name] = amount
    state = "granted" if allowed else "wait"
    print(f"{name}: {state}, candidate={projected} GiB")

request("A", 15)
request("B", 15)
request("C", 15)

# 图中 7：教学中假设 A 已经物理释放，再删除预约。
del reservations["A"]
print("A: return confirmed (simulated)")
request("B", 15)

groups = [
    ("三步训练累计，越短越好", 1100.80, 503.69),
    ("含初始化和清理的总时间，越短越好", 1954.11, 1415.01),
]
for title, off, on in groups:
    print(f"\n{title}")
    for label, value in (("OFF", off), ("ON", on)):
        bar = "#" * round(40 * value / off)
        print(f"{label:<3} |{bar:<40}| {value:7.2f} 秒  {value / off:6.2%}")
PY
```

申请部分的预期输出如下，后面会打印本文所列条形图：

```text
A: granted, candidate=85 GiB
B: wait, candidate=100 GiB
C: wait, candidate=100 GiB
A: return confirmed (simulated)
B: granted, candidate=85 GiB
```

`candidate` 表示“若现在批准这条申请，需要承担多少显存”，不是实测显存。B、C 显示 100 GiB 时都没有真的分配。A 确认归还后，B 的候选总量重新降到 85 GiB，因此获准。这个例子展示为什么先等待可以避免已经知道会超额的申请，但不能用它证明实际吞吐或不会发生任何 OOM。

## 设计演进与交付边界

从设计目标看，Env 的工作分为三层。三层的实现和验收进度不同，不应统一标成“已经完成”。

| 层次 | 要解决的问题 | 当前交付程度 |
|---|---|---|
| 第一层：统一管理环境 | 把分散的容器启动、容量检查、归属和清理纳入同一资源服务，避免各执行进程独立竞争 | science / Harbor 主路径已有实现和真实运行证据，全部环境后端统一仍未完成 |
| 第二层：缩短 GPU 持有范围 | GPU 阶段结束后允许别的任务使用容量，同时保留当前任务容器、文件和 CPU 状态 | 显式 command 模式已实现，具有本文高压力三步训练证据。任意任务自动接入和同容器并发仍未完成 |
| 第三层：跨角色动态共享 | 按实际任务特征，在环境、推理和其他工作之间自动选择资源持有、卸载和恢复策略 | 有受控模型借卡组件实现，自动模式选择、通用上下文卸载和完整训练共享验收仍属于后续工作 |

下一次可以明确交付的目标是：冻结一份包含新修复的版本，在一个原生 science GPU 任务上完成执行、归属、严格评分和清理验收，再对这个冻结版本测量低压力开销。这样可以把“单个组件能工作”推进到“同一个真实任务能完整使用这一套能力”，同时保持收益数字与代码版本一致。

本文中的实验均为已经完成的测量，本次独立文档整理没有新增训练或 GPU 实验。本文提供的是阅读和交流所需的完整条件与结果，不包含模型权重、镜像、数据集或完整执行日志，因此单独保存本文即可理解结论，但不等于获得一套可离线复现完整训练的实验包。
