# Env 实现、实测收益与后续规划

> **核心结论，截至 2026-10-27**：Env 已具备 science / Harbor 路径的资源准入、跨任务 GPU 命令排队、统一作业执行和归属清理能力。在一次人工高显存压力的真实 PSRL science 三步训练对照中，OOM 尝试从 18 次降到 0 次，训练步骤累计耗时减少 **54.24%**，含初始化和清理的总时间减少 **27.59%**。收益来自减少失败重试，不是 CUDA 计算本身加速。
>
> 低压力下尚未证明稳定提速。可选 eBPF 进程归属后端已通过双 Docker 容器真实 CUDA 验证，新的故障恢复、逐卡预算和辅助容器限制已通过 CPU 回归，但尚未合并成一版完成原生 science GPU 任务的端到端验收。下一阶段优先完成这一闭环，再做通用接入、调度优化和自动策略选择。

本文是可单独转发的项目状态说明。背景、架构图、实验条件、结果数据和后续规划均直接写在本文中，不需要其他文件或图片。状态截止到 2026-10-27 本次汇总核验的范围，其他并行开发中的改动不自动纳入。性能数字来自明确版本的实验，不能当作全部新改动的性能结论。最新实现包含尚未提交的开发内容，**实现与验证完成不等于已经发布部署**。

建议先看三种设计总图，再看 baseline 与当前方案的对照表，最后阅读实测结果。需要讨论后续研发时，再进入自动模式选择与预测卸载章节。本文将固定 baseline、已经实现的 EnvRouter、尚未实现的自动策略分开标识。

## 先看整体：比较的是哪一层

PSRL 训练需要不断收集模型做题的过程：模型生成操作，环境执行操作，评分器检查结果，训练器使用这些轨迹更新模型。一次从开始到评分的完整尝试叫 **episode**，采集到的一条交互轨迹称为 **rollout**。同一道题采样四条 rollout，通常对应四个独立的环境会话，不等于在同一个容器里同时执行四条 GPU 命令。

Env 要解决的是：任务增多以后，谁能在哪台机器启动、允许占用多少资源、什么时候可以交给下一条任务，以及任务异常后如何确认资源已经收回。否则，即使模型正常生成，环境显存不足或资源残留也会拖慢训练数据供给。

**图 1：三种方案都服务于同一条训练链，主要改变环境资源管理这一层。** 下图是系统职责总览，不表示实验中三种方案都已实现。模型请求路由负责把请求送到模型，EnvRouter 负责环境资源，两者名称相似但职责不同。

```text
PSRL 训练器 → 派发题目、采集多条 rollout
                   ↓
             模型生成下一步操作 ←──────────────┐
                   ↓                         │
             环境执行命令 → 返回执行结果 ─────┘
                   ↓ 完成任务
              评分 → 轨迹进入训练更新

环境资源管理这一层的三个版本：

[固定 baseline，实验 OFF]
轮流分派任务 + 每进程限制会话数 + 预先指定可见 GPU
                   ↓ 当前已实现的扩展
[EnvRouter，实验 ON 使用其明确冻结版本]
共享资源账本 + 容量准入 + 显式 GPU 命令排队与归还确认
                   ↓ 后续设计，尚未实现
[自动策略]
识别任务状态 + 自动选 episode/command + 预测是否卸载与恢复
```

图例：上半部分是所有方案共有的训练与任务交互关系。下半部分是环境控制方式的对比，不是三层服务同时串行执行。ON 的性能结果只覆盖相应实验版本，不能直接作为未来自动策略的收益。

## 固定 baseline：设计与已有保护

**本文 baseline 固定为提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 的 science / Harbor 执行路径。** 这是一套已经能够执行真实训练任务的方案：先分派任务，每个执行进程控制自己的会话数量，再由 Harbor 创建 Docker 环境、执行、评分和清理。它没有本文新增的环境资源账本，也没有 `GpuDeviceGate` 整卡锁。以下设计依据该提交的实际实现核对，不用后来版本关闭 Env Service 的结果替代。

**图 2：baseline 与当前 EnvRouter 的总体结构。** 左右两列画的是同一批任务的两种管理方式，不是同时部署。W1 / W2 表示两个执行进程，GPU 归属与容量均以所在节点为单位。

```text
固定 baseline                           当前 EnvRouter
─────────────                           ──────────────
训练器按题目组轮流选择 worker             训练器读取资源与健康容量后选择 worker
      ├─ W1                                  ├─ W1
      └─ W2                                  └─ W2
         ↓ 各自管理                              ↓ 共同请求
 W1 会话数量闸门    W2 会话数量闸门          EnvRouter + 共享资源账本
         ↓                ↓                  ↓ 允许 / 等待 / 拒绝
 各自调用 Harbor 创建容器                  节点服务 + Harbor 创建受管容器
         ↓                ↓                  ↓
 配置文件预先指定 GPU 访问                 episode 预留 / command 阶段申请
         └──────┬─────────┘                  ↓
       GPU 驱动处理实际分配                 容量检查 → 设备授权 → GPU 执行
       容量够时可并行，争抢时可能 OOM        容量够时可并行，不足时排队
                ↓                            ↓
 任务结束，清理本次容器后释放数量名额       确认命令归还后释放 GPU 阶段预算
                                            ↓ 会话结束
                                       清理容器、释放其余预算
```

图例：左侧两个数量闸门彼此独立，只限制各自进程的在途会话数。右侧共享账本覆盖接入同一个 Router 的 worker 和所配置资源池，不等于已经拥有整个集群、其他 Router 或外部进程的全局调度权。右侧图中的命令排队与阶段归还对应 command 路径，episode 路径按会话保留预算。

baseline 的执行顺序与边界如下：

| 步骤 | baseline 实际做什么 | 能保护什么，不能保护什么 |
|---|---|---|
| 1. 选择 worker | 按题目组轮流分派，同题的多条采样尽量放到同一 worker | 保持组内执行位置一致，但该分派不检查环境节点的实时显存容量 |
| 2. 取得会话名额 | 每个执行进程用信号量限制并发 episode，配置项为 `max_concurrent_episodes` | 信号量可理解为固定数量的入场券。它限制会话数，不根据每个任务需要多少显存来决定是否放行 |
| 3. 创建环境 | Harbor 按任务配置启动 Docker，GPU 任务可以追加静态 Compose 配置 | Compose 是描述容器、挂载和设备的配置文件。设备映射说明容器能访问哪些 GPU，不会自动形成按显存容量分配的额度 |
| 4. 多轮执行 | 模型请求经过模型会话路由，任务容器执行工具命令，再把结果交给模型 | 已有模型交互、独立任务环境和异步执行能力。多个已获准的容器可以同时申请 GPU，没有整卡串行锁 |
| 5. 评分与结束 | 有任务超时、异常处理、评分恢复路径，并在结束收尾中按 Compose 项目清理容器与相关镜像，然后释放会话名额 | 已有基础隔离与清理。它不是新增的节点服务租约、命令阶段物理归还及控制器故障恢复协议 |

这里的并发上限是可配置的，源码默认值为每进程八个 episode，不代表本文所有实验都用了八并发。教学例子：同一节点上两个进程各设置四个名额，就可能合计启动八个会话。如果两者配置都指向同一张环境卡，它们共享物理显存，但两个本地信号量不会自动合并成一个全节点显存预算。

baseline 附带的 GPU Compose 示例指向节点本地 GPU 0，实际设备可以由实验配置替换。因此，不能笼统说“OFF 所有任务必然跑同一张卡”，准确说法是“访问哪些卡由静态配置决定，资源不足时不会由该路径自动按显存选卡或排队”。不同节点的 GPU 0 也不是同一张物理卡。

**必须避免三个误解。** baseline 已有会话并发限制、任务环境和清理，不能写成完全不管资源。设备映射也不等于预先占满整张 GPU，显存实际由运行中的程序分配和释放。baseline 可以自然出现跨容器 GPU 并发，但缺少这套显式的容量预约与命令归还协调。

尤其要区分：**baseline 的“按 episode 限数量”，不等于 EnvRouter 的“episode 显存预算模式”。** 前者只是本地有几张入场券，后者是在共享账本中持续为该会话保留 GPU 需求。当前 EnvRouter 的 episode 和 command 是共享资源管理之下的两个持有策略，baseline 并不是其中一个模式的别名。

## 三种设计的能力对照

| 比较点 | 固定 baseline | 当前 EnvRouter | 未来自动策略，尚未实现 |
|---|---|---|---|
| 核心决策 | 本进程还能启动几个会话 | 指定资源池此刻能否承载这份任务需求 | 哪种持有方式适合本阶段，什么时候让位总体更划算 |
| 控制范围 | 每进程数量限制，加静态设备配置 | 同一 Router 下的资源池、会话租约与显式命令 | 在已有授权范围内进一步管理阶段策略与恢复义务 |
| CPU / 主存 | 任务与容器本身可有限制，缺少这套跨 worker 统一需求账本 | 会话预算，新实现还纳入主容器、独立评分环境和辅助容器 | 把 offload 副本及恢复所需主存一并纳入决策 |
| GPU 准入 | 会话数量允许后，程序直接进行实际 GPU 分配 | 按需求、实测占用与未兑现预约检查，容量不足等待 | 预测峰值、可释放量和时间窗口，授权仍需实际检查 |
| 容量足够时 | 多个容器本来就可以并行 | 不同容器的受管命令也可并行，另有控制开销 | 优先使用现有余量，避免无必要的卸载 |
| 等待模型时 | 程序是否保留显存取决于自身行为，没有该框架的阶段交接协议 | command 完成且归还确认后释放预算，episode 继续保留 | 有安全恢复能力的 episode 可预测卸载并按约定恢复 |
| 模式选择 | 没有 EnvRouter 的 episode / command 策略选项 | 通过启动时资源池配置选择，不会自动识别切换 | 结合任务能力声明和观察自动选择，变化只在安全边界提交 |
| GPU 归属与回收 | 基础任务项目归属及结束清理 | 节点归属核验、命令授权和归还确认，可选 procfs / eBPF 身份后端 | 保留恢复需求、处理预测失误与借用者超时 |
| vLLM 同卡共享 | 静态设备访问不构成模型休眠与恢复协议 | 有受控借卡分支，但尚不能和 command 任意组合 | 协调模型与环境的依赖、成本和整体交接 |
| 已知收益边界 | 低压力时结构简单，额外调度成本较少 | 有本文限定条件下的高压力收益，低压力未证明稳定提速 | 目前只有设计与教学计算，没有真实性能结论 |

**图 3：同一张卡、同样四条 GPU 请求，决策差异在哪里。** 以下按实验容量做机制示意，不是新的测量。任务 CPU 与主存资源假设已足够。

```text
低压力：四条任务各实际分配 14 GiB，总计 56 GiB，卡上装得下
baseline    会话名额允许 → A、B、C、D 都可能成功重叠
EnvRouter   需求预算允许 → A、B、C、D 都可能成功重叠
结论        不能把原本就能并行的工作算成 ON 独有收益

高压力：已有约 70 GiB 外部占用，ON 池预算 90 GiB，每条预约 15 GiB
baseline    会话名额允许 → A、B、C、D 可同时争抢剩余显存
                         实际放不下的分配可能 OOM，实验再按规则补采
EnvRouter   70 + 15 = 85 → 放行 A
            70 + 15 + 15 = 100 > 90 → B、C、D 等待
            A 确认归还 → 放行下一条
结论        收益来自减少失败和重复工作，代价是增加准入与归还控制
```

图例：baseline 的“会话名额”属于本地数量闸门，ON 的 15 GiB 是预约预算，14 GiB 是实验实际分配，两者不能混为一谈。OOM 后重试是本次对照采用的共同实验规则，不是声称 baseline 自带完整的显存重试调度器。真实耗时、失败次数及生成差异在本文 Results 部分单列。

## 当前 EnvRouter：完整执行链

**图 4：当前 science / Harbor 的完整执行链。** Harbor 是实际组织任务环境、命令执行和评分的运行器。图中的分支有各自的接入和验收边界，不能理解成任意配置都能同时使用。

```text
[1] PSRL Trainer / AgentLoopManager
    读取任务需求，按组内 rollout 数选择有容量的健康 worker
                       ↓
[2] science runner / EnvServiceClient
    请求一次任务会话的资源租约
                       ↓
[3] EnvRouter + Ledger 资源账本
    unit 节点资源池：CPU、主存、会话槽位、GPU 预算
    决策：允许 / 等待 / 拒绝，异常资源先确认清理
                       ↓
[4] Harbor + ManagedDockerEnvironment
    启动并标记主容器、评分环境和 sidecar 辅助容器
                       ↓
[5] 统一 GPU 作业后端
    episode：会话期间保留 GPU 预算
    command：每条显式 GPU 命令申请，容量不足排队
                       ↓
[6] 节点服务：设备授权 → Docker 执行 CUDA → 任务遥测
    身份来自 procfs 或可选 eBPF，GPU 数据来自 NVML
                       ↓
[7] 命令归还确认 → 其他任务获准
    原容器可以继续 CPU 工作或等待模型
    评分、会话结束 → 按归属清理全部相关资源

独立分支 [8]：vLLM 推理副本 sleep → 容器借卡
              → 确认归还 → vLLM wake
              当前不与 command 配额模式组合
```

图例：各部分的职责、输入和输出。

| 编号 | 职责与数据流 |
|---|---|
| 1 | 任务派发器读取任务需求和同题采样条数，选择执行进程所在的节点。这一步是放置建议，还不是最终资源授权 |
| 2 | science 运行器将任务的 CPU、主存和 GPU 需求提交给资源服务，请求一次会话的资源租约 |
| 3 | EnvRouter 检查节点健康和遗留资源清理状态，账本核对容量，返回允许、等待或拒绝 |
| 4 | Harbor 创建执行与评分环境。容器附带所属租约标签，CPU 和主存限制覆盖主服务与辅助服务 |
| 5 | 统一后端管理执行、等待、超时和取消。命令模式还需在每次 GPU 工作前申请阶段预算 |
| 6 | 节点服务核对容器归属并授予设备权限，命令实际执行，同时记录属于本任务的 GPU 活动 |
| 7 | 命令结束后确认 GPU 物理资源归还，释放阶段预算。整个会话结束后清理容器并释放其余资源 |
| 8 | 独立借卡分支协调模型休眠、容器使用、确认归还、模型唤醒，不能跳过任何交接确认 |

**unit** 是配置中声明的本节点资源池。**lease，租约**是一次任务获准使用资源的凭证。两者都是调度状态，租约归零本身不能证明真实进程或显存已经消失。**NVML** 是 NVIDIA 提供的 GPU 管理查询接口，用于读取显存和 GPU 进程数据。

**CUDA** 是程序使用 NVIDIA GPU 执行计算的接口与运行环境。**vLLM** 是模型推理服务，负责生成下一步操作。**verifier** 是任务评分器，**sidecar** 是伴随主容器运行的辅助容器，例如提供网络控制的服务。它们虽然不直接负责模型做题，也会消耗资源，因此不能在预算和清理中漏掉。

这里的“统一 GPU 作业后端”只指 episode 与 command 共用执行、等待、取消和收尾接口，不代表已有 EnvWorker 路径与 Harbor 路径已经全面统一。

## 当前实现与验证程度

“已实现”表示能在当前源码中找到对应逻辑。“CPU 回归”验证控制逻辑，不代表已经经过真实 Docker、GPU 或分布式故障验收。各行证据可以有重叠，不能把测试数量相加当作独立验证规模。

| 能力 | 当前实现 | 已有证据与边界 |
|---|---|---|
| 会话资源准入与放置 | 按 unit 管理 CPU、主存、GPU 和会话槽位，派发考虑任务需求 | 已有真实 science / Docker / 训练运行。最新按整组需求和健康状态派发的修改，主要通过 CPU 回归 |
| 命令阶段 GPU 复用 | 不同容器的命令容量足够可重叠，容量不足排队。会话仍保留文件与主机资源 | 有真实容器并发和高压力训练证据。同容器当前仍串行 |
| episode / command 统一后端 | 两种持有范围共用执行、超时、等待、取消和收尾 | 已有组件验收。持有范围由启动配置选定，不会根据模型等待时间自动切换 |
| 显存预约记账 | 实测占用加尚未兑现的预约，可信归属用于避免重复计费 | CPU 反例及修复后高压力三步训练通过。预算不是显存硬隔离 |
| 启动与控制路径优化 | 节点异步预热，复用 NVML 连接，减少重复 Docker 查询，将同步准备移出事件循环 | 有固定 OFF 的低负载配对结果。短作业仍需计入服务初始化 |
| 生命周期与回收 | 作业状态、心跳、超时、按标签清理，归还确认前不释放不确定的 GPU 使用权 | 有真实容器清理证据。控制器重启重建和网络分区恢复尚未闭环 |
| 可信任务 GPU 归属 | procfs / eBPF 可选后端，按进程身份归属过滤 GPU 数据 | eBPF 已通过两个真实 CUDA 容器的独立记账和退出失效验证，尚未完成原生 science 严格评分验收 |
| 逐卡需求与容器集合预算 | 每张 GPU 单独检查。主容器、独立 verifier 和 sidecar 纳入 CPU / 主存预算与限制 | 新实现通过 CPU 控制逻辑及 Harbor 配置序列化回归，尚未完成真实多卡与全部容器限额验收 |
| 迁移暂停恢复与健康派发 | 迁移异常只释放自己的暂停持有者，故障节点停止新派发，恢复和重试有界 | 新实现通过 CPU 故障注入，尚未完成真实网关失联或节点故障实验 |
| vLLM 与容器同卡交接 | 显式绑定完整推理副本，sleep 后借出，确认归还后 wake | 已有两轮真实 Docker CUDA / vLLM 组件交接。未覆盖完整训练侧权重传输与路由 |

这些能力处于不同验收阶段。例如，逐卡预算已能拒绝“两张卡总量够、但一张卡放不下”的申请，辅助容器也已纳入预算，相关控制逻辑通过 CPU 回归。但这些新修改与 eBPF 后端并不属于下文三步训练使用的冻结代码，不能将下文提速归因于它们。

## Results：已经拿到的收益

**OFF 和 ON 的含义。** OFF 是固定历史版本的任务执行路径，ON 是启用 EnvRouter 的对应实验版本。下表 OFF 固定为提交 `0eeead861ffafed6bf31c962d259fd847775dcf9`，保持静态 GPU 映射与进程内 episode 信号量，没有添加整卡锁。信号量在这里用于限制单个进程允许同时运行的会话数量，它不是按整机显存动态准入的账本。

为使两组在相同环境运行，实验使用了必要的设备参数传递、Ray 节点地址、HTTP 调用和依赖兼容修复，并移除会影响其他任务的全局镜像清理。这些运行修复没有把 OFF 改成整卡串行，也没有给它加入 ON 的显存调度。当前代码仅关闭 Env Service 不能替代这个固定基线。

**低负载组件配对条件与结果：显存够用时，加上调度会不会变慢？** 这组实验于 2026-10-20 运行，回答的是这个开销问题。它与上面的真实训练对照不同：保留 science 的任务运行器，以及负责容器任务执行和评分的 Harbor，但用固定脚本代替模型决定下一步操作。因此，Docker 容器和 CUDA 显存操作都是真实的，没有调用模型生成指令，也没有更新模型参数。

```text
固定脚本给出相同任务动作
  ↓
science 运行器 → Harbor 创建任务容器
  ↓
OFF：普通命令执行              ON：申请命令预算 → 获准后执行 → 归还核验
  ↓                              ↓
同一张 GPU 上执行相同的 CUDA 显存操作
  ↓
校验输出 → 评分 → 回收任务容器 → 收集结果
```

这里的三个词可以这样理解：

- **组件**：只测完整训练系统中的“环境执行部分”，不包含模型生成、采样训练数据和参数更新。它是真实容器实验，但任务内容是专门构造的固定动作，不是在解 science 科学题。
- **低负载**：这批任务的显存需求远小于环境卡可用预算，不额外注入显存压力。ON 每条命令申报 2 GiB，四条同时申请合计 8 GiB，资源单元预算为 80 GiB。每条实际分配 1 GiB，另有 CUDA 运行时占用。这里不是说整个节点没有其他工作，也不是测满卡计算吞吐。
- **配对**：相同工作量分别跑 OFF 和 ON，组成一对。第一对先 OFF 后 ON，第二对先 ON 后 OFF，即 OFF → ON → ON → OFF。交换顺序用于减轻后运行一方可能获得的缓存优势，不代表消除了所有环境波动。

每次运行执行八条任务，分两批，每批四条并发。单条任务的动作如下，箭头表示先后关系，不按耗时比例绘制：

```text
建容器
  → 第一次 GPU 命令：分配 1 GiB → 写入并读回 42 → 持有两秒 → 退出释放
  → 容器内 sleep 八秒，此时该命令的 GPU 分配已经释放
  → 第二次 GPU 命令：同样分配、校验、持有两秒，再退出释放
  → 校验两次输出 → 评分 → 清理
```

两秒是**持有显存的时间**，不是连续高强度计算两秒。八秒是人为设置的空闲等待，用来构造“两次 GPU 操作之间暂时不用 GPU”的阶段，不是真实 vLLM 生成时间，也不是八秒 CPU 计算。ON 允许第一次命令的归还核验与这段等待重叠，第二次申请前确认归还。四次运行共完成 32 条任务、64 条 GPU 命令，均成功，无显存不足错误和重试。

OFF 使用固定 baseline `0eeead861ffafed6bf31c962d259fd847775dcf9`，保留静态 GPU 映射和进程内任务数量限制，没有整卡锁。ON 使用 `37a06ea8d32b05bbbf385ad40cb404b30ba01680` 加同步准备优化，因此比较的是两套执行实现，不能把全部差值归因于显存调度算法。双方另外有相同的八秒驱动准备窗口，ON 在其中预热节点服务。这与每条任务中间的八秒等待是两件事，未能重叠的初始化时间仍计入总耗时。

**为什么一行说快，一行又说慢？** 两对工作阶段 ON 省了约 10.84 秒，但初始化和驱动收尾额外花了约 14.03 秒，抵消后全程反而多约 3.19 秒。表中最后一行是这两个阶段之和，不包括 Python 导入前的进程启动和驱动结束后的独立物理释放复核。差值按原始未舍入记录计算。

这组数据支持的描述是：**在这两对小规模低压力组件实验中，ON 全程耗时接近 OFF，但没有证明稳定提速。** 第一对工作阶段更快、第二对略慢，样本不足以说明普遍规律。由于双方都没有 OOM 或重试，它也不能证明高压力保护收益，更不能称作完整 science 训练提速。评估真实训练时应看前面的训练对照，并保留那些实验各自的条件和限制。

**另两类收益目前是功能收益，不能换算为训练提速。**

- 进程归属：两个容器内部都出现 PID 8、同名程序时，eBPF 后端仍分别记到各自约 380 MiB GPU 进程显存。每个 CUDA 子进程显式分配 64 MiB，进程总显存还包含运行时开销，小内核均返回预期值 42。结束 A 后，A 的记录失效，B 继续运行。两者最终释放，GPU 无计算进程。这解决了当前部署缺少宿主 procfs 挂载时的记账障碍。验证调用真实节点授权、遥测、归还接口，但终止由验证脚本控制，不是完整 Agent 工具取消链路验收，也未启动训练。
- 同卡交接：一张 H20、Qwen2.5-3B-Instruct 模型，执行两轮受控 Docker CUDA 与 vLLM 交接，容器文件保留，模型恢复后可以生成，每次最多 16 token。没有包含完整训练侧 NIXL 权重传输与 SMG 模型请求路由。前者负责跨进程传递模型数据并登记传输内存，后者负责把模型请求分配给推理实例。因此当前只能声称受控组件交接可行，尚无完整训练吞吐收益结论。

## 为什么高压力下排队反而更快

可以沿真实配置做一个可手算的说明。以下加法省略驱动和 CUDA 上下文开销，是机制解释，不是逐次遥测值。

环境资源池预算 90 GiB，外部已经占 70 GiB，A、B 各申请 15 GiB。A 获准后，CUDA 进程可能还没来得及分配显存，此时查询 GPU 仍只看见约 70 GiB。如果只看物理占用，就容易再把 B 放进去。

当前公式是：

```text
用于准入的占用 = 当前实际显存
               + 每个已获准任务尚未兑现的预约

尚未兑现的预约 = max(申报预算 - 可信识别到的本任务当前占用, 0)

A 尚未实际分配时：70 + A 的 15 + B 的 15 = 100 GiB
100 > 90，所以 B 等待
A 完成并确认归还后：70 + B 的 15 = 85 GiB，B 可以进入
```

这个公式已用于当前准入实现，目的在于把“已经答应但还没分配”的显存也算进去。有可信任务归属时，从预约中扣除已经兑现的部分，避免同一份显存算两次。归属不可信时不给抵扣，可能保守地减少并发，但不能凭总显存增长猜测它属于哪条任务。

这也说明了 command 模式的价值：A 的 GPU 命令结束后，A 的容器还可以等待模型生成下一条指令，B 已经使用刚归还的 GPU 预算。容器生命周期与 GPU 预算持有时间被分开，CPU 状态和文件不必一起销毁。

**图 5：同一个任务中，会话名额、设备可见性和 GPU 预算不是同一件事。** 下面是概念时间轴，各栏不按真实时长比例绘制。

```text
任务阶段                 GPU 计算一  | 等模型 / CPU 工作 | GPU 计算二 | 结束
baseline 的会话数量名额   持有        | 持有              | 持有      | 清理后释放
baseline 的 GPU 可访问性  容器可访问  | 容器仍可访问      | 容器可访问| 容器回收
baseline 的实际显存      由程序分配  | 由程序是否释放决定| 由程序分配| 核对实际释放

当前 ON episode 预算     保留        | 保留              | 保留      | 清理后归还
当前 ON command 预算     申请并使用  | 确认归还后可复用  | 再申请使用| 收敛清理

未来可卸载 episode       使用状态    | 卸载 → 借给 B     | 恢复后使用| 收敛清理
                                    | B 归还 → A 恢复   |
```

图例：前三行描述 baseline 的不同属性，不能把“有设备访问权限”画成“必然占满显存”。当前 command 的等待阶段也不是瞬间归还，要等物理检查完成。最后一行是有恢复契约且预计有收益时的未来方案，不是目前 episode 已支持的通用行为。

不过，程序正在 GPU 上保存的模型、仿真状态或 CUDA 上下文不会因为“等待模型”自动搬走。episode 模式适合需要保留这类状态的任务。若要等待时卸载、下次恢复，必须由任务提供可执行的保存和恢复方法，并衡量切换成本。目前没有通用自动卸载机制。

## 仍然存在的边界

| 边界 | 对使用者意味着什么 |
|---|---|
| 显式接入 GPU 命令 | command 只管理走受控 GPU 接口的工作，不能自动识别任意 shell 命令或接入所有新任务 |
| 同容器 GPU 作业串行 | 已有 start / status / wait / cancel 作业接口，但本地执行锁及每租约单条活动命令约束仍在。异步提交不等于同容器并行 |
| 模式为启动配置 | `gpu_reservation` 当前由 unit 配置选择，不是仅靠 task.toml，也没有运行中自动选择 episode / command |
| 显存预算不是硬隔离 | 能阻止已知超额申请，无法强制任意 CUDA 程序不超申报，也不能阻止外部进程在准入后继续增长 |
| 多卡抵扣仍保守 | 已有逐卡预算与需求，但任务归属当前提供总量，不能拿总量猜各卡实际分布并抵扣 |
| 故障恢复尚未完整 | 没有持久化账本重建、跨 Router 全局唯一设备所有权、完整网络分区恢复，也没有运行中整条 episode 清理后跨 worker 重放协议 |
| 部署有条件 | command 依赖可写 cgroup v1 设备控制，即 Linux 按进程组限制设备访问的机制。eBPF 需要内核追踪权限和对应工具，当前不是任意节点即插即用，也未验收 cgroup v2 |
| 借卡分支独立 | vLLM 借卡绑定完整副本，当前限制每 unit 一个会话，不能与 command 配额模式任意组合 |
| 评分与调度不同 | 原生 GPU 任务严格评分需要可信任务活动归属。整卡繁忙不等于本任务在计算，旧 Gate B 回复节流不能提供这种证明 |

procfs 是 Linux 用文件形式暴露进程信息的接口。当前平台登录环境本身可能处在容器中，其 `/proc` 不一定能对应 GPU 驱动报告的宿主进程号。eBPF 是在 Linux 内核中运行受检查的小程序，这里用于登记进程身份及任务归属，GPU 数值仍来自 NVML。它绕开的是宿主 procfs 挂载需求，不是取消所有权限和部署要求。

两种身份方案的区别可以理解为“查进程档案”和“在内核中登记”。procfs 按宿主进程号查询出生时间与资源组。eBPF 则在节点确认容器归属后，登记这次命令对应的资源组和注册号，通过内核事件维护真实宿主进程号与出生时间。进程退出时使旧记录失效，避免进程号被重新使用后认错任务。身份采集失败时不抵扣未知占用，不能把采不到数据当作显存为零。

旧 Gate B 会根据 GPU 活动推迟给模型的回复，属于软节流，达到等待上限仍可能放行。它既不等同于当前 command 的容量准入，也不能保证评分采样期间的独占或归属正确。

## 为什么同卡借还还不能与 command 组合

**后续策略方向**：先使用其他有容量的独立 GPU，包括同机未被训推占用的卡。只有这些资源紧张时，才考虑 vLLM 保持服务时的安全余量，最后才评估长空窗中的 sleep / offload。设备级优先级已经接入派发与准入，在两张真实 H20 上完成了独立卡优先、注入压力后回退、释放压力后返回三阶段，三次 CUDA 返回 42，资源已清理。后备卡使用常驻显存压力模拟已有占用，没有真实 vLLM 或训练模型。模型峰值预约、计算干扰控制、窗口确认与提前请求处理仍未完成，不能据此宣称活跃训推共享已验收。总目标是整批任务更早完成，不能只按当前显存读数或 GPU 利用率决定。下文说明的是当前两条协议为何仍被隔开。

**截至 2026-10-27，二者在原理上可以分层组合，但当前实现没有把两套使用权协议接起来，源码明确拒绝这个组合。** 借卡回答“现在整套推理 GPU 交给模型，还是交给环境”，command 回答“环境资源池里的哪些命令现在可以使用多少 GPU 预算”。把普通命令批次叫作 command，容易误以为两套能力已经接通。

下面画的是两条现有路径，横向没有已实现的组合箭头。vLLM 是生成模型回答的推理服务，推理副本是一套能够完成生成的模型实例，可能跨多张 GPU。租约是一次会话的资源使用凭证，unit 是配置中的资源池。

```text
[1] science runner 取得 EnvRouter 会话租约
    │
    ├─ 独立环境 GPU，gpu_reservation=command
    │   [2] 统一执行后端提交显式 GPU 命令
    │     ↓
    │   [3] command 调度器排队、检查容量 → 节点授予 GPU 设备权限
    │     ↓ 命令执行结束
    │   [4] 撤销权限、确认旧句柄与 GPU 工作消失 → 释放命令预算
    │       容器继续 CPU 工作或等待模型，其他容器的命令可以申请
    │
    └─ 绑定 rollout_replica_rank，当前 gpu_reservation=episode
        [5] 借卡状态机 → 推理协调器 / vLLM 关闭生成准入
            等待在途生成，sleep(level=1)，检查每张卡的余量
          ↓
        [6] 恢复环境容器 → 执行两次模型调用之间的一批命令
          ↓ science agent 准备调用模型
        [7] 暂停本租约容器，确认整套 GPU 回到睡眠后基线
            → vLLM wake → 模型生成
          ↓ 模型调用结束，finally 再进入 [5]
        [6] 再次恢复容器，继续命令批次

[8] 会话结束或失败：清理本会话资源，确认归还后释放使用权
    借卡交接不确定时保持隔离，不能仅删除账本后继续使用
```

图例：各部分的职责和交接结果。

| 编号 | 职责和交接结果 |
|---|---|
| 1 | 运行器根据租约，接入借卡钩子或统一作业后端 |
| 2 | 统一后端执行命令生命周期，命令持有策略申请 GPU 预算 |
| 3 | 命令调度器排队准入，节点核对归属并授权设备 |
| 4 | 节点撤销访问并检查残留，确认归还后释放命令预算 |
| 5 | 借卡状态机申请整副本使用权，协调器登记预约，模型服务完成睡眠 |
| 6 | 节点恢复容器，模型请求结束后的收尾路径触发下一轮环境阶段 |
| 7 | 节点检查物理归还，借卡状态机在条件满足后唤醒模型 |
| 8 | 容器后端收尾，借卡状态机清理后解除副本预约，Router 处理失败隔离 |

**两个模式具体差在哪里。**

| 对比项 | 独立环境卡的 command | vLLM 同卡借还 |
|---|---|---|
| GPU 来自哪里 | 已配置给环境使用的卡，不主动指挥同卡 vLLM 睡眠 | 显式绑定一个推理副本的完整设备集合 |
| 谁持有使用权 | 每个会话保留主机资源，每条显式 GPU 命令单独申请和归还 GPU 预算 | 一个会话保留副本预约，在 ENV 和 MODEL 两个阶段之间切换 |
| 切换时机 | 显式 GPU 作业开始与结束 | science agent 的模型请求前后，一次模型回答可对应多条命令 |
| 并发范围 | 不同容器的命令容量够可重叠，当前每个会话至多一个等待或活动申请 | 当前 unit 要求 `max_containers=1`，仅一个借卡会话 |
| 模型思考时环境能做什么 | GPU 归还后，容器仍可继续 CPU 工作 | 环境容器保持暂停，文件和 shell 状态保留 |
| 归还判据 | 禁止新设备打开，并检查该容器残留设备句柄与 GPU 计算进程 | 整套 GPU 身份不变，无超出睡眠基线的 GPU 进程，显存回到基线容差内 |

command 的设备控制使用 Linux cgroup v1，即按进程组设置设备访问权限。撤销权限只阻止新的设备打开，不会自动让旧 CUDA 进程丢掉显存，所以必须额外检查旧句柄和 GPU 工作。借卡使用的 `docker pause` 也只暂停容器，不会释放它持有的显存。如果检查未通过，当前借卡节点会暂时恢复容器让已有工作完成，再重试检查，超过时间预算后进入失败处理。两条路径都没有实现任意长期 GPU 进程的自动保存与恢复。

**实现有三处明确边界。** EnvUnit 配置校验拒绝同时设置 `gpu_reservation=command` 与 `rollout_replica_rank`。运行器只给非借卡会话安装统一 GPU 作业后端。Docker 后端构造时再次拒绝同时传入作业后端与借卡绑定。因而当前“统一 episode / command 后端”只统一了独立环境卡上的作业执行，没有包含借卡这一资源来源。

这里限制的是同一个借卡 unit / 会话同时使用 command 协议。不同 unit 分别采用独立卡 command 和借卡 episode，不属于上述组合禁令，但仍要满足设备不重叠及各自部署条件。本次没有验证混合部署的完整运行。

**一个可以手算的例子，数字均为教学假设。** 假设一张卡有 24 GiB，模型醒着占 18 GiB，环境 A 的 GPU 命令需要 10 GiB。

1. 只用 command 调度，把模型当作外部占用时，当前余量只有 `24 - 18 = 6 GiB`。10 GiB 命令应等待。调度器不会因为命令在排队，就自动调用模型 sleep。
2. 用现有借卡路径，先让模型 sleep。假设睡眠后仍占 1 GiB，环境 A 运行时占用约为 `1 + 10 = 11 GiB`，另需满足安全余量。A 下一次问模型前，GPU 工作退出并归还显存，容器暂停，再让模型恢复到约 18 GiB。容量问题可以通过分时使用解决。
3. 假如未来去掉单会话限制，想让 A、B 两个命令各占 10 GiB，则模型睡眠期间约需 `1 + 10 + 10 = 21 GiB`。但 A 先结束并准备问模型时，B 还占着 10 GiB。A 的 command 归还成功，不能证明整张卡可以交给模型，贸然唤醒约需 `18 + 10 = 28 GiB`，超过容量。
4. 保留现有借卡物理检查会发现 B 的 GPU 进程与显存还在，从而拒绝立即交接。可它没有管理多个命令申请的整体退出顺序。必须新增协调协议，才能让 B 完成、阻止后续 C 插入、确认所有借用者归还，然后唤醒模型。

第 3、4 步是对未来组合设计的推演，**不是当前已观察到的组合运行 bug**，因为现有配置校验已经禁止这种组合。若后台 GPU 程序还反过来等待下一次模型回答，就可能形成“模型等 GPU 归还，GPU 程序等模型”的循环等待。集成时要明确允许的命令生命周期，不能靠取消所有检查来避开问题。

**建议怎样组合，以下尚未实现。** 将整副本的借还放在外层，将环境命令的配额分配放在内层。内层只有拿到外层确认的 ENV 使用权后才能授权 GPU。要切回 MODEL 时，先关闭内层新准入，再等待或按约定取消全部活动命令，确认物理归还，最后恢复模型。旧命令的延迟授权和归还消息还需要绑定到本轮借卡代号，不能影响下一轮。多卡副本必须整体交接，超时与异常也由同一套规则决定是否继续隔离。

先做单会话组合，可以复用作业等待、取消和执行接口，但并不会自动得到多任务装箱收益。放开多会话后，才需要进一步决定“模型请求和环境命令谁先运行、最多等多久”，避免任何一方长期饿死。不能把这个调度问题简化成“把 `max_containers` 改大”。每条小命令都 sleep / wake 还会增加交接成本，保留模型调用之间的批次边界可能更合理，需要真实工作量验证。

| 步骤 | 图中编号与入口 | 输入、输出及状态变化 |

**可运行教学示例。** 下面完整内嵌一个简化的状态检查模型，不需要其他文件。它演示“账本清零不等于显存归还，以及模型状态仍需有效”的两个条件，假设借卡阶段有 A、B 两个使用者。它不执行真实 sleep / wake，也不是当前生产协议。

```bash
python3 - <<'PY'
leases = {"A": 10, "B": 10}
baseline = 1
measured = 21
weights_valid = False

def next_action():
    if leases or measured > baseline:
        return "wait_for_physical_return"
    if not weights_valid:
        return "wake_and_restore_weights"
    return "serve_model"

print("active:", next_action())
leases.clear()
print("ledger_empty:", next_action())
measured = baseline
print("physical_returned:", next_action())
weights_valid = True
print("restore_verified:", next_action())
PY
```

输出依次为 `active: wait_for_physical_return`、`ledger_empty: wait_for_physical_return`、`physical_returned: wake_and_restore_weights`、`restore_verified: serve_model`。账本清零后，实际占用仍是 21，系统继续等待。模拟归还到基线 1 后，才进入模型唤醒和状态恢复，确认模型状态有效后才能服务。脚本对应图中 7、8，`weights_valid=False` 表示需要恢复模型内容的教学分支，不表示当前一级睡眠必然丢弃模型权重。

已有 CPU 教学验证与真实配置对象检查确认：独立卡的 episode / command 与借卡的 episode 可通过字段校验，借卡的 command 被明确拒绝。字段校验通过不等于节点部署或完整训练验收通过。现有 GPU 证据仍是两组不同问题的验证：2026-10-15 完成了两轮受控 Docker CUDA / vLLM 同卡交接，未覆盖完整训练侧权重传输与模型请求路由。2026-10-26 的高压力三步训练则在独立环境卡上验证了 command 调度收益。它们**不能拼成“command + vLLM 同卡共享已通过训练”的结论**。两组条件与结果已经包含在本文 Results 部分。

## 未来规划与验收标准

以下是**建议的推进顺序，不是已实现能力或排期承诺**。先让最新能力在一个真实任务闭环，再扩大可接入任务范围。自动选择 episode / command 需要资源画像和安全释放边界，适合放在这些基础之后。

| 优先级 | 工作内容 | 完成时应拿到的证据 |
|---|---|---|
| P0：原生任务与最新版本闭环 | 选一个原生 science GPU 任务，将显式 GPU 执行、可信归属、任务评分、取消和清理串起来。冻结包含最新修复的代码版本 | Docker 内真实 CUDA 工作得到本任务的活动证据。CPU 假工作不能借用别人的 GPU 活动通过严格评分。取消或正常结束后核实进程、容器及显存释放 |
| P0：补齐新修复实机验收 | 小规模核验逐卡预算、主容器 / verifier / sidecar 限额、节点失效停止派发和恢复清理 | 真实两卡中单卡放不下时拒绝或等待。全部容器限制与账本一致。故障下有界结束，不遗留全局暂停，不在清理未完成时放行 |
| P1：当前版本低压力基准 | 用相同成功工作量、固定 OFF 和冻结 ON，做少量顺序平衡对照 | 同时记录冷启动、工作阶段、总时间、等待、OOM 和有效 token，明确额外开销及适用负载。达到预设结论后停止，不自动拉长训练 |
| P1：通用任务接入与可观测性 | 把 GPU 阶段边界、峰值预算、作业生命周期、归属与清理做成明确适配契约，统一关键指标 | 新任务主要补资源声明和 GPU 执行适配，不需要复制 science 专用脚本。日志能区分准备慢、排队慢、执行慢和清理慢 |
| P1：服务故障恢复 | 持久化或可重建的租约、跨控制器设备所有权、清理确认后再调度 | 控制器退出重启或通信中断不会重复授权，不会把遗留工作当作已释放 |
| P2：提高剩余容量利用率 | 改善 FIFO，即先进先出队列中大任务挡住后续小任务的情况。允许能放下的小任务使用余量，并限制大任务的等待时间，完善多卡逐任务归属 | 在相同混合负载下减少空闲和等待，同时大任务有等待上界。不能只报告小任务变快 |
| P2：同容器多作业并发 | 按作业建立独立预算和进程归属，设备权限按活动作业生命周期管理 | 容量够时 A/B 重叠，不够时 C 等待。取消 A 不杀 B、不撤掉 B 所需权限，不错误归还 B 的预算 |
| P3：自动持有和卸载策略 | 基于任务能力、峰值、等待时长及释放恢复成本选择持续占用、command 或协作式卸载 | 比较释放加恢复成本与可利用等待窗口，只在有安全恢复方法且净收益为正时切换。不能通过检测“模型在生成”就强制撤走 CUDA 状态 |
| P3：完整训推与环境共享 | 将受控借卡接入完整训练的模型请求路由、权重有效性与传输登记，再评估和 command 的组合 | 模型正确恢复，容器物理归还后才唤醒，测量交接总成本和完整训练收益，避免只证明裸 sleep / wake 可调用 |

本阶段不把运行中活容器跨机迁移、任意 CUDA 程序强制抢占或最优调度器作为已有承诺。它们需要额外的任务恢复协议或系统支持。

## 专项设计：自动选择模式与预测式卸载

**本节是后续设计提案，不是已经实现或已经测出收益的功能。** 目标是新任务接入后，系统根据它的 GPU 状态、可释放边界、实际资源压力和预计等待时间，选择合适的持有策略，减少人工指定模式的负担。下面的数字全部是教学假设，与前文真实实验数字分开。

先看完整决策链。图中“任务适配器”是任务与资源服务之间的接口，负责说明如何安全停止 GPU 工作、保存状态和恢复执行。预测器负责估算时间，最终授权仍由资源账本和执行节点完成。

```text
[A1] 任务适配器：声明命令边界、持久状态、可卸载能力
         + 运行观测：任务进程、显存、阶段耗时、模型等待
                             ↓
[A2] 能力识别：无跨命令 GPU 状态 / 可恢复状态 / 未知或不可恢复
                             ↓
[A3] 选择持有方式
     无跨命令状态 → command，在命令边界确认归还
     有持久状态   → episode，再决定常驻或临时卸载
                             ↓
[A4] 检查是否有必要让位
     已有空闲容量够用 → 正常准入其他任务
     没有等待者       → 保持当前状态
     容量不足且有等待者 → 进入预测评估
                             ↓
[A5] 预测：剩余等待、卸载、借用者占卡、恢复、完成时间
     检查能力、逐卡容量、主存、期限与预计净收益
                ├─ 不满足 → 保持常驻，等待者排队
                └─ 满足   ↓
[A6] 安全点 → 卸载 → 确认释放 → 授权借用者
     → 借用者确认归还 → 原任务重新准入、恢复、校验
                             ↓
[A7] 记录实际成本和预测误差，调整后续策略
```

图例：A1 是任务能力接口，A2 / A3 是模式选择，A4 是实时压力判断，A5 是成本与收益估算，A6 是执行和资源交接，A7 是观测反馈。A2 至 A7 中的自动策略尚待实现。现有统一执行后端、资源账本、进程归属与受控借卡能力可以成为基础，但不能把它们等同于已经有了这套自动决策器。

**一、先区分“持有范围”和“状态是否常驻”。**

episode / command 回答的是“GPU 预算按整个会话还是按命令申请”。offload / reload 回答的是“已经存在的 GPU 状态怎样临时移出、之后怎样恢复”。offload 指把恢复执行所需的数据移到主机内存等位置并释放可归还的显存，reload 指重新申请资源、恢复数据和运行状态。暂停一个进程通常不等于释放显存，不能只停进程就给其他任务放行。

| 识别出的任务形态 | 建议模式 | 等待期间的行为 |
|---|---|---|
| 每条 GPU 命令独立，结束后没有后续必需的 GPU 状态 | 优先 command | 命令结束并确认归还后，其他任务可使用容量，不需要额外卸载上下文 |
| 一个长生命周期进程保存 GPU 模型或仿真状态，能够安全卸载并恢复 | episode，加可选卸载策略 | 会话、文件和恢复信息保留，只有满足成本与容量条件时才临时归还一部分 GPU 预算 |
| 有常驻 GPU 状态，但没有可靠恢复接口 | episode，保持常驻 | 不自动撤销仍被使用的容量，其他任务排队或选择别的资源 |
| 新任务行为未知，只有普通 shell 命令 | 先用保守的 episode 管理并采集画像 | 遥测用于提出模式建议，不凭低利用率直接卸载或切换 |

“episode 加可选卸载”需要新增阶段状态和预算交接协议。当前 episode 策略并没有这个通用能力，而且模式目前绑定在 unit 配置中。后续应把节点资源池的设备能力与每个会话的持有策略分开，让同一个受支持资源池能够管理不同类型的租约。不能只运行时修改一个 `gpu_reservation` 字符串，就认为原有预约、设备权限和状态已经完成转换。

例如，一个 science 程序在多轮交互之间保留 GPU 上的数值网格，它仍是一条完整 episode。等待模型时，可以在明确的迭代边界保存网格、卸载显存，之后恢复同一网格继续运行。这不是结束该 episode，也不是丢弃状态后重新开始一条 command。反之，如果每条命令都会自行加载输入、计算并退出，就适合按命令管理。密集短命令也可考虑合并为一个受控批次，避免反复准备的成本，但必须保留真实的安全释放边界。

**二、自动识别依赖“能力声明加运行验证”。**

系统可以自动选择策略，但不能仅凭程序名、GPU 利用率降到零或一次显存下降，就推断任意程序能够安全恢复。自动化的对象是选择过程，恢复能力仍需要任务框架或适配器提供。

| 输入信息 | 如何取得 | 用于什么决策 |
|---|---|---|
| GPU 工作入口与完成边界 | 受控工具调用、任务阶段事件、命令及其子进程完成确认 | 确定何时能申请、停止新增工作和检查归还 |
| 跨命令保留的状态 | 适配器说明，结合多轮进程和显存观察 | 区分无状态命令与常驻任务。显存回落本身不能证明后续不会使用旧状态 |
| 卸载与恢复能力 | 适配器提供停止新工作、等待当前计算完成、保存、释放、恢复和校验接口 | 作为允许卸载的前置条件，不由预测器凭空补出 |
| 可释放量与残留量 | 可信任务归属、逐卡实际测量 | 判断卸载后到底能容纳谁，不能把申报总量当作必然可释放量 |
| 时间和状态规模 | 记录每阶段开始结束、待保存数据量、恢复开销、模型请求状态 | 学习相似任务的卸载、借用和恢复时间 |
| 等待者与资源约束 | 调度队列、优先级、期限、主存和逐卡容量 | 判断让给谁，以及对原任务造成的等待是否可接受 |

初次接入时，已经由适配器保证独立命令语义的任务可以直接选择 command。其余任务先保持保守策略，经过有界的观察和恢复验证后再开放更积极的选择。多次观测只是增加时间预测的可信度，不能取代安全恢复契约。模式变化只在安全点或下一次会话开始时提交，旧预算与新预算必须一致交接。

如果一个被声明为独立命令的任务实际上留下后台 CUDA 子进程，系统应保留其占用、阻止错误归还并报告契约不符合，而不是先释放预算，再把“自动识别成 episode”当作补救。

**三、episode 是否卸载，先判断能否释放，再判断是否值得。**

第一步是确认卸载有必要。如果其他任务在现有余量里已经放得下，就按正常准入共享，不必搬运常驻任务。如果没有可执行的等待者，也不应为了追求更低的显存曲线反复卸载。

第二步是容量与恢复可行性。教学假设一张卡预算 80 GiB，A 常驻占 48 GiB，B 峰值需 40 GiB，GPU 安全余量 4 GiB。两者常驻合计 `48 + 40 + 4 = 92 GiB`，放不下。若 A 卸载后仅残留 4 GiB，则借出期间为 `4 + 40 + 4 = 48 GiB`，可以容纳 B。还必须给 A 的主机内存副本及额外缓冲预留空间，确认 B 归还后 A 能恢复。多卡任务逐卡检查，不能用另一张卡的空闲抵消本卡超量。

第三步才是时间预测。建议记录以下五个量，全部采用同一时间起点：

| 符号 | 含义 | 需要包含的实际开销 |
|---|---|---|
| W | 从现在到 A 再次需要 GPU 的剩余等待时间 | 模型请求的剩余排队和生成、CPU 阶段，不能照搬上一次完整等待时间 |
| O | A 从决定卸载到资源确认可借出的时间 | 等待当前计算安全结束、保存状态、传输、释放和节点确认 |
| B | 借用者获得资源到确认归还所占的时间 | 模型加载或唤醒、GPU 计算、可能的再次卸载以及归还检查 |
| R | A 从可恢复到重新可执行的时间 | 资源重新准入、reload、状态校验、必要的运行时重建和同步 |
| G | 留给预测误差的保护时间 | 避免实际稍慢或模型稍早返回就立刻冲突 |

不能只按“状态字节数除以传输带宽”估算 O 和 R，等待安全点、内存分配、重新初始化和通信竞争也会花时间。预测应按任务类型、状态规模、设备和当前竞争情况分类统计，采用偏短的可用等待窗口、偏长的交接耗时。没有可靠样本时，先保持常驻或进行有界的成本测量，不把未知成本当作零。

第一版预测器可以从简单统计开始：O / R 使用同类任务近期真实卸载恢复的分布，B 使用相同模型、输入规模和执行批次的占卡记录，W 结合当前请求排队情况、已生成长度、历史生成长度与速度估计剩余时间。生成可能提前结束，未来长度并不已知，所以 W 应给出范围和可信程度，不能把回复长度上限直接当作必然等待时长。例如 W 估计为 30 至 60 秒，就先按较短的 30 秒判断能否放入，而不是按 60 秒填满。每次阶段事件到达后更新预测，记录“预计”和“实际”的差异，持续偏乐观时提高余量或停用自动卸载。

对于“A 等待另一个设备上的模型返回，B 是独立等待者”的情况，第一版可采用保守窗口规则：

```text
O + B + R + G <= W

即：A 卸载、B 完成并归还、A 恢复，再加保护时间，
都应能放进 A 原本的等待窗口。
```

这是一条尽量不推迟 A 的策略，不是所有有收益调度的必要条件。后续若允许 A 增加少量延迟，可以在明确的延迟预算内放宽，但必须比较两边的收益和损失。

**四、“卸载加恢复小于别人省下的时间”是有用信号，还需要检查整体收益。**

首先明确优化目标：是尽快完成所有任务，还是让高优先级任务更快完成。不能把某个 GPU 多忙了几十秒，直接当成训练少用了几十秒。若借出的任务不在训练等待的关键路径上，它提前完成也可能不缩短这一步训练。

一种可解释的比较方式，是预测保持现状和执行让位这两套方案的完成时间。设 F 表示完成时刻，w 是体现优先级的权重，可以比较：

```text
预计完成时间净收益 = Σ w_i × (F_i_保持现状 - F_i_让位)

只在安全条件满足、净收益为正且超过误差余量时考虑让位，
同时约束原任务和其他任务的最大延迟。
```

如果目标是整批任务尽快结束，就直接比较两种方案中最后一个任务的完成时间，或训练数据汇合点的就绪时间。各任务等待时间的减少不能直接相加当作整批墙钟收益。让位方案的时间线上已经包含 O、B、R 时，也不能再把卸载恢复成本扣一遍，否则会重复计算。

下面用两组可手算例子说明。假设 A 的状态安全可卸载，B 是另一模型的一批有界请求，B 的占卡时间已经包含加载、执行和归还。两者不能同时放入当前 GPU，A 等待的模型运行在另一张卡上，不依赖 B。A 收到结果后还需 10 秒 GPU 工作，然后结束并释放资源。

固定 `O = 4 秒，B = 20 秒，R = 6 秒，G = 4 秒`，两个任务的完成时间权重均为一。以下均为教学假设，不是实测。

| 情况 | 保持 A 常驻 | 让 A 卸载后运行 B | 判断 |
|---|---|---|---|
| 长等待，W = 60 秒 | A 在 60 秒恢复计算，70 秒完成。B 随后运行，在 90 秒完成 | A 在 0 至 4 秒卸载，B 在 4 至 24 秒运行并归还，A 在 24 至 30 秒恢复。A 仍在 60 至 70 秒计算 | 窗口 `4 + 20 + 6 + 4 = 34 <= 60`。A 无延迟，B 提前 66 秒，整批从 90 秒降到 70 秒，节省 20 秒 |
| 短等待，W = 8 秒 | A 在 8 至 18 秒计算，B 在 18 至 38 秒运行 | B 仍到 24 秒才归还，A 到 30 秒才恢复，在 30 至 40 秒计算 | B 提前 14 秒，看似超过卸载恢复的 10 秒，但 A 推迟 22 秒，整批从 38 秒变成 40 秒。窗口也不满足，应保持常驻 |

这说明，用户提出的 `offload + reload < 让位节省的时间` 可以作为候选筛选条件，但不能只看受益的 B。原任务 A 的恢复延迟、其他受影响任务及完整完成时间必须一起考虑。长等待例子里，搬运成本被 A 原本就存在的等待隐藏，B 的计算提前完成，才带来实际整体收益。

**五、如果被让位的模型正是 A 等待的 vLLM，需要按依赖关系调度。**

前面的 W 假设模型在其他设备上生成。若 A 正等着同一张卡上的 vLLM 生成下一条指令，而 A 又占着使 vLLM 无法恢复的显存，那么“等待 vLLM 完成再决定是否卸载”可能形成循环等待。

这种情况不应把 vLLM 被阻塞的时间预测成一个可自由利用的空闲窗口。应显式标记依赖：A 要继续，必须先让 vLLM 获得 GPU。合法路径为“A 到达安全点并卸载 → vLLM 唤醒并生成结果 → vLLM 按协议归还所需容量 → A 重新准入并恢复”。预测目标是整条链的完成时间，需要计入两边的加载、卸载和模型权重有效性检查。

如果 A 无法安全卸载、两者又无法共存，就应在准入时避免这种组合，改用其他可服务副本或其他设备。自动选择器不能通过猜测未来会空闲来解决资源依赖冲突。现有受控 vLLM 借卡与 command 模式也尚未合成这套通用协议。

**六、预测只决定是否尝试，实际交接必须有确认。**

建议为可卸载 episode 增加以下状态。状态变化属于提案，不能认为当前已有同名完整状态机：

```text
常驻 → 停止新增 GPU 工作 → 到达安全点 → 卸载中
     → 已确认释放 → 借用者持有 → 借用者已确认归还
     → 原任务重新准入 → 恢复中 → 校验通过 → 常驻

任何阶段结果不确定 → 保留对应资源的占用或隔离状态
                    → 有界恢复或清理，不能直接重复授权
```

CPU 会话租约和恢复数据在卸载期间保留。GPU 账本只归还已经确认释放的部分，残留显存仍然计费。应记录恢复需求与恢复优先权，停止接纳会越过约定归还时间的新借用任务，但不能把同一份容量同时承诺给借用者和正在恢复的原任务。

预测 A 还会等待 60 秒，实际却在 15 秒返回时，应停止继续放入新借用者，等当前借用者在约定的安全边界归还，再恢复 A。不能为了兑现预测结果直接杀死一个没有恢复能力的任意 CUDA 程序。首版只接纳执行时间有上界或具备协作归还能力的借用者，超时按任务契约终止或隔离，确认物理释放后才能让 A 进入。

为避免短时间内反复搬运，还应设置最短驻留时间、两次卸载之间的冷却时间、连续错误后的退回常驻策略，以及每个任务的累计额外延迟上限。这些阈值需要通过实际负载校准，不在本提案中编造默认实测值。

**七、怎样逐步实现并验证。**

1. 先增加能力描述和时间观测，只生成“建议 command / episode / 可卸载”的记录，不改变任务行为。检查建议是否与真实命令、状态和释放边界一致。
2. 对已声明且验证过独立命令语义的任务，在会话开始时自动选择 command。对常驻任务保持 episode，补齐按租约记录策略与阶段的账本结构。
3. 选一个支持保存恢复的真实 science GPU 任务，先显式控制一次卸载和恢复。核验状态连续性、任务正确性、主机内存预算、物理释放以及恢复成本，再启用预测。
4. 用常驻方案与预测卸载方案做相同工作量的有界对照。同时记录 A 延迟、B 完成时间、整批耗时、搬运次数、主存峰值、预测误差和清理结果。必须包含“窗口长应该借出”“窗口短应该保持”“没有恢复能力不得卸载”“容量够无需卸载”四类输入。
5. 最后扩展到同卡 vLLM 依赖链、混合任务优先级和多个借用者。跨任务自动选择与物理交接通过之前，不追加大规模长时间训练来追求更大的提速数字。

下面是完全内嵌的 Python 教学模型，直接复制运行即可。它对应 A5 的时间线比较，不会加载模型、移动真实数据或操作 GPU，也不替代能力、显存和交接检查。它假设 A 等待的模型在另一张卡上，且等待时间不受本次搬运影响。

```bash
python3 - <<'PY'
def evaluate(wait, *, can_offload=True, has_waiter=True, already_fits=False):
    if already_fits:
        return "share", "已有容量足够，正常准入，不卸载"
    if not has_waiter:
        return "resident", "没有等待者"
    if not can_offload:
        return "resident", "缺少安全恢复能力"

    offload, borrow, reload, guard, a_tail = 4, 20, 6, 4, 10
    # A5：保持常驻时，B 必须等待 A 完成。
    keep_a = wait + a_tail
    keep_b = keep_a + borrow
    # A5：让位方案显式计入卸载、B 占卡和 A 恢复。
    yield_b = offload + borrow
    ready_a = yield_b + reload
    yield_a = max(wait, ready_a) + a_tail
    window_ok = ready_a + guard <= wait
    completion_gain = (keep_a - yield_a) + (keep_b - yield_b)
    batch_gain = max(keep_a, keep_b) - max(yield_a, yield_b)
    decision = "offload" if window_ok and completion_gain > 0 else "resident"
    detail = (
        f"A {keep_a}->{yield_a}s, B {keep_b}->{yield_b}s, "
        f"sum_gain={completion_gain}s, batch_gain={batch_gain}s"
    )
    return decision, detail

cases = [
    ("long_wait", 60, {}),
    ("short_wait", 8, {}),
    ("no_restore", 60, {"can_offload": False}),
    ("enough_capacity", 60, {"already_fits": True}),
    ("no_waiter", 60, {"has_waiter": False}),
]
for name, wait, options in cases:
    decision, detail = evaluate(wait, **options)
    print(f"{name}: {decision}, {detail}")
PY
```

预期输出：

```text
long_wait: offload, A 70->70s, B 90->24s, sum_gain=66s, batch_gain=20s
short_wait: resident, A 18->40s, B 38->24s, sum_gain=-8s, batch_gain=-2s
no_restore: resident, 缺少安全恢复能力
enough_capacity: share, 已有容量足够，正常准入，不卸载
no_waiter: resident, 没有等待者
```

`sum_gain` 是两任务完成时间改善的合计，`batch_gain` 是整批结束时间的改善。短等待行展示的是被拒绝的让位方案会造成什么后果，实际决策保持常驻，并不真的把 A 延迟到 40 秒。这些结果只验证教学模型的算术和决策，不是自动策略已进入框架或取得性能收益的证据。

## 完整生命周期与独立可运行演示

| 步骤 | 图中编号 | 输入与状态变化 |
|---|---|---|
| 1. 放置 | 1 → 2 | 按实际组大小读取需求和健康容量，选择 worker。此时尚未取得最终执行许可 |
| 2. 会话准入 | 2 → 3 | 提交资源需求，等待节点探活和清理确认后返回允许、等待或拒绝 |
| 3. 容器创建 | 3 → 4 | 运行器将租约配置交给 Harbor，在最终容器集合施加标签和限制 |
| 4. GPU 工作 | 4 → 5 → 6 | 统一后端选择持有策略。command 经命令排队和预算检查，节点授权后才执行 |
| 5. 并行收尾 | 6 → 7 | 等待撤权和归还确认。采用后台归还时，CPU / 模型规划可继续，下一条 GPU 工作仍必须服从归还状态 |
| 6. 结束与异常 | 7 → 3 | 评分后释放会话，异常进入按归属清理。待清理资源不能因为租约计时到期就直接重新使用 |
| 独立分支 | 8 | 借卡状态机在模型和环境阶段交替，不能将其伪装成 command 路径里的一个无条件步骤 |

下面的演示直接包含全部代码，安装 Python 3 的机器即可运行，不需要 PSRL 仓库、其他脚本、Docker 或 GPU。复制整个命令块到终端执行即可。

**这是教学模拟，不是生产调度器。** 它用简化账本模拟图中 3、5、7 的申请、等待和确认归还，假设外部占用一直为 70 GiB，已获准任务还没实际分配。实际系统还需检查进程身份、设备权限、节点健康、并发请求和真实释放状态。脚本最后还用本文表格中的数值生成上面的文本条形图，图表数据无需外部文件。

```bash
python3 - <<'PY'
capacity = 90
measured = 70
reservations = {}

def request(name, amount):
    # 图中 3、5：把已承诺但尚未分配的额度计入准入。
    projected = measured + sum(reservations.values()) + amount
    allowed = projected <= capacity
    if allowed:
        reservations[name] = amount
    state = "granted" if allowed else "wait"
    print(f"{name}: {state}, candidate={projected} GiB")

request("A", 15)
request("B", 15)
request("C", 15)

# 图中 7：教学中假设 A 已经物理释放，再删除预约。
del reservations["A"]
print("A: return confirmed (simulated)")
request("B", 15)

groups = [
    ("三步训练累计，越短越好", 1100.80, 503.69),
    ("含初始化和清理的总时间，越短越好", 1954.11, 1415.01),
]
for title, off, on in groups:
    print(f"\n{title}")
    for label, value in (("OFF", off), ("ON", on)):
        bar = "#" * round(40 * value / off)
        print(f"{label:<3} |{bar:<40}| {value:7.2f} 秒  {value / off:6.2%}")
PY
```

申请部分的预期输出如下，后面会打印本文所列条形图：

```text
A: granted, candidate=85 GiB
B: wait, candidate=100 GiB
C: wait, candidate=100 GiB
A: return confirmed (simulated)
B: granted, candidate=85 GiB
```

`candidate` 表示“若现在批准这条申请，需要承担多少显存”，不是实测显存。B、C 显示 100 GiB 时都没有真的分配。A 确认归还后，B 的候选总量重新降到 85 GiB，因此获准。这个例子展示为什么先等待可以避免已经知道会超额的申请，但不能用它证明实际吞吐或不会发生任何 OOM。

## 设计演进与交付边界

从设计目标看，Env 的工作分为三层。三层的实现和验收进度不同，不应统一标成“已经完成”。

| 层次 | 要解决的问题 | 当前交付程度 |
|---|---|---|
| 第一层：统一管理环境 | 把分散的容器启动、容量检查、归属和清理纳入同一资源服务，避免各执行进程独立竞争 | science / Harbor 主路径已有实现和真实运行证据，全部环境后端统一仍未完成 |
| 第二层：缩短 GPU 持有范围 | GPU 阶段结束后允许别的任务使用容量，同时保留当前任务容器、文件和 CPU 状态 | 显式 command 模式已实现，具有本文高压力三步训练证据。任意任务自动接入和同容器并发仍未完成 |
| 第三层：跨角色动态共享 | 按实际任务特征，在环境、推理和其他工作之间自动选择资源持有、卸载和恢复策略 | 有受控模型借卡组件实现，自动模式选择、通用上下文卸载和完整训练共享验收仍属于后续工作 |

下一次可以明确交付的目标是：冻结一份包含新修复的版本，在一个原生 science GPU 任务上完成执行、归属、严格评分和清理验收，再对这个冻结版本测量低压力开销。这样可以把“单个组件能工作”推进到“同一个真实任务能完整使用这一套能力”，同时保持收益数字与代码版本一致。
