# 等待还是重新加载：前期长命令实验

> **核心结论**：当已有模型的 GPU 还要忙很久时，在另一张空闲卡加载副本，可以让两条长命令更早完成。本次两对机制对照合计从 **202.519 秒降至 124.805 秒，减少 38.37%**；与固定旧 runner 的一对比较减少 **37.15%**。计划中的 9 个正式区块完成了 5 个，已完成的配对通过同工作量与输出核对，其余组保留未完成状态。

这是 **2026-11-13 前期实验**。更完整的三种策略、短等待、临界等待和故障检查见[后续矩阵实验](warm-placement-matrix.md)，机制与源码教程见[代码阅读指南](../../knowledge/warm-placement-code-guide.md)。本页集中保留前期实验独有的初次负结果、计时审计、长命令算例和失败证据。

## 1. 实验想回答什么

新命令 A 需要模型 A。GPU 0 已有模型 A，却正在执行命令 B；GPU 1 空闲，但还没有模型 A。这里把已有模型的卡称为**热卡**，把需要加载的卡称为**冷卡**，描述的是模型缓存状态。

```text
等热卡：B 先结束 → A 使用已有模型执行
用冷卡：加载模型 A → 执行 A，同时 GPU 0 继续做 B
```

比较两条路径，需要同时考虑等待、加载与执行：

```text
热卡预计完成时间 = B 剩余时间 + A 执行时间
冷卡预计完成时间 = 加载 A 的时间 + A 执行时间
冷卡预计至少快 2 秒，且容量足够时，选择冷卡。
```

预测器读取 B 已完成的进度，每 16 步形成一个块，丢掉首次预热块，使用近期完整块的每步耗时中位数乘剩余步数。中位数是排序后的中间值，可减轻单个慢块的影响。进度缺失或过期时，A 继续在热卡排队。

两张卡由真实 EnvRouter 申请资源，原生 EnvWorker 启动各自容器和常驻模型服务；放置选择由研究驱动完成。两份 **episode 租约**覆盖服务的整个生命周期，期间持续记账模型显存，结束后再物理清理。该路径验证已提交 GPU 命令的放置，生产 Router 的默认决策仍沿用已有路径。

## 2. 怎样保持对照公平

任务取自 PostTrain 已有模型与 GSM8K 的两个公开数学样本。程序固定模型主体，仅更新最后一层归一化的缩放参数 `model.norm.weight`。每条命令恢复同一初始参数、重建优化器并固定随机种子，确保两边从同样状态开始。

| 项目 | 固定条件 |
|---|---|
| 目标 A / 阻塞 B | Qwen3-4B-Base / Qwen3-1.7B-Base |
| A / B 工作量 | 1536 / 2048 次参数更新，两条公开样本交替重复 |
| A 到达 | B 至少完成 64 步之后 |
| 画像，即独立测量准备成本 | A 在两卡各 128 步，B 在热卡 128 步 |
| GPU | 两张启动前空闲 H20，每卡约 95.6 GiB；各用 20 GiB 逻辑预算 |
| 初始缓存 | 热卡已有 A+B，冷卡无 A；A 约 7.49 GiB，B 约 3.21 GiB |
| 进度 | 每 16 步向节点本机临时目录原子发布完整文件 |
| 容器 | 实际 8 CPU 配额、48 GiB 主存、private IPC、64 MiB 共享内存 |
| 计划 | 三轮、9 个正式区块，总预算 1500 秒，提前固定执行顺序并交换卡角色 |

GiB 是容量单位，1 GiB = 1024 MiB。20 GiB 为调度逻辑预算，设备物理容量仍是约 95.6 GiB。IPC 是进程间通信；两后端采用相同容器条件。

| 对照 | 实际执行链与行为 |
|---|---|
| 当前机制 OFF | 当前 EnvRouter / EnvWorker 与同一服务，A 始终等热卡 |
| 当前机制 ON | 相同执行器，预计收益超过 2 秒且容量足够时在冷卡加载 A |
| 固定旧 runner | 提交 `0eeead861ffafed6bf31c962d259fd847775dcf9`，静态 GPU Compose，A 等热卡 |

机制 OFF 用来隔离放置选择的作用，固定旧提交另行比较。旧 runner 保留 GPU 参数下传、依赖来源与清理等必要运行补丁，完整差异保存于证据；其原有资源调度语义保持不变。当前源码为 `6aa328d` 加当时未提交研究实现，双方使用同一冻结服务、模型、数据、PyTorch `2.9.1+cu128` 和 Transformers `5.2.0`。

**主指标**从提交 B 前计时，到 A、B 的请求都返回为止，回答整组工作何时结束。A 完成延迟从 A 到达计时到服务完成，回答新命令少等多久。初始化、画像与冷卡清理单列，因此读百分比时须使用同一计时范围。

## 3. Results：长命令的完成时间

下表单位为秒，列出全部 5 个正式区块。

| 轮次 | 执行链 | A 等待 | A 加载 | A 执行 | A 完成延迟 | 整组完成时间 |
|---|---|---:|---:|---:|---:|---:|
| 1 | 固定旧提交 | 49.446 | 0 | 48.673 | 98.125 | 100.057 |
| 1 | 当前 OFF | 49.813 | 0 | 48.803 | 98.624 | 100.442 |
| 1 | 当前 ON | 0.143 | 10.633 | 50.236 | 61.017 | 62.882 |
| 2 | 当前 OFF | 50.431 | 0 | 49.828 | 100.266 | 102.077 |
| 2 | 当前 ON | 0.125 | 10.478 | 49.519 | 60.127 | 61.924 |

两次 ON/OFF 配对分别减少 **37.40%、39.34%**，按两次整组时间合计减少 **38.37%**。固定旧提交只有第一轮完整配对，结果为 `100.057 → 62.882 秒`，减少 **37.15%**。

把冷卡副本清理请求也加上，ON/OFF 合计减少 **38.16%**，相对旧 runner 的一次比较减少 **37.04%**。收益在计入副本清理后仍保留。完整服务寿命中的初始化与画像摊销，仍需按实际请求量另算。

全部完成配对的模型、步数、数据摘要、最终参数摘要和逐步损失摘要一致。实际共执行 19456 次任务内参数更新，其中正式区块 17920 次、画像 1536 次。这里统计的是任务程序更新，实验没有执行 PSRL 策略训练。

## 4. 跟着一次真实决策算收益

第一轮 ON 决策时，B 已完成 64/2048 步。根据当时三个有效进度块，预测剩余 **49.664 秒**，实际剩余 **49.117 秒**，高估约 0.547 秒。A 的校准加载成本约 11 秒，因此预计少等的时间远大于加载与 2 秒门槛，选择冷卡。

```text
热卡：B 再执行约 49.12 秒后结束
冷卡：通道等待 0.14 秒 → 加载 A 10.63 秒 → 执行 A 50.24 秒
A 到达到服务完成：61.02 秒
提交 B 到两条请求都返回：62.88 秒
```

OFF 中 A 自身执行 48.80 秒，ON 为 50.24 秒。**收益来自把等待变成两卡并行**，同时支付了约 10.6 秒加载和额外 A 副本显存。用实测四舍五入可手算：串行约 `51+49=100 秒`，复制并行约 `max(51,11+50)=61 秒`。

5 个区块的剩余预测绝对误差约为 0.060、0.184、0.547、0.863、1.642 秒，平均 0.659 秒。这是同一类固定工作量的五次观察；其它任务需检查自己的进度稳定性。

## 5. 初次实验为什么没胜过旧执行器

初次协议中 A 只有 256 步，执行约 9 秒，B 为 2048 步。ON 的 A 更早完成，但当时整组尾部指标为 **70.81 秒**，旧 runner 为 **66.10 秒**。原结果保存在[初次证据](warm-wait-or-rebuild-evidence.json)。这份尾部指标从 A 到达开始，与后来的主指标起点不同，分别阅读。

审计发现，B 的步内计算接近，较大差异出现在原步计时之外：

| 初次执行链 | B 计算墙钟 | 步内累计 | 步外差额 |
|---|---:|---:|---:|
| 当前 OFF | 77.776 | 53.656 | 24.120 |
| 当前 ON | 71.271 | 53.116 | 18.154 |
| 固定旧 runner | 57.650 | 52.375 | 5.275 |

OFF 比旧 runner 多 20.126 秒，其中 18.846 秒位于步计时之外，约占差额 93.64%。原记录未分别测文件访问、序列化与 CPU 调度，这些因素的贡献仍待定位，见[初次差异审计](warm-wait-or-rebuild-initial-audit.json)。

随后长实验在启动前统一两项条件：所有组改为本机进度文件、每 16 步发布，并把 A 延长为 1536 步。A 较短时，能通过重叠节省的总时间本来就有限；较长的 A 才更容易看清并行收益。这两项变化一起实施，故各自的独立贡献未分离。

新条件下，第一轮旧 runner 的 B 墙钟为 51.091 秒、步内累计 51.034 秒，进度写入约 52.1 毫秒；A 对应为 48.673 秒、48.631 秒、37.9 毫秒。秒级外围膨胀在这组没有重现。新旧条件的完整记录分别保留。

## 6. 未完成组、故障与资源清理

三轮 9 个正式区块实际完成 **5 个**。第二轮旧 runner 完成画像后，剩余预算少于 145 秒的入场门槛，因此未提交正式命令；第三轮未启动。原计划状态保持 `incomplete`，已完成的两对机制比较与一对旧基线比较可独立使用。

初次当前组还遇到一次启动故障：Ray 依赖来源检查反序列化动态模块时，无法导入 `long_study_backend`，当次服务与 GPU 工作均为零。修复只把来源查询改为自包含远程函数，保存失败、补丁与指纹，再检查清理后恢复该未开始工作的组。已完成旧基线保留原结果。

原 1500 秒截止时间包含修复经过时间，总流程约 **1316.82 秒**结束，后续采样受入场门槛与清理预留限制。各已启动运行最终所属容器为 0、GPU 无计算进程、约 0.188 MiB 驱动占用，原生 Router 活动租约归零。

本次未取得 CPU 限流快照，也未采集运行中 GPU 频率与利用率，只有任务计时和启动/收尾状态。两张目标卡独立使用，容器 CPU 配额仍共享宿主调度。

## 7. 结果的适用条件

可采用此思路的场景是：工作总量与进度可报告、热卡存在明显等待、冷卡有容量，而且加载成本小于可省等待。未知停止时间、输入长度突变或进度过期时，现有研究路径保留热卡排队。

复制会增加约 7.49 GiB 的 A 副本。若其它任务即将需要冷卡，这项选择的整体收益可能改变。当前实验验证的是固定已提交工作，两条公开样本重复为长命令；自然 agent 的队列、模型变化、资源竞争与覆盖比例，需要另做调查。

后续矩阵已覆盖长、短和临界等待以及部分故障条件，见[完整对照](warm-placement-matrix.md)。本页与[模型亲和探索](joint-gpu-placement.md)分别使用自己的工作量与计时范围，结果各自成立。
