# 真实模型命令的驻留与跨卡放置探索

> **核心结论**：在两张 GPU 执行六条短训练命令时，把使用同一模型的命令放在一起，可减少重复加载。在每卡 10 GiB 逻辑缓存预算下，简单模型亲和相对先进先出，均衡组合平均少用 **42.7%** 时间，偏斜组合少用 **55.5%**。更复杂的联合枚举有快有慢，当前应先把简单亲和作为基线。

实测日期为 2026-11-13，基于 `6aa328d` 加当时未提交研究实现。2026-11-16 整理本文只读既有结果。实验验证同一研究执行器中的任务放置，生产 EnvRouter 的能力仍以[当前设计](../../knowledge/current-design.md)为准。

## 问题与全局流程

假设六条训练命令都已提交，分别使用三种模型，两张 GPU 各能执行一条。直接把下一条派给空闲卡，可能让同一模型在两卡重复加载；把同模型命令尽量放同一卡，可以省准备时间，也可能让另一卡等待。实验比较哪种安排更早完成六条工作。

**模型亲和**是尽量把同模型请求放在一起；**GPU 缓存**是请求结束后继续把模型留在显存。缓存放不下时采用 LRU，即先移除最长时间未使用的模型。每种策略拥有相同进程、缓存和容量，只改变顺序与放置。

```text
[J1] 既有公开样本、固定预训练模型、两次参数更新程序
       ↓ 一批六个命令均已提交，不知道未来 Agent 还会做什么
[J2] 独立画像：分别测量模型加载、执行时间与参数字节数
       ↓ 所有策略得到同样信息与同样显存预算
[J3] 先进先出 / 按时长排序 / 模型亲和 / 联合枚举规划
       ├→ [J4] GPU A 的专属进程与模型缓存
       └→ [J4] GPU B 的专属进程与模型缓存
                  ↓ 每次先恢复原始可训练参数，再完成两次更新
[J5] 核验数据身份、训练损失、更新后参数摘要与显存观测
       ↓ 清空缓存，计入本批结束时间
[J6] 退出所属容器，核实 GPU 与容器物理释放
```

图例：图里每个部分对应的源码位置。

| 编号 | 函数与职责 | 对应源码 |
|---|---|---|
| J1 | 原有本地 PostTrain 训练核心 | [execute](../../../../examples/posttrain_bench/local_model.py#L9) |
| J2 | `launch` 运行独立画像、建立固定工作集合 | [experiment.py](../../env-service-verification/scripts/joint_gpu_study/experiment.py#L170) |
| J3 | 动态队列派发与静态计划 | [run_block](../../env-service-verification/scripts/joint_gpu_study/experiment.py#L119)、[plan](../../env-service-verification/scripts/joint_gpu_study/planner.py#L94) |
| J4 | 固定设备身份、模型字节估计、LRU 缓存与执行 | [Worker](../../env-service-verification/scripts/joint_gpu_study/worker.py#L22)、[run](../../env-service-verification/scripts/joint_gpu_study/worker.py#L66) |
| J5 | 对同一命令逐项核验参数和数值 | [analyze.py](../../env-service-verification/scripts/joint_gpu_study/analyze.py) |
| J6 | 只删除本实验拥有的容器 | [close](../../env-service-verification/scripts/joint_gpu_study/experiment.py#L111) |

本实验从已接入任务抽取真实训练程序，回放一批已经提交的工作。两张卡并行执行，每卡内部一次一条命令。各策略只处理这六条已知请求，保持样本和更新次数相同。

这些缓存与队列方法已有广泛应用，本实验检查其在当前真实任务中的收益。源码可按 J1 至 J6 继续追问。

## 真实工作量与对照条件

使用 PostTrain 已准备的 Qwen3-1.7B、Qwen3-4B、SmolLM3-3B 三个模型，以及 AIME、GSM8K、HumanEval 公开样本。程序固定模型主体，只用 AdamW 优化器更新最终归一化参数 `model.norm.weight` 两次。该本地协议把训练控制在很小范围，主要用于观察加载与放置。

每批六项。均衡组合为三个模型各处理 AIME 和 GSM8K；偏斜组合为 1.7B 处理三套数据、4B 处理两套、3B 处理一套。两套组合在实验前固定，没有挑选成功的到达次序。每个命令采用相同的最多 192 个输入 token 与 64 个答案 token 截断。

| 策略 | 实际行为 | 已保留的强对照能力 |
|---|---|---|
| FIFO，先进先出 | 哪张卡实际空闲，就取下一条到达的命令 | 常驻进程、相同 LRU 模型缓存、相同显存预算 |
| LPT，长任务优先 | 以画像估计的加载加执行耗时排序，仍派到实际空闲卡 | 同上，且得到与联合策略相同的画像 |
| affinity，模型亲和 | 将同模型请求成组，按预计完成时间平衡两卡 | 相同加载与容量成本模型，保留模型复用 |
| joint，联合枚举 | 枚举六项当前请求的两卡顺序与分配，按模型缓存变化估算整批结束时间 | 相同信息与预算，实际计入规划开销 |

joint 用小规模枚举作为机会参照，最多比较 `6! × 7 = 5040` 种分配与顺序。大队列需另选可扩展算法。它优化的是画像给出的预测值，实际并发加载的 CPU/存储争用、画像误差与遗漏的淘汰成本，仍会改变实机结果。

硬件为两张启动前空闲 H20，各约 95.6 GiB，1 GiB = 1024 MiB。每进程使用相同的 10 GiB 或 24 GiB **逻辑预算**，另在该预算中预留 1 GiB 激活空间。它限制缓存策略可使用的额度，物理设备容量仍为 95.6 GiB。24 GiB 可容纳全部三个模型。

模型参数字节数约 3.205、7.492、5.728 GiB，合计约 16.425 GiB。预算检查使用 PyTorch 张量分配观测，不含 CUDA 上下文与分配器未使用的保留空间，不能称显存硬隔离。实测期间峰值重置位置发生一次仪表调整，训练逻辑未变，两个文件版本的内容指纹均已保留。全部样本能覆盖训练阶段，不能保证统一覆盖加载瞬时峰值，故不以本结果证明显存准入安全性。复现入口已改为先保存脚本快照，容器只读运行快照，避免后续编辑影响实验。

所有策略先共享同一画像过程。正式批次开始时 GPU 模型缓存为空，操作系统文件缓存已经预热。计时包括规划、全部命令、末尾缓存释放，排除容器建立、Python 导入、画像和开头清空。全部模型预先在两卡驻留的温热对照尚未运行，不能把冷模型批次收益当作长期平均收益。

每次执行恢复原始 norm 参数、清除梯度并新建优化器，避免前一条命令训练状态污染下一条。程序用更新后参数的 SHA256 摘要替代保存 checkpoint 文件。SHA256 是内容指纹，相同摘要连同完全相同的损失和输入身份用于核对回放结果。没有运行隐藏样本 verifier，故不能声称最终 benchmark 得分或学习效果提高。

## Results：实测结果

原计划 24 组，预算内完整保存 **21 组、126 条命令**；900 秒预算到期后收尾，含清理共 901.92 秒。126 条命令的输入、损失、更新后参数摘要与更新数量核对一致。其中 20 组组成五套完整四策略对照，下表使用这些完整配对；另有一组仅 FIFO，单列保留。整体计划状态为超时未完成，见[全部证据](joint-gpu-placement-evidence.json)。

| 相同条件与重复数 | FIFO | LPT | 模型亲和 | 联合规划 |
|---|---:|---:|---:|---:|
| 每卡 10 GiB，均衡组合，各两次均值／秒 | 32.104 | 52.220 | 18.404 | 18.572 |
| 每卡 10 GiB，偏斜组合，各两次均值／秒 | 43.489 | 33.658 | 19.334 | 18.467 |
| 每卡 24 GiB，均衡组合，各一次／秒 | 32.814 | 51.319 | 17.234 | 18.215 |

10 GiB 条件下，模型亲和相对 FIFO 的均值分别少约 **42.7% 与 55.5%**，四次配对均更快。24 GiB 单次均衡组合少约 **47.5%**。均衡组合中 FIFO/LPT 每批加载六次模型，亲和与联合只加载三次；偏斜组合 FIFO 加载五次，亲和三次。减少重复加载解释了主要方向，24 GiB 结果还说明容量够用时冷批次仍可能重复准备。比例的计时范围是命令批次，准备与画像单列。

联合规划相对亲和的四个 10 GiB 配对改善分别为 **+0.83%、-2.63%、+18.70%、-14.32%**，有快有慢。24 GiB 单次慢约 **5.70%**。偏斜组合两次均值约改善 4.5%，同时重复间波动明显，新增收益仍需更稳定证据。

| 模型 | 参数大小／GiB | 10 GiB 画像加载中位数／秒 | 温热两次更新耗时中位数／秒 |
|---|---:|---:|---:|
| Qwen3-1.7B | 3.205 | 6.573 | 0.052 |
| Qwen3-4B | 7.492 | 11.555 | 0.066 |
| SmolLM3-3B | 5.728 | 9.474 | 0.051 |

这三项耗时说明收益主要来自准备和模型驻留，而非 GPU 算术负载均衡。画像没有统一预测并发加载时的 CPU 与文件访问争用。实验后节点另一张卡出现非本实验的工作，本实验两张目标 GPU 已为 0 MiB、无计算 PID，所属容器为零。未停止或清理其他工作，也没有整机 CPU/I/O 独占保证，因此小幅策略差异尤其不能做确定归因。

预算到期后没有扩大实验。温热对照和原程序 checkpoint 的独立比对均未运行，原型只做跨策略输出一致性核验及源码核对。各条件下样本数量有限，只用于发现收益机制，不宣称统计显著或整套题库平均加速。

## 为什么会有收益以及什么时候失效

这组程序的加载耗时远高于两样本训练。加载包含 CPU 模型构建、读取权重和传入 GPU，不是纯粹的 GPU 拷贝时间。执行时间包括分词、张量构建、前向计算、两次更新和同步，也不是单独的内核计时。

教学例子：两个相同模型请求都已就绪，GPU A 已有模型，GPU B 没有。假设每条执行 0.06 秒，在 B 上准备模型要 10 秒。全部留在 A 约 0.12 秒；为了让两张卡都有工作而立即将第二条送到 B，整批反而要等约 10.06 秒。这不是实测值，但说明 GPU 空闲不意味着复制状态必然划算。

只有当 A 上排队等待明显超过在 B 上的重建成本，复制才可能有利。对很短的命令，应优先考虑状态位置；对长训练命令，复制一次可能换来长时间并行，结论不同。需要比较完整队列和共享资源成本，不能仅比较某一条命令的独立时长。

这也解释为什么先测显存与加载，再决定要不要预测 kernel 时间。几毫秒的计算时间估计即使非常准确，也无法补偿额外十秒的模型准备。全部模型都已经驻留在两卡时，这个加载避免机制会减弱，剩下的只是执行时长和队列顺序，必须用温热对照检验。

## 耗时预测与研究价值

本实验没有训练预测器，也没有实现风险约束或置信区间。所有策略使用 AIME 独立画像中的加载时间和温热执行时间，随后应用到 GSM8K 与 HumanEval。画像的作用是提供可落地的初始估计，不是保证新输入的时间不变。证据汇总单列估计误差，不使用已完成正式任务的未来结果倒推当时决策。

需要同时评价三层结论：第一，真实工作是否有可避免的重复加载。第二，简单亲和能否取得这项收益。第三，复杂联合规划能否进一步超过简单亲和。只有第三层稳定成立，才有证据投入复杂控制器。前两层即使成立，也不能独立证明论文创新。

进一步的问题是：已有模型的卡忙碌时，值得等还是复制？[后续系统矩阵](warm-placement-matrix.md)使用进度预测比较等待和加载，完成 48 个核心区块、5 个故障与容量区块，保留其余 4 个缺项。它与本页六命令实验分别记录。[代码指南](../../knowledge/warm-placement-code-guide.md)提供完整机制和 CPU 教学脚本。自然 Agent 改代码后的模型版本识别、自动依赖发现和跨机器迁移仍需专门设计。

## 生产接口与下一步边界

研究容器持续使用两张空闲 GPU，模型驻留期间显存一直属于该实验。现有 [command 归还](../../../../psrl/workers/env_service/command_gpu.py#L259)要求撤销权限并确认物理释放。若要把跨请求缓存接入生产，应另记录持续驻留的占用，明确版本失配、淘汰和释放流程。

后续[等待或重建矩阵](warm-placement-matrix.md)选择持续 episode 租约承载常驻服务，在这个生命周期内检查放置。通用 command 缓存与自然 Agent 轨迹的长期收益仍是独立问题。

本页对照固定在同一研究执行器。需要比较固定旧提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 时，使用[对应实验入口](../env-design-and-results-brief.md)的结果与协议。

## 跟着图读源码

1. J1：先读现有 `local_model.execute`，确定只有两条公开样本和 norm 参数发生训练，不把轻量协议理解成完整模型微调。
2. J2：`experiment.launch` 检查 Docker、GPU UUID 与设备 minor number，再由两个 Worker 建立专属进程。UUID 是设备的稳定身份，minor number 是内核设备号，不能从 GPU 序号直接猜。
3. J3：`run_block` 对 FIFO/LPT 使用共享队列和真实完成回调，亲和与联合策略使用静态队列。两 GPU 的 future 并发推进，不是把所有命令顺序运行。
4. J4：`worker.run` 检查容量、按需淘汰与加载，恢复原始 norm 后执行，返回数值和分段耗时。
5. J5：`analyze.py` 核对完整批次六个任务一项不漏，跨策略输入和训练输出一致，并报告预测误差。温热对照脚本已准备但未运行，不作为本页证据。
6. J6：无论正常结束还是异常，`Worker.close` 定向回收自己创建的容器。控制器记录退出后的设备状态，不能只以 Python 函数返回证明显存已释放。

## 复现与验收

所有命令从仓库根目录运行。CPU 回放只依赖标准库，可先使用以下教学模拟，不启动 GPU。

```bash
python - <<'PY'
import sys
sys.path.insert(0, 'docs/env-worker-deep-dive/env-service-verification/scripts/joint_gpu_study')
from planner import plan, predicted_finish
p = {'A': {'bytes': 4, 'load_s': 10, 'compute_s': 1}}
jobs = [{'id': str(i), 'model': 'A'} for i in range(4)]
for policy in ('fifo', 'lpt', 'affinity', 'joint'):
    q = plan(jobs, p, [[], []], 8, policy)
    print(policy, [[j['id'] for j in x] for x in q], max(predicted_finish(q, p, [[], []], 8)))
PY
```

这里是教学时长，FIFO/LPT 的静态画像分配为 12，亲和把四项留在一张卡为 14，联合也为 12。脚本实际运行得到上述数值。它展示亲和不是永远最好：足够多的执行工作可以抵消第二次加载。真实 FIFO 采用空闲设备动态派发，教学中的静态模型不能替代实机结果。

GPU 复现必须先按[集群运行规则](../../../psrl/psrl-run-guide/cluster-preflight.md#集群踩坑总表与最小复现2026-10-13)核查节点、目标设备、Docker、CUDA 和依赖。`ASSETS` 是已准备的 PostTrain 模型与数据目录，`PYTHON_PREFIX` 是已安装依赖的只读环境，`OUT` 是全新结果目录。命令默认使用设备 0 与 1，必须先确认可用。无需安装或下载依赖。

```bash
python docs/env-worker-deep-dive/env-service-verification/scripts/joint_gpu_study/experiment.py \
  --assets "$ASSETS" --python-prefix "$PYTHON_PREFIX" --output "$OUT" \
  --gpus 0 1 --budget-seconds 900
```

达到已声明的任务数量或时间上限后结束，不追加更大模型或更多训练。运行失败及不完整结果保留，不将部分完成写成全量通过。
