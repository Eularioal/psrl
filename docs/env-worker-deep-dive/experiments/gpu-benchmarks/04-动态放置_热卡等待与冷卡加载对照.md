# 动态放置：热卡等待与冷卡加载对照

> **核心结论**：已有模型的 GPU 忙碌时，是否值得换卡，取决于“还要等多久”和“另加载一份模型要多久”。本实验中，预测策略在长等待场景把两条命令全部完成的平均时间从 **86.11 秒缩短到 52.80 秒，减少 38.69%**。短等待时，它选择继续复用已有模型，节省了额外加载的开销。等待接近加载成本时，两种选择耗时接近，预测策略比直接等待慢 **0.81%**。
>
> 四类核心场景共 **48 组对照全部完成**。故障与容量检查完成 **5/9 组**，其余四组因剩余预算不足而未启动。已完成的配对均通过工作量、输出和运行条件核验。

最新更新：2026-11-16，仅重写报告并核对既有证据与相关源码。GPU 数据来自 2026-11-13 的实验，版本为 `6aa328d` 加当时未提交研究代码，冻结版本保存在原始证据中。该策略由研究驱动调用，生产 Router 默认沿用原有调度路径。之后新增的[命令可预测性门控](../../knowledge/02-资源与调度/08-命令预测_适用条件与时长估计.md)另有 CPU 验证，本文百分比继续对应原冻结策略。

## 1. 实验要解决什么问题

假设新命令 A 需要模型 A。GPU 0 已经加载了这个模型，却正在执行另一条命令 B。GPU 1 空闲，但还没有模型 A。此时有两个选择：

```text
                         新命令 A 到达
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
GPU 0：已有模型 A                     GPU 1：尚未加载模型 A
先等正在执行的 B 完成                  先从本地文件加载模型 A
再执行 A                               再执行 A，同时 GPU 0 继续做 B
             │                                 │
             └──────── 比较 A 何时完成 ─────────┘
```

这里把已有模型的卡称为**热卡**，把需要加载模型的卡称为**冷卡**，“热”和“冷”描述缓存状态。换卡执行的做法是在冷卡增加一个模型副本，B 继续在原卡运行。

**关键取舍是：复用可以省去加载，换卡可以省去等待。** B 很快就结束时，继续等通常更划算。B 还要运行很久时，花一些时间加载模型，可能让 A 提前很多完成。本实验检验预测器能否根据 B 的进度选对这条路，以及预测失准和显存限制会带来什么代价。

这张图中的放置决策对应 [WarmPlacementController.decide](../../../../psrl/workers/env_service/warm_dispatch.py#L237)，A、B 的提交与等待对应 [matrix.study](../../env-service-verification/scripts/warm_router_study/matrix.py#L185)。完整调用关系、源码阅读路径和可运行 CPU 教学实验见[代码指南](../../knowledge/02-资源与调度/09-动态放置_热卡等待与冷卡重建代码.md)。

## 2. 怎样比较三种策略

### 对照策略

三种策略使用相同的模型、输入、执行器和显存容量检查，只改变 A 放在哪张卡。

| 策略 | 怎么选 | 希望检验什么 |
|---|---|---|
| 直接等待 `affinity` | A 一直使用热卡，等 B 结束 | 复用已有模型的收益与等待代价 |
| 优先复制 `always_copy` | 冷卡容量足够且成本信息可用时，加载副本并执行 A | 尽早并行是否值得付出加载成本 |
| 预测选择 `predictive` | 比较两条路径的预计完成时间，冷卡预计至少快 2 秒才换卡 | 能否在长等待时换卡、短等待时复用 |

此外，还运行了固定旧提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 的 runner，即组织和执行任务的程序。它通过静态 GPU Compose 分配在热卡排队，与三种当前策略分别运行。旧版本使用同一模型服务和工作量，保留必要的 GPU 参数下传等运行补丁，完整补丁记录在原始证据中。

### 模型与工作量

A 使用 Qwen3-4B-Base，B 使用 Qwen3-1.7B-Base，输入是两个 GSM8K 公开样本。每次只更新最后归一化层的参数向量 `model.norm.weight`，其余权重固定。每条命令都恢复初始参数、重建优化器并固定随机种子，保证在两张卡上从相同训练状态开始。

四类场景通过改变更新次数，控制 A 的工作量和 B 的剩余等待：

| 场景 | A 更新次数 | B 更新次数 | 关注点 |
|---|---:|---:|---|
| 小目标 `default` | 2 | 128 | A 自己很快，加载成本是否反而成为主要开销 |
| 短等待 `short` | 1024 | 128 | A 工作量大，但等 B 的时间短 |
| 临界等待 `boundary` | 1024 | 512 | 等待与加载成本接近 |
| 长等待 `long` | 1024 | 2048 | 花时间加载能否换来更多并行 |

每类场景、每种策略运行三次，固定旧 runner 也各运行三次，共 `4 × (3 + 1) × 3 = 48` 组核心对照。三次运行分布在三个时间区块，期间交换热卡位置，并轮换三种策略的执行顺序。

### 怎么预测，怎么计时

B 每完成 16 步报告一次进度。预测器跳过首个预热块，用近期完整块的每步耗时中位数，乘以剩余步数。A 在 B 至少完成 64 步后到达，通常已有三个可用块。模型加载时间和 A 的执行时间由本区块开始时的独立短运行测得，这一步称为**成本画像**。

```text
A 在热卡完成的预计时间 = 等 B 的剩余时间 + A 执行时间
A 在冷卡完成的预计时间 = 加载模型 A 的时间 + A 执行时间

冷卡容量足够，且“冷卡时间 + 2 秒 < 热卡时间”时，选择冷卡。
```

预测器最多保留近期八个块的观测，本实验使用单个预计值作决策。2 秒差额用于避免为很小的预计收益换卡。进度过期或不足时，策略回到热卡等待。

报告区分三个计时范围，后面的算例会逐一对应：

| 指标 | 从哪里计到哪里 | 回答的问题 |
|---|---|---|
| **两条命令全部完成时间，主指标** | 提交 B 前，到 A、B 的请求都返回 | 这一组工作总体快了多少 |
| A 的完成延迟 | A 到达，到服务完成 A | 新来的命令少等了多久 |
| 含副本清理的总时间 | 主指标，再加清空冷卡的请求耗时 | 把额外副本释放掉之后，收益还剩多少 |

容器初始化和成本画像单独记账。主指标描述已准备好服务后的这一组工作，完整实验的准备和收尾耗时见第 7 节。

结果体现了同一个取舍：

- **小目标和短等待：复用更合适。** 预测策略都选择了热卡。优先复制为加载付出了额外时间，小目标耗时达到 13.30 秒，而等待只需约 3.54 秒。
- **长等待：增加一个副本更合适。** 预测策略三次都选择冷卡，耗时从直接等待的 86.11 秒降到 52.80 秒。三次分别减少 38.62% 至 38.76%，收益在这三次观察中接近。相对固定旧 runner，累计耗时减少 38.10%。
- **临界等待：两种做法接近，切换门槛与运行波动会影响结果。** 预测策略保留热卡，均值比直接等待慢 0.81%。

在长等待中，预测选择和优先复制几乎一样快，均值只差约 0.05 秒。预测策略的价值体现在**同时识别两类情况：值得加载时加载，等待更划算时复用**。

### 把四类场景放在一起看

每个时间区块取四类场景各一次，先相加耗时，再计算下降比例：`1 − 预测选择累计耗时 / 对照累计耗时`。

| 对照 | 四类各一次的累计耗时下降 | 加入冷卡清理后的下降 |
|---|---:|---:|
| 直接等待 | **19.14%** | **18.29%** |
| 优先复制 | **12.78%** | **12.09%** |
| 固定旧 runner | **18.28%** | **17.91%** |

这个汇总使用预先规定的等次数组合，方便观察策略在不同场景间的取舍。实际任务的平均收益还取决于长等待和短等待各占多少。若只组合短等待、长等待各一次，相对直接等待的累计耗时减少 27.24%，加清理后减少 26.18%。

## 4. 跟着一次真实决策算收益

第一次长等待实验中，A 到达时，B 已完成 `64/2048` 步。调度器当时掌握三个数：

| 决策输入 | 估计耗时 | 来源 |
|---|---:|---|
| B 还要运行多久 | 51.211 秒 | 最近三个完整进度块 |
| A 自己要运行多久 | 33.289 秒 | 本区块成本画像 |
| 冷卡加载模型 A 要多久 | 11.007 秒 | 本区块成本画像 |

于是两条路径的比较是：

```text
热卡等待：51.211 + 33.289 = 84.500 秒
冷卡加载：11.007 + 33.289 = 44.296 秒

冷卡快约 40 秒，超过 2 秒门槛，容量也足够 → 把 A 发往冷卡。
```

实际执行时，A 花了约 0.157 秒等待通道、10.827 秒加载、32.751 秒计算，从到达到完成共 **43.740 秒**。B 同时在原卡继续执行，其实际剩余时间为 **51.134 秒**，与预测值相差约 0.077 秒。

**A 提前结束后，整组仍要等 B。** 从最初提交 B 算起，两条请求都返回用了 **53.000 秒**，再加上清空冷卡副本共 **54.466 秒**。因此，A 的延迟、两条命令的完成时间、含清理时间分别反映用户等待、整体进度和完整收尾成本。

长等待三次平均来看，A 的延迟从 **84.20 秒降到 44.09 秒**，减少 **47.64%**。含副本清理的整组时间从 **86.60 秒降到 54.28 秒**，仍减少 **37.31%**。

## 5. 预测出错或显存不足时会怎样

正常的当前后端核心对照中，36 次 B 剩余时间预测的平均绝对误差为 **0.084 秒**，最大 **0.660 秒**，平均绝对相对误差为 **0.365%**。

这些观测来自固定模型、固定输入长度和重复更新程序，适合检验按步数推算剩余时间的机制。为观察出错代价，实验另外主动改变了预测值、进度新鲜度和服务预算。

| 主动改变的条件 | 完成次数 / 计划 | 策略的实际选择 | 主指标均值 | 对应正常场景耗时 | 说明 |
|---|---:|---|---:|---:|---|
| 短等待预测放大 10 倍 | 2/3 | 两次都换卡加载 | 46.52 秒 | 36.49 秒 | 错误高估导致多花 27.48%，需要提高估计可靠性 |
| 进度报告年龄增加 10 秒 | 2/3 | 将预测标为未知，保留热卡 | 36.76 秒 | 36.49 秒 | 过期时仍能采用等待路径 |
| 冷卡服务预算降到 6 GiB | 1/3 | 服务拒绝接纳 A，保留热卡 | 86.06 秒 | 53.00 秒 | 模型与临时空间超过预算时，容量约束优先 |

故障单元与正常单元按相同重复编号配对。6 GiB 检查改变的是服务获准使用的预算，设备本身仍有空闲显存。该样本主要验证服务能守住容量条件，完成时间接近同编号直接等待的 **86.55 秒**。

## 6. 结果适用于什么范围

这组实验支持在**两张同型 GPU、已知总步数、可报告进度、每命令重置训练状态**的条件下，根据等待与加载成本选择位置。与直接等待相比，主要收益来自长等待时利用另一张卡并行处理 A。

推广到实际系统还需考虑四点：

1. **工作量是否可预测。** 本实验的程序按固定步数重复。任意 Agent 下一步会生成什么命令、何时结束，需要额外的预测依据。
2. **状态能否在另一张卡重建。** 本实验每条命令从固定初始参数开始。连续训练要保留中间权重、优化器和数据位置，换卡时需要对应的恢复协议。
3. **资源与任务规模。** 本次只有一条活动 B 和一条新来的 A，第二张卡可用。更多排队任务、多机、异型 GPU、模型淘汰和与 vLLM 共享设备仍需分别验证。
4. **结果的重复范围。** 三次重复共用常驻服务，旧 runner 先运行，存在时间漂移影响。表中给出均值，图中保留每次观测和最小至最大范围，统计范围限于这些时间区块。

复制新增显存占用，加载也会消耗时间。本报告的收益指标是完成时间，显存作为容量约束检查，能耗和整体集群资源效率留待专门实验。

## 7. 实验配置与证据核验

### 配置和计量条件

| 项目 | 实验条件 |
|---|---|
| GPU | 同一节点两张 NVIDIA H20，单卡约 95.6 GiB，启动前无计算进程 |
| 容器 | 各 8 CPU、48 GiB 主存，独立进程间通信空间、64 MiB `/dev/shm`，共享 CPU 核 |
| 软件 | 镜像内 Python、PyTorch `2.9.1+cu128`、Transformers `5.2.0` |
| 输入 | 两个 GSM8K 公开样本，提示最多 192 token、答案最多 64 token |
| 模型预算 | 每服务预算 20 GiB，按已驻留模型、其他持续状态和 1 GiB 执行临时空间共同检查容量 |
| 当前执行链 | EnvRouter 发放 episode 租约，资源许可贯穿环境会话 |
| 旧执行链 | 固定旧 runner 与静态 GPU Compose，补丁随证据保留 |
| 计时 | 主指标由同一驱动的单调时钟测量，A 的分段时间来自同机服务与驱动 |
| 观测 | 每 16 步发布完整进度，每约两秒采样 GPU 利用率、显存、频率和功率 |

GiB 和 MiB 分别按 `1024³`、`1024²` 字节计量。单调时钟是持续向前的计时基准，本实验的容器共享同一主机时钟，多机部署需另行校准计时方法。

### 工作量和输出核验

48 个核心单元和 5 个已完成故障单元，均通过源码来源、计时、容量及清理核验。配对检查比较模型身份、步数、输入、优化器更新数、最终参数和损失序列的内容指纹，保证比较的是同一份工作与相应输出。

实际执行 **80,664 次更新**，其中正式命令 78,360 次、成本画像 2,304 次。完整计划为 89,112 次更新，尚缺的故障单元仍保留在计划里。两后端共记录 482 条成功服务请求。

有一条短等待的优先复制样本耗时 **51.81 秒**，其中开始执行前等待 **5.30 秒**。该样本保留在均值和图中，等待来源包含驱动、通道和排队，具体成因待进一步定位。该条件最快的 45.46 秒也高于正常预测选择。

### 资源观测与实验总耗时

第 4 节的长等待样本中，冷卡框架分配峰值约 **7962 MiB**，设备采样显存最高 **8541 MiB**，设备口径还包含 CUDA 等额外开销。冷卡 24 次有效采样的平均利用率约 **34.38%**，热卡约 **42.29%**，计算单元 SM 的频率均为 **1980 MHz**。

CPU 配额限流检查覆盖旧后端完整运行与当前后端核心阶段，观察到两容器限流计数增量均为零。当前后端最终 CPU 遥测缺失，核心阶段的结论来自另一次覆盖该时段的只读快照。完整遥测、计数口径和逐单元时间保留在[证据 JSON](warm-placement-matrix-evidence.json)。

| 实验过程 | 固定旧后端 | 当前后端 |
|---|---:|---:|
| 初始化 | 30.76 秒 | 50.07 秒 |
| 成本画像 | 118.90 秒 | 119.91 秒 |
| 已完成区块主指标合计 | 514.52 秒，12 组 | 1675.16 秒，41 组 |
| 提供者清理 | 16.21 秒 | 3.72 秒 |
| 后端整个生命周期 | 739.37 秒 | 1995.86 秒 |

整个实验耗时 **2782.10 秒**，还包含源码冻结、状态读取、检查和归档。两后端执行组数分别为 12 和 41，策略效果使用第 3 节的同场景配对比较。上表用于记录实验成本。

### 停止、清理与代码版本

实验设置 3000 秒执行预算，每组开始前先检查剩余预算。结束时，两后端清理错误列表为空、所属容器数为零，当前后端两张卡的租约均已归还。后续独立检查确认 GPU 计算进程为空，两卡显存整数读数均为 0 MiB。

GPU 实验结束后，父进程中断、超时和子进程异常退出的回收逻辑另做了增强，相关 **120 项 CPU 回归通过**。这些测试覆盖放置与预测边界、进程监督、取消、采样及分析审计。性能数字对应冻结的 GPU 实验版本，代码入口链接指向可读的修后实现。

## 8. 复现方法与代码入口

### 运行实验

先按[集群预检](../../../psrl/psrl-run-guide/02-集群预检_依赖地址与GPU资源核验.md)核对 GPU 身份、路由、Docker 和容器 CUDA，再从 PSRL 仓库根目录激活项目环境。下列变量按执行环境设置：

| 变量 | 含义 |
|---|---|
| `ASSETS` | 包含两个固定模型与两条公开输入的本地 PostTrain 资产目录 |
| `SERVICE_PYTHON` | 镜像中安装好匹配 PyTorch、Transformers 与 CUDA 依赖的 Python |
| `NODE_IP` | 现场确认的执行节点路由地址 |
| `BASELINE_REPO` | 固定 `0eeead8` 的隔离工作树及已披露运行补丁 |
| `IMAGE` | 含模型服务依赖的本地镜像，监督器会记录实际摘要 |
| `RUN_DIR` | 本次新建、独立的原始证据目录 |

```bash
STUDY=docs/env-worker-deep-dive/env-service-verification/scripts/warm_router_study
RUN_DIR=../benchmark-runs/warm-matrix-reproduction
python "$STUDY/matrix_suite.py" \
  --root "$RUN_DIR" --assets "$ASSETS" \
  --container-python "$SERVICE_PYTHON" --node-ip "$NODE_IP" \
  --baseline-repo "$BASELINE_REPO" --image "$IMAGE" \
  --gpus 0 1 --budget-s 3000
```

`--gpus` 使用现场核对的设备 index。监督器登记完整计划，将执行脚本与策略模块保存到 `source-snapshot/` 和 `policy/`，记录内容指纹、镜像、工作树差异与原始输出。资源清理只针对本次所属进程、容器和租约。

### 读取证据和生成图表

本报告原始目录为工作区的 `benchmark-runs/warm-matrix-20261113/`。公开 JSON 从该目录提取可共享字段，保留逐单元结果和缺失项。分析本报告的历史数据时，将 `RUN_DIR` 设置为该目录；分析新实验时，使用上面的 `warm-matrix-reproduction` 目录。

```bash
EVIDENCE=docs/env-worker-deep-dive/experiments/gpu-benchmarks/warm-placement-matrix-evidence.json
FIGURES=docs/env-worker-deep-dive/experiments/gpu-benchmarks/figures
python "$STUDY/analyze_matrix.py" --root "$RUN_DIR" --output "$EVIDENCE"
python "$STUDY/plot_matrix.py" --evidence "$EVIDENCE" --output-dir "$FIGURES" --allow-incomplete
```

这两条命令只分析记录。对本文的原始数据，分析器写出证据后返回退出码 1，表示 57 组计划仅完成 53 组。制图参数 `--allow-incomplete` 允许展示已核验的 53 组，并标注各条件的实际样本数。条形表示均值、点表示真实重复、竖线表示最小至最大观测范围。
