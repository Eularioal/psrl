# GPU 性能反馈调度：扩展压力实验

> **核心结论**：GPU 计算正确，计时仍可能选错程序。给测量留出保护窗口，避免了本次观察到的严重选优错误；但后台长工作仍决定整组何时结束，前台变快未必带来整组提速。当前固定两轮测量已经优于本次自适应规则，应优先保留简单保护与合适的采样预算。

## 场景与执行流程

场景是：agent 为一道 GPU 程序优化题提交几个正确实现，评分器需要比较谁更快，再决定保留哪个。GPU 上还有其他工作；即使显存足够，计算、显存带宽或执行机会的竞争仍可能让评分变慢或改变测量值。本次固定候选程序，直接研究评分过程，不额外运行大模型生成和策略训练。

**先看一个真实的选错案例。** 对 79 行输入的 `rmsnorm_h4096`，无竞争参考中最快实现用时 6.397 微秒，Gemini 候选用时 15.328 微秒。共享计算时却测成 6.352 与 6.139 微秒，于是评分器误选 Gemini。两个程序数值都正确，但选中的程序按目标参考慢 **139.6%**。

这说明需要同时检查“算对了吗”和“快慢比较可靠吗”。该题前后参考都选择同一赢家，单候选参考漂移最高约 3.5%，远小于这次错误幅度。异常中较慢程序反而看起来更快，底层计时、CPU 提交与 GPU 队列时序的因果贡献仍待定位。

```text
[1] 官方算子、输入与四个候选 → 冻结实验协议
                      ↓
[2] EnvRouter 准入 → 原生 EnvWorker 创建容器 → 一条受管 GPU command
                      ↓
[3] 容器内研究控制器：正确性检查 → 多轮计时 → 选择候选
          │ 请求保护                      ↑ 返回测量值
          ▼                               │
[4] 后台 GPU 工作者：同步已提交计算 → 暂停提交 → 恢复并完成固定工作量
                      ↓
[5] 汇总评分与全部工作的完成时间 → 退出进程 → Env 清账、回收容器
```

图例及跟着图读源码：顺序表示依赖关系，[3]、[4] 是并发进程，不是单线程顺序执行。

| 步骤 | 输入、动作与输出 | 源码 |
|---|---|---|
| 1 | 筛选原始工作负载，保留候选源代码，写入固定协议 | [prepare.main](../../env-service-verification/scripts/feedback_pressure/prepare.py#L11) |
| 2 | 创建真实 Router、申请会话，设置完整单卡容量，启动原生容器 | [探针 run](../../env-service-verification/scripts/flashinfer_env_probe.py#L22) |
| 2 → 3 | `exec_gpu` 提交整条实验命令，返回后检查命令账本 | [experiment](../../env-service-verification/scripts/feedback_pressure/driver.py#L14)、[生产 execute](../../../../psrl/workers/env_service/gpu_execution.py#L109) |
| 3 | 官方正确性与计时函数产生每个候选的结果 | [collect](../../env-service-verification/scripts/feedback_pressure/worker.py#L140) |
| 3 ↔ 4 | 每个后台工作块同步完成；控制器取得执行锁才开始保护测量，随后恢复 | [pressure_worker](../../env-service-verification/scripts/feedback_pressure/worker.py#L18)、[protect/release](../../env-service-verification/scripts/feedback_pressure/worker.py#L100) |
| 5 | 等固定后台工作完成，退出进程，核对账本与物理资源 | [finish/close](../../env-service-verification/scripts/feedback_pressure/worker.py#L119)、[探针清理](../../env-service-verification/scripts/flashinfer_env_probe.py#L169) |

EnvRouter 是资源分配入口；EnvWorker 是执行容器任务的后端；command 指一条受管理的 GPU 命令。

**保护窗口**指一段暂不允许后台提交新 GPU 工作的时间。进入前必须等已提交计算执行完；本次用协作进程和执行锁实现，不是对任意程序强制抢占。暂停期间显存仍保留，因此不能据此释放显存账本。Env 目前只管理外层命令，内部保护窗口属于实验原型，尚未接入跨容器调度。

这些代码如果有理解上的问题，可以随时追问。

## 实验设计与术语

使用 FlashInfer-Bench 的官方算子定义、随机张量生成、候选代码、正确性检查与计时函数。四类算子是两个隐藏维度的 **RMSNorm**（按均方根缩放特征）、**融合加法与 RMSNorm**（合并相加和归一化）、**GEMM**（通用矩阵乘法）。每类取小、中、大三个原始输入，共 12 题、48 个“题目 × 候选”组合。全部通过 H20 可移植性检查；候选原声明 B200，因此本报告不是官方排行榜成绩。

**候选**是同题的一份程序实现。**采样轮**指每个未停止比较的候选调用一次官方计时器；一次调用本身还有官方预热和多次内层测量，不等于只运行一次 GPU 内核。GPU 内核指实际在显卡上执行的计算程序。

| 策略 | 实际行为 | 要检验什么 |
|---|---|---|
| 持续共享 `shared` | 正确性检查与五轮计时都允许后台运行 | 无测量保护的现状对照 |
| 全程保护 `exclusive` | 从正确性检查开始暂停后台，测五轮 | 简单保守方案是否已经足够好 |
| 逐次保护 `per_call` | 正确性检查共享，每次计时单独申请保护，五轮 | 频繁进入保护的成本 |
| 成组五轮 `group5` | 正确性检查共享，整个计时批次保护，五轮 | 仅合并保护窗口的收益 |
| 成组两轮 `group2` | 同上，固定两轮 | 更少采样的强简单基线 |
| 自适应 `adaptive` | 同上，先两轮，根据候选差距决定是否追加，最多五轮 | 按比较结果分配测量预算是否有额外价值 |

自适应规则：最快两者的差距超过“最快值的 5%”和“四倍采样波动”中的较大者时停止。波动用 **MAD**（中位绝对偏差），即“样本与其中位数之差的绝对值，再取中位数”；例如样本 10、11、12，中位数为 11，偏差为 1、0、1，MAD 为 1。本规则是固定启发式，不提供统计置信保证；达到五轮仍不满足时会记录未解决状态。

主矩阵有四种背景：无竞争、4 个显存拷贝进程、4 个矩阵乘法进程、8 个混合进程；配合两种题目批次与六种策略，共 144 组。4 题批次分别取小、中、大输入；12 题批次对相同全部题目重复三次。因此不能把所有行都说成“同题独立重复三次”。每个后台进程完成 1200 个工作块，每块 8 次计算或拷贝。

补充实验将混合压力增至每进程 6000 块，比较五种策略与三个 4 题输入组，共 15 组；不重复逐次保护。它在另一张空闲 H20 上独立运行，CPU 配额由 4 增至 16，主存由 16 增至 32 GiB。**GiB** 为容量单位，1 GiB = 1024 MiB。跨两套实验不直接比较绝对耗时，也不能把差异都归因于后台时长。每套实验内，各策略的设备和配额相同。每卡 unit（资源单元）按整卡容量登记，单容器申报 48 GiB 显存预算；这是准入申报，不是硬件显存隔离。探针的冻结副本只调整这些资源参数。

本次比较目标是无竞争单卡性能；若任务目标本来是并发服务吞吐，就应固定并发协议，不能把去除竞争当成唯一正确条件。

所有后台都是人工注入的可重复 GPU 压力，前台是真实官方算子计算。比较完成同样多的后台工作；保护等待、暂停造成的延后都计入。策略执行顺序随机打乱，候选计时顺序轮换。整个命令开始、结束各测七轮无竞争参考值。

## Results：收益与代价

先读清三个指标：**反馈时间**计到前台测量数据齐备；**整组时间**计到前台与同样多的后台工作全部结束；**选择损失**是所选程序相对无竞争最快程序慢多少。比如参考最快为 10 微秒、选中为 12 微秒，选择损失就是 20%。

计时相对误差为 `|测量值/无竞争参考值-1|`。**P95** 是把误差排序后取 95% 位置的值，用于观察较差情况。前后共 14 轮参考合并取中位数，参考自身也有波动，近似并列题目按该条件解释。表内单列组内测量，进程创建、编译与清理计入最后的运行总时间。

**主矩阵：每组平均整组时间，单位秒。** 每格包含相同的六组输入配置。4 CPU 配额出现限流，以下是综合资源压力结果。

| 策略 | 无竞争 | 4 拷贝进程 | 4 计算进程 | 8 混合进程 |
|---|---:|---:|---:|---:|
| 持续共享 | 3.09 | 9.98 | 10.42 | 25.20 |
| 全程保护 | 3.11 | 8.83 | 9.20 | 22.97 |
| 逐次保护 | 3.13 | 9.41 | 9.77 | 24.04 |
| 成组五轮 | 3.12 | 9.37 | 9.77 | 24.07 |
| 成组两轮 | 1.29 | 7.59 | 7.96 | 22.20 |
| 自适应 | 2.14 | 8.42 | 8.84 | 23.06 |

成组两轮相对持续共享，在拷贝、计算、混合压力下分别减少整组时间 **24.0%、23.6%、11.9%**，各自六对比较方向一致。它包含减少采样的收益，不能归为新调度算法收益。持续共享在三个压力场景各出现一次超过 5% 的选优损失，均集中在同一道题；保护策略未出现这种损失。

**持续竞争补充：每组平均时间，三组不同输入。** 共享策略的 240 次采样开始时都有后台工作；其余策略在保护条件下测量。

| 策略 | 反馈时间／秒 | 整组时间／秒 | 计时误差 P95 | 损失超过 5% 的选择 |
|---|---:|---:|---:|---:|
| 持续共享 | 18.83 | 60.52 | 6.02% | 1/12 |
| 全程保护 | 1.57 | 60.47 | 0.87% | 0/12 |
| 成组五轮 | 4.42 | 60.50 | 0.90% | 0/12 |
| 成组两轮 | 3.52 | 59.59 | 0.98% | 0/12 |
| 自适应 | 3.97 | 60.06 | 1.34% | 0/12 |

全程保护的反馈时间减少 **91.7%**，但整组时间只少 **0.09%**；成组两轮整组时间少 **1.54%**。后台长工作决定了整组何时结束，不能把前台加速比例当作完整任务加速。样本少，这些小幅差异不构成普遍加速保证。

全部 12 题的候选前后参考漂移最大约 5.9%；近似并列时保留这种波动范围。选择和损失由保存的测量数据离线重算。

## 怎样理解结果与研究价值

**有价值的部分：保护测量条件。** 两套实验均出现显存充足、计算正确却选错程序的情况，说明显存安全不能替代反馈协议。工程上可以先提供明确的测量保护阶段；目标条件、计时后端和返回的不确定性也应一起记录。

**尚未成立的部分：复杂策略的新增收益。** 成组五轮与逐次保护在主矩阵中耗时接近，合并窗口没有明显优势。两者进入保护累计等待分别约 0.17 与 0.86 秒，相对整个矩阵很小。自适应在主矩阵全部 24 对和补充实验全部 3 对中，都比固定两轮更慢，且未观察到更小的超过 5% 选优损失；当前规则不值得作为核心研究贡献。

**阶段共享也可能吃亏。** 补充实验里，全程保护即使测五轮，反馈仍比“正确性检查共享、只保护两轮计时”更快，因为共享使前面的检查受到干扰。是否共享需要看实际阶段成本，不能仅按“正式测速以外都可共享”划分。

建议先保留简单保护与采样预算标定，把研究结论收窄为“性能反馈需要显式资源条件”。若继续做论文级系统方案，下一关应是跨容器保护协议，以及完整 agent 任务在同等反馈质量下的完成时间；本轮证据尚未证明这项额外贡献。

与 YARN（Hadoop 的集群资源管理体系）的关系，是借鉴“应用协调者知道还需要什么结果，资源管理者提供执行条件”的分工。工程上做到成组保护并不自动成为新的研究贡献。若简单固定两轮已经满足同样的选择质量，复杂的自适应协调必须再证明自己的额外价值。

本次目标是**选出好候选**。如果训练需要所有候选准确的数值奖励，则“第一名选对”还不够；不能直接把本次减少采样的结论推广到完整奖励向量，更不能声称学习效果提高。

## 复现证据与验证边界

两套实验分别占用一张独立空闲 H20，实际通过 EnvRouter 和原生 EnvWorker 的 command 路径。共 **159 组、20,560 次组内官方计时调用**，另有前后参考、预热和正确性检查。每卡遥测采样峰值均为 9 个 GPU 进程、10,783 MiB 显存、100% 利用率；这是计算与带宽压力，不是显存耗尽实验。

主矩阵和补充实验的运行总时间分别为 **1808.98、1097.60 秒**，包含准备、参考测量及清理。监督预算分别为 3000、2200 秒，均在预算内结束。主矩阵 CPU 快照记录 9020/14132 个配额周期发生限流，补充快照为 0/7712；这是运行中累计快照，不冒充全程独立 CPU 性能实验。

- [主矩阵原始测量与协议](feedback-pressure-evidence.json)、[持续竞争原始测量与协议](feedback-sustained-evidence.json)：含全部样本、候选、配置、版本、源文件校验值与清理摘要。
- 基准源码为 `6aa328d` 加冻结工作区；FlashInfer-Bench 为 `15618a6`，trace 数据为 `da91508`。运行前冻结资产，未修改官方候选源代码。命令内部使用官方函数的自定义研究控制器，不是完整官方排行榜运行。
- 官方默认配置：10 次预热、50 次内层计时、3 份随机输入。日志确认未安装 CUPTI（NVIDIA 的 GPU 性能追踪接口），使用官方自动回退的 CUDA 事件计时，即 GPU 队列中的起止时间标记。前后共 14 轮结果合并取中位数作为参考。
- 两次退出码均为 0，命令账本活动数及显存申报归零，所属容器均删除，目标 GPU 无计算进程，收尾遥测仅约 0.19 MiB 设备占用。未清理其他实验的资源。
- 新增脚本 Ruff 检查通过；全库预提交检查在隔离副本运行，因已有无关行长与注释问题未通过。一次补充启动发生在文件准备完成前，未创建 GPU 任务，修正启动顺序后才开始实验；没有删掉失败的性能组重跑取好结果。

本次只新增研究脚本、证据与报告，未修改生产调度策略。已更新 YARN 研究正文和实验导航；[当前设计](../../knowledge/current-design.md)的能力边界仍适用，无需改为“已支持跨容器测量保护”。主目录改动尚未提交、推送或合并。
