# 显存压力：提前排队与失败重试

> **核心结论**：在一张 H20 上完成相同的 **7 项服务任务、14 次请求**，固定旧版发生一次显存不足并重试，修复后的 Env 提前按预算排队，全部首轮通过。驱动总时间从 **158.48 秒降至141.73 秒，减少10.6%**；任务阶段减少17.9%。本实验验证真实模型争用下的准入与回收。

实验执行于 **2026-11-02**。2026-11-16 从原 FINDINGS 整理为独立报告，只读原始结果。固定旧版为 `0eeead861ffafed6bf31c962d259fd847775dcf9`，Env 组为 `8d1fc65230d7bd4c78305e140c41ac8b5ea14fb0` 加当时未提交记账补丁，实际执行文件指纹保存在[来源证据](episode-pressure-provenance.json)。

## 1. 为什么服务没有请求也会占显存

推理服务先把模型加载到 GPU，随后可以处理多次请求。短客户端完成请求后退出，后台服务仍在，模型继续占显存。

本次每项任务启动一个真实 Mistral 服务，处理一道 MMLU-Pro 问题，用独立 CPU 命令等待30秒，再处理第二道问题。中间30秒模型始终驻留。**一次服务任务的资源持有范围覆盖两次请求和间隔**，因此使用 episode，即完整任务生命周期预算。

若七项都直接启动，它们可能同时加载七份模型。数量并发上限只限制“有几个任务”，显存准入则还检查“这些任务承诺占多少空间”。实验要观察显存争用时，提前排队能否比失败后重来更划算。

## 2. 怎样比较两组

两组使用同一张启动前空闲 H20，总显存97871 MiB，约95.6 GiB。1 GiB = 1024 MiB。先启动两个服务，均准备好接收请求后，一次提交其余五项，任务集合与到达规则相同。

| 条件 | 固定旧版 OFF | 修复后的 Env ON |
|---|---|---|
| 最大任务数 | 原有进程内上限7 | 容器槽上限7 |
| GPU 使用 | 静态设备映射，模型直接竞争整卡 | 整卡资源池，每项预约20480 MiB，即20 GiB |
| 执行路径 | 旧Docker runner | EnvRouter准入、原生EnvWorker执行 |
| 模型与请求 | 相同模型、镜像、BF16精度、上下文2048，每请求最多16个token | 相同 |
| 重试 | 仅确认CUDA OOM的项，在首轮全部结束后重试一次 | 相同 |
| 预算 | 组内900秒、driver1000秒、单任务最多400秒 | 相同 |

CUDA 是 NVIDIA GPU 的计算平台，OOM 指显存分配不足。该对照使用真实模型自然争用，完整任务均通过生产 runner；外层实验固定动作，验收的是执行与资源管理。

## 3. Results：相同工作量的完成时间

```text
OFF：先到2项 → 再到5项 → 首轮6成功、1显存不足 → 重试1项
ON ：先到2项 → 再到5项 → 预算允许的先运行，其余等待 → 清理后接续
两组最后都完成7项任务、14次请求。
```

| 指标 | OFF | ON |
|---|---:|---:|
| 首轮成功 | 6/7 | 7/7 |
| OOM / 总尝试数 | 1 / 8 | 0 / 7 |
| 最终成功任务 / 请求 | 7 / 14 | 7 / 14 |
| GPU计算进程采样峰值 | 7 | 4 |
| 显存采样峰值 | 84.57 GiB | 56.38 GiB |
| 初始化 | 0.27秒 | 9.93秒 |
| 任务阶段，含失败、重试与各任务清理 | 158.05秒 | 129.79秒 |
| 最终清理 | 0.15秒 | 2.00秒 |
| 驱动总时间 | **158.48秒** | **141.73秒** |

任务阶段少 `1-129.79/158.05≈17.9%`，完整驱动少 `1-141.73/158.48≈10.6%`。ON 初始化较长，同时省掉一次失败加载与重试。两组成功请求逐样本文本与token数完全一致。

工作阶段从首批提交前到全部逻辑任务返回，包含服务就绪、等待与清理。驱动总时间另加私有Ray初始化和最终收尾；环境激活、模块导入和镜像构建单列在此范围之外。相同就绪门槛在两组达到的时间不同，剩余五项相对工作开始的到达时刻分别是19.18秒、28.57秒。

## 4. 用真实数字理解排队和记账

**第七项为什么加载失败？** 日志显示，已有六个模型进程各占约13.81–14.09 GiB，第七项要一次申请13.50 GiB，当时仅余11.23 GiB。它只建了约316 MiB的GPU上下文，模型尚未加载成功。因此采样看到七个进程时，其中只有六份完整模型。

**ON 为什么最多四项？** 每项承诺20 GiB，四项合计80 GiB，第五项会使承诺达到100 GiB，超过95.6 GiB设备容量。每项实际约14.1 GiB与20 GiB预约间的空间，保留给任务后续增长。若希望进一步提高并发，需按真实峰值校准预约或设计可撤销预算。

**已经加载的模型怎样避免重复计费？** 假设先把整卡实测显存与全部预约直接相加，同一份已加载模型会同时出现在两者里。修复通过可信进程归属识别已兑现的预约，再计算剩余承诺。

一条真实ON采样为四个活动租约、三个等待者：

```text
整卡实测占用 = 57165.6875 MiB
四项总预约   = 81920 MiB
已核实任务占用 = 57140 MiB
有效占用 = 57165.6875 + 81920 - 57140
         = 81945.6875 MiB ≈ 80.03 GiB
```

在这条样本中各项实用量都低于自己的预约，可用上述简式。一般公式逐项保留尚未兑现的承诺，见[显存准入图解](../../knowledge/02-资源与调度/01-显存准入_实测占用与预约预算.md#9-episode-归属记账修复)。旧的直接相加会得到约135.83 GiB。同一运行中有44条采样观察到等待者，槽数上限仍为7，记录体现的是显存准入。

## 5. 结果适用范围与清理

这是固定旧版与修复版的**完整执行路径对照**。双方后端不同，版本与必要运行补丁各自记录；结果支持这一真实模型压力场景的收益，单个记账函数的独立性能贡献需另做消融。

任务使用真实服务、模型和请求。PSRL策略优化器、InferenceBench官方完整质量评分及自然agent的自由优化任务，分别有其它验收目标。此次只有一对，保留具体任务规模和时间范围。

ON一条账本遥测超时保留缺失，17条CPU/主存资源或缓存观测错误单列。最终逐actor查询及独立Docker查询均无所属容器，GPU无计算进程，两组NVML残余约0.1875 MiB，ON租约归零。实验按预先一组OFF、一组ON运行后停止。
