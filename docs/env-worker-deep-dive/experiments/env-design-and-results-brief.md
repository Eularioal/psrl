# Env 设计与收益简版

> **核心结论**：EnvRouter 在 PSRL 的任务执行层增加统一资源预算，让 GPU 容量足够的任务并行、放不下的任务排队，并在确认资源归还后放行下一条。在一次人工高显存压力的真实 science 三步训练对照中，显存不足失败从 **18 次降为 0 次**，含初始化和清理的总耗时减少 **27.59%**。低压力下尚未证明稳定提速。

本文可独立转发，设计与阶段验证核对至 2026-10-28。性能数据来自下文注明的历史实验版本，不代表全部最新改动已经完成联合验收或发布部署。

## 当前设计

PSRL 训练时，模型生成操作，任务环境执行并返回结果，最后把交互轨迹和评分用于训练。EnvRouter 管理的是其中的**环境资源分配与回收**。

```text
PSRL 派发任务 → 模型生成操作 ←─────────────┐
                    ↓                    │
              环境申请执行资源            │
                    ↓                    │
       EnvRouter：选择资源池、检查统一账本  │
           容量够 → 获准    不够 → 等待    │
                    ↓                    │
       Harbor 创建 Docker 容器并执行命令  │
                    ↓                    │
       节点服务确认 GPU 归还 → 返回结果 ──┘
                    ↓ 任务结束
             评分 → 清理 → 训练更新
```

Harbor 是任务运行器，负责组织容器执行与评分。账本记录同一 Router 管理范围内已经承诺的 CPU、主存、GPU 显存和会话名额，结合实际显存占用决定是否允许新工作。**任务结束、账本扣减和物理显存释放是不同的事，因此需要归还核验。** 预算用于准入控制，不是 CUDA 程序无法突破的显存硬上限。

上图以 command 路径为主线。一次完整任务称为 episode，产生的交互轨迹称为 rollout。一个任务会话可以包含多轮“模型生成 → 命令执行”，容器通常跨轮保留，不会每执行一条命令就重建。一次会话的具体分工是：

| 环节 | 谁负责，发生什么 |
|---|---|
| 放置与会话申请 | PSRL 选择执行 worker，即承接任务的进程。运行器向 EnvRouter 申报需求，获准后取得租约，即本次资源使用凭证 |
| 容器准备 | Harbor 创建并标记属于该租约的容器。CPU、主存和会话名额按会话管理，等待 GPU 时这些资源仍可能被占用 |
| GPU 命令准入 | 统一后端申请命令预算，Router 检查容量，节点服务获准后打开设备访问。没有容量时异步等待，不能先启动再补账 |
| 执行与归还 | 命令结束后进入归还核验，确认相关 GPU 使用已结束才释放预算。归还尚未确认时，不能把同一份容量再次分配出去 |
| 会话收尾 | 评分结束或任务异常后，按归属清理主容器及辅助资源，释放剩余预算。清理不确定时阻止受影响资源继续授权 |

GPU 预算目前有两种持有方式，执行、超时、取消和清理共用后端：

| 模式 | 预算什么时候持有 | 适合什么任务 |
|---|---|---|
| episode，按完整任务会话 | 从会话获准到结束持续保留 | 需要跨命令保留 GPU 模型或中间状态的任务 |
| command，按 GPU 命令 | 每条显式 GPU 命令执行前申请，结束并确认归还后释放 | GPU 工作分成独立阶段，阶段之间可以释放显存的任务 |

例如，command 任务执行完一次 GPU 程序后，可以保留容器文件，继续 CPU 工作或等待模型生成，让其他任务使用已经释放的 GPU 容量。**这不等于自动搬走仍在运行的程序或显存状态。** 模式目前由启动配置选择，新任务仍需声明资源需求并接入对应执行接口。

下面用同一条任务的两个 GPU 阶段说明区别，时间仅为教学假设：

```text
任务动作：GPU 工作 5 秒 → 等模型回复 20 秒 → GPU 工作 5 秒
episode ：[────────── 会话 GPU 预算持续保留 ──────────]
command ：[申请、执行、归还]  无 GPU 阶段预算  [再次申请、执行、归还]
容器文件：[──────────────── 始终保留 ────────────────]
```

如果两次 GPU 工作都是独立程序，第一次退出后能释放全部相关显存，就适合 command。若任务启动了一个常驻 GPU 模型，第二次还要使用第一次留下的模型状态，则不能仅因“正在等回复”就撤销其预算，应该先用 episode，或以后通过明确的保存与恢复接口让位。episode 保留的是需求预算，并不意味着独占整张卡，其余容量足够时仍可接纳其他任务。

**显存预约为什么不能只看监控数值？** 获准的命令可能还在启动，尚未真正分配显存。如果此时只查当前占用，就可能把已答应给 A 的空间又交给 B。当前记账将“实测占用”与“已批准但尚未分配的部分”相加。只有能可信地确认某份实际占用属于 A，才从 A 的预约中抵扣，避免重复计算。CPU、主存和显存账本都只覆盖接入该 Router 的管理范围，不是整个平台的全局调度器。

当前不同容器的受管 GPU 命令可以重叠，同一容器内仍串行。独立 GPU 优先选择已有真实容器验证。显式配置的模型同卡余量共享也已通过小规模功能验证，但尚未证明完整训练吞吐收益。

## 与 baseline 的区别

baseline，即对照基线，固定为 PSRL 提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 的 science 执行路径。它已有任务并发限制、容器执行、超时和清理，**没有整卡串行锁**。

```text
baseline                                  EnvRouter
每个执行进程限制会话数量                    多个执行进程共同申请资源
             ↓                                         ↓
静态配置容器可访问的 GPU                    共享账本检查容量与预约
             ↓                                         ↓
程序直接申请显存                            容量够才授权，不够等待
             ↓                                         ↓
结束后清理容器                              确认归还，再释放预算
```

| 对比点 | 固定 baseline | 当前 EnvRouter |
|---|---|---|
| 准入依据 | 本进程还有几个任务名额 | 资源池能否容纳任务申报需求 |
| GPU 选择 | 静态设备配置 | 在已配置、已授权的候选资源内按容量与优先级选择 |
| 显存充足 | 多个容器本来就能并行 | 多个容器也可并行，但增加控制开销 |
| 显存不足 | 数量名额允许时仍可能同时争抢，导致 OOM，即显存不足失败 | 将实测占用和未兑现预约一起核算，放不下就排队 |
| 阶段结束 | GPU 程序自行释放，框架无该阶段预算交接协议 | command 确认归还后释放预算，会话和文件可以保留 |
| 清理 | 按任务容器项目清理 | 增加作业归属、租约和节点归还核验，异常未清理时阻止继续授权 |

baseline 的限制按执行进程分别生效。例如两个 worker 各允许四个会话，合计就可能启动八个。若都静态映射到同一张 GPU，它们会争用同一份显存，但两个数量限制不会自动合并为节点显存预算。反过来，静态配置也可以指向不同 GPU，因此不能把 baseline 概括成“所有任务必然挤在一张卡”。

**为什么排队可能更快？** 用实验配置做容量示意：预算 90 GiB，外部已占 70 GiB，每条命令预约 15 GiB。第一条获准后，合计承诺为 85 GiB。第二条若也获准则达到 100 GiB，超过预算，所以必须等第一条释放。GiB 是显存容量单位。

baseline 的任务数量限制并不知道这笔显存加法，可能允许多个任务一起尝试。放不下的任务失败后需要重新采样或执行。ON 的收益来自**少做失败和重复工作**，不是让单个 GPU 运算本身变快。容量宽裕时，两种方案都可以并行。

## Results：已有收益

下表 OFF 均使用上述固定基线，ON 使用各实验冻结的 EnvRouter 版本。必要的设备参数、依赖和运行兼容修复未改变 OFF 的静态 GPU 映射与本地并发限制，也未给它增加整卡锁。

| 场景 | OFF | ON | 结果与含义 |
|---|---:|---:|---|
| 高压力，三步训练累计 | 1100.80 秒 | 503.69 秒 | 减少 **54.24%**，主要减少采样等待与失败补采 |
| 同一实验，含初始化和清理的总时间 | 1954.11 秒 | 1415.01 秒 | 减少 **27.59%**，约节省九分钟 |
| 同一实验，显存不足失败 / 总尝试 | 18 / 30 | 0 / 12 | 双方最终都完成三步、接受十二条轨迹 |
| 低压力，一步真实训练 | 141.47 秒 | 145.98 秒 | ON 多约 **3.19%**，双方四路 GPU 操作成功重叠，无 OOM |
| 低负载，环境组件两对合计总时间 | 213.96 秒 | 217.15 秒 | ON 多约 **1.49%**，包含初始化和驱动收尾，不包含模型训练 |

**高压力条件必须与数字一起阅读。** 2026-10-26 使用 Qwen3.5-4B、两个 LAPS 科学程序修复题，每题采样两条轨迹，训练三步。训练和推理使用三张卡，环境另用一张 H20。环境卡人工常驻占用 **70 GiB**，双方每条轨迹再加入 **14 GiB、15 秒的受控 GPU 阶段**，ON 按 15 GiB 预约、90 GiB 总预算准入。ON 为 `b52a82d` 加显存准入修复。

因此，这是真实 PSRL science 训练链中的**人工高显存压力对照**，不是原生科学题自然产生的 GPU 压力，也不是模型与环境同卡共享实验。只有一次三步对照，双方生成文本长度不同，奖励和策略梯度均为零，能说明该条件下的执行效率，不能说明学习效果提高或普遍提速倍数。

**收益具体来自哪里？** 为拿到相同的十二条接受轨迹，OFF 共尝试三十条，其中十八条因显存不足失败，ON 只尝试十二条。在该压力条件下，两组成功 GPU 阶段的并发峰值都只有一，ON 观察到四个会话存活、一个 GPU 命令执行、三个等待。它没有凭空增加 GPU 容量，而是把失败后的重新执行变成执行前等待。三步采样等待累计从 1044.43 秒降到 443.00 秒，模型更新累计反而从 41.67 秒增加到 49.57 秒，因此不能把收益解释成模型更新计算加速。

低压力训练同日运行，去掉 70 GiB 常驻压力，保留每条 14 GiB 的 GPU 阶段，仅跑一步。ON 为尚未加上述修复的 `b52a82d`，采样等待只多约 0.17 秒，训练更新和生成长度也不同，所以不能把 3.19% 全算作调度开销，也不能替代修复后的低压力验收。

低负载组件实验于 2026-10-20 运行，ON 为 `37a06ea` 加同步准备优化。固定脚本经真实 science 运行器和 Docker 执行 GPU 操作，每轮八任务、四并发，每任务两次分配 1 GiB、持有两秒，中间等待八秒。采用 OFF → ON → ON → OFF，共 32 条任务全部成功。两对工作阶段的快慢方向不同，**尚无低负载稳定提速结论**。

这组组件实验主要检查“显存够用时，多一层调度会不会很贵”。两对工作阶段 ON 省约 10.84 秒，但初始化和驱动收尾多约 14.03 秒，所以总计反而多约 3.19 秒。这里的工作阶段包含容器启动、执行、评分和任务清理，不是纯 GPU 运算时间。固定持有和等待也不等于持续高强度计算或真实模型生成。

**其他已验证的进展属于功能收益。** 它们解决可用性和资源管理问题，目前不能叠加到训练提速数字中。

| 能力 | 已有真实验证 | 仍需区分的边界 |
|---|---|---|
| GPU 进程归属 | 通过 eBPF，即内核事件采集机制，区分两个容器的 GPU 进程，结束一个不影响另一个记账 | 为缺少宿主进程文件视图的部署提供可选后端，不代表所有部署都能免配置使用 |
| 独立 GPU 优先 | 独立卡有容量时选它，放不下时选择允许的后备卡，容量恢复后重新优先独立卡 | 后备卡在该实验中只是压力模拟，没有真实模型训练 |
| 模型同卡余量共享 | Qwen2.5-3B、单张 H20，模型保持生成时容器执行小型 GPU 命令，两类进程同时存在 | 已验证小规模共存，没有完整训练吞吐或模型响应损失对照 |
| 已睡眠窗口复用 | 模型已经睡眠时允许环境使用窗口，提前唤醒会等待命令归还，恢复后生成有效 | 利用已知状态，不是预测空窗后主动决定卸载模型 |

## 下一步重点

**1. 先用其他 GPU，再利用模型安全余量。** 优先同机或其他已授权节点的独立 GPU，资源紧张时才考虑模型所在的卡。模型当前空闲显存不一定等于可以长期借出的容量，还要为后续推理临时张量留空间。已有优先级和显式推理共享能力，接下来补齐真实负载下的模型响应、环境耗时和总完成时间对照。训练峰值预算与完整训推共存仍需完善，不默认打断 vLLM 模型推理服务。

**2. 自动选择 episode / command。** 先由任务适配接口声明“是否跨命令保留 GPU 状态、能否安全释放与恢复”，再结合运行观测选择持有策略。无跨命令状态的阶段使用 command，有持久状态的阶段保留 episode。未知状态先保守持有，不仅凭 GPU 利用率低就判断可以回收。已有统一执行后端，自动识别和运行时切换仍是规划，切换应在安全边界完成。

**3. 预测是否值得卸载与恢复。** offload 指把需要保留的状态移到主存等其他存储，reload 指重新加载回 GPU。对必须保留状态的 episode，只有存在等待者、资源不足、可以安全恢复且预计总收益为正时才考虑让位。决策需要同时估计卸载、借用任务执行、归还核验和恢复时间，不能只比较“搬出去有多快”。

教学例子：A 预计还要等模型回复 40 秒，B 正等待 GPU。假设 A 卸载需 3 秒，B 执行 20 秒，归还核验 2 秒，A 恢复需 5 秒：

```text
不让位：A 保留状态并等待 40 秒 → A 下一阶段或结束后，B 才有机会执行
让位后：卸载 A 3 秒 → B 执行 20 秒 → 核验 2 秒 → 恢复 A 5 秒
        合计 30 秒，若预测成立，可在 A 需要继续前完成交接
```

这不是实测收益，只说明何时值得评估。如果 A 实际 10 秒就收到回复，让位可能拖慢 A。未来策略必须留出预测误差余量，为 A 预留恢复容量，必要时停止新借用，并比较双方完成时间，而不只追求 GPU 占用率。**利用已睡眠窗口已有功能验证，预测并主动决定卸载尚未实现。**

**4. 补齐通用接入和并发边界。** 用原生 science GPU 任务验证最新执行、评分、取消和清理全链路，再完善同容器多命令并发。后者需要每条命令独立预算、进程归属和取消，容器设备权限则按所有活动命令统一管理。例如 A、B 同时执行时取消 A，只回收 A 的进程和预算，不能撤掉 B 仍在使用的设备权限。这是框架能力补齐，不能只通过调大实验脚本并发数实现。
