# Env 实验结论：什么情况下更快，证据有多大

> **核心结论**：已有实验证明，在会发生显存争用或长时间等待的受控场景，Env 的准入与放置机制可以缩短完成时间。收益取决于工作负载：三步训练压力对照少用 **27.59%** 总时间，常驻模型压力对照少用 **10.6%**；低负载同期配对则耗时接近。任务能运行、策略训练能闭环和调度能提速，分别有各自证据。

本页整理于 2026-11-16，只读固定报告与证据。实验跨多个日期和代码版本，每一行使用自己的工作量与计时范围。想先理解组件分工，可读[当前设计](../knowledge/current-design.md)；想复查数字，进入对应报告。

## 固定基线的有效性能证据

这里的 **baseline（基线）**固定为提交 `0eeead861ffafed6bf31c962d259fd847775dcf9`：通过静态配置分 GPU，保留进程内并发限制。表中的 OFF 使用这一版本及已披露运行补丁，ON 使用每次报告记录的修复版本。**OOM** 是显存不足导致分配失败。

| 场景、相同工作量和计时范围 | OFF | ON | 怎样理解 |
|---|---:|---:|---|
| Science 人工高显存压力，3 步、12 条接受轨迹，含初始化与清理 | 1954.11 秒，18 次 OOM | 1415.01 秒，0 次 OOM | 完整流程少 **27.59%**，见[三步训练](science-single-gpu-training-control.md) |
| 常驻 Mistral，7 项任务、14 次相同请求，驱动总时间 | 158.48 秒，1 次 OOM | 141.73 秒，0 次 OOM | 少 **10.6%**，见[整卡压力对照](gpu-benchmarks/FINDINGS.md#episode-记账修复后的整卡压力对照) |
| 低负载合成任务，OFF/ON/ON/OFF 两对，每组 8 项，含初始化与收尾 | 213.96 秒 | 217.15 秒 | ON 多 **1.49%**，两对方向不同，见[同期配对](router-baseline-control-validation.md) |
| PostTrain 长等待，A 1024 步、B 2048 步，三次时间块均值 | 85.291 秒 | 52.796 秒 | 工作块少 **38.10%**，含请求、等待、加载、计算与返回，准备和画像单列，见[等待或加载矩阵](gpu-benchmarks/warm-placement-matrix.md) |

**用三步训练理解收益来自哪里。** 两组最后都得到 12 条接受轨迹。OFF 在争用中发生 18 次显存不足，需要等待或补采；ON 的准入控制让任务在容量允许时进入，该组 OOM 为 0。因此节省的是执行等待和失败成本。三步训练计时之和为 `1100.80 → 503.69 秒`，减少 54.24%；连初始化和清理一起看则是上表 27.59%。两个百分比回答不同范围的问题。

该 Science 对照使用独立环境 GPU 和人工压力，生成长度不同、奖励及梯度为零，验收目标是训练链执行效率。常驻 Mistral 则用真实服务自然竞争显存，没有 PSRL 策略更新。PostTrain 矩阵使用固定步数命令，三次时间块复用常驻服务，模型能力与自然工作流分布另有评测目标。

**低负载为何没明显收益？** 资源本来就够用时，减少失败与排队的机会有限。工作阶段两对合计 ON 少 6.31%，但含初始化与收尾多 1.49%。应同时报告这两个范围，并保留该结果作为适用条件。

## 功能验收与机制探索

下面按要回答的问题分组。GPU 任务接入、并发机制和研究策略均使用真实工作，但各自的验收终点不同。

| 要回答的问题 | 已有结果 | 证据范围与入口 |
|---|---|---|
| 任务能否进入策略训练 | 六类代表题完成真实采样、一次优化器步骤、v1 发布和后续评分 | [接入详情](../milestones/science-gpu-full-onboarding.md)，全部题库覆盖见[现状表](../milestones/science-gpu-bench-status-and-roadmap.md) |
| MPS 能否支持并发训练 | 两份各 10 步，普通 CUDA 22.499 秒，MPS 20.160 秒；完整短流程 133.150/136.010 秒 | 两组都开 Router，训练段少10.4%、短流程多2.1%，见[MPS报告](mps-training-comparison.md) |
| 推理到来就暂停环境是否更快 | 合作式可正确继续；256 次更新连续请求时，现有共享/暂停为2.355/2.696秒中位数，暂停配对多14.49% | [真实共存对照](resident-compute-sharing.md)：36个区块，无MPS，同版本策略对照，轻量工具无需无条件暂停 |
| 热卡等待还是冷卡加载 | 亲和/预测长等待均值 86.113/52.796 秒，三对合计少38.69%；临界等待预测多0.81% | [矩阵](gpu-benchmarks/warm-placement-matrix.md)：48个核心区块完整，故障/容量完成5/9，总计53/57 |
| 性能反馈能否更可靠 | 159组中，共享出现严重选优错误；保护避免已观察的超过5%选择损失，自适应慢于固定两轮 | [压力实验](gpu-benchmarks/feedback-pressure.md)：固定候选、单容器人工后台工作，主矩阵还受到CPU配额限流 |
| 同机 command 池能否按相同工作量运行 | 288次正确性测试通过 | [同版本机制对照](../research-proposals/dynamic-command-placement.md#14-results真实-ray-与相同工作量对照) |
| SWE 准备前移能否减少完整耗时 | 普通/前移整组均值63.456/63.567秒，工作量一致 | [服务准备前移](../research-proposals/non-timing-gpu-scheduling-scenarios.md#results真实-score-服务题与准备前移对照)：预算持有减少，完整时间接近 |
| FlashInfer 能否分段 | 16项正确性通过，整批/分段均值33.09/32.05秒，首项后约剩0.33秒 | [分段报告](gpu-benchmarks/flashinfer-batching.md#保留评估器分段的-results)：复用同一评估器，GPU全程持有 |

等待/加载矩阵按四核心场景等次数相加时，预测比当前亲和少19.14%，比优先复制少12.78%，比旧 runner 少18.28%。这是预先规定的等案例组合；自然任务中的占比需单独调查。

该矩阵末尾容器 inspection 缺失；近末尾独立快照覆盖36个原生核心区块，显示当时无CPU限流，区间还含画像和部分故障工作。两后端的容器和GPU物理释放另有核验。原始观测范围随数字一起保留，详见[公开证据](gpu-benchmarks/warm-placement-matrix-evidence.json)。

## 引用规则与后续验证

引用性能数字时，一起写明**基线版本、任务、工作量和计时范围**。例如“3步、12条接受轨迹、含初始化清理少27.59%”，读者才能判断数字的含义。功能通过、耗时减少和模型能力改善分别报告。

已有证据支持若干明确条件下的收益。下一步需要更多自然 Agent 工作负载、统一版本和相同反馈质量的对照；可先从现有已验收任务中选择代表，再按问题设有界实验。文档整理期间没有启动新训练。历史逐文件核验见[文档审计](../../tools/docs-freshness-audit.md#7-2026-11-11-实验文档全量审查与重整)。
