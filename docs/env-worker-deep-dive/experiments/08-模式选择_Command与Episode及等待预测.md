## 研究问题与实际实现

本轮分开验证三件事。第一，自动选择后，租约、显存账本和实际执行器是否遵循同一种协议。第二，在相同真实模型更新与评分工作量下，释放命令间空档能否缩短整批完成时间，以及原任务是否多等。第三，真实保存、借用和恢复的时间是否支持简化公式，以及运行前的历史预测有多大误差。

已实现的 auto 在会话准入时选择模式。适配器声明 independent_commands 且未要求成本预测时可以使用 command；已校准预测建议保留时选 episode。如果适配器设置 gpu_timing_required，预测不足或失效时同样保留 episode。resident_state 或 unknown 始终使用 episode。每份租约分别保存结果，同一个 unit 可承载两类会话。执行中的命令不会突然改协议，物理归还仍须检查设备句柄、映射和 CUDA 进程。本次 PostTrain 三臂实机实验使用能力分流，成本建议和缺少画像时的保守分支到混合账本的接线另有 CPU 回归。

成本预测与能力分流有不同职责。前者判断一次借用是否可能让 A 多等，后者判断任务应遵守哪一种资源生命周期。预测器目前由实验控制器消费，生产默认配置没有自动睡眠推理模型，也没有把常驻 Python 服务强行改成可恢复命令。

## 持有模式对照

使用当前主目录同一份代码，比较显式 episode、显式 command 与 auto。这里遵循本阶段用户指定的“同版本固定资源池”对照，不使用历史 PSRL 分支。执行节点是用户私有节点，设备以本次 NVML UUID 和现场映射为准，原始地址与 UUID 留在本地证据中。

工作负载来自已接入的 PostTrain 本地协议：Qwen3-4B-Base，以 GSM8K 公开样本更新最终归一化权重 8 次，然后用独立 Python 进程加载提交文件，在私有样本上计算答案似然。奖励与时间无关。这是本地有界评分协议，不是官方 GSM8K 答案准确率，也没有启动 PSRL 策略训练。

每组两个会话 A、B，每个各有 train、verify 两条命令。A 完成 train 后进入受控间隔，B 在此时到达；A 间隔结束后提交 verify。间隔分别为 6 秒与 30 秒，用于对照短、长空档，不声称来自真实 agent 的自然轨迹。

一张 H20 上统一设置 20,000 MiB 环境预算，每个会话申报 14,000 MiB，GPU 同时只准入一条命令，CPU 与主存允许两个会话。20,000 MiB 是这次环境池的预算，并非 H20 的物理总容量。这样三组都必须面对同一份 GPU 容量约束。原始账本和执行时间均随结果保存。

对照同时记录：从 A 提交会话到两者清理完成的总时间；从 A 第一条命令开始到两者完成的工作时间；初始化、B 的会话排队和 A 下一条 GPU 命令排队。首次启动 Router/节点服务的成本单列，避免把一组冷启动和另一组热启动混作调度收益。

每条命令运行相同更新次数，核对提交权重哈希和独立评分一致。短 GPU 计算并不意味着短命令，Python、依赖和模型准备都可能占用已授予的 GPU 阶段，必须计入占卡时间。

**长空档出现了可利用的排队空洞，但性能差距不能全部归给策略。** 30 秒组的 auto 比 episode 少用 93.78 秒，约 31.6%。在去掉最后清理后的工作阶段，两者相差 94.63 秒，其中约 41.30 秒来自命令之外的时间减少，约 53.33 秒来自命令持有阶段本身变短。四条命令中的模型准备合计也从 122.41 秒降至 97.02 秒。运行顺序、缓存、宿主和共享文件系统负载可能影响后一部分，本次没有隔离其因果。因此证据支持“归还空档可以让 B 提前推进”，尚不能把 31.6% 当作稳定的纯调度加速比。

**短空档还显示了原任务被长命令挡住的风险。** auto 和显式 command 在本任务中解析为相同的 command 协议，却分别出现 0.96 秒和 98.98 秒的 A 排队。这是实际入队顺序变化：auto 组中 B 的容器准备约 6.04 秒，A 在 6 秒空档后先提交；command 组中 B 的容器准备约 4.64 秒，先占到卡，A 随后只能等待其长命令完成。用一次试验的 A 等待直接比较两个等价协议，会得出错误结论。此处最有价值的观察是：在空档与准备时间接近时，稍小的到达变化会产生很大的取回延迟。

**auto 为什么没有发现六秒组的 episode 更快。** 本实验的 auto 只接入“独立命令可以归还”的能力规则，没有提供成本预测，也没有要求必须有预测证据。它因此选择 command，并没有在两种策略之间预测、试跑、比较总完成时间。表中的 auto 和 command 耗时差异是等价策略不同运行的结果，不能算自动优化收益。六秒组也没有固定各条命令的实际执行时长：episode 四条命令持有 GPU 合计约 258.53 秒，auto 约 308.57 秒，这约 50 秒变化超过了命令之外约 15 秒的节省。不能把整批变慢直接归因于“A 被 B 挡住”。固定工作、零交接成本时填空档的收益，以及后续依赖使结论改变的例子，见[完整时间线推导](../knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md#用完整时间线比较保留与归还)。

所有 12 次 train 的提交权重哈希相同，12 次 verify 的本地奖励均为 0.4359629485025163。各组四条命令内部报告的实际模型计算合计约 3.06–3.10 秒，而整批需要 200–330 秒，当前瓶颈明显在进程、模型准备和交接。另有一个真实 unknown 能力案例选择了 episode，命令返回后账本仍计入 14,000 MiB，证明保守分支也接到了实际执行路径。

## 预测公式与真实借还

第二组使用另一张独立 H20。A 为真实 Qwen2.5-3B vLLM 实例，B 为 PostTrain Qwen3-1.7B 本地更新命令。A 通过现有 sleep/wake 接口保存和恢复，B 通过真实 EnvRouter、Docker 与命令归还路径执行。推理在完成恢复后运行固定 64 token 请求，核对恢复前后的确定性 token 完全相同。

记录 O 为关闭新请求至模型睡眠完成，B 为环境命令提交至物理归还确认，R 为模型唤醒并重新开放生成。A 的请求在受控时刻到达。提前恢复和按需恢复分别使用：

```text
提前恢复的额外等待 = max(0, O+B+R−G)
按需恢复的额外等待 = max(0, O+B−G)+R
```

本实验直接测量请求到达到可以进入模型服务之间的等待。公式使用实测分段验证时间线；预测器使用此前已完成周期估计，预测结果在执行前落盘。二者分开汇报，避免用已经知道的未来耗时证明预测准确。

校准按短、长空档画像各收集三个完整周期。随后保留未参与校准的周期检验预测。历史包络允许的额外等待预算为 1 秒。原计划还包括“过去属于长空档的会话突然在 6 秒返回”、再次观察后的保留决策和按需恢复；实际预算内只完成前八个周期，后述额外场景未取得完整 GPU 证据。

首次预测不足时，正常策略保留 A；实验中为采集校准与观测不利结果而强制借卡的周期会明确标注 calibration 或 forced。这些强制样本不计为自动策略成功决策。

## 预测结果与误差解释

八个完成周期包含六个校准周期、一个强制观察周期和一个真正按预测建议借卡的周期。它们的 vLLM 输出 token 全部与睡眠前的固定请求一致，B 的更新文件哈希也全部一致。

| 周期与用途 | 运行前预测 A 多等 / 秒 | 实测 A 多等 / 秒 | 应怎样理解 |
|---|---:|---:|---|
| 三次短空档校准，G 约 6 秒 | 尚未形成预测 | 69.99、67.39、61.95 | 强制采样，借用远长于空档 |
| 三次长空档校准，G 约 70 秒 | 尚未形成预测 | 均约 0 | 借用与恢复在 A 返回前完成 |
| 短空档留出样本 | 67.37 | 34.36 | 预测建议保留；实验强制借卡以观察误差 |
| 长空档留出样本 | 0 | 约 0 | 预测建议借出，实际执行了借出 |

“留出”指本次结果没有参与生成本次预测，只使用之前已完成的历史。两个留出样本平均绝对误差 16.51 秒，其中一个误差为 33.01 秒，一个几乎为零。只有两次，逐次报告比给出一个精确的平均指标更有意义；其中自动借出的完整样本只有一次。

**公式的真实算例。** 第一个周期从开始保存到归还耗时 2.2814 秒，B 从提交到确认归还耗时 73.5805 秒，恢复 A 耗时 0.1334 秒，A 的请求在 6.0021 秒到达。代入得到约 69.9932 秒，与实测 69.99325 秒一致。八个周期的最大对齐误差约 12 微秒。这说明本实验的串行边界与计时关系成立，预测准确度仍要看上一张表中的事前估计。

**33 秒预测偏差来自哪里。** 短空档历史 B 耗时为 73.58、73.04、67.62 秒，新一轮只花 39.30 秒；G 仍然约 6 秒，恢复仍约 0.15 秒。因此主要变化是 B 的准备与运行总时间，直接沿用历史中位数高估了等待。由于这个样本的策略本来建议保留，该误差表现为可能过于保守，而非自动放行导致超预算。另一类更危险的错误是把短空档误判为长空档：它可能把本应保留的卡借出。本轮对应周期在期限到达时被截断，不能用其未完成数据证明或否定风险控制能力。

预测器已提供按画像清除历史的接口；实验驱动在中断或异常后使对应画像失效。这项收尾修复通过 CPU 回归，没有重新启动 GPU。超时样本的含义是“至少已运行这么久，最终多久还未知”，应避免把它记成零，也应避免只留下快任务的历史而让预测越来越乐观。当前保守处理是重新校准，后续可以研究如何利用这类只有时间下界的样本。

## 下一步研究应解决什么

本轮优先级应从“换一个更复杂的预测模型”转向“让预测对象更稳定，并限制误判的损失”。当前真实命令的 GPU 更新不到几秒，模型准备却变化几十秒。先暴露准备阶段、缓存是否命中、状态在哪一级存储，以及准备完成的事件；能在占用 GPU 前完成的 CPU 工作提前进行。这样既可能减少无效持有，也能让 B 的预测更有依据。相邻工作与原创性边界见[主文档相关工作](../knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md#相关工作已经做到哪里)。

下一层问题是 A 返回的不确定性。真实 rollout 的空档应按当前阶段、已等待时间、工具结果和模型版本估计，而不是在实验里事先给出 6 或 70 秒。先记录实际轨迹上的候选借卡机会和预测，观察“有等待者、没有独立卡、空档够长”三者同时成立的比例，才能判断论文场景是否充分。

如果 B 能在明确的检查点保存进度，调度器还可以选择借用一小段，而非承诺整条长命令。教学假设一个训练命令共需 300 秒，每段最多 2 秒，到段末保存归还 0.5 秒，恢复 A 0.5 秒；A 提前回来时的阻塞就可按最多约 3 秒分析，而不是等待剩余数百秒。研究点会落到段长、状态版本、保存成本和 RL 批次依赖的联合决策。现有任意 shell 命令没有这种可撤回保证，预测器本身也不能补出这个保证。

## 证据边界与启动问题

本轮覆盖自动模式解析、混合账本、真实命令执行、vLLM 保存恢复与历史预测。受控间隔不能证明真实 PSRL rollout 中存在相同比例的可用空档。对常驻环境服务的任意状态保存、跨机器迁移、训练梯度或模型效果，本轮不作推断。

资源检查发现另一组既有训练会在后续阶段使用最初空闲的设备，因此首次准备在本实验命令执行前中止，改用其资源范围之外的 GPU。另一次预测组在预检发现设备已占用而退出。随后模型启动发现测试工具传入 `worker_extension_cls="auto"`，当前 vLLM 将它当成完整类路径解析而失败。已按安装版本的接口改为空字符串。上述失败均保留日志，尚未执行借卡周期的组不混入性能统计。

实验采用后台独立进程、外部期限和内部异步期限。实际脚本、任务源码与环境模块保存在对应结果目录的 source 中。主目录基于提交 `c5f2d65a70f6923c992a7be867edd0864db2bd0c` 加未提交修改，分支为 research/env-elastic-partition。本轮改动尚未提交或推送，目录中还有其他 session 的修改。

自动模式矩阵完成六组后，按“证据齐备即停止”的规则向所属 driver 发送 SIGINT；第二轮刚开始的 `1-command-6` 未计入结果。原始脚本将取消记录为 failed，原始状态保留，停止原因另存 stop-request.json。预测实验的外部期限为 950 秒，包含导入和初始化；退出码为 124，截断的是编号 8 的周期。其 Ray actor 随进程组超时退出，产生了清理 RPC 错误，最终物理检查仍确认所属容器为空、GPU 无计算进程。两者都是“有完整可分析前缀的提前结束”，没有把全流程状态改写为通过。

自动组清理后 NVML v2 记录 GPU 使用 0.19 MiB，预测组为 3.44 MiB，两者均无计算进程；驱动保留显存单独统计。新的脚本在 Ray 初始化后重新安装停止处理器，运行中及时保存状态，默认只跑一轮矩阵。后续后台入口建议外层 timeout 使用 `--foreground`，只通知 driver，让其先完成所属资源清理；外部预算应另留导入、初始化和清理余量。本轮启动器的原始配置保持原样以供复查。

针对性验证覆盖了 137 个不同测试案例，包括模式解析、混合账本、真实命令调度器的 CPU 回归、任务元数据传递和等待预测；最后补充画像失效和缺少成本证据时的保守准入后，重新执行策略、预测器和账本三个文件的 47 个测试并通过。源码与脚本通过 Ruff 检查，七篇受影响文档的 870 个本地链接通过路径、锚点与源码行号范围检查。公式的按需恢复分支、画像失效与条件剩余空档有 CPU 证据；提前返回后自适应和按需恢复的完整 GPU 周期仍未验证。

## 复现与源码

先执行[集群预检](../../psrl/psrl-run-guide/02-集群预检_依赖地址与GPU资源核验.md)，确认目标 GPU 当前使用情况及其他任务之后会用到的设备。不得因设备当前空闲就默认没有正在运行任务的分配。固定模型与数据目录，使用新的输出目录，勿复用其他任务的容器或 Ray 集群。

- [自动选择策略](../../../psrl/workers/env_service/reservation_policy.py)、[等待预测器](../../../psrl/workers/env_service/reuse_prediction.py)：纯 Python 实现。
- [自动模式实机入口](../env-service-verification/scripts/auto_reservation_study.py)：单卡三策略配对，训练每条仅 8 次小更新，支持指定间隔、重复次数与总期限。
- [预测实机入口](../env-service-verification/scripts/reuse_prediction_study.py)：单卡真实模型保存、PostTrain 借用、模型恢复，记录事前预测和事后误差。
- [结果汇总](../env-service-verification/scripts/analyze_auto_reservation.py)：仅汇总完整组，保留运行状态及物理清理状态。
- [可移植汇总证据](automatic-reservation-evidence.json)与[静态结果图](../../_static/img/document-figures/explained-automatic-reservation-70f6d6f.png)：完整组的时长、输出一致性和逐次预测误差；图由汇总脚本的 `--figure` 生成。
- 原始结果位于本地 env-service-verification/results 下的 auto-reservation-20261118-02、reuse-prediction-20261118-03；前序编号保存启动失败与迁卡记录。

运行入口都提供 `--help`。模型、数据、仓库和私有节点地址通过显式参数传入。后台启动使用 setsid/nohup，并为进程设置外部超时；结束后按本次标签检查容器集合，按目标 GPU 检查计算进程和显存，确认清理再进行下一组。
