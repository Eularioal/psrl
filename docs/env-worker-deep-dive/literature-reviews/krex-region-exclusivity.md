# KREX 精读：共享 GPU 上怎样取得可信的性能测量

> **核心结论**：KREX 把独占范围缩小到命令中的测量关键区域。测量前阻止竞争者继续提交 GPU 工作，等待已有工作完成，再冻结竞争进程并保护 CPU 提交线程。区域外恢复共享。这让许多评测任务共用 GPU，同时使计时接近无竞争执行。它没有提供“任意竞争持续存在时还能还原独占耗时”的算法，也没有最坏情况误差保证。
>

## 1. 从完整流程理解论文

论文标题是 **KREX: Concurrent Kernel Benchmarking on Shared GPUs via Region-Granular Exclusivity**，可译为“通过区域级独占，在共享 GPU 上并发评测计算内核”。kernel 在这里是 GPU 上执行的计算程序，例如矩阵乘法或归一化，不是操作系统内核。kernel agent 是用大语言模型编写这些程序、运行评测、依据结果继续修改程序的智能体。

以下是依据论文 §3、§4 重画的概念图，主要展开 NVIDIA 路径。它不是 PSRL 已有调用链，也不是从作者开源代码绘制的图。

```text
agent 或固定评测脚本作者：标记完整测量区域
                   ↓ 提交命令
[0] dispatcher：为新 client 配对一个常驻 context process
                   ↓
client：导入、编译、输入准备、正确性检查，可以和其他命令重叠
    │ GPU API 经转发交给 context process，再提交到 GPU
    │ 进入已标记的区域
    ▼
[1] 每 GPU 的 coordinator：只准许一个测量持有者
    ↓
[2] 关闭提交门，记录持有者和本轮 epoch
    ↓              其他 context process 的后台线程协作
[3] 等待主机提交结束，再同步所有相关 GPU context，确认本轮排空
    ↓
[4] 冻结同卡竞争者的进程树，其他 GPU 使用独立的 CPU 核集合
    ↓
[5] 清理 L2 缓存影响，将持有者提交线程绑定到保留 CPU 核
    ↓
[6] 在保护范围内预热并测量，取得候选和参考的时间
    ↓
[7] 完成区域主机提交，解冻其他进程
    ↓
[8] 重开提交门，释放区域锁，区外并发继续
    ↓ 命令退出
[9] 清理该命令资源，健康 context 留给下一命令，坏 context 替换
```

图例：图里每个部分对应的源码位置或原文位置。

| 节点或箭头 | 责任与状态变化 | 可查位置 |
|---|---|---|
| 标记 → 0 | 作者声明测量意图，命令与 context 进程配对 | 论文 §4.1、§4.3，未在本地找到对应 KREX 实现 |
| client → context → GPU | 驱动 API 拦截及跨进程调用，context 拥有设备执行状态 | 论文 §4.3，不能映射成 PSRL 的普通 shell 执行 |
| 1、2 | 单持有者仲裁和阻止竞争提交 | 论文 §4.2，Fig. 4 |
| 3 | 等待主机提交计数归零，并取得各 context 的设备完成确认 | 论文 §4.2，后台线程并行完成，非单线程依次调用 |
| 4、5 | 保护主机执行、初始化测量环境 | 论文 §4.2，AMD 差异见 §5 |
| 6 | 执行作者标记的区域 | 论文 §4.1、§4.2，区域正确性由作者负责 |
| 7、8 | 按先解冻后开门的顺序恢复共享 | 论文 §4.2，异常退出另走恢复协议 |
| 9 | 资源清理、健康检查和 context 复用 | 论文 §4.3 |

**它解决的问题**是 GPU 评测容量不足与性能反馈失真的冲突。一个评测命令通常经历 Python 导入、编译、构造输入、验证结果、预热、反复计时。GPU 不必在全部阶段都被同一命令独占，尤其 CPU 准备期间，整卡锁会让其他已准备好的任务也只能等待。

论文区分三种粒度：E1 对完整 agent 会话独占，E2 对整条评测命令独占，E3 只对关键测量区域独占。关键区域可以包含许多 kernel 及预热，不等于只锁住一条 GPU 指令。

原创教学例子：四条命令各需 90 ms CPU 准备和 10 ms 测量。假设 CPU 核足够，准备可以完全重叠，暂不考虑 GPU 正确性检查。整命令串行需要 `4 × (90 + 10) = 400 ms`。如果四条命令同时准备，再串行计时，每次切换另花 1 ms，则共需 `90 + 4 × (10 + 1) = 134 ms`。计时本身仍然串行，收益来自其他阶段的重叠。真实系统还有排空、冻结、内存占用与初始化成本，不能直接期待 400/134 倍实测收益。

## 2. 为什么共享会把优化方向带偏

性能反馈用于选择下一版代码，因此测得稳定还不够，必须测到目标条件下的性能。

原创教学例子，单位为 ms，数字不是论文数据：

| 候选 | 无竞争时间 | 竞争造成的倍率 | 共享时测到的时间 |
|---|---:|---:|---:|
| A | 10.0 | 1.10 | 11.000 |
| B | 10.2 | 1.01 | 10.302 |

无竞争时 A 更快，但共享测量会选 B。差异可能来自计算单元、显存带宽、缓存与 CPU 提交路径的不同敏感性，不能默认所有候选都乘同一个减速系数。即使共享的两列都精确重复 100 次，中位数仍然会给出错误排序。

可用下式帮助区分问题，但它只是解释模型，不是论文提出的估计器：

\[
T_{obs}=T_{target}+\Delta_{contention}+\Delta_{state}+\Delta_{runtime}+\epsilon
\]

其中目标时间对应指定设备、输入、缓存和时钟协议，竞争、运行状态和运行时转发可以造成系统偏差，随机项才是通常靠增加样本来降低的部分。KREX 主要通过控制执行条件减少这些偏差，而不是在输出后减掉一个估计常数。

GPU Event 是在设备执行流中记录时间的标记。它能避免把异步提交函数的返回误当成计算完成，但不能自动消除两个标记之间的竞争。CPU 调用返回、GPU 队列完成、计时结果可读取，是三个不同事件。参见 [CUDA 异步执行指南](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)和 [Event API](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-runtime-api/group__CUDART__EVENT.html)。

## 3. 怎样建立真正可测量的独占窗口

**第一步，标记正确的边界。** 论文接口是 `region.critical()`。由固定评分器提供区域时，agent 只交候选代码，不能改测量规则。由 agent 编写整个程序时，则由 agent 自己标记。KREX 不验证边界是否正确。

下面是教学伪代码，函数名表示职责，不是可运行 KREX 示例：

```python
prepare_inputs_and_compile()
check_correctness()
with region.critical():
    warm_up_with_the_declared_cache_policy()
    candidate_time = measure_candidate_until_gpu_completion()
    reference_time = measure_reference_under_the_same_protocol()
report(candidate_time, reference_time)
```

预热用于消除首次初始化等非目标成本，也会改变缓存状态，因此不能机械地只包围 start/stop 两个时间标记。自动调优器内部也可能偷偷测量，需要一起考虑。冷缓存还是热缓存应由目标指标决定，参考和候选都遵守同一个协议。

**第二步，阻止新的竞争提交，而且不能留竞态窗口。** 区域锁保证只有一个持有者。提交门 gate 则约束其他进程的真实 GPU 调用。仅有“大家测速前拿同一把锁”，不能阻止别人仍在区外进行 GPU 正确性检查。

NVIDIA 路径在可能产生设备工作的调用前，先增加主机提交计数，再检查 gate。发现别的持有者就撤销计数并等待，否则执行调用，返回时再减计数。这样的顺序加上有序原子操作，确保关门同时发生的提交，要么被阻止，要么被后续排空覆盖。先看门、再增加计数会留下“刚看见门开着，测量方就以为没有未完成提交”的空隙。

新 context 的注册也与关门串行化。关门前注册的进程必须排空，关门后到来的进程不能提前使用 GPU。创建和清理 context 同样受协议约束，否则设备初始化也可能穿过测量窗口。

**第三步，等待已经进入 GPU 的工作真正结束。** context 是驱动维护的 GPU 执行环境，包含设备资源和提交状态。一个 CPU 线程把 kernel 放进队列之后，可以立刻返回，而 GPU 还在计算。

因此主机提交计数等于零，只说明没有线程仍在提交调用中。每个竞争 context 进程还需要后台排空线程，同步自己管理的全部 context，包括候选新建的次级 context。不能只让测量进程同步自己的 context 就宣称整张卡已空。

原创时间线：B 在 `t=0` 提交工作，GPU 要到 `t=5 ms` 才做完。A 在 `t=2 ms` 请求测量。此时暂停 B 的 CPU，B 的 GPU 工作仍然存在。正确做法是先关门，再等到 `t=5 ms` 得到排空确认，之后才能开始 A 的测量。这里的 3 ms 是隔离成本，不是 A 的 kernel 耗时，但必须计入评测服务的总延迟。

每轮排空还带 epoch，即本轮请求的唯一代号。例如第 7 轮收到“第 6 轮完成”的迟到消息，不能据此开始计时。确认必须属于当前轮次，且所有参与者的计数均为零。

**第四步，排空后再保护 CPU。** GPU 无竞争仍不足以保证多 kernel 测量可靠。假设一个操作需要连续发射 K1、K2、K3，如果发射 K2 的 CPU 线程被编译任务抢占，GPU 做完 K1 后会空等，时间标记之间仍可能出现额外空洞。若整个计算已预提交到设备，这类影响会小得多，不能把 CPU 争用对所有 kernel 都描述成同样严重。

KREX 使用 Linux 的 freezer cgroup，即把一组进程及其子进程作为整体暂停的机制，冻结同卡其他租户。必须在排空之后冻结，否则用于完成驱动调用和同步的线程也可能停止，排空协议无法完成。

其他 GPU 的租户不必全部冻结。系统为每张 GPU 划分互不重叠的物理 CPU 核集合，并靠近相应 NUMA 节点，即主机内对这张卡访问较近的一组处理器和内存。测量线程绑定到该集合内的保留核。分核并不等于主机共享缓存、内存带宽、内核中断全部完全隔离。

**第五步，整理测量状态，再执行区域。** 论文在进入测量前用 L2 大小的缓冲区做 memset，以减少其他任务留下的 GPU 二级缓存状态影响，同时完成线程绑核。它是在规定缓存条件，不是证明缓存和温度等一切历史影响都已消失。隔离确认失败、超时、参与者死亡时，不应继续输出一个看似正常的测量值。

**第六步，按正确顺序退出。** 正常退出先保证区域调用完成主机侧提交，再解冻竞争进程，最后开门和放锁。不能先放锁再慢慢解冻，否则下一位已冻结的进程可能被上一轮迟到的解冻操作恢复。异常恢复也绑定持有者身份与 epoch，并在 GPU 工作结束及资源恢复后继续服务。

以上排空细节主要描述 NVIDIA 实现。论文 §5 的 AMD 路径用设备完成信号递减计数，因此计数归零本身具有设备完成含义，不照搬 NVIDIA 的“主机计数归零后再同步 context”。AMD 实验还要求初始化后才加入 freezer cgroup，规避评估系统上的初始化失败。

## 4. 为什么只缩小锁的范围还不够

一旦允许很多命令同时准备，另一个瓶颈会暴露：反复创建 GPU context。论文在测试平台上观察到初始化和 context 创建会取得节点级驱动锁，即使目标 GPU 不同也可能串行。这是所测软件栈的发现，不应直接推广成所有驱动的固定性能。

NVIDIA 路径把两个生命周期分开。client 是一次候选程序的进程，执行结束就退出。context process 长期存活，持有已经创建的 GPU context，依次服务多个候选。dispatcher 在新命令开始时配对两者，不在每次 kernel 调用中参与调度。

驱动 API 拦截层把 client 调用写入共享内存队列，context process 取出并执行。RPC 是远程过程调用，这里跨的是本机进程，不代表必须通过网络。kernel 启动尽量单向异步转发，让传输与 GPU 执行重叠，事件和同步则需要相应的回复或等待。

这种代理可能新增发射延迟，尤其短 kernel 很敏感，所以论文专门比较经代理但不共享的 KREX-serial 与原生执行。减少转发成本不等于转发完全免费。

候选结束后会释放其显存分配、模块及主机注册资源，保留健康 context 和部分库缓存。若 context 因错误不可用，就替换整个 context 进程。**复用 context 不等于任意候选的模型权重或显存数据会永久保留，更不是把活跃 CUDA context 无损搬到另一张卡。**

AMD 主实验关闭了 context pooling，以避免该路径带来的较大测量失真。介绍结果时必须保留这个平台差异。

## 5. 精准测量究竟指什么

首先声明要测的量。以下三种问题有不同实验边界：

| 问题 | 正确计时范围 | 竞争应如何处理 |
|---|---|---|
| 候选在指定单卡上本身有多快 | 规定状态下的设备操作，完成事件前后 | 用可验证的隔离窗口减少干扰 |
| 共享评测服务多久给出结果 | 请求入队直到结果可用 | 竞争、等待、排空、初始化均属于真实成本 |
| 某程序在真实共存部署下多快 | 指定背景负载条件下的程序或服务延迟 | 背景竞争是测量条件，不能全部删除后宣称测到了共存性能 |

KREX 主要服务第一种目标，并评估实现它时第二种目标的吞吐。若你的课题要求训练和环境任务一直同时计算，就无法直接用 KREX 的隔离机制保证无竞争耗时。你需要让双方遵守短时安全点协议，或选择独立设备，或明确研究的是给定竞争条件下的条件性能。

GPU Event 测量与主机单调时钟各有用途。前者测设备流中的执行区间，后者测用户看到的端到端过程。排队 20 ms、排空 3 ms、候选 1 ms 的请求，候选时间可以是 1 ms，服务延迟至少是 24 ms，另外还可能有恢复成本。只报 1 ms 会隐去调度成本，只报 24 ms 又无法判断候选代码是否优化。

论文的保真度指标为：

\[
r_i=\frac{t_{measured,i}}{t_{native,i}},\qquad
P=\bigl(\operatorname{p95}(r_i)-1\bigr)\times100\%.
\]

native 指原生、每卡一次只运行一个命令的参照。p95 是把比例排序后查看第 95 百分位附近的值。`P=2.5%` 表示该分布的 95 分位倍率约为 1.025，不表示每个样本都在 ±2.5% 内，也不表示具有 95% 置信度。这个指标只看高估方向，低估也要另查。

原创反例：100 个比值中 94 个是 0.70，1 个是 1.02，5 个是 1.50。采用最近秩百分位定义，p95 膨胀只有 2%，但绝大部分结果低估了 30%。所以应同时报告中位数、双侧相对误差、误差阈值内比例和排序错误，不能只挑一个小的 p95。

排序错误也要按候选真实差距分组。两者相差 0.2% 时，重复独占也可能换顺序。相差 20% 却频繁换顺序，则更能暴露测量系统的问题。论文把第二次 native 执行也与第一次比较，以估计无共享时的自然波动。

## 6. Results：论文证据及不能外推的结论

下表来自论文 §6.1 至 §6.4，是作者的回放实验，不是本地复现。测试平台合计 16 张 H20 和 16 张 MI308X，回放超过 20,000 条实际 agent 评测命令。吞吐按每个 8 卡节点统计，一小时饱和回放排除了 LLM 思考延迟。

| 平台及主要配置 | native 吞吐 | KREX 吞吐 | 正文 Fig. 8 的 p95 膨胀 |
|---|---:|---:|---:|
| H20，每卡 16 命令，KREX 开 MPS | 16.0 命令/分钟 | 54.8，约 3.4 倍 | KREX 2.5%，native repeat 0.9% |
| MI308X，每卡 4 命令，关闭 context pooling | 19.4 命令/分钟 | 50.4，约 2.6 倍 | KREX 2.4%，native repeat 3.2% |

Fig. 8 的计时比较限于 native kernel 时长大于 1 ms 的命令，不能推广到所有短 kernel。Fig. 9 中小于 0.1 ms 的 kernel，即使 native repeat，p95 膨胀也达到 H20 的 12.1% 和 MI308X 的 7.6%。短测量并没有因为区域锁而自动变成精确计时。

**摘要与正文数字需分开引用。** v1 摘要和引言称，时长大于 10、1、0.1 ms 时分别为 0.30%、1.58%、3.90%。这三个阈值是重叠集合，不能改写成三个互斥区间。正文主实验则给出上表的 2.5% 与 2.4%。本次未找到足以把摘要数字对应到正文平台、配置和汇总口径的解释，PDF 与 HTML 都保留了这种差异。因此本文采用条件更明确的正文数据，不替作者猜测差异原因。

H20 的排序实验中，KREX 在各候选差距组内的排序反转率，与 native repeat 相差不超过 3 个百分点。这是“接近独占重复实验”的证据，不是错误率只有 3%，也不是所有排序都正确。

另一个重要消融：H20 每卡 16 并发且都开 MPS 时，无保护、仅 GPU 保护、完整 KREX 的 p95 膨胀分别为 23.87%、4.63%、2.45%。这支持 CPU 保护具有额外作用。主吞吐图中的 ungated 配置并未与 KREX 使用完全相同的 MPS 设置，不能仅凭该图归因所有吞吐差异，机制归因应看匹配配置的消融。

MPS 是 NVIDIA 允许多个进程共享 GPU 执行资源的多进程服务。论文并非全面排斥 MPS，而是用它促进区外并发，再用区域协议保护测量。MIG 是把 GPU 分成硬件资源子实例，测 MIG 的时间可以有效，但测量目标已经变成该子实例，不能直接当成完整 GPU 的时间。

论文 §7 明确的边界包括：合作型候选、人工或 agent 提供的区域边界、无理论最坏情况误差界、按槽位准入而非完整显存/CPU 需求调度、无区域公平性保证，以及尚待扩展的多 GPU 候选和多节点池。设备时钟属于部署级控制，需要整卡控制的任务会改走整卡租约。

由这些假设可推断：未受控外部进程持续往同卡提交工作时，受管租户之间的 gate 不足以建立全卡静默。GPU 利用率某一瞬间显示为零，也不能证明之后不会来新工作。冻结进程通常不会释放其驻留显存，准入仍需考虑总显存，不能把“没有计算竞争”等同于“资源全空”。这些是适用条件分析，不是本文实测出的新缺陷。

## 9. 对研究选题和实验设计的指导

**较值得验证的方向是：在已有可靠隔离基础上，调度获得足够比较证据所需的 GPU 时间。** 这是研究提案，尚未证明比已有方法更好。“只在测速时独占”与“复用 context”已经是 KREX 的直接贡献，不能再作为本课题主要新颖性。

例如 A 为 10 ms、B 为 20 ms 的比较，很快就可能获得稳定排序。A 为 10.00 ms、B 为 10.02 ms 时，则可能需要更多重复、交错对照，或者报告两者在当前预算下无法区分。一个固定 rollout 组的调度器可以同时看比较关系、当前不确定性、测量窗口切换成本和整组结果就绪时间。

难点不是简单多测几次，而是某个候选新增一个样本可能同时解决多个比较。相反，连续测量同一候选会占住独占窗口，推迟其他尚无证据的候选。把这些依赖表达为系统可以执行的协议，才可能产生区别于普通 FIFO 和独立自适应测量的机制。

对当前课题，建议按以下最小范围验证，不直接启动训练：

1. 固定一批正确候选、相同输入、相同设备与软件版本。覆盖明显差距和近似并列两类，并包含计算密集、带宽密集及短 kernel。先取得多次独占参考，不把一次结果称为绝对真值。
2. 统一编译、预热、缓存、计时和结果读取协议。需要无竞争时间时，候选和参考都在受控条件下测量。外部干扰无法纳入协议就转到独立设备，不能靠一次利用率采样宣称独占。
3. 记录请求到达、取得区域锁、排空完成、冻结完成、测量开始结束、解冻完成和结果返回。以唯一请求和 epoch 关联，分别算排队、转换、区域占用、候选时间及端到端时间。毫秒级调度与微秒级 kernel 指标不能混算。
4. 比较整命令独占、朴素共享、区域独占、区域独占加每候选独立自适应测量，以及再加简单批处理的强基线。若实现不了完整 KREX，准确标记为局部原型，不把弱化的替代实现写成原论文基线。
5. 吞吐、p95 膨胀、双侧误差、排序翻转、超时与失败、有效结果数都报告。自适应方法还要报告测量总预算、决策错误及“无法区分”的比例。只保留成功样本会低估坏条件的成本。
6. 使用预先给定的样本数、时间和资源上限。可采用随机化执行顺序或 A/B 交错的配对设计来降低慢漂移，但不能认为这消除了所有候选特有的竞争偏差。若根据中间结果决定何时停止，需要相匹配的序贯统计方法，不能反复查看普通固定样本置信区间直到它恰好显著。

如果做固定工作量的调度对照，两组候选及测量次数必须相同。如果研究的是自适应预算，则允许测量次数不同，但候选池、正确性标准、总预算约束和错误容忍目标必须一致，减少的测量次数本身就是需要披露的机制。

本地固定历史 baseline 仍遵循项目指定提交，不能用当前代码关闭某个开关代替。研究比较另需增加上面的区域隔离强基线，仅打赢静态 GPU 分配不足以证明对 KREX 有新增价值。

立项停止条件也要明确：若开销主要来自无法重叠的执行、测量只占极小部分、近似并列不足以影响反馈，或简单批处理已获得全部收益，则应收缩这条研究主张。冻结其他任务还会延迟它们，公平性和最大暂停时间属于可研究约束，但不能未经文献核查就宣称这是全新调度问题。

## 12. 可落地的测量协议与最小实验计划

本节是给 PSRL 课题的实验设计提案，不是 KREX 原文额外结论，也不是现有采集接口。本轮只运行 CPU 算例，没有执行下述 GPU 计划。首期要回答的问题限定为：**在同一批正确候选上，区域保护是否减少竞争造成的测量失真，以及代价是多少。** 自适应测量和训练效果不混入这轮验收。

**先固定测量对象。** 每个样本同时绑定候选代码哈希、输入规格与随机种子、设备 UUID、软件版本、缓存协议、重复次数和背景负载配置。UUID 是设备的唯一标识，避免把两张同型号但状态不同的卡混为同一参照。正确性验证在性能比较前完成，失败候选不应因运行得短而得到高性能分。

**原始计时与服务计时分开保存。** 以下是建议字段，不是当前 PSRL 已提供的 schema。schema 指日志记录中字段及其含义的约定。

| 字段 | 谁记录及何时记录 | 用途 |
|---|---|---|
| `request_id, region_epoch, candidate_hash, protocol_id` | 调度器与可信评分器传递同一组身份 | 关联命令、区域、代码和计时规则，拒绝旧轮次确认 |
| `arrived, lock_granted` | 同一服务端时钟域中记录接收和获得区域锁 | 分离区域等待与执行，不包括此前未记录的准备时间 |
| `gate_closed, drained, frozen, region_started` | 实际完成相应动作的执行器记录确认 | 定位隔离开销，不能在“已发请求”时就记为完成 |
| `region_finished, thawed, gate_opened, returned` | 执行器及服务端记录完成与返回 | 分离测量区域、恢复共享和结果返回 |
| `device_samples_ms, warmup_policy, repetitions` | 可信评分器读取已完成的 GPU 事件 | 保存原始样本与汇总规则，不能只保留最终平均值 |
| `status, reason, background_id, telemetry_status` | 执行器记录协议异常和观测条件 | 将失败、缺测、外部干扰与正常慢样本区分 |

同一机器内的区间时长使用一致的单调时钟，例如 `time.monotonic_ns()`，它不受墙上时间校准回拨影响。必须记录时钟域或启动身份，不拼接不同机器、不同启动周期的原始值。跨节点端到端延迟优先由一个请求方从发送到收到回复计时，各节点只报告自己的局部持续时间。GPU Event 返回的设备区间也不能直接与 CPU 时间戳相减。

原创算例：服务收到已准备好的请求为 0 ms，获得锁为 20 ms，完成隔离为 24 ms，保护区域结束为 27 ms，返回为 30 ms。保护区域含预热与读取结果，GPU 事件测出的候选时间是 1 ms。

| 项目 | 算法 | 结果 |
|---|---|---:|
| 等待 | 20 − 0 | 20 ms |
| 隔离转换 | 24 − 20 | 4 ms |
| 保护区域占用 | 27 − 24 | 3 ms |
| 恢复与返回 | 30 − 27 | 3 ms |
| 服务端总延迟 | 30 − 0 | 30 ms |
| 候选设备时间 | 由 GPU Event 单独读取 | 1 ms |

前四项相加等于总延迟，设备时间已经包含在区域工作中，不能再相加得到 31 ms。如果真实路径提前返回结果、后台继续归还，则另报 `resources_released`，不要强行让“结果可用”晚于“资源释放”。算法快慢、用户等待和系统可复用资源的时间是三个量。

**GPU 事件的读法要与执行方式一致。** 对单流候选，预热后记录 start，提交固定次数的候选调用，记录 end，等待 end 真正完成，再读事件差。多流候选需要把相关流的结束依赖汇合到 end 所在流，否则会遗漏工作。批量区间除以调用次数，得到的是该重复模式下的平均调用时间，缓存复用和发射流水可能让它不同于孤立单次延迟，不能悄悄更换测量目标。依据见 [CUDA Event API](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-runtime-api/group__CUDART__EVENT.html)。

**参考实现不能自动抵消竞争。** 假设参考独占耗时 12 ms，候选 10 ms，真实加速比为 1.2。共享时参考慢 25%，候选慢 10%，测得的比值是 `15 / 11 ≈ 1.364`，比真实加速比高约 13.64%。只有两者受到相同乘性影响等附加假设成立时，除法才会抵消干扰。交错测参考与候选可以降低慢漂移影响，但不能证明这种等比例假设。

**把竞争拆开施加。** 每类负载单独运行，保证能解释变化来源。以下仅是未来有界实验的输入设计。

| 背景负载 | 想触发的机制 | 必要观测 |
|---|---|---|
| 无背景负载 | 原生重复和运行时自身开销 | 至少两个独占轮次，区分自然波动与代理开销 |
| 同卡计算或带宽负载，分两次测 | GPU 执行和带宽竞争 | 保护前确有工作，测量前已排空，区域内无新竞争提交 |
| 同卡租户的 CPU 编译或发射线程压力 | CPU 提交被延迟 | GPU-only 与完整 CPU 保护的差异，CPU 绑定条件一致 |
| 入区前已有异步长任务 | 只关门却不排空的失败模式 | 旧任务的完成确认晚于关门，测量必须更晚开始 |

不受控制的外部 GPU 工作适合作为“独占条件不成立”的失败样本，不应混入合作式场景后宣称协议可处理它。高频 profiler 也可能改变被测时间，机制诊断和正式性能统计应分别进行，保持各对照的采集方式一致。

**先做小矩阵，再按失败原因展开。** 建议的首期固定上限是一个已确认可用的独立 GPU、3 类 kernel、每类 2 个正确候选、每配置 10 个独立测量块、每块固定 10 次计时。配置先取原生独占、运行时串行、无保护共享、仅 GPU 保护、完整区域保护五组，仅在相应实现真实可用时运行，不把缺失实现伪装成某个基线。最多 `3 × 2 × 5 × 10 = 300` 个块，测量阶段墙钟上限 20 分钟，失败块不自动补采。单块超时 10 秒或预先设定的更小任务上限，达到总预算就结束。资产准备和设备预检独立记录，准备失败不能算已运行的配置。

这些是建议预算，不是为了显著性推导的样本量。每块内部 10 次执行可能高度相关，不能当成 10 个独立实验。按块保存结果、按候选比较，两次独占测量之间也会变动。10 个块不足以稳定估计某一个候选的 p95，更不足以证明 1% 的排序错误上界。若当前预算只能支持探索性结论，就报告区间和样本量，不自动扩大实验。

机制消融保持 MPS 开关、上下文池、并发数、候选流及采集设置一致，一次只改变被研究的保护机制。原生独占与代理串行的差异单列为运行时成本。背景负载单独记录实际提交和运行量，不能把“完整保护主动暂停了更多背景工作”描述成在相同背景吞吐下实现收益。若负载从始至终没有形成竞争，就将该项标记为条件未触发。

**失效判据提前写好。** 旧 epoch 确认、参与者未全部登记、排空失败、GPU 事件未完成、测量期间 gate 所有权丢失、超时或 GPU 错误，均不能产生一个标为有效的独占计时。正常完成但很慢的样本不能仅因偏离预期被删除。遥测缺失不补零，也不自动判定任务失败，但依赖该遥测才能确认的条件必须标为未知。所有无效与失败尝试仍计入服务总成本和失败率。

验收时同时查看：独占重复的自然波动、共享引入的额外偏差、双侧误差、排序变化、有效结果吞吐、区域等待、隔离成本及最大暂停时长。若 GPU-only 与完整保护近似相同，可能当前负载没有触发 CPU 瓶颈，不应把它改写成“CPU 保护永远没用”。若完整保护仍失真，按未受控提交、未完成设备工作、CPU 竞争、缓存或时钟状态、代理发射开销逐项定位，不先增加重复次数掩盖问题。

第 10 节脚本新增两个 CPU 算例，分别输出 `20 + 4 + 3 + 3 = 30 ms` 的分账及 `1.200 → 1.364` 的参考归一化偏差。它只检查公式和教学数字，不验证日志采集完整性，也不证明 GPU 协议正确。
