# 智能调度：模型决策的已有工作与研究选择

> **核心结论**：已有研究让大语言模型直接选设备、从源码和日志补充调度信息，或离线生成调度算法；Google 也报告将 AlphaEvolve 生成的启发式用于 Borg。对 PSRL，优先研究“模型能提供什么传统观测没有的信息”，再比较简单策略、小模型和在线 Agent。建议从异步语义提取或离线策略生成开始，保留确定性的准入、版本核验与物理归还。把 LLM 接进 Router 本身不是充分的论文贡献。

核对范围：2026-11-13 的公开一手资料；本地源码基于 `6aa328d56eff746c2ae6d9fd766b2f3f76b4a670` 与主目录未提交内容，局部核对 `warm_dispatch`、`step_predictor`、direct command 准入与归还。论文结果是作者报告；本文未复现其系统，也未启动 GPU 或模型推理实验。

## 1. 调度大脑究竟指什么

**调度**决定“哪个已就绪的工作，在什么时刻，去什么设备，以什么资源配置执行”。本篇真正要判断的是：模型能提供什么普通调度程序还不知道的信息，以及获得这些信息花的时间能否收回。

例如一条测试命令即将运行，调度器知道 GPU 0 排队 12 秒、GPU 1 空闲，却不知道测试是否必须重新加载模型。只比较队列可能选错。模型若能从代码差异中解释“模型没变，只改了评分逻辑”，就可能帮助系统选择合法复用路径。但设备是否合法、实际是否还有容量，仍需由执行前的普通程序检查。

“用模型调度”至少有四种含义：

| 模型做什么 | 输入 → 输出 | 在线每个动作都调用 LLM 吗 |
|---|---|---|
| 直接决定动作 | 当前任务与资源 → 设备/队列/动作 | 可以是，但还需核验与执行层 |
| 为调度器补信息 | 代码、日志、历史 → 阶段、时长估计、进度 | 通常低频或按事件调用，派发仍可由算法完成 |
| 离线生成算法 | 旧策略、目标、评估反馈 → 新的评分函数代码 | 否，部署后执行普通代码 |
| 学习数值策略 | 队列与依赖图 → 优先级、并行度 | 在线运行小型神经网络，未必是 LLM |

还要区分：**为 Agent 工作负载做调度**与**让 Agent 当调度器**。DynaRL、RollArt 涉及前者，并不能因此推导其调度器是在用大模型推理。原有[两篇精读](02-论文精读_RollArt与DynaRL的Agent调度.md)与本文是互补关系。

## 2. 有哪些值得看的工作

这里按机制相关性筛选，没有将所有条目称作顶会论文，也不把作者原型当作工业上线。

| 工作 | 可核实状态 | 模型真正负责什么 | 对我们的价值 |
|---|---|---|---|
| [Agentic CPU-GPU Scheduling for Heterogeneous AI Workloads](https://arxiv.org/abs/2607.22242) | 2026-07 arXiv 预印本；本次未核实正式会议发表 | 结合工具画像和监测反馈，为工具选 CPU、立即 GPU 或排队 GPU | 最直接的 Agent 设备选择对照 |
| [SchedMate: Semantic-Aware Scheduling for GPU Clusters with Large Language Models](https://arxiv.org/abs/2510.03334) | 2025-10 完整版预印本；早期同名工作为 NSDI 2024 poster，不能称正式长论文 | 读代码、日志和历史，辅助预测、进度跟踪和故障处理 | 最贴近“理解环境命令”的信息来源 |
| [LarS: LLM-based cost-aware task scheduling for cloud computing systems](https://link.springer.com/article/10.1186/s13677-025-00822-0) | Journal of Cloud Computing，2025 正式期刊 | 微调 LLM 根据任务、虚拟机状态及目标选择映射 | 直接模型选动作确有已发表工作；对象是云任务与虚拟机，不是我们的 GPU 命令 |
| [AlphaEvolve](https://arxiv.org/abs/2506.13131) | 2025 white paper；有 Google 官方部署报告 | 离线生成、评估、改进调度评分代码 | 工业启发最强：模型搜索策略，线上确定性执行 |
| [ADRS: Let the Barbarians In](https://arxiv.org/abs/2512.14806) | 2025 技术报告/预印本，本次未核实正式会议 | 用生成—评估—改进循环搜索系统算法，含云调度案例 | 将已有回放和验证工具变成策略评估器 |
| [DynaSchedBench](https://proceedings.mlr.press/v306/cao26z.html) | ICML 2026 正式论文 | 评测逐步在线 LLM 调度 Agent | 告诉我们怎样避免“会推理所以必然调得好”的假设 |
| [Decima](https://web.mit.edu/decima/) | SIGCOMM 2019 正式论文 | 用强化学习训练神经网络，在运行时选作业阶段和并行度 | “模型做调度”早已有之；数值问题必须比较小模型 |

**DynaSchedBench 不是 GPU 论文。** 它的对象是动态柔性车间调度：工序有依赖，机器有加工能力，运行中还会出现新作业等变化。其观察是完整结构信息可能不如精简观察，工具增强和反思也不稳定胜过强派发规则。这是评估方法上的提醒，不能据此声称 GPU 上的 LLM 调度已经被证明无效。

**Decima 不是自然语言 Agent。** 它学习作业依赖图上的策略；依赖图即“哪些阶段必须等哪些阶段完成”的有向图。其目标和实验对象也不同于 PSRL 固定组所有 rollout 完成时间，所以不能直接套用收益数字。

## 3. 三条最相关路线怎样工作

### 直接在线选动作：Agentic CPU-GPU Scheduling

论文把工具调用表示为带依赖的计算图。分析工具先测 CPU/GPU 时间、加载成本与显存，模型读取这些画像和运行反馈，输出下一轮的设备映射。动作分为 CPU 执行、立即用 GPU、进入 GPU 队列；监测器补充竞争下的实测并探测少量替代方案。[正文 §2–4](https://arxiv.org/html/2607.22242v1)

它报告在 13 个场景中找到穷举最优映射。边界很重要：每场景四个工具，调度模型和工具使用独立 GPU，且最优映射的发现依赖画像或运行反馈。不能从这种小规模结果推导到任意软件命令、无限变化任务或大集群。主文选定映射的工具执行延迟，也不能自动视作包含模型推理、探测和资源消耗的完整服务成本。

**启发是闭环与观测，待验证的是模型的增量。** 必须比较“同样画像与探测给简单成本策略会怎样”。如果收益主要来自探测，而模型只完成数值大小比较，就不应归因于大模型理解能力。

传统调度器通常只看到“请求几张卡、排多久”，并不了解脚本究竟在训练还是反复加载。SchedMate 的 Agent 以目录和启动命令为入口，用列文件、读文件工具提取模型、数据与配置，再结合历史近邻预测运行特征；其他模块读日志跟踪进度、处理故障。其 standalone 调度仍使用预测时长做短作业优先。[正文 §3–4](https://arxiv.org/html/2510.03334v1)

论文报告 Scheduling Advisor 平均分析延迟约 **9 秒**，使用专用 GPU。长训练作业可以摊薄这个成本，短命令则未必。[§5.2](https://arxiv.org/html/2510.03334v1#S5.SS2) 因而我们更适合在代码或配置发生重要变化时分析一次、缓存解释，让每次派发使用快策略。这里的缓存必须绑定版本，不能让旧脚本的解释控制新命令。

论文中的物理集群数量与部分百分比存在文本/表格口径疑点，本文不据这些数字判断优势。早期发表状态见[作者项目页](https://wang-zerui.github.io/publication/schedmate/)，poster 不代表完整版顶会发表。

### 离线生成算法：AlphaEvolve 与 ADRS

<!-- paper-figure:paper-alphaevolve-fig01 -->
这张原图展示另一条路线：模型改进调度程序，线上再执行得到的程序。

[![AlphaEvolve: A coding agent for scientific and algorithmic discovery，图1：生成、评价与程序库反馈环](../../_static/img/literature-reviews/paper-alphaevolve-fig01-screen.png)](../../_static/img/literature-reviews/paper-alphaevolve-fig01.png)

**原图来源：**Alexander Novikov et al.，[原文](https://arxiv.org/abs/2506.13131v1)，图1，PDF第3页，arXiv 2506.13131v1。[CC BY-NC-ND 4.0. Unmodified figure excerpt, format conversion only.](https://creativecommons.org/licenses/by-nc-nd/4.0/)。仅截取图形区域与等比例显示，中文说明置于图外，访问于2026-11-23。

**怎样读这张图。** 上方由人定义目标与评价器，下方Prompt Sampler从程序库和历史反馈构造输入，LLM ensemble生成修改，Evaluators pool运行并打分，结果写回Program database，开始下一轮搜索。反馈环更新的是候选程序集合。

**与本节的联系。** 用于Env时，可以离线搜索并发上限或放置评分函数，经过相同工作量回放验证后再上线。每次派发是否需要调用LLM，是另一个选择，不能把离线程序搜索的收益算成在线推理的收益。
<!-- /paper-figure:paper-alphaevolve-fig01 -->


Google 的 Borg 管理数据中心任务。AlphaEvolve 生成机器评分函数的代码，经过模拟和测试后部署；Borg 先筛选可行机器，新函数负责候选排序。Google 报告该方案平均回收约 **0.7% 全球计算资源**，这是其部署报告的口径，不是“GPU 利用率增加 0.7%”，也不是 PSRL 可直接套用的加速比。[论文 §3.3.1](https://arxiv.org/html/2506.13131v1#S3.SS3.SSS1)、[Google 部署说明](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

线上执行的是生成的普通函数，不是每个任务都请求 Gemini 做推理。这个区别决定了推理延迟是否进入调度关键路径，也说明模型不必替代整个调度器才能有价值。

ADRS 是“用 AI 推动系统研究”的生成—评估—改进方法：模型根据接口、旧算法和评估反馈提出新代码，再由真实系统或模拟器评估。它包括多区域云调度等案例，但仍依赖可信评估器。[报告](https://arxiv.org/abs/2512.14806) 对我们可以借鉴为：限定模型只改候选评分函数，禁止它改任务、评分器和完成标准，用独立轨迹检验结果。

## 4. 用一个完整例子判断模型的价值

以下全是**教学假设，不是 PSRL 或论文实测**。

两个设备都允许执行请求 A。GPU 0 已有 A 所需模型，但前面还有 12 秒任务；GPU 1 空闲，却没有这个模型。A 计算本身为 4 秒，GPU 1 加载模型需 20 秒。为了算得清楚，假设这里的加载不能提前重叠，且归还成本已经计入 4 秒。

| 方案 | 等待 | 重建/加载 | 执行与归还 | 预计反馈时间 |
|---|---:|---:|---:|---:|
| 等 GPU 0 的已有模型 | 12 s | 0 | 4 s | 16 s |
| 立即去 GPU 1 | 0 | 20 s | 4 s | 24 s |

只看空闲卡会选 GPU 1，反而多花 8 秒。但只要这些数字已知，普通代码计算 `等待 + 重建 + 执行` 就能选对，**这个例子本身不证明需要 LLM**。

把背景换成：命令是 `python evaluate.py --candidate v7`，调度器还不知道它会重用已有模型、重载候选代码，还是重新训练。模型可能通过脚本和代码差异解释：“变的是评分函数，模型身份未变，可尝试已有的合法复用路径。”这才是候选语义价值。它仍要由明确依赖、代码版本和实际加载协议核验，不能仅凭模型解释就跳过重建。

如果确实只需 2 秒加载，那么 GPU 1 为 `2 + 4 = 6` 秒，应切换。变化来自任务真实成本，不能在看到模型决策后反过来编造成本。如果语义建议过时，原先 2 秒已经变成 20 秒，执行前应重验，而不是继续相信旧解释。

**模型延迟也要算。** 在必须先等模型返回、分析不能与其他工作重叠的假设下：旧方案需 16 秒，模型推荐的新方案纯执行需 6 秒；若同步咨询花 12 秒，总计 18 秒，反而更慢。若只花 1 秒，总计 7 秒，才有净收益。若能异步预分析，则按真实重叠时间线计时，不能固定把所有时间机械相加。

因此要区分**决策质量**与**决策成本**。提前分析且缓存结果，可以把部分成本移出派发的等待链；代价是缓存可能过期。代码、模型或数据版本变化时重新核验，就是为了确保“提前得到的信息”仍描述“现在要执行的任务”。这与编译器缓存、查询计划缓存的基本取舍相通：复用有价值，但复用条件必须明确。

还有一个易误解处：模型可以读出“脚本没有指定 GPU”，但不能因此把任意 CUDA 命令改到 CPU。只有已支持且结果协议等价的 CPU 路径才是合法候选；改变数值精度、训练步数或随机种子可能改变任务含义，不属于纯调度优化。

## 6. 可以研究什么以及怎样否证

### 更适合作为主候选的问题

**在多轮软件任务持续改变代码的条件下，任务语义能否改善合法执行计划，并带来超过统计预测和简单成本策略的净收益？**

这里的“执行计划”只涉及已允许的准备时机、候选设备、复用路径和排队顺序，不允许改变工作量、评分标准或丢掉必须完成的 rollout。语义输入可以包括启动脚本、代码差异、调用依赖和错误日志；队列、显存和释放状态仍来自系统。

可以比较三条实现路线，第一条最适合低成本起步：

1. **异步提取语义，再做快决策。** 按版本生成阶段和依赖描述，调度时只读结构化结果。收益必须来自新增信息，而非把已有的成本比较换成提示词。
2. **离线搜索简单策略。** 冻结函数接口和评估器，让模型生成评分规则；在线只执行通过检查的代码。研究价值取决于未见负载上的稳定收益、搜索成本和泛化，不是“模型写了函数”。
3. **在线 Agent 做受限规划。** 仅在信息缺失、成本高或负载发生重要变化时调用，超时退回简单策略。只有在模型能改善决策且收益覆盖推理/探测开销时再深入。

**选择模型的依据是信息形态。** 全是数值、稳定队列和已知成本时，简单规则、小型回归器或强化学习策略通常应先试。存在复杂脚本、频繁改动和难以结构化的依赖时，LLM 才有更明确的候选优势；优势仍须实测。

### 必须分开的两个实验问题

| 问题 | 公平比较 | 结论边界 |
|---|---|---|
| 模型是否会更好决策 | 所有策略拿到相同结构化观测、候选与探测预算，比较成本模型、小模型、在线 LLM | 不能让 LLM 独享未来完成时刻或穷举最优答案 |
| 模型能否提供额外信息 | 固定同一个调度算法，分别提供规则解析、统计预测、LLM 语义提取 | 不能把模型猜出的依赖直接当真实依赖；应独立审核 |

进一步做“完整方案”的总成本比较。若语义提取有效，但普通算法已能利用它，应把贡献准确表述成语义观测机制，不强称 LLM 规划更优。

### 有界的最小研究路线

这是**后续提案，本次不执行模型/GPU 实验**。

1. 首轮只做离线研究：从现有记录固定最多 12 条命令，覆盖准备与 GPU 执行混合、热状态可复用、代码修改影响依赖三类。人工审核真实依赖，不能用模型自己的解释给自己打分。
2. 以工程证据确定合法候选，记录决策当时可见状态；按任务/项目分离探索与独立测试记录，不能把同一轨迹稍改名字同时放两边。样本太少时只报告探索发现，不声称泛化。
3. 保留三类强简单对照：现有同机池；亲和加原生缓存/准备前移；基于实测成本的预测放置。策略比较使用相同任务工作量。后续 Env 系统主基线统一为同次冻结实现的静态环境卡池、episode 持卡、满池排队。Command、共享和其他机制单列消融，旧提交结果仅保留历史含义。
4. 预设最多 24 次模型咨询、总计最多 10 万输入输出 token，探索阶段最多 3 个策略候选；独立测试前冻结提示词、模型版本和规则。实际外部调用与 GPU 验证另开任务，不在本文自动启动。
5. 主指标保持固定组全部有效结果返回时间 `T_group = max(C_i) - t0`。其中 `C_i` 是第 i 条轨迹有效反馈返回时刻，`t0` 是组释放时刻。单条命令变快不保证整组变快；不得以丢慢任务、少跑训练步数或改变评分协议获胜。
6. 同时报告推理时延、token/设备成本、探测成本、建议过期率、非法建议率与回退率；核算真实重叠，不把缺失观测补为零。先做只给建议、不影响执行的“影子模式”，再决定是否值得接线。
7. 停止条件：简单策略已选同样动作；性能收益被推理开销抵消；新信息无法核验；优势只出现在训练轨迹而非独立测试。证据不足时保持“未证明”，不继续堆 Agent 或扩大 GPU 实验来追收益。

这与[训推借卡提案](../research-proposals/06-训推借卡_可撤回执行与反馈依赖.md)的关系是：模型可以帮助解释任务或选择已审核策略，但不能替代借卡协议、显存预算、时长未知时的撤回机制与物理释放。与[KREX 精读](03-论文精读_KREX共享GPU测量保护.md)的关系是：性能反馈必须可比，否则离线搜索可能只是在选择测量噪声中的偶然赢家。

python3 docs/env-worker-deep-dive/env-service-verification/scripts/agent_scheduler_brain_demo.py
