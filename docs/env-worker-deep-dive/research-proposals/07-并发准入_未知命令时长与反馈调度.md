# 并发准入：未知命令时长与反馈调度

> **核心结论**：公共研究问题是：当多个 Agent 不断提交时长未知、资源需求不同的 GPU 工作时，怎样根据实际争用与反馈依赖，联合决定准入并发和设备放置，使固定工作量更早完成，同时保持结果与性能测量有效？预测剩余时间和合作式暂停是可选能力。本文保留整任务池化的固定旧 runner 对照：只让 2/6 个任务更早返回，整批反而慢 35.22%。共同场景探索已定位到重复准备成本，[依赖复用实验](08-运行准备_重复准备成本与GPU就绪调度.md)在缓存已准备好的条件下使六类代表任务均更快，尚未确立新的通用 GPU 排程算法。
>
> 核对范围：2026-11-16，主目录 `c5f2d65` 加工作区内容。历史共享、预测与反馈报告保留各自版本。本页的试验调用固定 `0eeead861ffafed6bf31c962d259fd847775dcf9` runner，使用已有独立工作树及明确记录的运行兼容补丁。没有改共享服务或生产调度器。

## 共同问题和真实边界

Agent 在接收一次反馈后才决定下一步，它的完整计算序列事先未知。命令可能编译算子、训练模型、评估候选，或者启动推理服务。单个 GPU 能看到很多进程，却不知道它们是否正在争用同一种资源、哪些结果会解锁下一步工作。静态绑定可能留下空闲卡，无条件并行可能互相拖慢，无条件串行又会失去有益重叠。

准入指决定一个已提交工作何时允许开始。并发度指同一时刻允许运行的工作数量。放置指选择执行设备。把它们放在统一控制面，并不要求所有任务使用相同并发度，也不表示可以随时迁移活进程。

本题首先优化在既定资源上的任务完成时间。GPU 利用率只能辅助判断，100% 利用率可能对应大量低效争用。有效吞吐是单位时间内完成且通过正确性检查的工作量，不能把失败重跑也算成产出。任务质量与耗时分别报告，不为更快而减少训练更新、候选、评分样本或输出长度。

## 已有机制怎样组成统一控制面

下面是建议结构。试验只实现入口的两个简单准入对照，图中自适应与反馈优先级尚未落地。

```text
[A] 多条 Agent 轨迹提交实际 GPU 工作
       ↓ 已知本次资源需求、版本和结果接收者
[B] 统一待执行队列与完成反馈依赖
       ↓ 候选策略：等待年龄、已获服务量、公平性
[C] 容量安全检查 + 并发控制 + 设备放置
       ├ 普通计算：在容量合格设备上允许有益重叠
       ├ 需要独占性能测量：使用声明的保护协议
       └ 无可验证执行边界：保留整命令或整会话粒度
[D] Docker / EnvWorker 执行实际工作
       ↓ 完成、错误、实际时间、占用和版本
[E] 返回反馈，核对物理释放 → 更新队列和并发策略
```

图例：图中各部分对应源码与实现状态。

| 节点 | 本地对应 | 状态 |
|---|---|---|
| A、B | [pilot.run](../env-service-verification/scripts/admission_study/pilot.py#L50)读取六任务清单 | 试验是同时提交参考解任务，不生成自然 Agent 轨迹 |
| C 试验准入 | [execute](../env-service-verification/scripts/admission_study/pilot.py#L127)选择静态分配或空闲槽位队列 | 本文比较两个准入策略，脚本另支持不改准入的本地依赖对照 |
| C 生产容量 | [command_gpu.py](../../../psrl/workers/env_service/command_gpu.py) | 既有生产准入机制，本试验没有把新策略接进去 |
| D | [固定 runner 装载器](../env-service-verification/scripts/warm_router_study/baseline.py#L119) | 校验固定提交和实际导入，调用该版本 `run_harbor_episode` |
| E | [pilot 的 finally](../env-service-verification/scripts/admission_study/pilot.py#L168) | 保存完成与评分，检查所属容器和整卡物理释放 |
| C 自适应与 B 反馈依赖 | 尚无对应生产算法 | 本文设计提案，不能把简单队列试验当作该算法验证 |

## 算法假设与一个手算例子

建议研究的最小算法只在提交和完成边界决策，不自动打断任意 shell：

1. 先排除显存、主存、CPU 或测量协议不满足的设备。显存需要包含常驻模型和计算临时空间，不能只统计容器数。
2. 在可执行集合中使用公共队列。等待太久的工作优先，其他工作按其会话已经消耗的实际 GPU 时间排序，避免单个会话一直占先。已消耗量是历史观测，不是未来时长预测。
3. 根据同类工作在不同并发下的实际有效完成率调整允许的并发度。每次只试一个相邻档位，保留不探索的对照窗口，计入探索成本。没有可比较样本时保持静态安全配置，不把未知进度当作零。
4. 有独立进度报告的程序可以更快发现争用，但不是所有程序必需。没有报告且仍在运行的命令属于未完成样本，不能因为“尚无完成”就判定它慢，也不能从只先完成的短任务推断全部工作都变快。
5. 常驻服务与工具共享使用独立资源优先原则。只有容量和性能边界允许才共享推理 GPU。已有共享收益不支持无条件暂停，是否限制新工具进入需要真实干扰证据。

这仍是算法假设。尤其第三步存在严重因果识别问题：后一个窗口可能恰好来了更轻的任务，完成率提高不一定是并发策略更好。需要按实际代码、输入、设备条件分组，或者用相同轨迹回放做配对验证。Agent 持续改代码会降低可比较样本数量，这个困难并未被“在线学习”一词解决。

**教学假设**：两项工作独占时各需 10 秒。并发后，如果各自还能保持独占时 80% 的速度，两项约 12.5 秒都完成，比串行 20 秒更快。如果互相争用后各自只剩 30% 的速度，并发约需 33.3 秒，串行反而更快。算法不一定要知道每项剩余几秒，但必须收集足以区分这两种运行条件的证据。

本地 [demo.py](../env-service-verification/scripts/admission_study/demo.py)是标准库教学计算。本次实际运行得到 20 / 12.5 和 20 / 33.33 两组成本，断言通过，数字是人为设定，不能称为 GPU 性能结果。

## 为什么不能保证所有任务加速

统一调度框架可以覆盖多类工作，但收益来自条件，不来自 benchmark 名字。只有一项工作且资源充足时，调度无法让原有内核凭空变快。工作已经平衡且没有争用时，控制开销可能反而增加完成时间。未知时长、不可抢占、在线到达的系统，也不可能总在决策时知道后续最优选择。

| 类型 | 可共同优化的部分 | 仍需保留的区别 |
|---|---|---|
| PostTrain / MLGym / autoresearch | 准入、队列、计算与加载争用 | 常驻状态、训练预算和可重建性不同 |
| KernelBench / FlashInfer / FastKernels | 编译准备与执行准入、避免资源竞争 | 测速要保持明确设备和干扰条件 |
| InferenceBench / SWE-Serve | 常驻显存、启动并发、服务测试 | 服务代码版本和评分计时范围不能改变 |
| MLE / AIRS | 训练任务准入与 CPU/GPU 阶段 | CSV 评分常不需要 GPU，AIRS 还有独立接入路径 |
| RE-Bench | 多种已提交 GPU 工作的公共排队 | 生成、裁判等待、固定计算并非同一执行契约 |

因此合理目标是，在预先选定的多类任务和并发压力组合上，相对固定旧基线有较高获益覆盖率，在无压力条件下退化可控。少数代表题的结果不能称为全题库覆盖。建议后续把“较好”预注册为整批时间减少至少 10%，至少 80% 的代表场景达到该门槛，且没有场景恶化超过 5%。这些是待检验的验收门槛，不是当前实测。

## 与已有研究的区别和重叠

2026-11-16 查阅以下原始论文页面。这里是定向近邻核查，不能保证穷尽所有研究。

| 工作 | 已覆盖的内容 | 对本课题的约束 |
|---|---|---|
| [Tiresias，NSDI 2019](https://www.usenix.org/conference/nsdi19/presentation/gu) | 未知训练时长下，用已获服务信息进行调度与放置 | 不预测时长、按已获服务量排序都不是新的贡献 |
| [Gandiva，OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/xiao) | 利用重复迭代特性做时间共享、运行观察与迁移，关注多作业反馈 | 迭代安全点和反馈更快已有直接先例 |
| [MARS，2026 年 11 月 v3](https://arxiv.org/abs/2604.26963v3) | 内存受限的 Agent 推理中，联合工作流准入与引擎调度，减少 KV 缓存反复淘汰 | 工作流准入、反馈依赖和缓存压力本身也已有近邻。KV 是推理中缓存的注意力键和值 |
| [Agentic CPU-GPU Scheduling，2026](https://arxiv.org/abs/2607.22242v1) | 对异构工具考虑立即 GPU、GPU 排队与 CPU 执行，使用运行反馈处理争用 | “工具异构性 + 运行监测”不足以构成创新，而且本地一些 GPU 题不允许改成 CPU 协议 |

可能剩余的研究差异是：未知且不断变化的 GPU 工具程序、性能反馈有效性要求，以及工具结果与下一轮 Agent 推理之间的在线依赖，怎样共同决定并发和资源份额。要成立，需要实验证明这三者的耦合带来简单池化、固定并发和已有公平策略解决不了的损失。目前没有这样的完整证据。

## 小实验协议和结果

小实验先比较两个简单端点，用于判断是否有必要继续自适应并发研究：

- static：固定旧 runner，六项任务同时提交，按清单轮流静态绑定到两张 GPU，每卡三项。旧有进程内并发上限为八，不添加整卡锁。
- pool：同一个固定旧 runner，在外部维护公共 FIFO 队列，每张卡同时一个完整任务，空闲卡取下一项。FIFO 是按到达先后执行。本策略不用时长预测，也没有新生产 Router。

这两组同时改变准入上限和可放置设备，因此即使有收益，也不能把原因单独归于动态选卡。后续必须加入“静态绑定但每卡一个”和“池化但允许原有并发”的消融对照，才可区分原因。消融就是每次只去掉一种机制观察差别。

使用六个已准备的参考任务：KernelBench、FlashInfer、PostTrain GSM8K 1.7B、MLGym MNLI、本地 MLE、RE restricted MLM。全部执行原有 oracle 参考解与独立 verifier，不接模型生成，不修改计算或评分。两张同型号独立 GPU，策略顺序为 static / pool / pool / static。每个任务记录从共同提交到返回的时间，队列等待计入，整批计到全部任务结束，容器初始化和 runner 清理包含在内。资产准备在计时前，不使用故意睡眠或人工显存占位。

预算为一次 1200 秒完整矩阵，另留物理清理时间。首次启动发现旧 runner 的 GPU override 被当前 Harbor 独立 verifier 清空，五项 GPU 评分失败，本地 MLE 的 CPU 评分成功。源码定位到 Harbor 的 `_separate_verifier_env` 主动移除 `extra_docker_compose`。这是设备传递问题，不能作为基线调度劣势。保留首轮失败，实验任务副本为两个策略一致补入 verifier 设备与驱动库映射，原 benchmark 和共享依赖保持原样。

本次六类各一个参考任务，不能代表全部题库。没有测 AIRS、InferenceBench、SWE-Serve、FastKernels 和 autoresearch，原因是本次限定小矩阵，而不是这些类别已被证明无收益。当前题库覆盖数量与上游完整协议仍查[任务路线图](../milestones/02-Science现状_任务覆盖与接入路线.md)。

验收成功表示原评分流程有效完成。KernelBench 记录性能但本地奖励取正确性，不能据此声称并发时获得了独占性能真值。RE 的独立评分有随机采样，观察到小幅分数变化，因此不声称六类分数全部逐位相同。所有策略仍执行相同输入资产、训练更新数与评价协议。评分随机性的完整控制是后续严格对照的缺口。

**结果：预定 4 个区块、24 次完整任务执行全部完成，原评分协议有效，未得到普遍加速。** 顺序为 static 180.48 秒、pool 246.90 秒、pool 240.16 秒、static 179.73 秒。两次 static 平均 180.10 秒，pool 平均 243.53 秒，整批慢 **35.22%**。正式矩阵耗时 847.95 秒，低于预设 1200 秒预算。相比旧静态分配，每类任务的返回时间如下。

| 代表任务 | 旧静态分配均值 / 秒 | 简单池化均值 / 秒 | 从共同提交到完成的变化 |
|---|---:|---:|---|
| kernel | 75.87 | 55.07 | 减少 27.42% |
| posttrain | 180.05 | 133.13 | 减少 26.06% |
| flashinfer | 84.89 | 116.42 | 增加 37.14% |
| mlgym | 175.94 | 243.48 | 增加 38.39% |
| mle | 59.24 | 182.21 | 增加 207.59% |
| re | 71.32 | 241.99 | 增加 239.32% |

两个获益任务在两次配对中都更早完成，其余四类在两次配对中都更晚。这里的 2/6 是六个固定参考任务，不是按题库全部任务统计的收益覆盖率。先执行的任务受并发限制后自身更快，后执行的任务多等了前面的任务。以第一轮 MLE 为例，池化排队约 134.6 秒，自身执行约 51.9 秒，合计约 186.4 秒，旧基线约 63.4 秒就返回。忽略入队等待就会把这个明显退化误写成执行加速。

当前按完整 episode 限并发，还把导入、容器准备和 CPU 工作一并排队。现场曾观察到任务容器在运行而两张卡 GPU 利用率为零，因此整任务数不能充当实际 GPU 压力的精确代理。本次没有完整分阶段遥测，不能把差异全部归因于 GPU 计算竞争。静态映射按固定清单轮转，不声称它是最优静态放置，也没有故意限制旧基线为整卡串行。

RE 评分器的随机采样导致 loss 与 reward 有小幅变化，其他五类的任务 reward 在四次运行中一致。这里支持相同任务协议完成，不支持所有权重或模型输出逐位一致。没有重新选择样本、调短任务或重跑到出现优势。

[公开结果摘要](../experiments/gpu-benchmarks/common-admission-evidence.json)保留逐区块、逐任务、评分、排队及执行时间、固定源码与原始证据 SHA256。SHA256 是按文件字节计算的摘要，可用于核对证据是否变动。完整工作区日志还保留首次设备传递失败及 baseline 补丁。收尾现场查询没有运行中的容器或 GPU 计算进程，两张实验卡只剩约 3 MiB 驱动占用，没有以账本归零代替物理检查。

**研究决策**：停止把“公共队列 + 每卡一个完整任务”作为通用加速算法，该策略的 24 次对照保留原结果。共同场景探索转向准备、计算与评分的真实阶段数据。[运行依赖与就绪报告](08-运行准备_重复准备成本与GPU就绪调度.md)已完成另一项预先固定的 36 次对照：保持旧并发，仅改变依赖读取位置，六类均获益。该结果不推翻本文的池化负结果，也不证明自适应并发或就绪准入已经实现。


## 跟着源码复现与后续门槛

先按[集群预检](../../psrl/psrl-run-guide/02-集群预检_依赖地址与GPU资源核验.md)检查独立空闲卡、Docker 和容器 CUDA。实际已在目标节点运行容器 CUDA 加法，结果为 8.0，确认 CUDA 可执行，不仅是设备可见。本试验直接调用旧 runner，不启动 Ray 集群，也不加入共享 Ray。

源码阅读顺序是 `run` 固定版本与检查设备 → 建立同协议任务副本 → `execute` 排队或静态提交 → 原 `run_harbor_episode` 执行 → `finally` 记录结果和容器 → 区块边界核验 GPU 物理释放。不同任务以协程并行等待 Docker 操作。协程是在等待期间让其他任务继续执行的函数，不表示 GPU 内核一定同时运行。代码若有疑问，可以沿这个顺序追问。
