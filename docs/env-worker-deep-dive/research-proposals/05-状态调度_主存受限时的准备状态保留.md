# 状态调度：主存受限时的准备状态保留

> **核心结论**：这个受控原型研究 CPU 主存中的准备状态缓存：两份转换后模型权重共约 3.91 GiB，3 GiB 缓存池装不下两份，5 GiB 装得下。调度器决定先准备谁、保留谁、淘汰谁，目标是少做重复转换，并让每个会话及时拿到本轮全部结果。

例子中的 A、B、C、D 是四份独立工作目录，各经历三次“修改代码，再运行两项检查”，合计 24 条 GPU 检查命令。它们共用一个程序、一张 GPU 和一份 CPU 缓存。**3/5 GiB 约束的是主存缓存，GPU 执行另行检查显存容量。** 修改与到达顺序由脚本安排。

真实 GPU 原型已运行，复杂策略相对合理强对照的稳定收益仍不足。[真实任务核查](04-状态复用_真实任务中的收益空间核查.md)进一步发现，SWE 参考补丁和训练候选通常会修改运行时或权重，因此本文保留为受控机制证据；后续选题先验证真实场景是否满足复用条件。

2026-11-13 重新核对会话生成、代码变更、缓存与执行路径，并运行 CPU 教学脚本；GPU 数据仍使用 11-12 的固定记录。生产 EnvRouter 的通用跨命令版本管理尚待实现。

## 旧代码问题修到了哪里

需要区分三种结论。

| 问题 | 已有证据 | 能否概括为框架已修复 |
|---|---|---|
| 基线每条命令是否清空环境 | 固定基线已有容器、文件及任务自行保持的进程延续 | 不能说基线没有状态保留 |
| 改了磁盘代码，旧 Python 服务会不会自动变 | 不会自动变。常驻进程可能继续执行已导入的旧函数 | 是应用的条件性风险，不能说所有基线任务必然出错 |
| 本原型能否固定执行版本并拒绝过期交付 | 对完整声明的依赖、遵守同一编辑锁的写入者，故障注入与真实模型交付检查通过 | 只覆盖这个适配器，尚未接入生产 Env |

一个具体例子：旧服务已导入 `OFFSET=0`。Agent 将磁盘文件改成 `OFFSET=10`，这个服务不重启也不重新读取代码，仍可能返回旧偏移的结果。基线若每次启动新 Python，本来就会读到 10。基线若把固定模型留在服务里，而把打分代码放到每次新建的小进程中，也能保持正确。

原型采用后一种拆分，并补上快照与交付检查。任务请求版本 V1，实际执行也必须是 V1。若结果返回前已经切到 V2，而调用方要求当前版本结果，交付会被拒绝。拒绝不是把旧结果神奇地改成新结果，需要调用方重新提交当前版本。

[固定基线专题](../knowledge/02-资源与调度/07-状态复用_基线状态寿命与版本正确性.md#results真实固定基线与强对照)记录了历史真实 EnvWorker 对照：人工拆分为 22.326 秒，版本管理原型为 22.374 秒，基本持平。盲目复用服务的 5/8 错误是特意构造的错误复用对照，**不是直接运行原始基线就必然发生 5/8 错误**。不能把已有正确基线说成错误，再以此制造性能贡献。

本次又运行了 [10 项标准库交付回归](../env-service-verification/results/memory-state-20261112/publication-regression.json)。它覆盖代码错配、模型身份错配、过期结果、显式历史版本及编辑与交付竞争，但不验证任意未声明文件、恶意写入、自动依赖发现、崩溃恢复或通用 Python 热更新。

## 场景与真正受限的资源

切入点是**多个代码修改会话反复运行 GPU 正确性检查，而 CPU 缓存无法同时保留全部转换后权重**。是否通过只看数值和代码版本是否正确，运行速度是系统研究指标，不进入任务分数。

**“四个会话”实际建立了什么。** 在一个实验容器里，程序创建 `session-0` 到 `session-3` 四个目录。为便于阅读，下文叫 A、B、C、D。每个目录有自己的 `helper.py`、`scorer.py`、`loader.json`，并记录当前代码版本及检查是否完成。它们可以保存不同代码，但使用相同的两份固定模型权重，CPU 转换缓存也共用。例如 A 用过的一份转换后语言模型权重，之后 B 也可以用，不需要因为目录不同就再复制一份。

**“每个三轮”是三次修改代码后检查，不是三个训练 step。** 以 A 为例，脚本安排如下。`x` 是某次模型计算得到的数值，表中的公式确实对应脚本写入的打分代码。

| A 的轮次 | 脚本写入的打分规则 | 随后发生的事 |
|---|---|---|
| 第 1 轮 | `结果 = x` | 固定这一版代码，提交本轮两项 GPU 检查 |
| 第 2 轮 | `结果 = 1.1*x + 1` | 等 A 的第 1 轮两项都完成，再经过预设等待，修改代码并提交两项检查 |
| 第 3 轮 | `结果 = 1.2*x + 2` | 等 A 的第 2 轮两项都完成，再修改代码并提交最后两项检查 |

B、C、D 按同样方式走三轮，只是偏移数分别再加 10、20、30。这些编辑用于检验“权重可以复用，但结果必须使用该会话当前的代码”，不是在训练或更新模型参数。**教学数值**：假设一次模型输出 `x=2`，A 的三版打分应分别给出 2、3.2、4.4。这不是实验测得的模型输出。

**“每轮两条检查”具体计算什么。** 在 mixed 场景，每轮提交下面两项，提交顺序由固定随机种子安排。

| 检查 | 固定使用的模型 | 一条检查真正做的工作 |
|---|---|---|
| 语言模型检查，下文简称 L | Qwen3-0.6B | 在 GPU 上装入模型，给定 8 个词元编号，运行一次前向计算，将指定输出相加成一个数，与独立参考值比较 |
| 分类模型检查，下文简称 C | Qwen3-Reranker-0.6B-seq-cls | 换用分类模型，完成同样长度的固定输入计算及独立数值核对 |

词元编号是模型接收的整数输入。本原型使用 `100..107` 或 `101..108`，不是让 Agent 回答一道自然语言题。每次检查随后还把输出交给该会话本轮的打分代码，核对公式和代码版本。这里的“两条”是两个短数值探针，不是运行两遍原始 benchmark 完整评分，也不是两个持续驻留的 GPU 服务。文中“一条命令”对应原型中的一个检查请求和一次 `runtime.execute` 调用，不代表通过生产 EnvRouter 发起一次 Docker 命令。

这样就能把数量直接列出来。

| 会话，即一份工作目录 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 总检查数 |
|---|---|---|---|---|
| A | 语言与分类 | 语言与分类 | 语言与分类 | 6 |
| B | 语言与分类 | 语言与分类 | 语言与分类 | 6 |
| C | 语言与分类 | 语言与分类 | 语言与分类 | 6 |
| D | 语言与分类 | 语言与分类 | 语言与分类 | 6 |
| 合计 | 8 项 | 8 项 | 8 项 | 24 |

表格按轮次计数，不表示四个会话必须同步推进。开始只提交 A1、B1、C1、D1 各两项，共 8 项。如果 A1 两项先完成，A 就能在预设等待后提交 A2，此时 C 或 D 完全可能还没完成第 1 轮。A1 只完成一项时，A2 不能提交。这种“同一个会话要等本轮两项都回来”的规则，在后文称为**反馈屏障**。不同会话之间没有这个屏障，GPU 上的检查仍是一条接一条执行。

四个、三轮、两项是为有界机制实验手动选的规模，没有声称是 benchmark 的原生规模或真实 Agent 轨迹分布。四个工作目录让调度器同时有多个等待者可选，三轮让复用跨越多次代码修改，两项让“一轮何时完全收到反馈”与“单项何时完成”产生区别。实验不需要固定恰好这三个数字才能研究该问题。

**3 GiB 和 5 GiB 到底限制哪里。** 从模型文件到本次检查，数据分成以下几层，不能把它们都叫显存。

```text
磁盘上的原始模型文件
    ↓ 公共初始化读取，保留原始表示的 CPU 权重
CPU 主存里的原始权重                    不计入这项缓存配额
    ↓ 可选：先把权重数字转换成目标精度
CPU 主存里的转换后权重缓存              ← 3 GiB / 5 GiB 限制这里
    ↓ 当前检查把权重装入 GPU 模型
GPU 显存中的本次模型，执行一次计算       不是 3 GiB / 5 GiB 限制的对象
    ↓ 删除本次 GPU 模型
后续命令仍可使用保留在 CPU 主存里的转换后权重
```

图例：原始权重由 [ModelRuntime.__init__](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L48) 保留。CPU 转换由 [prepare](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L91) 完成。检查预算的是 [run_block](../env-service-verification/scripts/state_reuse_study/memory_study.py#L74)，它核对实际保留的转换张量。装入 GPU、运行和释放本次模型都在 [execute](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L113)。这些源码如果有理解上的问题，可以继续按数据移动方向追问。

“转换精度”是改变权重中数字的存储格式。本试验把 L 从 BF16 转成 FP32，把 C 从 FP32 转成 BF16。BF16 每个数占 2 字节，FP32 每个数占 4 字节。转换需要 CPU 时间，并会得到一份需要占用主存的权重。保存这份转换后的结果，下次可以省掉重复转换，**不会省掉本次 GPU 计算，也没有缓存模型答案**。两种转换方向是研究配置，不代表原始 SGLang 任务默认这样运行。

两份真实转换张量大小见 Results。这里先用它们解释容量选择。

| 缓存对象或配额 | 大小 | 对调度有什么影响 |
|---|---|---|
| L 的转换后 CPU 权重 | 约 2.80 GiB | 可被四个工作目录后续的 L 检查共用 |
| C 的转换后 CPU 权重 | 约 1.11 GiB | 可被四个工作目录后续的 C 检查共用 |
| 同时保留 L 与 C | 约 3.91 GiB | 不是四个会话分别各存 3.91 GiB |
| CPU 缓存上限 3 GiB | `3.91 > 3` | 两份单独都放得下，但不能同时保留，需要决定保留哪份或本次不建缓存 |
| CPU 缓存上限 5 GiB | `3.91 < 5` | 两份都可保留，作为“不需要因容量不足来回淘汰”的对照 |

因此选 3 和 5，是为了分别落在 3.91 的两侧，不是 GPU 恰好有这两种显存大小，也不是不同会话分配不同额度。两组使用同一张 GPU，没有改成 3 GiB 卡或 5 GiB 卡。GiB 是二进制容量单位，1 GiB 为 `1024**3` 字节，这里不将其与十进制 GB 混写。

用一个具体顺序看影响：准备好 L 后执行 C，再执行 L。在 3 GiB 配额下，如果每次缺少缓存都强行建立新缓存，就会“删 L、建 C、删 C、重建 L”。在 5 GiB 下，建好 L 后还能加入 C，最后一次 L 直接使用保留的权重。另一种 3 GiB 下可选的做法是 C 本次从原始权重直接装入 GPU，不建立 C 缓存，保住 L。这里要比较的就是这些选择的真实总成本。缺少所需转换缓存叫 miss，已经保留叫 hit，后文的“亲和调度”则是优先执行能使用现有缓存的检查。

容器的硬主存上限另为 16 GiB，包含原始权重、Python、框架和临时分配等。3/5 GiB 只是其中由实验管理的一部分，不是整个程序总主存上限。因此本实验没有把宿主机物理内存耗尽，也没有注入内存耗尽错误，不能把结果说成解决了真实宿主机 OOM。

**两类场景为什么不同。** mixed 每轮一项 L、一项 C，更容易出现两个模型来回切换。bursty 则让同一轮两项都使用 L 或都使用 C，不同会话形成一批同类检查，观察简单地“优先跑当前权重适用的命令”是否已经足够。两类场景都保持 4×3×2=24 项，不通过少做检查得到速度优势。

**与原始任务和生产框架的距离。** 模型资产来自已接入的 SWE-Serve 题 `ss-sgl22544-score-multi-item-delimiters`，原题包含语言模型和序列分类模型的 score 检查。本原型只借用两种模型构造短数值检查，没有运行原题完整 test.sh，更没有运行 science 训练。原题测试自身已有类级引擎复用，不能把这部分算成新收益。原始完整评分的历史记录也不能代替本次原型的验收。

所有命令都在同一张现场空闲的私有 GPU 上串行执行，不干扰 vLLM，不共享计算单元，不进行跨卡或跨节点放置。每次释放的是本条检查创建的 GPU 模型，公共 CUDA 运行时仍可占用显存，不能推导每条结束时整卡显存读数归零。每条命令重新建立 GPU 模型，是本机制试验的生命周期约束。若真实任务允许把全部模型长期留在 GPU 上，且显存充足，就应把这种常驻方式列为更强对照。本次没有验证真实 GPU 交接压力。

可直接运行[逐项讲解脚本](../env-service-verification/scripts/state_reuse_study/memory_walkthrough.py)，观察第一轮先提交 8 项、A 只完成一项时不能进入下一轮、A 可以在 C/D 第一轮尚未结束时进入第二轮，以及 3/5 GiB 缓存的不同结果。

```bash

```

脚本调用真实的 `workload`、`Arrivals.issue`、`Arrivals.finish`，但用每项 1 秒的虚拟时间代替 GPU 执行，只对缓存字节数做算术，不实际分配几 GiB 主存。它不启动模型、Docker 或 GPU，也不执行快照打分，不能拿它输出的时间当性能结果。本次已实际运行：A 在虚拟第 5 秒提交第 2 轮时，C/D 仍有第 1 轮检查未完成，最终共完成 12 轮、24 项。顺序 L、C、L 在 3 GiB 配额下建立三次缓存，在 5 GiB 配额下建立两次。这里的三次与两次只是这个教学顺序的转换次数，不是重新测得的 GPU 性能。

## 主存为什么不能直接相加 RSS

<!-- chapter-figure:chapter-warm-layers -->
主存放不下之前，先分清要留下的准备究竟在哪一层。

[![主存放不下之前，先分清要留下的准备究竟在哪一层](../../_static/img/document-figures/chapter-warm-layers-screen.png)](../../_static/img/document-figures/chapter-warm-layers.png)

GPU模型、CPU权重和就绪容器的容量与重建成本不同。下面的受限主存算例有自己的池容量，不能把几种内存混在一起。 [放大查看 SVG](../../_static/img/document-figures/chapter-warm-layers.svg)。
<!-- /chapter-figure:chapter-warm-layers -->


RSS 是进程当前映射且驻留在主存里的页面总量。它可能包括共享库、只读模型文件映射、私有张量和分配器尚未归还的空间。两个进程映射同一批文件页面时，各自 RSS 都可能计入这些页面，简单相加会重复计算。

**教学假设。** 两个进程分别映射同一份 2 GiB 只读权重，又各有 1 GiB 私有工作区。每个 RSS 可以接近 3 GiB，相加得到 6 GiB，但唯一物理页面约为 2+1+1=4 GiB。文件页面还可能由操作系统回收，不能把它与不可回收的私有张量一律视为同样压力。

PSS 是按共享者数量分摊页面后的统计，可以辅助理解物理占用。Private Dirty 表示该进程私有、已修改的页面，常用于观察转换后的匿名张量。它们仍不是本实验状态池的精确计费器，因为 Python、框架分配器和临时对象也会改变这些数值。

本原型采取两层观察。

1. 状态池按**实际转换张量的唯一缓冲区字节数**计费。若两个参数共享同一张量，不能重复转换或重复收费。代码用底层地址、偏移、形状和步长识别本适配器中的绑定别名。
2. 同时读取 `/proc/self/smaps_rollup`，保存 RSS、PSS、Private Dirty 等指标。淘汰后删除张量引用，运行垃圾收集，再请求普通 CPU 分配器归还空闲页。张量预算归零不自动等于所有进程页面立即归还。

实现见 [tensor_key](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L40)、[memory](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L23) 与 [trim](../env-service-verification/scripts/state_reuse_study/memory_runtime.py#L34)。这一缓冲区识别适用于被测权重，尚未实现任意重叠张量视图的通用区间去重。

[![先画清输入与状态的对应关系，再讨论内存不够时淘汰谁](../../_static/img/document-figures/chapter-state-dependencies-screen.png)](../../_static/img/document-figures/chapter-state-dependencies.png)

可复用状态必须仍对应本轮模型、数据与代码；按依赖失效能避免“为了省准备，继续用旧状态”的错误。 [放大查看 SVG](../../_static/img/document-figures/chapter-state-dependencies.svg)。
<!-- /chapter-figure:chapter-state-dependencies -->


本实验同时存在三类不同寿命的对象。

| 对象 | 什么变化会使它不能直接复用 | 本原型的寿命 |
|---|---|---|
| 只读原生权重映射 | checkpoint 或加载方式改变 | 公共运行时持续保留，所有对照都有 |
| 转换后的 CPU 权重 | checkpoint、精度或影响张量表示的依赖改变，或内存淘汰 | 可跨多个命令与打分代码编辑保留 |
| 打分函数及其导入模块 | `helper.py`、`scorer.py` 等声明依赖改变 | 每条命令用新进程加载固定快照 |

例如会话 C 的第 1 轮把模型输出变成 `输出×1.0+20`，第 2 轮改成 `输出×1.1+21`。这次编辑没有改变权重或精度，因此 CPU 转换状态仍可用，但两轮必须执行不同打分代码。实验对每条结果分别核对模型数值、变换公式、代码快照身份和发布代次。源码内部的会话及轮次编号从 0 开始，正文为了阅读方便从第 1 轮讲起。

这一安全性依赖**显式边界**：候选修改只涉及轻量打分文件，固定模型运行时代码没有改变。若候选修改模型实现、注意力算子、权重加载器或未声明配置，本适配器并没有自动找出所有影响，也不能默认继续复用。尤其不能仅凭模型文件没变，就认定整个旧 GPU 引擎仍有效。

本次 504 条完整命令的审计说明这条边界内的数值与版本一致，不等于已经完成任意 Agent 程序的状态有效性管理。原型的模型依赖清单由控制器固定，尚未验证动态更换模型、动态精度和任意框架扩展。完整依赖声明与共同编辑锁仍是[状态协议](../knowledge/02-资源与调度/07-状态复用_基线状态寿命与版本正确性.md#状态版本契约与受控验证)的必要条件。

## 调度器具体决定什么

最重要的选择不只是谁先运行，还包括**这次是否值得建立缓存**。

| 策略名 | 命令顺序 | 状态选择 |
|---|---|---|
| direct | 先到先执行 | 原生权重直接装入新 GPU 模型，不建立转换状态 |
| stage | 先到先执行 | 每条命令转换、使用、立即丢弃，隔离“转换路径”本身的效果 |
| lru | 先到先执行 | 缺失就准备，预算不足淘汰最近最少使用状态 |
| gdsf | 先到先执行 | 依据历史频率、准备成本和大小计算保留优先级 |
| affinity | 优先当前缓存命中命令 | 用普通 LRU 保留状态 |
| critical | 优先完成当前剩余检查条数最少的一轮 | 用 gdsf 式保留 |
| locality-dp | 联合搜索当前命令顺序与状态动作 | 最小化当前有限窗口内总执行时间 |
| feedback-dp | 相同动作和搜索窗口 | 最小化当前各轮反馈完成时间之和 |

FIFO 是先到先执行。LRU 是优先淘汰最久没用的对象。gdsf 借鉴 [FaasCache 的 Greedy-Dual-Size-Frequency](https://afuerst.github.io/assets/FaasCache.pdf)，使用逻辑时钟加“频率×准备成本/大小”。它是本研究的适配控制，频率生命周期等细节不同，不能称为逐项复现原论文。

这里只有两份状态，3 GiB 只能存一份，因此缓存 miss 时往往没有“淘汰谁”的多选空间。LRU 与 gdsf 很多时候动作等价，不能拿它们的时间差证明某种淘汰算法更优。`critical` 只数剩余条数，尚不是考虑真实剩余耗时的最强短作业优先策略。实验中的八个名称也不等于八种在所有场景都不同的行为。

两个 dp 策略采用**动态规划**：把大问题拆成“剩下哪些当前命令、当前保留哪些状态”的子问题，记住子问题答案，避免重复枚举。最多看四轮，每轮最多两条未完成检查，总计八条。正式动作只有三种。

1. `direct`：用原生权重直接执行，保留原有转换缓存。一次 miss 不必挤掉仍有价值的旧状态。
2. `reuse`：命中时使用当前转换状态。
3. `prepare`：先淘汰必要状态，再做真实精度转换，执行并保留新状态。转换不超前于当前命令，也没有 CPU/GPU 重叠。

令 `R` 是当前窗口中的剩余命令，`S` 是已保留的状态集合，`d` 是动作预测耗时。递推式为：

```text
V(R, S) = min[ w(R) × d(命令, 动作, S) + V(R 去掉该命令, 执行后的状态集合) ]
```

`locality-dp` 的权重 `w=1`，因此减少总工作时间。`feedback-dp` 的权重是尚未完成的轮数。假设三轮都在等结果，某动作多耗 1 秒，就让三轮各多等 1 秒，累计代价是 3 秒。一轮完成后，后续每秒只影响剩下两轮。这正对应各轮完成时间之和，不是凭空设计的命中率奖励。

这只是**当前可见窗口的短视优化器**。它不知道下轮代码、下一轮何时到达或总轮数，不会读取脚本中的未来思考时长。也没有保证整个多轮任务的全局最优。非 FIFO 策略共享老化保护：最老请求等待超过画像中最慢 direct 命令耗时的四倍时，本次选择必须服务它。命令不可抢占，运行和控制开销仍可能让实际等待超过该触发阈值。

以下数字都是教学假设，不是模型实测。

**例一：为什么一次 miss 可以不建立新缓存。** 状态池容量为 3 单位，里面已有语言模型 L，占 3。分类模型 C 占 2。准备 L 需 6 秒，准备 C 需 4 秒，复用执行均需 1 秒，淘汰需 1 秒。直接执行 C 需 5 秒。当前请求是 C、L、L。

| 选择 | 中间步骤 | 总耗时 |
|---|---|---|
| 每次 miss 都准入 | 淘汰 L 1 秒，准备并执行 C 5 秒，淘汰 C 1 秒，准备并执行 L 7 秒，再复用 L 1 秒 | 15 秒 |
| C 直接执行，保留 L | 直接 C 5 秒，不动 L，随后两次各复用 L 1 秒 | 7 秒 |

第二种做法没有少做 C 的验证，也没有缓存答案，只是不为一次 C 请求破坏后面两次 L 所需的准备状态。若未来连续来了大量 C，另一种选择可能更好，不能事先把完整未来请求交给在线策略。

**例二：总工作量一样，反馈时间也可能不同。** 两轮都已就绪，不使用缓存。A 轮有 2 秒和 10 秒两条检查，B 轮有两条 2 秒检查。

| 顺序 | A 的反馈完成 | B 的反馈完成 | 两轮完成时间之和 | 最终完成 |
|---|---|---|---|---|
| A 的两条，再 B 的两条 | 12 秒 | 16 秒 | 28 秒 | 16 秒 |
| B 的两条，再 A 的两条 | 16 秒 | 4 秒 | 20 秒 | 16 秒 |

B 更早得到反馈，不代表 GPU 总工作变少。只有 B 的后续思考或下一轮工作因此能与其他执行重叠，最终整组时间才可能进一步缩短。真实后续依赖不存在时，不能把反馈收益冒称吞吐收益。

已实际运行的 CPU 教学脚本覆盖两个例子，不需要 Torch、模型、Docker 或 GPU：

```bash
python docs/env-worker-deep-dive/env-service-verification/scripts/state_reuse_study/memory_demo.py
```

观察到缓存例子的总虚拟时间为 15 秒与 7 秒，反馈例子的完成时间之和为 28 秒与 20 秒。脚本注释 M1 到 M5 对应前图的队列、状态和决策步骤，但没有真实快照打分、GPU 准入或物理内存管理。它另外将四条请求的规划结果与独立穷举比较，并检查零缓存容量时仍完成所有工作。

5 GiB 已完整执行的策略中，feedback-dp 比 critical 总时长慢约 35.4%。由于该场景只完成五种策略，不能声称比完整八策略中的最优慢了这个比例。它是明确的负面观测，也不能直接归因于反馈目标不好。

**噪声没有删掉。** mixed 的 locality-dp 有一条复用命令达到 8.192 秒，其中实际计算仅约 0.046 秒，大部分额外时间在加载和退出清理。bursty 中 locality-dp 与 lru 也有数秒命令。它们准备和命中计数相近时，仍会出现较大总时间差。因此不能只挑联合策略与这些慢格子相比，宣称近两倍调度收益。原始分段耗时和长命令诊断保存在 summary 中，本研究没有选择性删除异常值，也没有通过不断重跑找漂亮结果。

**完成与停止边界。** 容器主动预算 450 秒，内部工作预算 430 秒。到达内部上限时停止，控制器约 432.78 秒退出，原始状态为 `failed`，原因是预算到期，不是 OOM 或数值检查失败。保存了 21 个完整块，即 504 条完整命令，独立审计的数值、代码版本和张量预算全部通过。另有 stage 的 7 条部分发布结果，保留原始目录，但不参与完整块性能比较。没有为补齐表格延长 GPU 运行。

## 回放反例与收益归因

回放用真实画像成本加虚拟时间，不执行模型，不能称为 GPU 吞吐实验。网格为四种命令组合、四个随机种子、四种主存预算和三种思考间隔，共 192 个场景，每个比较八策略。策略看不到未来到达。总虚拟工作量一致，真实 GPU 阶段使用未出现在该网格中的种子 17 和间隔倍率 2，但仍属于预设机制探针，不是自然分布的无偏测试集。

最初回放没有淘汰画像，默认淘汰成本为零，得到了偏乐观的 3 GiB 平均总时长改善约 0.6%、反馈改善约 5.6%。补上实测淘汰成本后，同一网格直接重算，没有扩大 GPU 实验。它改变了结论，正式判断应使用[校准回放](../env-service-verification/results/memory-state-20261112/replay-calibrated.json)，零淘汰版本仅保留作成本遗漏证据。

下表“改善”均逐场景相对 direct、stage、LRU、gdsf、affinity、critical、locality-dp 中该指标最好的一个，再对同容量的 48 个场景取算术平均。负数表示更差。这是较严格的描述性参照，**不是一个能预知每个场景最佳策略的可部署控制器**。

| 状态池预算 | 总时长平均改善 | 平均轮反馈改善 | 总时长改善超过 1% 的场景 | 总时长恶化超过 1% 的场景 |
|---|---|---|---|---|
| 0.8 GiB | +0.77% | +4.29% | 7/48 | 4/48 |
| 1.3 GiB | +0.23% | +4.25% | 7/48 | 8/48 |
| 3.0 GiB | -1.48% | -0.09% | 11/48 | 19/48 |
| 5.0 GiB | -1.20% | +5.09% | 8/48 | 14/48 |

0.8 GiB 小于任何一份状态，所有策略只能 direct，仍出现部分反馈改善。这是有用的反证：**这一部分来自命令顺序，不是主存复用。** 5 GiB 能保存全部状态，仍有反馈改善，同样不能归因于内存竞争。3 GiB 才是两份状态竞争的核心条件，而完整成本回放在这里没有平均增量。

画像还可做一个保本计算。语言状态每次复用大约节省 `0.830-0.236=0.594` 秒，建立加最终淘汰需约 `0.435+0.334=0.769` 秒。忽略其他影响，至少使用两次才可能回本。分类状态每次节省约 0.222 秒，建立加淘汰约 0.374 秒，同样至少两次。若新建 C 还要破坏 L 的后续复用，则需要再加机会成本，不能只看 C 自己的两次命中。

两个细节使研究主张必须收窄。

1. 在 mixed 中，两个 dp 都只准备两次，但 locality-dp 时间显著更长。大幅时间差主要不能由准备次数解释。
2. 在 bursty 中，affinity、critical、gdsf 和两个 dp 都是五次准备、十九次命中。复杂搜索没有发现明显不同的复用结构。普通策略已经覆盖了主要机会。

当前实机计时还包含 fresh GPU model 的退出清理，校准回放没有覆盖全部控制、快照与打分开销，也不建模这些开销的波动。因此回放只能检验成本假设，不能替代实机的稳定性证据。

## 已有研究覆盖了哪些想法

定向查阅采用作者论文、会议官网或论文原文。下表用来约束贡献表述，不代表穷尽检索，也不把未复现论文的摘要数字当成本系统结果。

|---|---|---|
| [HELIX，PVLDB 2018，§4.2 与 §5](https://www.vldb.org/pvldb/vol12/p446-xin.pdf) | 跟踪迭代修改，判断等价状态，选择重用、重算及有限存储下的中间结果保留 | “改代码后只重建失效部分”和“预算下选缓存”已有直接近邻 |
| [FaasCache，ASPLOS 2021，§4](https://afuerst.github.io/assets/FaasCache.pdf) | 按频率、冷启动成本、大小和时效决定保温与淘汰 | “准备贵就留，太大就淘汰”不足以独立立题 |
| [PRETZEL，OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/lee) | 多模型服务中的共享与内存优化 | 公共运行时和共享模型状态不能直接认领新颖性 |

| [Pheromone，NSDI 2023，§4.2](https://www.usenix.org/system/files/nsdi23-yu.pdf) | 数据触发、工作流依赖、缓存函数与数据局部性调度 | “把数据状态和执行队列一起看”不能笼统声称无人做过 |

| [EfficientAgent，2026 预印本，§3 至 §4](https://arxiv.org/html/2609.33762v1) | 并发 Agent 的主存工作集、缓存写入准入与抖动 | “主存不足时拒绝写缓存比一味缓存更好”已有很近的 KV 研究 |

KV 缓存是模型推理时保存的注意力键和值，用于避免后续重复处理相同前缀。本研究保存的是工具准备出的 CPU 张量，二者状态类型不同，但“有限主存、复用概率、写入准入、工作流完成时间”的方法重叠依然需要承认，不能仅靠更换状态名建立新颖性。

## 值得继续的问题与立项门槛

现在更值得问的不是“LRU 换成动态规划会不会更好”，而是：

> **代码不断修改时，一份工具状态还剩多少合法用途？系统能否利用已经可见的版本依赖和反馈条件，选择保留一种较小的状态、暂缓一种昂贵准备，或者直接旁路，减少无效准备并保持评测语义？**

这里的关键是合法用途真的会随代码编辑而变化，而不只是某份固定模型下一次什么时候被访问。本次只修改轻量打分代码，权重准备始终有效，因此还没有检验这条核心研究假设。它测到的是普通状态准入与命令重排的成本，不能包装成变更感知策略的收益。

**原题补丁复核也没有给出大状态失效的现成证据。** 已只读核查 score 题的真实参考补丁和原始测试 fixture，并保存[静态审计](../env-service-verification/results/memory-state-20261112/reference-state-audit.json)。补丁修改 11 个 Python 文件，涉及注意力、输出分数、请求批次、Tokenizer 管理及服务参数，没有修改 checkpoint 文件。原始测试在四个类级 fixture 中分别建立、销毁引擎。这是一个参考修复的静态审计，不是 Agent 的多轮编辑轨迹。

| 原题中的状态 | 实际变化依据 | 能得出的结论 |
|---|---|---|
| checkpoint 文件与原生映射 | [补丁路径清单](../env-service-verification/results/memory-state-20261112/reference-state-audit.json)没有权重文件 | 可能继续复用，但加载配置与表示依赖仍要检查，不能仅凭未改权重保证一切有效 |
| 旧引擎内已经导入的注意力、logits 和 pooler 代码 | [注意力改动](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L1)、[logits 改动](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L135)、[pooler 改动](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L303) | 原题不能简化成只替换轻量打分函数，直接复用整个旧引擎不满足新代码语义 |
| 每请求的分隔位置与批次字段 | [Tokenizer score 改动](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L729)、[ForwardBatch 改动](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L1008) | 需要按输入和新代码重新计算，但本次没有证据说明它们构成数 GiB 的昂贵主存状态 |
| CUDA graph 与推理前缀缓存 | [MIS 参数处理](../env-service-verification/results/memory-state-20261112/reference-changes.patch.txt#L1085)明确禁用 CUDA graph、radix cache 和 chunked prefill | 不能违背原题机制强行复用这些状态来获取收益 |
| 类级模型引擎 | [语言模型 fixture](../env-service-verification/results/memory-state-20261112/reference-test-score-engine.py.txt#L61)、[分类 fixture](../env-service-verification/results/memory-state-20261112/reference-test-score-engine.py.txt#L281) | 原题本来已在同一类测试内复用，不能把每条断言当作一次原始冷启动 |

因此 score 题适合提供真实模型资产和正确性语义，也适合研究“哪些状态能合法留下”的接口，但当前不足以作为“大量昂贵状态随编辑部分失效”的论文主场景。需要找到实际具有这一特征的任务，不能为了适配想法而把原题改成大量额外转换。

一个待验证的具体场景是 GPU 正确性代码修复：会话先修改打分边界处理，随后可能修改加载精度或算子实现。原生权重文件、转换后的 CPU 张量、依赖候选实现的编译产物具有不同有效范围。主存不足时，框架应在合法的表示之间选择，不必只在“全保留”和“全丢弃”之间二选一。这个场景仍需要真实编辑轨迹与原始验证器支持，不能把这里固定的打分改动当作其证据。

**推荐先做一项研究资产，而不是生产复杂控制器：从原始正确性 benchmark 记录少量真实修改与测试轨迹，形成可审计的状态生命周期图。** 图中每个状态都应有建立成本、大小、实际读取依赖、哪些修改会使它失效，以及原始测试是否允许复用。若采用显式适配器，就承认适配范围，不承诺自动理解任意 shell 程序。

立项前至少满足以下条件。

| 门槛 | 需要的证据 | 不满足时的处理 |
|---|---|---|
| 真实可避免成本 | 原始测试中的准备成本在普通文件缓存、合理常驻服务之后仍明显 | 收缩为加载优化或停止，不靠增加重建制造调度收益 |
| 真正状态竞争 | 至少三份不同状态或表示，真实有效工作集超过给定预算 | 两份状态只能存一份的例子仅保留作机制演示 |
| 修改影响状态选择 | 真实代码改动改变部分准备状态的有效范围，同时保留未受影响部分 | 若所有昂贵状态始终有效，就按普通缓存问题处理 |
| 强对照后的增量 | 版本正确的人工拆分、文件缓存、LRU/成本缓存、缓存亲和、按剩余耗时完成整轮及合法 GPU 常驻 | 优势只相对逐命令冷启动时，不做复杂策略贡献 |
| 公平且可归因 | 同一原始测试、相同命令和数值结果，计入建立、释放、控制及失效浪费 | 只有缓存命中或局部耗时下降不能通过 |
| 真实训练或服务意义 | 小规模真实 Agent 闭环中，更早反馈减少最终完成时间或同预算完成更多正确任务 | 不由脚本化思考空窗外推训练吞吐与模型效果 |

论文贡献若成立，更可能来自**可验证的状态表示选择与执行控制机制，以及真实轨迹中现有缓存无法处理的失效和竞争规律**。动态规划只是用来估计空间和构造强对照的工具。现有数据尚未通过这些门槛，因此没有把该方案接进生产，也没有开始训练调度模型。
