# 运行准备：重复准备成本与GPU就绪调度

> **核心结论**：找到一个在本次六类代表任务上均有收益的共同场景：多个 GPU 环境反复启动，依赖同一套共享存储上的 Python 软件环境。保持固定旧 PSRL runner、GPU 静态分配、并发和任务协议，仅复用节点本地的只读依赖副本，六类任务平均完成时间均减少 **19.91% 至 59.74%**，整批减少 **54.03%**。三组交错配对共 36 次任务全部完成独立评分，18 个逐类配对全部更快。
>
> 这是**依赖已准备好时的收益**，每次任务内部的初始化、导入与模型加载均已计时。首次复制 13.54 GB 花了 333.40 秒，将它加回本次三个 ON 区块，累计 530.68 秒，对应 OFF 为 429.17 秒，**计入复制后慢 23.65%**。约第五批回本是均值外推。实验驱动启动、前置校验等尚缺独立计时，因此现有证据是任务边界实测与成本拼接，完整冷启动端到端收益仍待验证。

## 共同场景是什么

一次 GPU 工具调用的总时间，不只是显卡计算。程序需要创建环境、启动 Python、导入 PyTorch 等软件库，然后才能训练模型或执行算子。任务结束后，独立评分进程也可能重新导入这些库。

版本标签W1、D1、C1、v1/v2是教学记号。沿①磁盘与进程不一致、②依赖分类、③核对与局部重建、④正确性和成本对照阅读。正文的固定基线实验在CPU模型上验证，受控适配器使用文件快照、新评分进程及发布前核验，不是任意程序通用热更新。 [查看矢量图](../../_static/img/document-figures/state-version-match.svg)。
<!-- /figure:state-version-match -->

这里的“依赖”是程序运行需要的软件文件，例如 Python 解释器、PyTorch 和 Transformers。“本地副本”是把这些文件放到执行机器的本地文件系统，减少反复访问共享存储。它没有保留前一个任务的训练参数，也没有复用前一个任务的分数。

本次六类任务原本就在 Compose 配置里以只读方式挂载同一个共享 Python 环境。该环境含 133223 个普通文件，全部文件内容约 13.54 GB。Python 导入涉及查找模块、读取文件和软件包信息，GPU 尚未开始计算时就可能耗费数秒或更久。本次没有采集逐次文件系统调用，不能把全部差异精确归因于某一种元数据操作。

只读挂载表示容器能读取这些依赖，但不能修改它们。实验把挂载的宿主来源换为完整复制的本地目录，容器内看到的路径保持原样，因此无需重写程序里的 Python 路径。输入、参考解、评分脚本、模型、更新次数和 GPU 配置均保持相同。

这比“训练命令的执行时间必须可预测”更少依赖题目内容。无论随后执行矩阵乘法还是模型训练，都要先启动软件环境。但收益仍有条件：依赖原本就在本地镜像中、长期使用同一进程，或主要时间是长时间 GPU 计算时，这个瓶颈可能很小。

## 真实调用流程与源码

下图是**本次实际实验**，不是生产 Router 已有的新算法。

```text
[A] 一次性复制同版本依赖到执行节点本地目录
    校验部分关键文件与版本，实际运行容器 CUDA 探针

[B] 建立两组任务副本
    OFF：只读挂载原共享依赖

[C] 同时提交六项任务，按原静态规则分到两张 GPU

                          ↓
[D] 固定旧 PSRL runner → Harbor → 参考解执行
    软件导入 → 原有 GPU 计算 → 交付本次产物
                          ↓
[E] 新的独立 verifier 容器读取本次产物并执行原评分
                          ↓
```

## 固定旧基线对照结果

**先把实验理解为：让同一套题做两遍，只改变程序从哪里读取软件依赖。** 本实验中的 OFF 和 ON 分别表示“读取共享存储”和“读取提前复制到本机的副本”。两组都使用固定旧 PSRL runner，比较的是依赖读取位置。这里的 ON 没有开启一个新的 GPU 调度算法，也不是当前 Env Service 与旧版 PSRL 的整体对照。

一次取 KernelBench、PostTrain、FlashInfer、MLGym、MLE、RE 各一个代表题，六道题一起提交，叫作“一批”。这不是六个完整题库。每道题直接运行已准备的参考程序，再用独立评分程序检查产物。例如 PostTrain 执行真实的 GPU 参数更新并交付模型，评分程序随后读取该模型。实验没有让 LLM 现场生成新方案，因此两组可以重复执行同样的工作。

| 比较项目 | OFF：共享读取 | ON：本地读取 |
|---|---|---|
| 任务程序、输入、模型、计算量、评分方式 | 同一套 | 同一套 |
| 执行框架 | 固定旧 PSRL runner | 同一个固定旧 PSRL runner |
| GPU 和分配规则 | 两张 H20，六任务固定分配，每卡三项 | 相同 |
| CPU、内存限制和并发上限 | 使用原设置，进程内并发上限八 | 相同 |
| Python、PyTorch 等依赖的读取位置 | 共享存储上的原目录 | 执行机器上的只读副本 |
| 为本地副本支付的一次性成本 | 无需复制 | 先复制 333.40 秒 |

两组每次都新建任务和评分环境，进程仍然要导入软件和加载模型。本地文件副本改善的是读取速度，并没有把已经算好的任务结果拿来评分。镜像原本已在执行节点，因此本实验不包含镜像下载。

为了检查结果能否重复，总共跑六批，顺序固定为 **OFF / ON / ON / OFF / OFF / ON**。OFF 三批，ON 三批，每批六题，所以总共执行 `2 种方式 × 3 次重复 × 6 道题 = 36 次任务`。两种方式分开跑，前一批结束并确认资源释放后再启动下一批。交错次序降低“某种方式总在前面或后面”带来的影响，仍属于有限次数的配对实验。

总预算 1500 秒，没有依据中途结果替换题目或增加重跑。验收门槛为缓存就绪后的六类均值至少改善 10%，每类三个配对方向均为正，所有 36 次评分有效。该门槛已通过。

计时从各区块的共同提交时刻开始，到 runner 返回为止，包含入队等待、环境创建、参考解、独立评分和 runner 内部清理。每个区块之后再核验物理释放。一次性依赖复制成本单独列出，不能隐藏在稳态结果中。

**怎样读两种时间指标？** 提交一批六题时统一按下秒表。某题完成计算、评分和 runner 清理并返回时，记录这道题的“完成时间”。最后一道题返回、区块内记录和容器查询结束时，记录“整批完成时间”。六题并发推进，所以整批时间接近最晚完成的题，不能把六道题的时间相加。例如教学假设中，两题同时提交，分别在第 10 秒和第 15 秒返回，整批约 15 秒结束，而不是 25 秒。

结果表中的“均值”则来自重复实验：例如 OFF 三批整批时间分别为 140.15、146.79、142.23 秒，平均为 143.06 秒。ON 三批为 66.97、62.65、67.66 秒，平均为 65.76 秒。因此任务批次耗时减少率为 `(143.06 − 65.76) ÷ 143.06 ≈ 54.03%`。这个百分比回答“依赖已经在本地时，一批任务快多少”。首次复制是否值得，要用后文的成本累计单独回答。

**初始化和导入究竟算在哪里？** 任务进程和评分进程每次启动后的 Python 导入、CUDA 初始化、模型加载都发生在 runner 调用内部，因此已经包含在下表中。本地文件副本只加快读取，每次新进程仍会执行导入。另一个层次是实验驱动自身的初始化：[旧 runner 装载](../env-service-verification/scripts/admission_study/pilot.py#L56)、设备与镜像预检、[任务配置副本准备](../env-service-verification/scripts/admission_study/pilot.py#L99)发生在[区块计时起点](../env-service-verification/scripts/admission_study/pilot.py#L125)之前，没有进入该表。逐任务计时截至[完成时间记录](../env-service-verification/scripts/admission_study/pilot.py#L170)，后续外部容器检查和区块后的 GPU 物理复查也应与 runner 内清理区分。

| 时间项目 | 下表是否计入 | 当前证据 |
|---|---|---|
| 任务及评分容器创建、进程启动、依赖导入、模型加载 | 是 | 包含在 runner 调用的完成时间内 |
| 原有计算、独立评分、runner 内清理 | 是 | 同一提交到返回边界 |
| 一次性复制依赖 | 否 | 另有 333.40 秒实测，可拼接成本 |
| 实验驱动启动、导入、前置检查与任务副本准备 | 否 | 缺少分项耗时，不能假定为零或两组完全抵消 |
| 镜像和原始资产下载 | 否 | 实验开始时已经存在 |
| runner 返回后的物理释放复查 | 逐任务时间不含 | 区块内部分容器查询计入整批时间，区块后的 GPU 复查另行执行 |

| 代表任务 | OFF 均值 / 秒 | ON 均值 / 秒 | 完成时间减少 | 三组配对的减少范围 |
|---|---:|---:|---:|---:|
| KernelBench 方阵乘法 | 63.69 | 47.16 | **25.96%** | 22.42%–31.40% |
| PostTrain GSM8K / Qwen3-1.7B | 143.01 | 65.68 | **54.07%** | 52.23%–57.34% |
| FlashInfer RMSNorm 代表任务 | 70.91 | 48.52 | **31.58%** | 26.38%–39.67% |
| MLGym MNLI | 139.67 | 56.23 | **59.74%** | 57.48%–63.05% |
| 本地 MLE digits | 54.77 | 43.87 | **19.91%** | 14.02%–27.73% |
| RE restricted MLM | 63.63 | 46.95 | **26.21%** | 20.32%–34.75% |
| 整批全部完成 | 143.06 | 65.76 | **54.03%** | 三个区块均更快 |

表中“减少 54.03%”表示花费时间约为原来的 46%，不是吞吐提高 54.03%。固定工作量的整批速度比约为 2.18 倍。三次配对支持本节点、本配置下的重复性，不等于已经做了跨机器统计验证。

36 次任务均执行参考解与独立评分，没有用缓存分数代替计算。KernelBench、FlashInfer 等保留原正确性检查。五类任务的 reward 在六次运行中完全相同。RE 的评分会随机采样文本位置和掩码，分数存在小幅变化，但六次交付的 `basic_model.pt` 字节摘要完全相同，PostTrain 六次交付的 `adapter.safetensors` 也完全相同。这证明这两个任务的交付模型文件没有因读取位置变化而改变，不等于所有任务、所有中间张量都已逐位核验。KernelBench 的计时数据处于原有并发环境，本结果不证明独占显卡时的算子性能真值。

组件探针也用了交错顺序。共享依赖的两次完整容器探针是 32.13 和 31.73 秒，本地副本是 5.30 和 5.57 秒，软件版本相同，四次 CUDA 求和均为 8。CUDA 小计算与初始化约 0.39–0.62 秒，主要变化发生在导入阶段。该探针用于解释机制，不计作六类任务的性能样本。

## 以一个 PostTrain 任务解释收益

这个任务的输入是固定基础模型、训练样本和评分样本。参考程序只更新模型最终归一化层，执行原有两次参数更新，交付本次权重。独立评分器创建新的模型实例、读取这份权重，再评价固定样本。

以三次运行的分阶段均值为例：

| 环节 | OFF / 秒 | ON / 秒 | 应怎样解释 |
|---|---:|---:|---|
| 初始容器准备 | 5.34 | 8.04 | 本地副本并没有让每个环节都变快 |
| 参考解进程执行 | 60.06 | 13.71 | 含软件导入、模型加载和原有训练，不是纯 GPU 内核时间 |
| 独立评分 | 64.03 | 30.34 | 含评分侧准备和原评分计算 |
| 其余编排与交接 | 13.58 | 13.59 | 基本相同，包含未单列的交接和清理等时间 |
| 完整返回 | 143.01 | 65.68 | 从同一个提交边界算出的真实收益 |

可以把过程理解为：每个新程序仍然要读教材、做题和交卷，只把反复读取教材的位置从共享存储移到执行节点。这里真正没有省掉的是训练更新和评分计算，节省的是每次重启程序时的部分准备时间。

MLGym 的参考解执行均值也从 55.42 秒降到 9.01 秒。MLE 的评分本来就是较轻的 CPU 评分，变化很小，其主要收益发生在训练进程，因而整体改善只有约 20%。这说明六类收益来自共同准备开销，但该开销占每题总时间的比例不同。

## 第一次准备与回本条件

本地缓存不是免费的额外资源。首次完整复制耗时 **333.40 秒**，约占 **13.54 GB** 文件内容空间。缓存命中指需要的依赖版本已经存在于该节点，后续任务可以直接读取；它不表示任务已经算过。

用实测整批均值做一个明确标为**外推**的计算：

```text
连续 N 批的 OFF 时间 ≈ N × 143.06 秒
复制一次后连续 N 批的 ON 时间 ≈ 333.40 + N × 65.76 秒
每批节省 ≈ 77.30 秒
333.40 ÷ 77.30 ≈ 4.31，因此约第 5 批开始抵消复制成本
```

以“一次复制完成后，六项任务同时提交”为初始状态，可以给出如下**补入复制成本的首次返回时间**。第三列是原任务边界实测均值，第四列是实测复制成本与均值相加，没有额外计入缺失的驱动启动和校验时间。

| 代表任务 | OFF / 秒 | ON 缓存就绪 / 秒 | ON 首次准备加任务 / 秒 |
|---|---:|---:|---:|
| KernelBench | 63.69 | 47.16 | 380.56 |
| PostTrain | 143.01 | 65.68 | 399.08 |
| FlashInfer | 70.91 | 48.52 | 381.92 |
| MLGym | 139.67 | 56.23 | 389.63 |
| MLE | 54.77 | 43.87 | 377.27 |
| RE | 63.63 | 46.95 | 380.35 |
| 整批全部完成 | 143.06 | 65.76 | 399.16 |

例如 PostTrain 的 65.68 秒包含约 8.04 秒容器准备、13.71 秒参考解执行、30.34 秒独立评分、13.59 秒其余编排与交接。后面三个环节包含相应的进程初始化、导入和加载。首次任务需要先等待整套依赖复制，所以从复制开始到结果返回的已知成本约为 `333.40 + 65.68 = 399.08` 秒。六项任务共享同一次复制，每项返回时间都经过这段等待，整批总时间只加一次 333.40 秒，不能把它加六次。

将批次连续累计，得到：

| 工作量 | OFF / 秒 | ON 加一次复制 / 秒 | ON 相对 OFF | 数据性质 |
|---|---:|---:|---|---|
| 1 批，每批六任务 | 143.06 | 399.16 | 慢 179.02% | 实测复制与任务均值拼接 |
| 3 批 | 429.17 | 530.68 | 慢 23.65% | 三个实际区块耗时求和，再加实测复制 |
| 5 批 | 715.28 | 662.20 | 快 7.42% | 按实测均值外推 |
| 10 批 | 1430.57 | 991.01 | 快 30.73% | 按实测均值外推 |

三批的 OFF 来自 `140.15 + 146.79 + 142.23` 秒，ON 来自 `333.40 + 66.97 + 62.65 + 67.66` 秒，计算使用原始未舍入值。这些区块实际交错运行，表内是按策略归组的成本拼接，不是分别从启动命令到三批结束的连续秒表记录。现有证据足以说明：缓存就绪后执行更快，但本次三批工作量还没有抵消首次复制。严格的完整冷启动端到端时间还应包含驱动启动、必要校验和收尾复查，需两组使用同一个外层起止边界才能实测。

这个回本计算只计复制成本，额外版本校验、缓存管理和争用成本还需加入。因此适合把它作为长寿命节点、反复启动 GPU 工具的候选机制，不能建议每个一次性短任务先复制整套环境。整个六任务批次回本，也不等于每一类在独立承担全部复制成本时都同样快回本。

## 可以提炼什么公共研究问题

建议把公共问题具体化为：

> **在 Agent 不断修改程序、GPU 命令时长未知的情况下，怎样联合安排环境与数据准备、版本正确的状态复用和 GPU 准入，使任务等待更短，同时避免显卡等待准备、重复搬运和过度预热？**

“准入”指何时允许一个工作开始占用受控资源。“就绪”指这个工作依赖的指定版本文件和必要准备已经完成。它是可以检查的当前状态，不要求知道命令将来还要运行多少秒。

设计上可以分成两个队列，但以下是**待验证提案**：

```text
命令到达 → 确认代码、依赖和输入版本
             ↓
          准备队列：有界执行文件搬运或明确允许的 CPU 准备
             ↓ 本次所需状态已就绪
          执行队列：等待容量合格的 GPU → 执行 → 返回反馈
```

这张提案图暂无对应的新生产实现。上面的真实实验仅验证其中“依赖准备可复用”这一环节，ON 的 GPU 分配仍是旧静态规则。不能把本地文件缓存的收益全部记到未来的 GPU 调度策略名下。

与预测任意命令剩余时间相比，可以先利用三类确定信息：本次依赖的实际版本、各节点已具备的状态、GPU 是否已经物理归还。空闲设备上有就绪工作时直接执行，尚未就绪的工作继续准备。是否还需要预测器，应在这个简单对照之上再验证。

真正需要研究的难点是：本地空间有限时保留什么；多个准备请求是否拥塞网络和磁盘；代码修改后什么状态仍有效；为了等一个热节点而放弃空闲 GPU 是否值得。仅按文件名判断相同不可靠，必须区分依赖版本、Agent 改写的代码、训练中的权重和本次评分产物。已有[真实状态核查](04-状态复用_真实任务中的收益空间核查.md#先回答什么才算可复用)详细解释这些区别。

下一阶段要比较“原共享读取”“单纯本地缓存”“缓存加就绪准入”三组，才能证明 GPU 决策的独立增量。还需要加入依赖已在镜像中的任务，避免把共享存储部署方式误当成所有 bench 的本质。本次不改写已有[生产能力入口](../knowledge/01-架构与执行/01-Env架构_现状与完整执行流程.md)为已实现该算法。

## 跟着图读源码与复现

按实际执行顺序阅读：

1. **A**：[runtime_probe.run](../env-service-verification/scripts/admission_study/runtime_probe.py#L33) 检查关键文件摘要和空闲 GPU，以相同镜像运行两种挂载方式，结果包含软件版本和实际 CUDA 计算。
2. **B**：[prepare_copy](../env-service-verification/scripts/admission_study/pilot.py#L21) 接收原任务、目标目录和依赖位置。它不改程序，只改任务副本的 Compose 挂载，并为两组评分器补同样的设备传递兼容配置。
3. **C → D**：[run](../env-service-verification/scripts/admission_study/pilot.py#L50) 建立任务清单，多个 [execute](../env-service-verification/scripts/admission_study/pilot.py#L127) 协程同时调用旧 runner。协程是在等待容器操作时允许别的任务继续执行，不表示所有 GPU 内核必然同时计算。此处 `static` 和 `local` 使用相同的静态选卡表达式。
4. **D → E**：[runner 调用点](../env-service-verification/scripts/admission_study/pilot.py#L148) 进入 Harbor，运行 oracle，即预先准备的参考解，然后启动独立 verifier，即评分程序。它们仍运行真正的 GPU 计算。这里没有让 LLM 生成命令，也没有运行完整策略训练。
5. **F**：[任务 finally](../env-service-verification/scripts/admission_study/pilot.py#L168) 记录结果和所属容器，[区块边界](../env-service-verification/scripts/admission_study/pilot.py#L186)检查 GPU 进程与显存。[分析器](../env-service-verification/scripts/admission_study/analyze_locality.py#L19)要求清单完整且恰有一个独立评分结果，不丢弃失败或重复运行。

可先运行不需要 GPU 的[教学脚本](../env-service-verification/scripts/admission_study/locality_demo.py)：

```bash
python docs/env-worker-deep-dive/env-service-verification/scripts/admission_study/locality_demo.py
```

它把内容摘要作为缓存键。摘要是由文件字节算出的固定标识，内容改变时标识也改变。两次请求版本 A 复用一个文件，版本 B 得到另一个文件，已经绑定 A 的任务仍读 A。脚本实际已运行，输出两次 `VERSION A` 和一次 `VERSION B`，断言通过。时间例子 `3×5=15` 对 `6+3×2=12` 是教学假设，不是 GPU 测量。真实原型是完整目录复制，并没有实现该教学模型所表示的生产缓存版本管理服务。

真实实验前须按[集群预检](../../psrl/psrl-run-guide/02-集群预检_依赖地址与GPU资源核验.md)激活指定环境，固定旧源码导入，确认空闲 GPU、镜像、容器 CUDA、资产与可用本地空间。以下变量均指本次专属路径，不覆盖共享环境：

```bash
mkdir -p "$LOCAL_RUNTIME"
timeout 480 /usr/bin/time -f 'elapsed_s=%e' -o "$EVIDENCE/copy.time" \
  rsync -a --stats "$SHARED_RUNTIME/" "$LOCAL_RUNTIME/" > "$EVIDENCE/copy.log"

python docs/env-worker-deep-dive/env-service-verification/scripts/admission_study/pilot.py \
  --manifest "$SIX_TASK_MANIFEST" --baseline "$FIXED_BASELINE" \
  --output "$EVIDENCE/matrix" --gpus 0 1 --budget 1500 \
  --policies static local local static static local \
  --runtime-prefix "$SHARED_RUNTIME" --runtime-cache "$LOCAL_RUNTIME"
```

必须确认复制退出码为零并完成容器探针后才启动矩阵。完整汇总还需要保存协议清单、复制退出码、探针结果和执行脚本摘要，字段与本次公开证据一致。运行 `analyze_locality.py <本次证据目录> <输出 JSON>` 会计算逐类配对、分阶段耗时与复制成本外推。

## 证据与适用范围

[公开证据](../experiments/gpu-benchmarks/runtime-locality-evidence.json)保留六区块、36 项结果、每类配对、软件导入探针、脚本摘要、准备成本与清理状态。完整日志位于工作区 `benchmark-runs/runtime-locality-20261116/`，包含固定 baseline 补丁、冻结协议、执行时源码和 Harbor 的独立 trial 记录。

本次复制正常结束，探针核对 Python、PyTorch、Transformers 三个关键文件摘要及软件版本。12 对任务副本、124 对文件完成对照：还原依赖挂载来源后 Compose 内容相同，其余文件字节相同。运行后的完整依赖目录大小与时间戳复查超过预定 90 秒预算，没有宣称完成全目录逐文件复核。所有真实任务均使用只读挂载，36 次评分完成，不代表已经实现可抵御源目录并发修改的生产快照服务。

收尾查询无运行或残留实验容器、无 GPU 计算进程。两张目标卡约 3 MiB 驱动占用，本地依赖副本保留用于复现，没有占用模型显存。代码和报告是主目录未提交内容，未推送远端。

**覆盖的是六类各一个本地代表协议。** AIRS、autoresearch、InferenceBench、SWE-Serve、FastKernels 没有进入这组矩阵。已有资产审计也显示部分任务把依赖放在镜像内，不应为了制造差距把它们迁到共享存储再测。因此“六类在这个共同场景全部获益”已验证，“全部 11 类及其完整题库均加速”仍未验证。GPU 排程、自然多轮 Agent、完整 PPO 策略训练和真实训推共卡的独立收益也不能由本实验推出。
