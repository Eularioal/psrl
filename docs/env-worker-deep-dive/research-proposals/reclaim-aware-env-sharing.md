# 训推与 GPU 环境协同借卡：可撤回执行与反馈依赖

> **核心结论**：首轮真实共存实验已经完成：环境在完整训练更新后暂停并继续的机制可行，但没有超过现有共享。256 次更新与连续请求下，合作式暂停相对现有共享的配对耗时增加约 14.49%，推理时间却几乎相同。下一步应先找确实存在模型干扰与前后依赖的真实任务，再判断何时值得暂停，而不是默认新推理一到就暂停环境。详见[完整实验](../experiments/resident-compute-sharing.md)。MPS、模型卸载与 Megatron 保持为独立扩展。
>
> 这是研究提案，不是已部署策略。MPS 并行、机会共享、有界抢占、工具反馈优先和组完成调度各有先例。可能的研究空间是异构 GPU 工具真实退卡能力与其诱发的后续推理需求之间的联合决策，尚未证明新颖性和真实收益。
>
> 核对范围：共享、控制门禁、MPS 和归还链基于 2026-11-13 对主目录 `6aa328d` 加未提交内容的核查。2026-11-16 新增合作式研究适配器，并完成 36 个真实 vLLM 与图像任务对照区块，执行源码和清理证据单独保存。随文 CPU 模拟与历史 GPU 证据保持各自原始条件。本文补充[共享专题](../knowledge/vllm-env-opportunistic-sharing.md)，实现现状仍以[当前设计](../knowledge/current-design.md)为入口。

## 建议的实验路线

先按下面顺序决定是否继续，不同时展开所有能力。后文保留机制、源码与论文对照，实际实验优先级以本节为准。

| 阶段 | 要回答的问题 | 实验范围 | 进入下一阶段的依据 |
|---|---|---|---|
| 1. 验证借用与让出计算 | 环境用了模型空闲计算时间后，能否及时让开，净收益是否为正 | 单个真实 vLLM 副本、一个真实 GPU 工具。模型保持常驻，留够峰值显存，不启用 MPS | 合作式让出实际可执行，模型额外延迟符合事先约定，固定工作量总耗时有改善 |
| 2. 验证调度策略增量 | 动态选择工具、执行片段和让出时机，能否超过简单策略 | 相同执行协议下比较固定片段、固定片段加组优先级，以及候选动态策略 | 稳定胜过强简单组合，收益包含恢复与调度成本 |
| 3. 分别验证扩展 | 同时计算或借更多显存是否进一步划算 | 先单独测 MPS，再另测已睡眠窗口的显存收回。Megatron 放到最后 | 每项独立证明净收益与保护边界，不用前一项成功替代验收 |

**第一阶段只保留环境显存、让出计算。** 环境的显存始终记账，模型的配置、缓存和峰值空间不能被挤占。没有资源共存条件时，报告该场景不适用，不靠缩小模型配置制造收益。图像任务现已通过[研究适配器](../env-service-verification/scripts/resident_sharing_study/worker.py)在完整更新后同步并暂停，生产通用命令的自动撤回接口仍需实现。

三组完成同样数量的模型请求和环境训练更新：

| 对照 | 行为 | 用途 |
|---|---|---|
| A：计算串行 | 模型与环境按约定顺序完成，环境不插入模型工作期间，保留相同显存状态 | 给出计算串行的总耗时与模型延迟参照 |
| B：现有显存准入共享 | 留足模型余量后允许 Env 与常驻 vLLM 共存 | 测出现有路径实际带来的计算干扰 |
| C：合作式让出计算 | 空闲时推进环境，新推理到来后完成当前小段便停止新增环境计算，之后继续 | 检查可控让出是否比自由共存更划算 |

**B 不等于新推理必须等整条环境命令结束。** 当前常驻共享允许普通生成继续。整条命令未归还导致 sleep、wake、权重同步等待，是另一种控制操作边界。不能为了展示 C 的优势，把 B 改造成原代码没有的整任务互斥。

首轮选用现有 MLGym 图像分类，保持各策略的更新数、数据顺序和最终准确率评分一致。普通 GPU benchmark recipe 仍要求 episode unit，本轮另用真实 command 租约与合作式适配器接线。原始 8 次更新与预先设定的 256 次更新分别报告，结果显示：接线和原位置继续可行，小任务上的暂停策略没有取得增量。

第一阶段只看四项：固定工作量总耗时、模型新增等待与生成速度、环境让出和继续的成本、环境工作量与最终结果。几次短请求不用于声称 P99 保证。先测真实片段耗时，再选恢复预算，不使用教学模拟的 100 毫秒作为实测承诺。

一个完整例子是：环境正在训练图像分类器，此时有新的 vLLM 请求。B 允许双方按实际 CUDA 行为竞争，C 在完成当前完整训练更新并确认 GPU 工作结束后停止新增计算，让模型生成，之后环境继续。最终两组必须完成相同请求和相同更新数。若 C 只是让模型更快、却把同一批总耗时明显拉长，需要报告代价，不能只展示局部指标。

第一阶段已经完成三轮顺序轮换配对，原始及延长工作量各测间隔与连续请求，共 36 个测量区块。每区块 20 秒、主实验 720 秒、外层进程 900 秒上限。主函数含公共初始化和清理约 472.9 秒，所有区块完成，所属 GPU 与容器已释放。完整 science 训练没有启动，本任务的 GPU 验证到此停止。

第二阶段才是论文候选：比较动态策略与“同样可让出计算的工具、固定片段、已有组优先级”。调度须让后续推理在环境实际完成后产生，保留真实依赖。下一批数据提前就绪属于局部收益，不能直接写成完整训练提速。

如果第一阶段退让不可执行、真实空闲太短或恢复开销吃掉收益，先停止这个工作负载，不直接扩大到多卡训练。若第二阶段没有超过强简单组合，就保留工程能力，不把策略宣称为已成立的论文贡献。

## 1. 全局关系：谁借卡，谁要求归还

GPU 工具是环境执行的实际计算，例如训练一个图像分类器、检查候选模型或运行 CUDA 程序。vLLM 负责生成 agent 的下一步指令，Megatron 负责训练策略模型。这些程序可能属于同一个学习流程，彼此存在先后依赖。

```text
[1] vLLM / Megatron 设备所有者
    报告当前阶段、保留显存、允许干扰和恢复需求
                         ↓
[2] EnvRouter 的借用决策
    独立 GPU 优先 → 检查显存、干扰、可退卡能力
                         ↓
[3] GPU 工具执行适配器
    提交一个可撤回片段 → [4] direct 时分 / MPS 并行
                         ↓
[5] 到达安全点，停止新增 GPU 工作
    ├─ 计算收回：确认已提交计算结束，必要状态仍在显存
    └─ 显存收回：转存完整状态或取消重跑，验收实际释放
                         ↓
[6] 归还成功才允许相应模型控制操作继续
    失败 → 隔离并报告，不能把超时当作释放成功
                         ↓
[7] 环境结果 → 下一轮 vLLM → 可用于训练的数据 → Megatron
    这些依赖反过来影响 [1] 的后续需求与 [2] 的选择
```

**图是建议结构。** 现有代码有其中若干基础组件，没有完整的主动撤回或联合决策器。普通生成目前不会因共享票据等待，第 6 步主要对应已有 sleep、wake、权重同步等受门禁保护的操作。新方案还需独立处理正常生成时的计算干扰。

## 2. 当前已经实现什么

| 问题 | 实现与证据边界 |
|---|---|
| 能否优先用其他卡 | 有独立 GPU 优先，包括同节点其他卡。只有独立候选不足才评估显式模型共享资源 |
| 能否用常驻 vLLM 的剩余显存 | 已有 direct command 路径，要求模型临时空间 profile、逐卡余量和设备绑定。不是任意输入下的峰值证明 |
| MPS 是否真的有效 | 环境专用卡上有同 server 客户端和真实 CUDA 重叠证据，不能推广为 vLLM/Megatron 同卡已验收 |
| 是否测过持续 Env 计算对 vLLM 的拖慢 | 已有 36 个当前代码机制对照。该小图像任务中 vLLM 生成时间基本持平，环境自身变慢但重叠有益；高强度工具竞争仍需独立验证 |
| Megatron 卡能否照同样方式接入 | 尚未接入。Trainer 拒绝 rollout 共享副本与其他模型角色重叠，不能删除检查后就视为安全共享 |
| 训推突然要恢复，能否马上收回 | 新命令会被控制等待挡住，既有命令不会因此主动撤回。共享 watchdog 从授予时起算，默认 30 秒后删所属容器，再验收物理归还 |

历史 MPS 配对是两个 autoresearch 训练任务，各预热 3 步、计时 10 步。普通 CUDA 并发为 22.499 秒，MPS 为 20.160 秒。完整流程则为 133.150 与 136.010 秒。两组均经过 Router，只有一次配对，不是固定历史 OFF baseline。这说明并行有实际作用，也说明短流程的初始化、准备和清理可能抵消训练段收益。详见[原报告](../experiments/mps-training-comparison.md)。

历史小型 CUDA 共享证据见[共享专题第 10、11 节](../knowledge/vllm-env-opportunistic-sharing.md#10-常驻共享kv-上限与已睡眠窗口)，本轮图像任务的模型配置、计时、准确率与权重一致性见[新实验报告](../experiments/resident-compute-sharing.md)，两者保持各自条件。

## 3. MPS 能并行，但不承诺没有干扰

MPS 是 NVIDIA 的多进程服务，使不同 CUDA 进程的内核具备同时执行的条件。内核是提交到 GPU 执行的一段程序。SM 是执行这些线程的计算单元。

没有 MPS 时，默认计算模式仍可以有多个进程分配显存并提交计算，通常由不同 CUDA 上下文之间的时间片切换提供共享。不能把它理解成第二个进程一定等第一个程序全部结束。MPS 则可以在同一服务管理下让跨进程内核重叠，但实际重叠仍取决于内核资源、依赖和启动配置。参见 [NVIDIA MPS 官方说明](https://docs.nvidia.com/deploy/mps/latest/when-to-use-mps.html)及[架构说明](https://docs.nvidia.com/deploy/pdf/CUDA_Multi_Process_Service_Overview.pdf)。

同时执行时，程序仍共享 SM、显存带宽、缓存和功耗预算。教学假设：vLLM 单独用 100 毫秒完成一批生成，共享后用 120 毫秒，即使环境也得到了计算机会，推理仍慢了 20%。若这批生成处在后续训练的必经路径上，训练也可能被推迟。

`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE=20` 是客户端可用活跃线程的上限，不是永久划出 20% 的 SM，更不是承诺 vLLM 只慢 20% 或不慢。当前实现只在新客户端启动时设置这个参数。已启动客户端不能靠改环境变量即时缩到另一份额。官方还有其他上下文级或新版分区机制，不能不核对部署版本就当作本机已有能力。[官方配置边界](https://docs.nvidia.com/deploy/mps/latest/when-to-use-mps.html#execution-resource-provisioning)

因此建议将 MPS 作为一种可选择的执行后端。无 MPS 时先验证合作式时分借用，有 MPS 时再验证保守并行。两种方式都要检查实际模型延迟，并允许发现干扰后停止共享。不能仅凭 GPU utilization 偏低就断定有安全空窗，训练通信和内存访问也可能是关键工作。

## 4. 未知结束时间怎样变成可管理的风险

完整命令的持续时间可以未知，例如 agent 写了一个根据验证分数动态决定何时停止的训练程序。调度器很难可靠预测它究竟还要跑 3 秒还是 30 分钟。

可行的第一步是要求工具提供**安全点**，也就是程序能完成当前小段工作、停止提交后续 GPU 工作，并保持结果一致的位置。图像研究适配器已在完整优化器更新之后设点，一批独立评分也可以尝试在小批次之间设点。普通命令仍需应用明确适配，显存收回则需要额外的转存与释放协议。

安全点必须确认异步 CUDA 工作已经结束。Python 执行到循环末尾，不等于 GPU 已算完。若要释放显存，还必须处理模型、优化器状态、随机数状态、缓存分配器和其他仍存活的引用。只保存权重不等于可以原样续训，`SIGSTOP` 或 Docker pause 也不释放显存。

设定三个教学值：

- 每个执行片段最多 100 毫秒。
- 片段结束后的同步、转存或清理最多 30 毫秒。
- 模型允许这次恢复最多多等 150 毫秒。

最坏需要 `100 + 30 = 130` 毫秒，因此在这些前提成立时可以借用。若每段要 250 毫秒，同样的恢复预算就不能接纳。这里不需要预测整条命令会执行多少段。

具体过程：环境在第 100 毫秒开始第二段，模型在第 150 毫秒请求恢复。第二段在第 200 毫秒完成，随后清理到第 230 毫秒，模型多等 80 毫秒。命令原本总共要执行 4 秒还是 40 秒，不改变这次等待。剩余工作以后继续。

**这不是对任意 CUDA 程序的承诺。** 100 毫秒必须是受支持工具的保守执行边界，包含实际 GPU 耗时。历史均值或一次测量不能充当最坏上界。长内核、不可控子进程、共享带宽变化或设备故障会破坏假设。统计上界只能支持概率性的延迟目标，不能写成严格实时保证。

三类命令应区别接纳：

| 命令类型 | 允许的退卡方式 | 应计入的代价 |
|---|---|---|
| 合作式工具 | 到安全点，保存所需状态并按要求释放资源 | 当前片段剩余时间、转存、再次加载 |
| 可安全重跑的命令 | 取消本次执行，下次从合法状态重跑 | 已浪费计算、清理、重建，以及外部副作用处理 |
| 无法合作且不能可靠取消重跑 | 独立卡或明确的长期预约，暂不进入需要及时归还的共享池 | 等待空闲资源。不能把 shell timeout 当作无损抢占 |

所谓副作用，例如上传文件、写数据库或提交一次外部训练任务。杀掉进程不会自动撤销它们，重跑还可能重复执行。因此“能杀”与“能安全重跑”必须分开。

## 5. 计算收回与显存收回分开处理

**常驻余量共享。** 教学假设：80 GiB GPU 上模型当前使用 58 GiB，额外保留峰值增长 8 GiB，环境占 8 GiB，总计 74 GiB。若真实最大配置符合这个保留范围，模型恢复计算未必要求清掉环境的全部 8 GiB。停止环境新增计算并确认旧内核结束后，可能保留其显存状态，减少以后重建。

但这需要受控工具确实不能继续发射内核，并且保留显存继续记账。当前禁止新设备 open 不能阻止已有上下文继续提交计算，所以现有代码尚不支持把这个过程作为已完成的计算收回。它是新执行协议要补的部分。

**睡眠窗口借用。** 若模型睡眠时环境借用了 40 GiB，而模型唤醒需要恢复到至少 66 GiB，`40 + 66 > 80`。这时仅停止内核不够，必须释放足够的环境显存。需要转存多少、多久能放回 CPU、是否有足够主存，都进入本次准入与撤回的预算。

对 vLLM 的 KV 缓存也要区分物理池与逻辑使用。KV 是注意力机制缓存的键和值。已有环境核对版本通常预分配物理池，逻辑 token 增长是在池内分块，不代表每次都向设备扩池。但临时激活、CUDA 图和其他算子仍可能需要额外空间，不能把启动后空闲占用当峰值，更不能依赖 KV 重算来挽救 Docker 造成的物理显存 OOM。具体版本和源码核对见[共享专题](../knowledge/vllm-env-opportunistic-sharing.md#10-常驻共享kv-上限与已睡眠窗口)。

对 Megatron，需按前向、反向、优化器更新及通信阶段登记峰值。多卡训练还应以整个协同训练组判断恢复条件。一张卡迟返会拖住同步，不能因其他卡暂时不忙就继续塞任务。额外占用的“卡秒”可用等待时间乘受影响卡数描述，但端到端延迟不能直接再乘一次卡数。

## 6. 怎样把退卡代价放进调度决策

先保持用户的优先级：能满足需求的独立卡优先，资源紧张后才考虑训推卡。每次借用分别检查：

1. **显存预算**：模型实占、未来增长空间、环境尚未兑现的预约和新需求能否同时容纳。
2. **干扰预算**：模型正常计算期间，允许多少额外延迟。MPS 线程上限只是控制手段，最终仍看真实延迟与训练进度。
3. **恢复预算**：模型要求收回时，到下一个安全点和完成所需清理是否来得及。
4. **进度收益**：推进这条环境命令，能否更早交付需要的数据，收益是否足以抵消慢下来的训推、取消重跑和恢复成本。

第 4 项要看完整流程。环境完成会触发下一次推理，推理再产生新的环境工作。调度改变了后续请求的到达时刻，所以请求流不能一直被当成与策略无关的固定输入。对比策略时应重放相同任务与依赖，让后续请求在前置步骤实际完成后出现，而不是给两组硬塞相同的绝对到达时间。

第一版决策可以保持可解释，不必先训练另一个调度模型：工具列出执行 1、2、4 个完整更新的片段候选及退卡方式。Router 先排除显存或恢复预算不满足的候选，再比较推进当前所需数据的价值与干扰、恢复开销。片段太小会增加调度和恢复频次，太大则放大迟返风险。新策略要研究的具体变量就是选哪个工具、选多大片段，以及恢复请求到来后选择继续到点、立即转存还是取消重跑。

到安全点检查撤回，不等于每个小片段都必须将全部状态存盘或卸载。没有恢复请求时可以续借，继续保留合法状态。只有实际需要交还对应资源时才支付同步及所需转存成本。若没有可信执行边界，则该候选不能进入有恢复期限的池。近期观测的速度只能作为收益估计，不能自动变成严格期限保证。

教学例子：训练的下一批还差轨迹 A。A 需要 300 毫秒环境计算，再需要 200 毫秒模型回复。另有环境命令 B，需要 2000 毫秒，但不影响这一批。先 B 后 A，数据在第 2500 毫秒才齐。先 A 再回复，只需 500 毫秒。B 不是永远不做，之后仍需通过等待上限或公平份额避免饿死。这是依赖调度的基础动机，不是新算法证据。

同样不能固定“环境永远让模型先走”。如果模型只是等待环境产生下一条请求，把环境无限压低优先级会延长整个流程。反过来，外部在线推理有明确延迟要求时，环境不能为本任务收益擅自突破该要求。允许让路多少，应来自已配置的服务目标与训练预算。

建议的控制流程是：所有者报告恢复需求和绝对截止时间，Router 原子停止新借用，再对当前作业选择到安全点归还、取消重跑或拒绝继续共享。节点返回物理验收回执，成功才允许对应控制操作继续。超过期限返回隔离失败，不能虚报成功。累计的恢复和干扰开销达到阶段预算后停止借用，避免很多次“小延迟”累积成明显训练退化。

代价必须以同一固定工作量的实际完成时间比较。模型本来就需要的唤醒成本，不应全部算成环境新增损失。环境触发的额外卸载、取消浪费和再次加载则必须计入。并行分支节约的秒数不能直接相加，应检查哪条依赖路径决定最终完成时间。

第一版可复用现有“删除所属 Env 容器，再确认归还”的保守回收路径，但会丢活进程状态。细化到单个 GPU 作业需要节点持久登记作业、进程组或 cgroup、所有权代数，避免旧取消消息误杀新任务。合作式保留与恢复应从少量明确工具开始，不能宣称支持任意 shell 程序迁移。

## 7. 与论文相比，哪些已有先例

以下是原论文已覆盖的范围，不把组件换名字算作创新：

| 工作 | 已有能力 | 本课题需要额外证明的差异 |
|---|---|---|
| [Orion，EuroSys 2024](https://anakli.inf.ethz.ch/papers/orion_eurosys24.pdf) | 拦截内核发射，按计算与显存访问需求减少并行干扰 | 不能把计算干扰感知本身作为新贡献 |
| [ConServe，ICML 2026](https://proceedings.mlr.press/v306/qiao26i.html) | 在线和离线 LLM 共存，token 调度、层级抢占、增量 KV 管理 | 一般的短粒度空闲利用已有先例 |
| [Valve](https://arxiv.org/html/2604.07874v1) | 有界计算抢占、限频显存回收和重算代价 | KV 页回收不等于任意 Docker 工具的状态和副作用恢复 |
| [ROSE](https://arxiv.org/html/2605.06534v2#S4.SS1) | Agent rollout 借在线推理资源，压力恢复时回收和重派 | 论文环境是独立集群的 CPU 容器，GPU 借用者是可控 rollout 模型 |
| [BiDiRL](https://arxiv.org/html/2607.09207v2#S6.SS3) | 训推资源双向互借、分块执行与撤回待执行块 | 运行块允许完成。任意 GPU 工具的实际撤回能力与后续需求还需额外接口和决策 |
| [WEAVE](https://home.cse.ust.hk/~weiwa/papers/weave-osdi26.pdf) | 跨 RL 任务阶段编排、填充依赖空窗与主存保留状态 | 多阶段协同和保留状态本身已有工作 |
| [VenusRL](https://arxiv.org/html/2610.03286v1#S4.SS3) | 组完成优先、工具返回后的推理抢占及 KV 管理 | 不能把“关键组先做”当新贡献。其沙箱主存管理不等于 GPU 工具退卡 |
| [Agentic CPU-GPU Scheduling](https://arxiv.org/html/2607.22242v1) | GPU 工具的立即执行、排队、CPU 执行选择，考虑依赖和加载成本 | 调度模型与工具卡隔离，没有证明训推所有者恢复时的工具撤回协议 |
| [ToolSched](https://arxiv.org/html/2611.05269v1) | shell 命令级准入、资源预测和检查点恢复 | 其资源模型主要是 CPU、主存与 I/O，不能直接作为显存收回验证 |

因此建议把候选问题限定为：**GPU 工具同时占用训推资源并产生后续推理需求时，如何根据工具真实可撤回粒度，联合选择运行片段、归还时机和依赖推进顺序。**

可能的机制贡献是把工具的合作式安全点、可安全重跑和不可撤回三类能力暴露给调度器，让它选择是否借、每次借多久、何时值得付出退卡代价。若只是把 Valve 式优先级与 VenusRL 式组优先级拼接起来，没有进一步决策或实测差异，就还不足以支撑研究贡献。当前阅读范围未发现完全相同验证，不等于证明学术界无人做过。

## 8. 从现有 benchmark 选择切入场景

首选非耗时评分任务，例如本地 MLGym 图像分类。它用模型在私有测试标签上的准确率评分，调度对速度的改变不会直接变成奖励。当前训练代码已有[批次循环与完整优化器更新](../../../examples/mlgym_bench/vision.py#L80)，评分使用[准确率或 BLEU](../../../examples/mlgym_bench/vision.py#L118)。BLEU 是文本输出与参考描述匹配程度的指标。

当前[通用 GPU benchmark agent loop](../../../examples/gpu_benchmarks/agent_loop.py#L21)对普通 verifier 明确要求 episode unit。研究实验另用真实 command 资源路径与[合作式工具适配器](../env-service-verification/scripts/resident_sharing_study/worker.py)，保留原评分。它验证工具执行机制，没有替换完整 Agent recipe。

图像训练函数增加了可选更新钩子，默认仍执行原来两轮且不调用钩子。研究适配器在同一活进程中保留模型、优化器与数据，只停止新增计算，36 个区块的同工作量最终权重一致。当前末尾保存的文件只包含权重，尚不足以支持退出进程后的原样续训或跨 GPU 状态恢复。

先在这种受控任务上验证“合作执行”与“取消整条重跑”的差异，再加入稍大的现有模型训练或模型评分任务。小图像任务便于验收，但可能太小，无法形成值得发表的收益，不能据接入成功就扩展结论。

任意 agent 自写程序可作为不可撤回类别的负面对照。遇到不合作命令应拒绝借用或采用明确的取消重跑语义，不能修改程序含义来假装所有 benchmark 都可以安全切分。KernelBench 等耗时评分场景由另一条研究线处理，本提案不以其奖励作为主要证据。

## 9. 最小验证和停止条件

实验顺序、第一阶段三组对照和预算见[建议的实验路线](#建议的实验路线)。使用私有节点，按预检核实实际资源。第一阶段只测常驻模型、足够显存与无 MPS 的合作式计算让出，不同时引入模型卸载或 Megatron。

第二阶段增加固定片段、固定片段加已有组优先级作为强简单对照，动态策略须在相同执行能力下比较。若之后研究睡眠窗口的显存收回，再加入整任务取消重跑对照，不能用这类结果替代常驻余量共享的结论。

MPS 是单独的后续扩展。必须验证模型与环境真正进入同一服务，再比较实际并行与前面的时分借用。不能只给 Env 设置 MPS 变量就称共用服务成立。

观察项目包括固定工作量完成时间、下一批数据何时就绪、vLLM 请求和 token 延迟分位数、训推累计等待、GPU 显存峰值、退卡确认延迟、浪费计算与恢复成本。P95/P99 是分别覆盖 95%/99% 样本的延迟分位点，几次短请求只能检查机制，不能声称这些尾部目标已经得到可靠验证。

Megatron 后续单列验证，至少要覆盖真实同步组的前向、反向、优化器与通信阶段，证明某张卡受影响不会被单卡平均利用率掩盖。不能用 vLLM 成功代替训练峰值协议，也不能把显存压力占位当真实训推共存。

实验按问题分别限定预算。机制验收先设置几条命令和有限恢复事件，不默认启动完整 science 训练。若必须比较 PSRL 原始基线，则仍使用 `0eeead861ffafed6bf31c962d259fd847775dcf9`，并单列同版本策略消融，不能以当前关闭开关替代固定提交。

满足以下任一条件即停止扩展并报告：

- 真实任务几乎没有符合恢复预算的可用片段。
- 转存和恢复比利用到的空窗更贵。
- 共享没有缩短固定工作量完成时间，或突破训推保护预算。
- 新策略未稳定胜过相同执行机制下的强简单组合。

这些结果意味着方案适用范围有限或没有足够研究价值，不应继续靠改弱基线、延长实验或理想化任务寻找漂亮数字。

## 10. 跟着图读源码

1. **入口 → 1**：`Trainer._init_gpu_lending` 读取设备归属，校验完整 rollout 副本，拒绝与其他 owner 重叠，再绑定共享服务。输入是显式 unit 配置，输出是可共享模型的句柄及设备约束。
2. **1 → 2**：`validate_env_sharing` 汇集模型临时空间 profile。`acquire_env_command` 在条件变量保护下检查模型状态和控制等待，成功则登记共享票据。这是并发原子检查，不是全局未来负载预测。
3. **2 → 3、4**：`GpuCommandScheduler._grant` 复核容量和模型票据，节点开放设备访问，统一执行层运行作业。direct 与专用卡 MPS 是不同分支，当前不能组合为模型共享 MPS。
4. **控制请求与 4 并发**：`GpuControlGate.operation` 登记控制等待，阻止新共享命令插队，但等待既有票据自然归还。正常生成不经过这把控制门禁。新的主动撤回回调尚未实现。
5. **4 → 5**：`revoke_gpu_command` 关闭未来设备访问，检查原有句柄和可归属进程消失。作业取消由执行层另行处理，Router 的 command cancel 不能自动当作杀进程。
6. **5 → 6**：确认归还之后，`release_env_command` 移除票据并唤醒条件变量上的等待者。共享超时 `_expire_shared` 是另一条并发清理路径，删除所属容器后再次验收，失败维持隔离。
7. **7 的外层循环**：benchmark agent loop 调用 Harbor episode 编排交互并收集轨迹，`Trainer.fit` 选择并调用 step strategy。[完整批次策略](../../../psrl/trainer/ppo/strategies/full_batch.py#L26)先等数据齐，[细粒度重叠策略](../../../psrl/trainer/ppo/strategies/fine_grain_overlap.py#L24)则有不同启动边界。图中的依赖应按当前配置接线，不把示意图当成现有单线程执行顺序。

## 11. 可运行教学模拟与验证边界

从仓库根目录运行：

```bash
python3 docs/env-worker-deep-dive/env-service-verification/scripts/env_reclaim_contract_demo.py
```

[脚本](../env-service-verification/scripts/env_reclaim_contract_demo.py)只用 Python 标准库，不导入 PSRL，不创建容器，不调用 GPU。它模拟图中 2 的准入、3 到 5 的片段完成和归还假设，以及 7 的简单前置依赖。完整命令时长藏在教学执行器里，调度函数只看片段结束与所有者恢复请求。

本次实际运行的 CPU 输出为：

| 执行器内部命令总长 | 等自然结束的所有者等待 | 100 毫秒片段加 30 毫秒归还的等待 |
|---|---|---|
| 400 毫秒 | 280 毫秒 | 80 毫秒 |
| 4000 毫秒 | 3880 毫秒 | 80 毫秒 |
| 40000 毫秒 | 39880 毫秒 | 80 毫秒 |

所有者均在第 150 毫秒到达。脚本另扫描 0 到 999 毫秒的整数到达时刻，观测最大等待为 129 毫秒，符合 130 毫秒的假设上界。250 毫秒片段被恢复预算拒绝。依赖例子输出下一批数据就绪时间 2500 与 500 毫秒。

这些数字都是教学输入及确定性计算结果，**不是实测 GPU 延迟、MPS 加速比或新策略收益**。脚本预先假定了片段和清理有界，不实现实际 CUDA 同步、显存卸载、状态恢复、干扰预测或故障处理。隔离失败分支只演示不能将失败报告为物理归还成功，不能证明真实故障下一定能按时收回。其用途是让不依赖整条命令结束预测的思路可以手算并运行复核。
