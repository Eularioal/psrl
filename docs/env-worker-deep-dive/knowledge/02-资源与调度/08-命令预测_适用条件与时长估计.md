## 1. 从一个真实问题看完整流程

一条新命令 A 要使用某个模型。GPU 0 已有该模型，但正在做 B。GPU 1 空闲，但需要重新加载模型。这里的 GPU 是执行张量计算的显卡。把模型放进显存称为“驻留”，已有所需模型的设备称为“热卡”，需要加载的设备称为“冷卡”。这些词描述模型状态。

教学条件：B还运行12秒，冷卡加载5秒，A计算4秒。等热卡为16秒，去冷卡为9秒；图中还区分A提前与整批收益。 [查看矢量图](../../../_static/img/document-figures/wait-or-reload.svg)。

如果 B 还需 30 秒，加载 A 只需 5 秒，换卡可能值得。如果 B 还需 1 秒，继续复用通常更快。难点就在于，我们必须在 B 结束之前判断它还要多久。

本模块把两个问题分开：**先判断这份时间预测是否有足够依据，再比较等待和重建成本。** 第二个问题的公式很简单，第一步决定这个公式何时值得使用。

常驻模型服务采用 `episode` 持有期，也就是整个环境会话期间持续登记 GPU 预算。租约是账本发给服务的资源许可。只要模型还在显存，服务就要继续持有相应许可，最终退出才统一清理和归还。

```text
[P1] 适配器登记命令：身份、固定工作量、显存需求、可否重建
       │
       ▼
[P2] 执行中的服务发布进度：完成步数、分块耗时、报告年龄
       │
       ▼
[P3] 可预测性检查，observe / auto 采集，off 跳过
       ├─ 当前报告：身份一致、未回退、够新、速度稳定
       └─ 历史完成：同类命令样本够多、误差可接受、未过期
       │
       ▼
[P4] 当前模式 + 候选设备成本 + 状态可重建性
       ├─ off / 条件不足 → 容量安全的普通放置
       ├─ observe → 普通放置，额外计算剩余预测并校准
       └─ auto 且条件齐全 → 比较排队、加载和执行时间
       │
       ▼
[P5] 提交选定设备的队列 → 调用受管理提供者 Provider 协议执行
       │
       ▼
[P6] 真正完成：observe / auto 核对原预测，更新校准历史
       └──────────────────────────────────────────→ P3

服务仍持有模型时，episode 租约持续登记其 GPU 预算。
环境最终退出后，沿既有清理链核实物理释放，再归还租约。
```

适配器是把具体执行程序的数据转换成统一接口的一层代码。例如它知道训练程序每 16 步写一次进度，就把文件里的字段转换成 `StepProgress`。这层必须了解程序的真实含义，单凭 `python train.py` 这段字符串无法填写可靠契约。

这里的“门控”就是一组必须通过的条件。“回退”表示这次放置沿用普通容量规则，GPU 工作仍可继续。它避免把证据不足的时间数字用于有代价的模型复制。

整个流程只对已经提交、工作量有明确边界的命令做预测。未来轮次尚未生成的命令，留到实际提交后再进入队列。

## 2. 先说明这条命令究竟要做多少工作

**固定工作量**是预测的起点。例如“用这版代码、这个模型和这些输入，做 1024 次参数更新”。知道总步数和已完成步数，才有“还剩多少步”这个可核验的量。

| 命令 | 当前能否走固定步数预测 | 原因 |
|---|---|---|
| 已登记版本和输入，训练 1024 步，每 16 步上报 | 可以检查后续条件 | 总量与进度能对应 |
| 训练到验证指标不再提升 | 保留未知 | 提前停止的时间由未来结果决定 |
| 执行任意 shell 命令 | 保留未知 | shell 是通用命令解释器，命令内部可以运行任何分支 |
| 程序宣称 1024 步，报告却来自另一条命令 | 拒绝这份预测 | 数字看似合理也不能串用身份 |
| 固定 1024 步，但每步输入大小变化很大 | 可能因波动而退出预测 | 固定步数只解决工作量，尚未解决每步成本 |

调用者通过 `CommandSpec` 声明命令身份、模型、总步数和能否重建。`WorkloadKey` 标识产生时长的具体工作类型，包含代码版本、模型版本、输入特征、设备类型和运行环境版本。输入特征需要覆盖会改变成本的因素，例如 batch size、输入长度、数值精度和执行阶段。batch size 是一次同时处理的样本数，数值精度指用多少位表示一个数。

为什么模型名不够？同一个模型处理长度 128 和长度 8192 的输入，成本可以相差很大。模型代码没有变化，但换了 GPU 类型、编译设置或依赖版本，旧时长也可能失效。因此这里采用明确的身份分组，而不是把所有叫“模型 A”的记录混在一起。

`StepProgress` 再说明这一次命令目前到了哪里。它带自己的命令身份、工作类型、总步数、完成步数、每块步数及耗时，并记录报告已经过去多久。总步数和版本必须与登记时一致。进度倒退、修改已见历史、复用别的命令报告，都会让这次预测失去依据。

报告年龄应由同一计时域可靠提供。单调时钟是只向前计时、不随校准时间倒退的时钟，但不同机器的单调时钟起点可以不同。适配器不能把机器甲的单调时间戳直接减去机器乙的时间戳，得到一个看似精确的“年龄”。

**未知和零必须区分。** `total_steps=None` 表示总工作量未知。`actual_remaining_s=None` 表示没有拿到可用于校准的实际剩余时长。它们都不等于零。实际剩余零秒表示工作真的完成了，这是有证据的状态。调度快照还要表达服务是否仍忙碌，不能仅凭训练步数达到上限就认定 GPU 队列已可接下一条命令。

## 3. 怎样从进度估计剩余时间

<!-- chapter-figure:chapter-remaining-steps -->
先固定要做多少步，再估计剩余步骤和收尾需要多少秒。

[![先固定要做多少步，再估计剩余步骤和收尾需要多少秒](../../../_static/img/document-figures/chapter-remaining-steps-screen.png)](../../../_static/img/document-figures/chapter-remaining-steps.png)

图用100步、已做80步的教学数字示范。真实预测还需处理阶段变化、报告过期、准备与归还，并以完整结束的命令校准。 [放大查看 SVG](../../../_static/img/document-figures/chapter-remaining-steps.svg)。
<!-- /chapter-figure:chapter-remaining-steps -->


先看一组教学数字。程序每 16 步报告一块，已经做完 64 步。四块分别耗时 0.90、0.40、0.416、0.432 秒。第一块包含模型热身，把它排除后，每步耗时为：

```text
0.400 / 16 = 0.025 秒/步
0.416 / 16 = 0.026 秒/步
0.432 / 16 = 0.027 秒/步
```

中位数是把数值排序后位于中间的那个值，此处为 0.026 秒/步。命令总共要做 1024 步，还有 960 步，因此刚发布报告时，剩余点估计是 `960 × 0.026 = 24.96 秒`。“点估计”指给出一个代表值，实际执行仍会偏离。

跳过首块热身，是因为模型初始化和首次内核执行经常比后续慢。只有报告确实保留了从开头开始的历史时，才能把“第一块”认作热身。截取到一段中途窗口后，不能每次都无故删掉窗口第一块。

预测器还保存经验上下范围。它使用已见分块速度的分布，并加一定余量。“经验”表示范围来自有限历史观察。它能帮助控制器保守比较，但没有给出未来必然落在其中的数学保证。

### 3.1 波动大和逐渐变慢是两个问题

**波动**指同一阶段的速度忽快忽慢。把近期最慢的每步耗时除以最快值，得到一个速度比。0.025 到 0.027 的比约为 1.08，说明这一小段比较平稳。0.01 到 0.10 的比为 10，这时用一个中位数概括后续风险很大。

**漂移**指性能的基准正在移动。例如前半段每步约 0.02 秒，后半段已接近 0.04 秒。即使后半段内部很平稳，沿用早期速度也会低估等待。模块比较早段和晚段的代表速度，检查这种持续变化。

分块可能包含 CPU 准备、Python 调用、CUDA 同步和进度发布等实际开销，因此应测墙钟时间，也就是现实中过去多久。只测某个 GPU 内核会遗漏会阻塞下一条命令的其他工作。模型程序发生编译、输入增长或设备争抢时，应让这些变化体现在报告与检查中。

### 3.2 报告很旧时不能一直倒计时

假设下一块通常约 0.42 秒。报告刚过去 0.1 秒，可以把这段已过去时间用于调整当前未报告块。若 5 秒还没见下一块，可能是执行变慢、报告停了或程序卡在其他阶段。继续用“旧预计时间减去 5 秒”可能把等待错误算成零。

底层预测器按**下一整块**的经验上界检查是否过期。逐块报告的程序本来就不会每一步上报，不能拿单步时长作为失联门槛。超过允许范围时，预测进入 `overrun`，表示进度已超出当前模型的有效时间范围，剩余时间保持未知。

以上检查只回答“当前局部形态适合外推吗”。一个程序前 100 步一直稳定，之后进入很慢的评估阶段，局部预测仍可能错误。因此还需要真实完成历史。

## 4. 为什么还要等几条命令真正完成




**校准**是用之后真实发生的结果，核对之前预测得准不准。系统不能因为一条命令连续报告 100 次，就声称已有 100 条成功经验。这里至少要求同类工作有三条不同身份的命令真正完成，并拥有可比较的预测和实际时长。

每条命令第一次产生稳定预测时，保存一份原始预测作为校准边界。假设 B 在第 64 步时预测还需 25 秒，真正完成距该时刻 27 秒，这一条的误差约为 `|27 - 25| / 27 = 7.4%`。最终核对的是这份先前保存的预测。临近结束时再预测一次 0.1 秒，不能拿它替换原先的预测，从而把一个早期大错误藏起来。

“实际剩余时长”必须与保存预测的同一个边界对应。例如以保存时刻为起点，以服务真正允许下一条命令运行为终点。服务在最后一步之后仍可能同步、生成结果摘要或写文件。这些尾部时间会延迟队列释放，应计入相应的服务成本或校准结果。

假设三条独立命令各预测 25 秒，实际分别为 25、26、27 秒，误差约为 0%、3.8%、7.4%。当前报告也稳定时，这类工作才有机会通过自动门控。前三条尚未积齐的阶段，任务仍正常完成，预测只用于观察和学习。

### 4.1 用近期历史发现失准，也允许恢复

历史只保留有界的近期窗口，而不是把全部旧样本永久平均。假设已有很多次很准，但设备最近受到干扰，当前预测 25 秒，实际要 50 秒，这份新错误应该及时影响后续选择。继续拿数月前的准确记录稀释它，会让调度长期相信已经失效的模型。

“熔断”在这里指暂时停止让失准的时间预测改变放置。普通容量调度继续工作，影子预测和真实完成样本继续积累。等近期窗口中的不良记录被新的合格结果替换，条件再次满足，就可以恢复。它针对预测能力，并不要求停止 GPU 服务。

有界历史还包括两项限制：

- TTL 是 time to live，即记录的有效期。长期没有验证的画像和校准历史会过期，需要重新获得近期证据。
- 总记录数有上限。连续出现新代码版本或新输入类型时，内存中的分组和待完成记录不会无限增长。

这些校准历史保存在当前执行器的进程内存中。服务重启后会重新积累，当前模块没有把旧记录自动保存到磁盘再恢复。这样重启后的第一次自动资格也需要近期真实结果支撑。

版本改变时采用新工作身份，旧记录不会直接替新程序担保。此时需要重新校准，也就没有“刚才同名模型很准，所以新代码可以立即预测换卡”的捷径。

### 4.2 默认阈值怎样理解

以下是当前代码默认值，可以显式配置。阈值表达工程上的保守选择，需要结合工作负载再研究其收益与代价。

| 检查 | 默认要求 | 为什么需要 |
|---|---|---|
| 当前进度样本 | 跳过开头 1 块热身后至少 3 块，默认至多看近期 8 块 | 单个块不足以判断稳定性 |
| 分块速度比 | 最大每步耗时 / 最小每步耗时不超过 1.5 | 避免大幅忽快忽慢 |
| 前后段漂移比 | 前段和后段中位速度较大值 / 较小值不超过 1.25 | 避免沿用正在改变的速度 |
| 独立完成校准 | 至少 3 条同类命令，保留最近 8 条 | 重复报告不能增加独立经验 |
| 一条校准是否准确 | 绝对误差不超过 `max(0.25 秒, 实际剩余 × 25%)` | 很短的命令需要绝对误差下限 |
| 校准有效期 | 3600 秒 | 太久未确认的旧经验重新积累 |
| 历史分组和待完成记录 | 最多 128 个分组、256 条待完成记录 | 限制进程内状态增长 |
| 加载与执行画像 | 至少 3 个实际样本，最大 / 最小不超过 1.5，有效期 3600 秒 | 另一条路的成本同样要有证据 |
| 默认换卡门槛 | 预计优势超过 2 秒 | 避免为很小的点估计差额复制 |

校准要求近期窗口中每条可用记录均满足误差条件。短命令的绝对误差下限尤其容易误解：预测 0.1 秒、实际 0.2 秒，相对误差是 50%，但绝对误差仅 0.1 秒，在默认下限内仍可接受。因此判断直接使用表中公式，实际剩余为零时也无须除以零。

## 5. 模型加载与执行画像也有适用范围

预测 B 的剩余时间只解决了比较式的一部分。选择冷卡还需要知道 A 的执行成本、冷卡加载成本，以及 A 前面有没有其他排队工作。

这里有两种不同的预测输入，必须按命令当前所处位置使用：

| 命令在做什么 | 用什么估时间 | 为何如此 |
|---|---|---|
| B 已在卡上执行 | B 的当前分块进度，加同类 B 的独立完成校准，估计从现在到结束 | 已完成部分应扣除，当前速度有直接观测 |
| 新到达的 A 尚未开始 | 匹配 A 固定工作量的完整执行画像，冷卡另加加载画像 | 此时没有 A 的当前进度，需要估计整条服务 |
| C 已排队但尚未开始 | 匹配 C 的完整服务画像，按排在前面的顺序累加 | 等待 A 时必须算上这些尚未执行的工作 |

因此 A 在决定放在哪里之前，无须先启动并报告三块。它即使只有两步，只要完整画像匹配，也可以参与选择。相反，若占卡的 B 很短，没来得及产生足够分块就结束，它通常无法启用在线剩余预测。这段等待由普通放置处理。

**成本画像**指在明确定义的工作配置下，记录多次实际耗时，形成这类工作的估计。加载画像描述“尚未驻留模型到可用”的成本，执行画像描述“服务开始处理命令到可处理下一条”的完整成本。它们各自需要样本数、稳定性、有效期和工作身份约束。

当前画像对象保存耗时元组及其适用身份。元组是创建后不能就地修改的数值序列。代码能检查样本数量、范围和时间，但独立样本的真实来源仍由提供者负责。同一命令轮询三次、复制同一个耗时三次，都不能作为合格的画像采集方法。

`observed_at_s` 应对应测量证据本身的时间。对一组保留样本，使用最早样本时间是保守选择。把旧元组重新包装成一个新对象时，不能顺便填入当前时间，让已经陈旧的测量重新获得一小时有效期。

同一命令在两种 GPU 上未必同速。GPU 类型匹配只解决硬件大类，还要匹配模型和代码版本、输入类型、总工作量及运行环境。1024 步的执行画像不能原样套给 2 步命令，加载模型 A 的画像也不能替模型 B 填数。

`model_id` 还承担缓存身份：同一个名字应始终对应同一版模型和相同驻留字节。模型权重版本或大小改变时，需要新的 `model_id`。调度器与队列执行器会拒绝已见身份被重新解释。提供者负责保证 GPU 里真实驻留的内容符合声明，模块没有从显存自动计算权重版本的能力。

排队时长是当前正在执行命令的剩余时长，加上前面所有已提交命令的服务时长。服务时长还要考虑轮到那个命令时模型是否仍在。只看当前 B、忽略已经排在 A 前面的 C，会系统性低估等待。存在无法估计的前序命令时，整段等待也应保留未知。

容量仍然先检查。模型在热卡已驻留，新命令仍可能需要临时显存，称为 workspace，包含计算中间结果与算子工作区。冷卡则既要装模型，也要留 workspace。时长再有优势，也不能把容量不足的设备选进来。

另一个必要条件是**状态可重建**。可重建指目标命令能从已登记的输入和版本，在另一设备恢复相同初始状态并正确执行。例如实验训练每次重置参数和优化器，就有明确起点。若命令依赖某进程中未保存的优化器、随机状态或 CUDA 对象，简单加载一份同名模型就不足以恢复。

本模块把“允许复制一个可重建目标”与“迁移正在运行的 B”区分开。B 持续在原卡运行，当前决策只选择新命令 A 的执行位置。

## 6. off、observe 和 auto 怎样控制行为

| 模式 | 实际放置 | 预测做什么 |
|---|---|---|
| `off` | 容量安全的普通放置 | 总开关关闭，保持普通行为 |
| `observe` | 容量安全的普通放置 | 计算剩余时间预测、记录资格原因并积累完成校准 |
| `auto` | 每次满足条件才允许预测改变放置 | 未通过检查的命令自动回到普通放置 |

`observe` 也称影子模式。它在后台计算当前命令的剩余时间、检查稳定性并积累完成误差，实际放置仍走普通策略。当前接口的影子范围是时间预测和资格检查，结果不附另一种设备放置建议。它适合先确认预测误差、模型版本和报告协议。

这里的 `off` 是当前模块的普通容量与亲和策略。用户指定的历史 PSRL baseline 则是提交 `0eeead861ffafed6bf31c962d259fd847775dcf9`，需要用该版本单独运行。两者是不同的对照，不能把本模块的 off 结果记作旧提交性能。

默认 `off` 是功能总开关。用户显式开启 `auto` 后，还存在逐命令的动态判断。因此“打开模块”与“每条命令都被预测调度”是两回事。当前报告通过、历史通过、加载与执行画像通过、相关排队成本可计算、目标可重建，以及设备容量合格，需要共同成立。

普通放置优先复用满足约束的现有热副本。没有热副本时，仍可按容量规则选择合法设备并首次加载。未知时间会保存在结果里，便于区分“按普通规则安排了”与“已经算出多久完成”。这让冷启动任务在没有历史时也能推进。

自动决策还保留切换门槛。例如需要预计优势超过 2 秒才复制，避免为了非常小的预计收益承担模型加载、观测误差和额外显存占用。经验区间模式可以要求更严格的优势，详见[底层比较公式](09-动态放置_热卡等待与冷卡重建代码.md#5-类型化成本与三种放置策略)。

## 7. 把一次调度从头算到尾

以下数字全部是教学假设。已有三条 B 类命令完成并通过误差校准。现在新的一条 B 总计 1024 步，已完成 64 步，近期速度稳定，最新报告也未过期。这里简化剩余时间为 25 秒。

A 需要模型 A。GPU 0 已驻留 A 和 B，正在运行 B，A 前面没有其他排队工作。GPU 1 没有 A，且当前空闲。近期匹配画像给出 A 的完整执行成本为 8 秒，加载为 5 秒。A 声明可以从固定初始状态重建。

前面的三条独立完成校准针对 B 类剩余时间。A 的加载与完整执行画像则来自适配器提供的匹配测量。新到达的 A 还没有运行，不需要先给 A 做一段进度采样才能选卡。

### 7.1 先检查容量

模型 A 需要 20 GiB，临时 workspace 为 4 GiB。GiB 是容量单位，1 GiB 等于 1024 MiB。

| 候选 | 已有 A | 还需申请的预算 | 当前可用预约预算 | 容量结果 |
|---|---|---:|---:|---|
| GPU 0 | 有 | 4 GiB | 6 GiB | 可以执行，先排队 |
| GPU 1 | 无 | 20 + 4 = 24 GiB | 30 GiB | 可以加载并执行 |

“可用预约预算”是账本可以承诺给任务的空间，来源需要可信地覆盖既有状态和未兑现预约。一次遥测读到的空闲显存无法替代这份预算。真实执行仍要通过既有准入接口。

### 7.2 再比较从现在到 A 完成

```text
热卡完成成本 = B 剩余 25 + A 执行 8 = 33 秒
冷卡完成成本 = 等待 0 + 加载 A 5 + A 执行 8 = 13 秒
切换门槛为 2 秒：13 + 2 < 33，选择冷卡。
```

冷卡启动 A 后，两张独立 GPU 可以分别推进 A 和 B。A 大约 13 秒后完成，B 继续在原卡完成。Python 协程负责同时等待两个外部请求，GPU 并行来自两张设备各自的执行服务。协程的细节见[协程、线程与进程](09-动态放置_热卡等待与冷卡重建代码.md#3-协程线程进程与-gpu-并行)。

### 7.3 同一规则怎样处理四个变化

| 改变的条件 | 判断过程 | 实际行为 |
|---|---|---|
| B 只剩 1 秒 | 热卡 9 秒，冷卡 13 秒 | 保留亲和等待 |
| GPU 1 只有 23 GiB 预算 | 23 小于所需 24 GiB | 冷卡排除，容量优先 |
| B 的报告停了，剩余未知 | 无法可靠证明复制省时 | 回到普通容量放置，继续观察 |
| A 依赖未保存的进程内状态 | 冷卡无法保证恢复同一工作 | 保留可执行的原状态位置 |

命令结束时，把原预测边界到实际完成的时长回报给预测器。如果 B 实际还用了 50 秒，历史误差会增加，后续同类命令可能暂时失去自动资格。这样“这次看起来稳定”与“最近真正算得准”共同决定下一次。

模型 A 在 GPU 1 完成请求后可以继续驻留，因而该服务必须继续持有包含模型的 episode 预算。episode 是环境会话持有期。普通 `command_gpu` 路径则要求逐命令确认 GPU 状态实际归还。保留常驻模型的服务要使用自己的受管理生命周期，不能在后台留下显存，再按普通 command 已归还来记账。

## 8. 跟着流程读代码

源码跳转见第 1 节图例。按下面的路径区分判断、并发与实际资源生命周期。

| 阅读顺序 | 重点看什么输入、分支和状态变化 |
|---|---|
| `submit → _snapshot → _admit` | 取得物理观察后核对队列版本号没有变化，在互斥范围内计算决策并入队。观察期间若有别的入队或完成，最多重新观察三次，持续变化则明确报重试错误 |
| `plan → _view → assess` | 已提交工作组成设备队列，当前命令报告产生可用预测或明确原因，前序未知工作让总等待保持未知 |
| `plan → _fallback` 或底层 `decide` | off 和 observe 使用普通放置，auto 先检查可重建与匹配画像，再决定是否有时间比较资格 |
| `_run_device → provider.execute → _progress` | 同卡串行，不同卡独立。提供者回调进度，软件锁只保护状态，耗时执行留在锁外 |
| `_complete → finish` | 成功返回确认完整工作，按首次预测边界计实际剩余，写入独立完成历史，再让下条命令开始 |
| `aclose → _close → provider.aclose` | 停止接新工作，取消并有限汇合所属观察和执行，提供者确认物理清理，失败则保留错误 |

“队列版本号”是每次队列状态变化时递增的计数，对应源码中的 `_generation`。例如查询物理状态前记住 7，查询返回后发现已变成 8，说明期间有人提交或完成过工作，刚才的物理观察可能已不对应当前承诺。此时重新观察，而不是拿旧预算继续分配。

“原子提交”在这里表示相对于同一执行器中的其他提交，检查与入队不能被穿插。例如两条新命令同时看到冷卡有足够预算，若各自检查后不立即登记，就可能一起承诺过多模型。执行器用 `asyncio.Lock`，即协程间互斥锁，让形成软件队列快照、决策与登记连成一个受保护步骤。

提供者的物理观察和耗时执行都在锁外等待，并给观察设置超时。每张卡有自己的串行工作协程，同卡命令按队列顺序处理，不同卡可以同时等待各自的外部执行。这样一条长 GPU 工作或一次慢设备查询，不会因为持有全局 Python 锁，让另一张卡的进度上报和完成回调也停住。

`ManagedCommandProvider` 用 `Protocol` 表达接口协议。接口协议描述调用者需要哪些方法及其含义，具体实现仍要连接真实服务或测试执行端。`device_snapshot` 返回物理模型驻留和可承诺预算，`execute` 执行完整工作并回调进度，`aclose` 负责停止所属工作、释放资源并确认结果。这些声明需要提供者兑现，调度器不会凭一个方法名认证物理 GPU 已清理。

高层接入在一个服务生命周期内复用同一调度器与执行器，才能积累历史。下面是嵌入既有 `async` 启动函数的调用示意，`provider`、`request`、`profiles` 与 `payload` 由具体适配器提供。`async` 函数是可以在等待处暂停的协程函数。

```python
from psrl.workers.env_service.managed_command import ManagedCommandDispatcher
from psrl.workers.env_service.predictive_scheduler import PlacementConfig, PredictionAwareScheduler

scheduler = PredictionAwareScheduler(PlacementConfig(mode="auto"))
async with ManagedCommandDispatcher(scheduler, provider) as dispatcher:
    result = await dispatcher.submit(request, profiles, payload)
    print(result.decision.reason, result.value)
```

配置行选择 `auto`，用 `off` 或 `observe` 替换字符串即可改变模式。`async with` 把执行器的整个使用范围包起来，离开范围时调用 `aclose`。`submit` 接收结构化请求、逐设备成本画像和原始执行负载，等待后得到真实提供者结果及本次实际决策。服务应在这个范围内连续提交自己的多条命令，结束时统一关闭，完整可运行写法见下一节脚本。

这些源码位置都可以直接跳转。任何一段代码或其中的前置知识有理解上的问题，都可以随时继续逐行拆解。

下面是可直接使用的低层接口示例，全部数字是教学数据。完整异步接线由下一节脚本展示。

```python
from psrl.workers.env_service.command_prediction import (
    CommandRuntimePredictor, CommandSpec, StepProgress, WorkloadKey,
)

key = WorkloadKey("code-v1", "weights-v1", "batch=2,shape=fixed", "H20", "runtime-v1")
spec = CommandSpec("attempt-1", key, "model-A:weights-v1", 100, relocatable=True)
progress = StepProgress("attempt-1", key, 100, 40, (10,) * 4, (1.0,) * 4, 0.0)
predictor = CommandRuntimePredictor()
assessment = predictor.assess(spec, progress, now_s=4.0)
print(assessment.reason, assessment.forecast.estimate_s)
predictor.finish(
    spec, succeeded=True, completed_steps=100, actual_remaining_s=6.0, now_s=10.0,
)
```

`key` 固定这一类工作的身份。`spec` 登记一次尝试，共 100 步，允许从相同起点重建。`(10,) * 4` 生成四个 10 步块，`(1.0,) * 4` 表示各耗时 1 秒，已完成 40 步。跳过首块后仍有三块，每步 0.1 秒，剩余 60 步，得到 6 秒预测。

首次输出为 `insufficient_calibration 6.0`，意思是可以算出影子时间，但尚无足够完成校准。`finish` 再说明从保存边界起实际用了 6 秒，并且全部 100 步成功完成，这才增加一条独立记录。后续尝试必须使用新的 `command_id`，重复打印同一报告无法让计数从一增加到三。

如果等待 `submit` 的调用者取消，`asyncio.shield` 会让执行器继续拥有已入队工作，调用者停止等待并没有释放 GPU。需要结束整个服务时调用 `aclose`，并核查提供者的清理结果。它给清理设预算，超时或物理释放无法确认时会报错，避免软件队列已退出却继续把设备当作可复用。

### 9.1 CPU 教学演示

在仓库根目录、已激活项目环境后运行：

```bash
PYTHONPATH=. python docs/env-worker-deep-dive/env-service-verification/scripts/command_predictability_demo.py
```

脚本使用真实 `ManagedCommandDispatcher`、门控与放置模块，提供者用确定的教学数据模拟进度和完成。它注入一个可控制的时钟，避免用真实等待 8 秒来展示 8 秒成本。注入表示把时钟作为函数参数传入，模块调用它获取当前时间，测试即可精确控制时间前进。

有校准准备的案例先通过同一执行器，顺序提交并完成三条不同身份的 B 类命令。observe 和 auto 据此积累历史，off 跳过预测与校准，即使完成这三条准备命令也不产生历史。缺少历史的 auto 案例则省略准备。正式案例中，B 共 100 步，完成 40 步，四个分块各 10 步、1 秒，剩余 6 秒。A 执行 2 秒，冷卡加载 1 秒。因此热卡需要 `6 + 2 = 8` 秒，冷卡需要 `1 + 2 = 3` 秒，超过 2 秒切换门槛。预期观察为：

| 教学案例 | A 放在哪里 | A 的教学完成成本 |
|---|---|---:|
| `off` | 热卡 | 8 秒 |
| `observe` | 热卡，额外积累预测校准 | 8 秒 |
| `auto`，校准齐备且当前稳定 | 冷卡 | 3 秒 |
| `auto`，缺少完成历史 | 热卡 | 8 秒 |
| `auto`，当前分块速度不稳定 | 热卡 | 8 秒 |
| `auto`，进度报告过期 | 热卡 | 8 秒 |

2026-11-16 已实际运行，六个案例的内置断言通过。表中的秒数是教学时钟下的模拟成本，脚本无须等待这些真实秒数。它验证数据确实经过项目模块的队列、进度回调和决策分支，不启动模型、容器、Ray 或 GPU，也没有测出新的 GPU 加速百分比。

### 9.2 固定步数 GPU 服务接入

专用入口 [guarded.py](../../env-service-verification/scripts/warm_router_study/guarded.py#L133)把新增模块接到已有的真实 PSRL 实验服务。它通过 EnvRouter 申请 episode 租约，由原生 EnvWorker 创建两个模型服务，再把请求交给 `ManagedCommandDispatcher`。默认 `--mode off`，显式传入 `--mode auto` 才允许逐命令预测决策。

适配器 [FixedStepServiceProvider](../../env-service-verification/scripts/warm_router_study/prediction_provider.py#L22)连接现有 socket 请求协议。RPC 是 remote procedure call，即向另一个进程或服务发请求、等待结果的调用方式。这里的服务在同一节点，通过 socket 交互。适配器先探测空缓存、显存预约预算、模型大小和 workspace，再登记不可变模型身份。已有[服务训练入口](../../env-service-verification/scripts/warm_router_study/server.py#L59)让每条命令恢复相同初始参数和优化器，因此可以在另一张卡重建目标命令。

忙碌服务的 socket 是串行处理的。若为了查状态向正在训练的服务再发一个 `ping`，查询本身就会排在训练后面，无法及时帮助选择。因此适配器从已确认的响应维护驻留账本，忙碌时通过本地原子进度文件观察，而软件队列继续登记正在加载和等待中的预约。这个协议要求两个服务由本次执行器独占管理，外部程序不能绕过它清空或修改模型。

入口按以下顺序执行：

1. 在两张卡上分别执行三条独立的冷启动 A 命令，步数与本次目标完全相同，测完整加载和服务成本，然后清空模型。
2. 初始化提供者，先以 `observe` 顺序完成三条 B 命令，得到真实剩余时间校准。为热卡准备 A 的模型副本。
3. 切换到用户指定的模式。正式提交 B，等它至少完成 80 步后提交 A，让新增门控选择排队复用或冷卡重建。
4. 两条请求都完成后保存决策、目标延迟与两命令总耗时。画像和校准属于准备阶段，单列 `guarded_preparation_s`。正式主计时从提交 B 前开始，到 A、B 两份响应均返回为止。
5. 提供者停止本次容器并核验设备释放，外层实验负责归还本次 Router 租约和最后收尾。失败响应或身份不一致也进入所属物理资源清理。

代码里“至少完成 80 步”是有界实验的到达规则，每 16 步报告时已有五块。它给完成校准和当前分块检查一个自然的观察点，仍可能因速度变化、画像不足或时效检查而保留亲和。它没有承诺本次一定换卡。

准备也会消耗 GPU 工作。完整入口共执行 8 条 A 类命令和 4 条 B 类命令：6 条 A 做逐卡画像，1 条 A 准备热副本，3 条 B 做校准，最后才是正式 A、B。声明的总更新数为 `8 × target_steps + 4 × blocker_steps`。报告把准备与正式计时分开，评估实际使用收益时仍应计算这些准备成本能够被后续多少命令摊薄。

下面是运行形状。尖括号字段必须替换为现场核对的值。先阅读[集群预检](../../../psrl/psrl-run-guide/02-集群预检_依赖地址与GPU资源核验.md#集群踩坑总表与最小复现2026-10-13)，激活项目环境，在目标执行节点确认两张独立空闲 GPU、Docker/CUDA、依赖来源和本地短路径。`<asset-directory>` 需要包含两个 Qwen3 模型与既有公开输入文件，不能只创建空目录。

```bash
PYTHONPATH=. python docs/env-worker-deep-dive/env-service-verification/scripts/warm_router_study/guarded.py \
  --root '<new-output-directory>' --assets '<asset-directory>' \
  --python-prefix '<driver-environment-prefix>' --container-python '<container-python-path>' \
  --node-ip '<verified-node-ip>' --gpus 0 1 --image '<verified-image>' \
  --budget-s 900 --target-steps 1024 --blocker-steps 2048 \
  --target-version '<immutable-target-revision>' --blocker-version '<immutable-blocker-revision>' \
  --mode auto
```

`--root` 必须是新的输出目录，`--budget-s` 是包括准备在内的工作预算，例子的 900 秒是运行预算示意，实际准备可能在该预算内无法完成，届时保留未完成结果。`--target-version` 和 `--blocker-version` 要标识本地真实权重版本，不能用不断变化的同名目录冒充固定版本。比较 off、observe、auto 时分别使用新的输出目录，保持相同工作量和资源条件。

当前适配器限于这套同机、同型号双卡、固定输入、固定步数、可重建的模型服务，两个服务的运行环境也要一致。它要求本地进度文件与 driver 使用同一主机的单调时钟，执行返回要确认命令身份、模型、完成步数、优化器更新数和驻留字节一致。独立[物理清理回调](../../env-service-verification/scripts/warm_router_study/guarded.py#L68)只处理本次资源。本次完成的是源码接线和 CPU 协议验证，尚未在 GPU 上运行这个新入口。

## 11. 当前 benchmark 中哪些值得使用这套机制

benchmark 是用来比较方法的一组任务和评价规则。本节判断的是**当前本地接入程序里的 GPU 工作**，不把某一类工作的机会扩展成整个上游题库已经获益。这里的收益首先指相同工作量更早完成、Agent 更早得到反馈。任务得分、模型质量和 PSRL 整体训练速度需要各自的实验。

**当前证据最强的是 PostTrain 衍生的固定步数长等待负载。** MLGym 的冻结 BERT 分类任务、RE-Bench Rust 的固定模型评分调用是值得继续核查的候选。InferenceBench 需要进一步拆分请求阶段。KernelBench、FlashInfer-Bench、FastKernels 的当前接入更接近编译、准备复用与干净测量问题，尚无这套预测换卡机制的直接收益证据。

### 11.1 已测到收益的是哪一种 PostTrain 场景

[历史 GPU 对照](../../experiments/gpu-benchmarks/04-动态放置_热卡等待与冷卡加载对照.md#3-results什么时候值得换卡)使用两张同型号 GPU，通过真实 PSRL EnvRouter / EnvWorker 执行固定工作。A 使用 Qwen3-4B，B 使用 Qwen3-1.7B，输入固定为两个公开 GSM8K 样本，只更新模型末层的一小组缩放参数。每条命令恢复相同初始参数和优化器，因此可以从另一张卡重新开始执行。它是从 PostTrain 提取的受控工作负载，不是自然 Agent 已完成了多种题目的完整研究过程。

下表每格是三次运行的平均秒数，统计从提交 B 前到 A、B 都返回。准备和画像另计。直接等待指始终复用热卡，预测选择指根据 B 的剩余进度决定是否到冷卡加载。

| 场景 | A / B 更新步数 | 直接等待 | 预测选择 | 证据支持的结论 |
|---|---:|---:|---:|---|
| 小目标 | 2 / 128 | 3.54 | 3.54 | 无明显增量收益，避免额外加载即可 |
| 短等待 | 1024 / 128 | 37.03 | 36.80 | 耗时接近，不能据此称为稳定优势 |
| 临界等待 | 1024 / 512 | 46.64 | 47.02 | 预测选择慢 0.81%，边界附近无稳定优势 |
| 长等待 | 1024 / 2048 | 86.11 | 52.80 | 整组耗时减少 38.69% |

长等待相对固定旧 PSRL 提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 的 85.29 秒，耗时减少 38.10%。同一长等待条件下，始终复制约为 52.75 秒，与预测选择接近。预测策略的价值是跨场景选择：长等待时复制，短等待时保留模型，避免小目标被加载成本拖慢。四类场景各出现一次的人工组合相对直接等待减少 19.14%，这个数字不代表自然 benchmark 的平均收益。

这些 GPU 数字属于 2026-11-13 冻结的低层策略。第 9.2 节新增的资格检查和受管理服务入口仅有 CPU 协议验证，不能把旧数字写成新增 `auto` 门控已经实机复测的结果。

### 11.2 逐题库判断与尚缺的接入

表中“候选”表示源码提供了可能适合的计算结构，尚未证明自然任务能获得净收益。冻结参数指执行训练时不更新这些权重。前向计算指输入经过模型得到输出或损失的计算过程，损失是模型输出与给定目标之间的差距。

| **FastKernels** | [当前每次子进程测一个 shape，预热一次、两次迭代、两轮](../../../../examples/fastkernels_bench/verify.py#L42)。shape 是张量各维度的大小 | **暂不优先。** 当前工作很短，主要是编译与测试准备，尚无昂贵常驻模型及预测复制收益证据 |

InferenceBench 还需单独看评分边界：[当前场景性能计时在服务就绪之后开始](../../../../examples/inference_bench/scenario_verify.py#L66)，所以降低服务加载耗时不自动意味着该性能分提高。

这张表的共同前提是：热卡真的有排队，另一张卡有满足预算的空闲容量，且目标命令能从确定状态重新执行。只有一张可用 GPU、冷卡显存不够、任务独占全卡或无法重建时，即使时间预测准确，也没有本机制的换卡收益。

### 11.3 为什么命令更早返回不等于整组大幅提速

**教学假设，以下数字不是实测。** B 占着热卡，还需 50 秒。A 使用已驻留模型，只计算 0.1 秒，但到冷卡加载需要 5 秒。冷卡空闲，两个命令之间没有数据依赖，也不相互干扰。

| 选择 | A 从到达到返回 | 从 A 到达起，A、B 都完成 |
|---|---:|---:|
| 等热卡 | `50 + 0.1 = 50.1` 秒 | 50.1 秒 |
| 冷卡加载 | `5 + 0.1 = 5.1` 秒 | `max(50, 5.1) = 50` 秒 |

A 少等了 45 秒，Agent 可以更早继续思考，但整组只少用 0.1 秒，约 0.2%。如果 A 自己要计算 30 秒，冷卡路径为 35 秒，整组则从 80 秒降至 50 秒，才有 37.5% 的整组耗时下降。区别在于有多少真实计算能与 B 重叠。

在上述简化条件下，令 B 的剩余时间为 `R`，A 的执行时间为 `E`，冷卡加载时间为 `L`，则：

```text
等热卡，整组时间 = R + E
冷卡执行，整组时间 = max(R, L + E)
整组节省 = min(E, R - L)
```

这说明三个量都重要：`R > L` 才有加载换等待的机会，`E` 决定单组能节省多少重叠时间，额外显存决定冷卡路径能否成立。真实多命令队列、共享设备干扰、清理和准备成本还要另算，不能把这个两命令教学公式当成全局最优保证。第 1 节图中的 P3、P4 分别对应预测资格与成本决策，具体模块、执行路径和可运行 CPU 演示见第 8、9 节。若读这些源码时有不理解的地方，可以沿图中编号继续追问。

### 11.4 如何选择下一组有意义的验证

当前合理顺序是先查 **PostTrain 的真实固定工作量命令**，再考虑 **MLGym MNLI** 与 **RE Rust 的固定输入评分工作**。不是把默认两步人为拉长后再次宣布同一种受控收益，而是检查自然任务是否确实反复提交相同计时条件的 GPU 工作，是否同时出现热卡长排队和另一卡可容纳副本。

当前门控默认需要至少三条同类独立命令的完成校准，工作身份包含代码、模型、输入、设备和运行环境，且总步数也必须匹配。如果 Agent 每轮都改代码、长度或配置，旧数据不能自动当新工作的保证。能预测的计算结构存在，不等于实际提交序列中有足够的同类历史。专门运行画像和校准也要消耗 GPU，只有后续复用足够多次才能摊薄准备成本。

下一组对照应保留同样的候选、输入、工作量、显存预算和合法进程复用，同时记录：

1. **覆盖率**：满足契约的命令占多少，消耗的 GPU 时间又占多少。不能用已接入题数或 quick-check 通过数代替。
2. **机制是否触发**：热卡剩余等待、冷卡加载、目标执行、可用显存、门控是否允许预测，以及最终选卡原因。
3. **收益在哪个计时范围**：每条命令反馈时间、整组完成时间、准备与副本清理、最后才是整个 Agent 或 PSRL 训练时间。
4. **强简单对照**：现有容量安全的模型亲和策略、始终复制，以及用户指定固定旧 PSRL 提交。新增模块的 `off` 是第一种对照，不等于固定旧提交。

目前尚未得到这些条件在自然 Agent 轨迹中的完整分布，因此不能给出“整个现有 benchmark 平均能提升多少”或“多少题必定获益”的百分比。本节完成的是源码与既有实验复核，没有新增 GPU 运行，也没有把新门控的 CPU 通过结果计为 GPU 性能证据。
