## 1. 全局流程与审查范围

```text
[1] runner / 训练启动方 → 创建或复用 EnvRouter
                              ↓
[2] 节点健康检查 → Ledger 准入 → 会话绑定 unit
                              ↓
[3] native EnvWorker / Compose 创建容器 → 提交受管 GPU 作业
                              ↓
[4] direct 命令队列 或 MPS 作业队列 → 设备授权 → GPU 执行
                              ↓
[5] 结果 / 评分 → 撤权与物理回收 → 归还预算
                              ↓
[6] 故障分支：暂停准入、隔离未确认资源 → 重试清理或人工恢复
```

## 3. 优先解决的工程问题

优先级是本次建议：P1 表示扩大使用范围前应补齐，P2 表示在现有受控范围内可继续使用但会限制效率或长会话。没有将本次未复现的风险写成线上事故。

### R1：同名 Router 复用配置核对，已实现待部署

`create_env_router` 创建或复用命名 actor 后，先读取服务启动时保存的配置契约，再与本次预期比较。契约包含声明配置、训推节点身份和协议版本，同时比较规范化结构与 SHA-256 指纹。不一致或旧服务没有契约接口时明确拒绝，不继续预热、不热改活动服务。

这里采用严格声明配置比较，字典键顺序被规范化，训练节点集合排序去重。省略默认项与显式默认值可能仍被拒绝，不宣称支持任意语义等价配置。应从同一份解析配置启动复用客户端。

源码见 [router_contract](../../../psrl/workers/env_service/router_contract.py#L10) 和 [创建入口](../../../psrl/workers/env_service/router.py#L752)。CPU 测试覆盖同配置复用、预算、后端、设备、节点身份、协议差异，以及缺契约接口和预热前拒绝。真实双 driver 集群部署未在本次运行。

### R2：节点只读诊断与受控恢复，已实现待部署

新增 [node_diagnostics](../../../psrl/workers/env_service/router.py#L581)，列出健康错误、重试耗尽、活动租约、退休待清理租约、阻断 unit、GPU 命令及旧借卡阶段。新增 [recover_node](../../../psrl/workers/env_service/router.py#L605)，允许管理员在耗尽后重新发起一次有超时的物理检查，并共享已在途探测。重试次数重开后，常规路径仍受原自动预算限制。

恢复不会直接清空资源字典或 GPU 隔离。节点查询成功和物理清理确认仍为不同条件，`healthy` 不保证全部任务获准。死节点仍有活动归属时保留旧句柄，孤儿 MPS 服务仍需人工处理。CPU 回归覆盖继续失败、超时、待清理、并发调用和活动归属保护，未进行真实 GPU 故障注入。

两个问题的初学者背景、完整例子、调用图和可运行实验见[配置复用与节点恢复](router-configuration-and-recovery.md)。R3 的重启持久化和跨控制器所有权不属于这两个入口的修复范围。

### R3：Router 重启与跨 Router 设备唯一所有权，扩展部署前 P1

**确认的架构边界。** 账本的租约、待清理记录、预算和测量保存在内存字典，见 [EnvUnitLedger.__init__](../../../psrl/workers/env_service/ledger.py#L66)。一个账本内校验配置，不等于不同 Router、不同 Ray 集群之间有统一设备所有权。

教学例子：A、B 两个独立 Router 都配置同一张 80 GiB GPU，各自在尚未实际分配显存时承诺 60 GiB。单个账本均未超额，但总承诺达 120 GiB。实测显存不能替代跨控制器的预约协调。本次未运行双 Router GPU 竞争实验。

如果仍是一套受控实验独占资源，可先明确单控制器部署约束。若要支持多用户或长期服务，则需要设备所有权协调、可恢复的租约状态，以及防止旧控制器在失去所有权后继续授权的代际凭据。不能只添加自动重启。

### R4：MPS 服务故障与真实接入证明仍缺验收，P1 验证项

`launch` 检查容器身份、IPC 和管道挂载，配置 MPS 环境后放行作业。它没有在运行期间持续证明该客户端仍由目标 MPS 服务管理。参见图中 4 和 [MPS 的故障边界](mps-parallel-execution.md#8-原理与当前效果应该怎样理解)。这是已知验证缺口，不能写成“已经测出静默退回普通 CUDA”。

建议先限定环境专用卡，覆盖服务在启动前消失、连接过程中失联、执行中退出、取消回执缺失四类故障。验收看作业是否明确失败、预算是否保留、相邻作业是否受影响、最终物理释放是否确认。还要保留 cgroup v1、可信任务域、客户端显存限额按进程生效等限制，不把该实现当作恶意多租户隔离。

### R5：严格队首准入会闲置可用资源，P2

direct 的 [acquire](../../../psrl/workers/env_service/command_gpu.py#L106) 和 MPS 的 [admit](../../../psrl/workers/env_service/parallel_gpu.py#L208) 都先找队首，后来的请求不能越过它。同机命令池共用一个 FIFO，并不是每张卡独立队列。FIFO 指先进先出，这是确定的策略，不是竞态或账本错误。

教学例子：unit 总预算 80 GiB，活动作业占 50 GiB。队首先来一个需要 40 GiB 的 A，后面 B 只需要 10 GiB。A 放不下，B 虽然放得下也要等，30 GiB 余量暂时闲置。MPS 并发机制无法自动解决这个上层排队问题。

建议考虑有限回填：允许能放下的小任务先运行，同时限制绕过次数、等待年龄或为队首保留容量，避免大任务一直等不到。是否缩短整组完成时间必须用相同工作量验证，不能仅看瞬时 GPU 占用。目标仍可保持整组反馈完成时间，不必另引入公平性优化目标。

### R6：作业数量上限是会话累计值，P2

[GpuJobManager.start](../../../psrl/workers/env_service/gpu_jobs.py#L61) 根据 `len(self.jobs)` 限制默认 128 项，已完成作业仍保留。MPS `submit` 也按同 lease 的累计记录数限制 128 项，见 [submit](../../../psrl/workers/env_service/parallel_gpu.py#L133)。所以即使每次只跑一条，第 129 次提交也会被拒绝。这是有意的有界保护，不是已确认内存泄漏。

短 episode 通常不会触发，但长会话或持久执行器池需要明确产品契约。若支持更长会话，应把活动上限与历史保留上限分开，提供终态确认和有界归档，保留去重与取消所需身份，不能直接删除所有完成记录或无限调高上限。

## 4. 后续能力与验证缺口

| 方向 | 当前状态 | 建议 |
|---|---|---|
| 自动 command/episode | 静态配置，部分任务有显式 command 接入 | 先建立任务能力声明，说明是否常驻 GPU、命令边界是否可靠、是否可重跑 |
| episode 自动卸载与恢复 | 没有通用实现 | 先选支持显式保存恢复的一个真实任务，测保存、加载、重建成本，再决定是否让位 |
| 下一条命令换卡或跨节点 | 显式同机 `command_gpu_pool` 已支持专用单卡 direct command 重新选卡。主机 unit 保留，GPU 按候选 unit 记账。跨节点、MPS 池、模型共享卡和活 CUDA 状态迁移不在该实现范围 | 不再把同机换卡列为未实现。先补完整 runner 与训练验收，再评估跨节点所需的数据和执行协议，见[动态放置](../research-proposals/dynamic-command-placement.md#11-已实现的同机命令池与资源账本) |
| MPS 自动选择并发数 | 准入关注容量，没有预测并发吞吐收益 | 先记录排队、初始化、执行、回收分段耗时，再做小规模任务特征分析 |
| 性能评分与并发干扰 | KernelBench command 已限制为专用 direct | 不为提高吞吐拆掉评分隔离，正确性评分和计时评分分开处理 |
| vLLM 共卡 | 有显式共享和睡眠借卡分支 | 环境专用 MPS 验证不能替代真实训推共存与模型性能边界验证 |
| 原请求跨 worker 重派发 | 有重试与补采，缺完整转移协议 | 先确认旧执行终止，再引入尝试身份、旧结果隔离和有界重跑 |
| 多节点派发吞吐与长期运行 | 有健康过滤、容量与负载偏好 | 不能将源码接入或单卡组件验收等同于长期多节点收益 |

已有 MPS 真实训练证据是训练段约一成收益，短流程整体不一定更快。高显存压力下减少 OOM、MPS 计算共享、完整训练提速是三个不同结论。具体数字继续以[实验报告](../experiments/mps-training-comparison.md)为准，不为 review 追加训练。

## 5. 建议修复包与验收条件

1. **配置与恢复入口**：R1、R2 本地实现已完成。配置不一致明确报错，节点故障有可读原因，恢复经过新的物理核对。下一步在真实部署中按相同边界验收。范围有限、能直接降低下一次实验误判和人工排障成本。
2. **MPS 故障矩阵**：处理 R4。先补服务失联和清理回执缺失验证，再根据失败点修改实现。不是先增加并发数。
3. **长会话与队列效率**：有实际需求时做 R5、R6。保护大任务，同时验证整组完成时间和有界历史存储。
4. **长期或多用户部署基础**：启用该部署目标前必须完成 R3，不能排在跨节点大规模实验之后。
5. **动态调度研究**：建立能力声明和分段成本数据之后，再推进自动模式、动态放置和卸载预测。把新策略与故障恢复分开验收。

没有要求现在把这些全部实现。用户可以按近期目标选修复包，单控制器实验与多用户服务的优先级不同。

## 8. 对照阶段路线图后的当前工作顺序

[2026-10-28 路线图](../milestones/env-status-and-roadmap.md)是固定阶段报告，其中“同容器并发尚未完成”等结论不能作为今天的实施清单。MPS 后端同容器并发已实现，direct 串行是该后端的语义。原生 GPU 接入已有后续代表任务证据，但不能推广成全部任务、全部评分和完整训练已验收。此次只修订工程审查的当前判断，不重写历史实验条件。

| 建议顺序 | 做什么 | 最小验收 |
|---|---|---|
| R1 已在本地完成 | 部署前核验命名服务升级与配置契约 | 同配置可复用，预算、后端或设备身份不同明确报错，不热改活动租约 |
| R2 已在本地完成 | 部署前核验节点诊断与人工恢复 | 重试耗尽后可受控恢复。清理不确定仍隔离，不通过清空账本放行 |
| 使用 MPS 前补 R4 | 服务启动、连接、执行与清理各阶段的故障验收 | 服务失联不会被当作正常成功，旧作业归还可核实，不误杀其他作业 |
| 长会话需求出现时做 R6 | 区分活动作业上限和历史保留上限 | 顺序完成 128 条后允许按契约继续，存储仍有界，旧请求身份可追溯 |
| 有混合负载时做 R5 | 有限回填与大任务等待保护 | 固定工作量下减少队首阻塞，不能让大任务无限等待 |
| 多控制器或长期部署前做 R3 | 可恢复租约、设备所有权和代际隔离 | 新旧控制器不能双重授权同一设备，重启后先核实遗留物理资源 |

R3 在单控制器独占实验下可先作为部署约束，但多用户或多 Router 部署时必须提升为前置项。优先级不表示已观察到生产事故。自动模式和卸载预测属于后续能力，不应为了做它们而绕过恢复与物理归还。

另需保留三类独立验收：完整 Harbor runner 走同机命令池的闭环、环境与真实训推共卡的峰值及性能边界、代表任务的真实评分与可重现资产。已有组件探针与历史训练各自有效，不能拼接成未经运行的完整部署结论。基准版本仍固定为 `0eeead861ffafed6bf31c962d259fd847775dcf9`，当前代码关开关不能替代。

## 9. 从训练执行链理解剩余工作

这里将“一次训练、一道题、一条 rollout、环境租约”沿用[调用链入门](router-configuration-and-recovery.md#11-启动方题目rollout-与环境申请)的含义。不是重新把每条 rollout 当作 Router 启动方。全局图和源码映射见第 1 节，从创建、账本、作业队列、执行到清理的阅读路径见第 6 节。

**当前状态有三类。** R1/R2 的代码与 CPU 回归已经有了，但真实服务升级验收尚待完成。R3 至 R6 是仍保留的架构边界、故障验证缺口或使用限制。自动模式、任意程序卸载和跨节点迁移是新增能力，不能算成已经承诺却完全失效的功能。

| 位置 | 剩余工作 | 影响与触发条件 | 怎么才算完成 |
|---|---|---|---|
| Router 创建和节点恢复 | R1/R2 真实部署验收 | 本地代码存在，不表示运行中的旧服务自动升级 | 真实服务同配置复用、异配置拒绝。节点耗尽后可受控重新检查，清理未确认不放行 |
| 共享账本和控制器生命周期 | R3 重启恢复及跨 Router 设备所有权 | 同一物理 GPU 被两个独立账本管理，或重建 Router 时原执行尚未清理 | 先恢复归属并核实遗留资源，再开放准入。旧控制器失权后不能继续授权 |
| MPS 启动、运行和取消 | R4 服务异常验收 | 使用多进程服务 MPS 在一张 GPU 上执行多个作业，服务途中失联 | 明确报告失败，未确认资源继续保留预算，取消一个作业不误伤其他作业 |
| GPU 命令准入队列 | R5 队首阻塞 | 大小请求混合时，队首需求超过剩余容量 | 有界允许小请求回填，同时保护大请求。用相同工作量检查整组完成时间 |
| 每环境 GPU 作业管理 | R6 活动作业与历史记录上限分离 | 一个环境会话中累计提交很多 GPU 命令 | 完成记录有界归档，活动上限独立计算，旧请求去重与取消仍有依据 |

**R3 为什么与 R1 不同。** R1 检查的是“找到同名旧服务时，规则是否相同”。R3 检查的是“谁有权管理物理设备，以及服务重建后如何找回原账”。不同名称或不同集群的两个 Router 不一定共享状态，因此 R1 不能代替 R3。

教学假设：一张卡容量 80 GiB，Router A 为尚未实际分配显存的工作预约 60 GiB，Router B 又用自己的账本预约 60 GiB。每本账都只看到 60，但总承诺已经是 120。即使配置完全相同，这个问题依然成立。真实系统还有实测显存和归属检查，因此这个算例说明架构风险，不证明实际生产已经批准这种超额请求。

另一个分支是 Router 重建。旧容器可能还在运行，新建空字典不能证明它们已消失。要解决它，需要保存或重建租约归属，并在重新调度前核对真实执行状态。更进一步，控制器每次接管设备应具有可识别的代际凭据，例如新控制器使用第 8 代，节点拒绝旧第 7 代的授权。这是设计方向，当前没有完整实现这套跨控制器协议。

单控制器、明确独占资源的受控实验，可以先把“不让第二套 Router 管同一张卡、异常后人工清理再重建”作为部署约束。如果目标改为长期服务、多用户共享或自动重启接管，R3 就应先做，不能依赖这个实验约束。

**R4 为什么先做故障实验。** MPS 是 NVIDIA 提供的多进程 GPU 服务，使多个 CUDA 客户程序通过服务共享 GPU 执行。CUDA 是程序使用 NVIDIA GPU 的运行接口。当前已有启动条件核对、按作业取消和清理保护，但没有完成服务在启动前、连接中、执行中消失，以及取消确认丢失的完整真实验收。正常运行成功不能回答这些异常下是否正确归还。也不能反过来把尚未验证写成已经发生过静默错误。

验收应观察四件事：调用方是否收到明确失败，未清理的预算是否继续保留，其他作业是否仍正常，最后相关进程、容器及显存是否确实释放。不是只看服务能否重新回答一次请求。MPS 的 [launch](../../../psrl/workers/env_service/parallel_gpu.py#L267) 与 [cleanup](../../../psrl/workers/env_service/parallel_gpu.py#L342) 是对应入口。

**R5 是效率问题。** 教学假设：容量 80 GiB，当前活动作业占 50，剩 30。队首 A 要 40，后面的 B 只要 10。严格先进先出时 A 等待，B 也不能越过 A，所以还有 30 的余量却不能运行 B。这叫队首阻塞。有限回填允许 B 暂时使用余量，但必须限制绕过次数或保留资源，否则持续到来的小任务可能让 A 一直等待。当前判断见 [direct 队首](../../../psrl/workers/env_service/command_gpu.py#L106) 与 [MPS 队首](../../../psrl/workers/env_service/parallel_gpu.py#L208)。这不是账本算错，也不等于已经证实训练瓶颈在此处。

**R6 是会话内累计限制。** 作业就是一次受管理的 GPU 命令。当前 [GpuJobManager.start](../../../psrl/workers/env_service/gpu_jobs.py#L61) 默认最多保留 128 项，[MPS submit](../../../psrl/workers/env_service/parallel_gpu.py#L133) 也限制同租约累计 128 项。因此同一环境里顺序执行 128 条、每条都结束，活动数虽然为 0，第 129 条仍可能被拒绝。这个限制不是整个训练只能产生 128 条 rollout，也不是同时只能运行 128 个环境。MPS 在[租约释放](../../../psrl/workers/env_service/parallel_gpu.py#L408)时会移除该租约的作业记录，问题范围是一个仍在使用的长会话。

要支持长会话，需要区分“正在占资源的数量”和“为查询、去重、取消保留的历史数量”。去重表示同一个请求重发时不能重复执行或重复记账，所以不能简单把所有完成记录删除。

**近期顺序。** 按继续受控单控制器实验的目标，先完成 R1/R2 真实部署验收，再补 R4 故障矩阵。确实需要长会话时做 R6，出现大小任务混合的排队负载时做 R5。若近期目标转为长期共享服务或多 Router，R3 提升为前置项。这些是按使用目标给出的建议，不是已经开始执行的任务。

同机自动换卡的公共能力、完整 Harbor runner 接线、真实训推共卡和评分任务验收仍应分别看待。同机 direct 命令池已有组件与真实 Ray 证据，不应重新列成完全没实现。已接入代表题也不表示全部题目与全部评分都通过。当前设计入口的对应能力表仍有效，本次只增加剩余工程工作阅读入口。
