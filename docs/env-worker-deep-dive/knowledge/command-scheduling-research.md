# 面向 rollout 组完成时间与反馈保真的 GPU command 调度研究

> **核心结论**：固定一组 rollout、要求全部完成时，目标是整组最后一个有效结果的返回时间。公平性不是独立优化目标。可做小规模可行性验证的候选是：利用组内反馈的精度需求，联合决定 GPU 测量批次、独占窗口和执行顺序，在限制反馈偏差的条件下缩短整组完成时间。该方向需要受控评分器配合，不能包装成通用黑盒 Docker 排队算法。当前不足以确定为独立研究主线，先验证测量成本占比和相对强基线的增益。 更一般的性能评估资源管理可作为上位问题，GRPO 组级精度是其特例。可复用流程不意味着所有时间指标共享同一误差模型或已有通用实现。
>

## 目标与全局流程

rollout 是 agent 从接收题目、生成方案、调用工具到返回结果的一条尝试轨迹。同一道题可以同时生成 G 条轨迹。command 模式规定 GPU 的申请与归还边界，不自动规定优化目标。本研究采用用户指定的固定组目标，不把 PSRL 的所有异步训练路径都假设成整批同步。

```text
[1] 同题固定 G 条 rollout，代码与工作量固定
       │ GPU 工具请求 / 生成与 CPU 等待可以交错
       ▼
[2] 可信 verifier：正确性检查、运行时间样本、评分映射
       │ group_id、阶段、测量不确定性、启动与归还成本
       ▼
[3] 提案：组级测量预算与调度器
       │ 选择下一测量批次、是否独占、是否需要复测
       ▼
[4] 当前 Env command 准入 → 节点授权 → Docker 中执行
       │ 测量结果                         │ 命令结束
       ▼                                  ▼
[2] 更新测量与反馈区间              [5] 物理归还确认 → 释放预算
       │ 未满足精度条件则回到 [3]          │ 可接纳下一命令
       ▼                                  │
[6] 全组有效反馈就绪 → 记录组完成时间 → 按配置计算学习信号
       │
       ▼
[7] 会话结束，清理容器与租约
```

图例：图里每个部分对应的源码位置。

| 编号 | 现有实现或提案及对应入口 |
|---|---|
| 1 | 固定组是实验协议。训练中用 `parent_id` 标识同组的入口见 [PSRL_compute_advantage](../../../psrl/trainer/ppo/utils.py#L231)，不表示 Env 已按该 ID 调度 |
| 2 | [evaluate](../../../examples/gpu_benchmarks/evaluate.py#L10) 调用上游评估并返回指标。阶段拆分、误差区间、精度契约尚未实现 |
| 3 | 尚无本地实现。当前 [GpuCommandScheduler.acquire](../../../psrl/workers/env_service/command_gpu.py#L58) 是 unit 内 FIFO，不能声称已有组级策略 |
| 4 | [ManagedGpuExecution.exec_gpu](../../../psrl/workers/env_service/managed_execution.py#L53)、[GpuExecutionBackend.execute](../../../psrl/workers/env_service/gpu_execution.py#L102)、[grant_gpu_command](../../../psrl/workers/env_service/command_gpu_node.py#L192) |
| 5 | [GpuCommandScheduler._return](../../../psrl/workers/env_service/command_gpu.py#L215)、[revoke_gpu_command](../../../psrl/workers/env_service/command_gpu_node.py#L207) 检查物理所有权释放 |
| 6 | [compute_score](../../../examples/gpu_benchmarks/reward.py#L6) 读取奖励，[PSRL_compute_advantage](../../../psrl/trainer/ppo/utils.py#L182) 按实际算法配置计算优势。组级精度认证尚未实现 |
| 7 | [EnvRouterCore.release](../../../psrl/workers/env_service/router.py#L241) 处理会话资源回收 |

主指标定义为 `T_group = max(C_i) - t0`。t0 是整组题目释放的统一时刻，C_i 是第 i 条轨迹的有效结果返回时刻。不能只从它获准使用 GPU 时开始计时，否则隐藏了排队。原始任务失败和基础设施失败分别报告。不能丢弃慢轨迹、缩小组大小或把未完成当作成功来缩短 T_group。

本研究只针对这组任务的执行与反馈。若进一步声称缩短 PSRL 训练总时长，还需要将策略生成、训练、裁判和异步流水线的真实依赖纳入测量。工具阶段变快不自动等于端到端训练变快。

## 为什么不把饥饿作为主课题

饥饿是一个已经可以运行的任务持续拿不到资源。开放服务中不断有新任务到达、优先级总偏向某类任务时，它是合理问题。但在固定有限组、每个任务工作量有限、没有无限重试且调度器持续推进的条件下，队列终会耗尽。“某条轨迹等得较久”通常是排序代价，不是无限饥饿。

如果一条轨迹真的永远不完成，T_group 就是无限大。因此基本可完成性已经包含在目标里。仍需处理取消、超时和资源泄漏，但没有理由另加“每条轨迹都尽快轮到”的公平性目标。把最长等待最小化，甚至可能伤害整组完成时间。

教学例子，一张 GPU，忽略交接开销，CPU 不争用：

- A：GPU 10 秒 → CPU 20 秒 → GPU 1 秒 → 完成。
- B：GPU 1 秒 → 完成。

| 顺序 | A 完成 | B 完成 | 平均完成时间 | 全组完成时间 |
|---|---:|---:|---:|---:|
| 先 B，再 A | 32 秒 | 1 秒 | 16.5 秒 | 32 秒 |
| 先 A，A 等 CPU 时跑 B | 31 秒 | 11 秒 | 21 秒 | 31 秒 |

第二种让 B 多等了 10 秒，平均完成时间也更差，却让整组早 1 秒完成。原因是 A 的长 CPU 阶段提前开始，B 被放进这个阶段。这里没有公平性收益，只有依赖链重叠的收益。它只说明目标区别，经典依赖图调度已经研究这类问题，不能把这个例子当作创新。

如果所有命令始终就绪、单卡独占、没有依赖空窗、切换成本相同，那么无论怎样排序，总完成时间都是总执行时间加固定切换成本。这个情形单纯换 FIFO 没有 makespan 收益，必须先确认真实工作负载具有可优化的空窗、并发、复用或可调整测量成本。

## 建议验证的课题

**候选题目：面向 rollout 组学习信号保真的 GPU 测量预算与 command 联合调度。**

实际问题是：GPU 调度不但影响“多久得到分数”，还可能改变基于运行时间的分数本身。不同 kernel 对共享计算、带宽和缓存的敏感性不同，统一乘一个修正系数不可靠。某次共享让 A 慢 10%、B 只慢 1%，可能把真实较快的 A 排到 B 后面。错误反馈随后影响 agent 修改方向或 RL 更新。

教学假设：参考实现耗时 12 微秒，A 独占耗时 10，B 为 10.1，奖励采用参考耗时除以候选耗时。独占时 A 得 1.2，B 约 1.188。共享后 A 为 11、B 为 10.201，奖励变为约 1.091 与 1.176，优劣倒置。参考时间固定仅用于说明差异污染，真实方法必须处理参考与候选的测量条件，不能直接沿用这个简化。

组相对策略优化 GRPO 将同题候选的奖励与组均值比较，形成优势值，表示本次更新应相对鼓励还是抑制该候选。教学式为 `A_i = (r_i - mean(r)) / (std(r) + eta)`，eta 是避免除零的小常数。实际标准差定义、mask 和估计器以训练配置为准。在两候选例子里，计时污染会直接翻转优势符号。多候选时，只有排名相同还不够，因为相对均值位置与优势大小也可能改变。

与对每个 kernel 要求相同计时精度相比，可以研究下游真正需要什么精度：

- 两个候选奖励相差很大时，一定范围的误差可能不影响所需学习信号。
- 一组候选表现接近时，相同绝对误差经过组标准差归一化可能被放大，需要更精确的测量。
- 一个候选的精度变化会改变组均值与标准差，因此任务精度不是彼此独立的。

拟议优化目标是最小化期望 T_group，同时限制全组优势偏差或实际反馈决策改变的概率。例如 `P(max_i |A_hat_i - A_iso_i| > delta) <= epsilon`。A_iso 指同一组候选按预先定义的独占参考协议得到的优势，不是假设存在无噪声真值。delta 是允许的偏差，epsilon 是风险预算。正式评分还要保留原始分数偏差、正确性和 benchmark 阈值约束，不能只保证优势不变。

**可能的研究差异**是把这个组内耦合的精度需求传给 GPU 调度器，联合选择下一个测量批次、独占窗口与重测，而不是每个候选独立追求统一精度。必须证明它优于“每个候选独立自适应测量 + 现有区域独占调度”。这项差异在本轮检索中未找到完全重合方案，但仍是待验证的候选，不能写成已经确认的首创。

如果只做黑盒 command 的顺序重排，评分器完全不可改，那么这个候选不适用。本轮没有证据支持把单纯 FIFO 改排序包装成一个确定新颖的强课题。

## 组级反馈需求的手算例子

这里的“组级”是说：是否继续给某个候选分配 GPU 测量时间，要看这次测量能否帮助整个组形成足够准确的反馈，而不只看该候选自身分数是否足够精确。它不表示自动给每条轨迹分配相同份额，也不表示已经加入了生产 Router。

沿开头全局图，2 提供原始测量，3 将误差传播到组反馈并选择下一批任务，4 和 5 执行与归还，6 接收达到精度要求的整组结果。现有代码映射及从入口到清理的阅读路径见本文首尾，新增的误差传播与决策部分仍是提案。

下面全部是教学假设：同题四个正确候选，奖励越大越好。区间是假定同时包含各自真实奖励的边界，不是从 GPU 实测得出的置信区间。

| 候选 | 当前奖励估计 | 假定误差半径 | 与组均值 1.01 的差 |
|---|---:|---:|---:|
| A | 0.80 | ±0.01 | -0.21 |
| B | 1.00 | ±0.01 | -0.01 |
| C | 1.04 | ±0.01 | +0.03 |
| D | 1.20 | ±0.12 | +0.19 |

先看未除标准差的差值 `d_i = r_i - mean(r)`。它的正负表示候选在组均值之上还是之下。它不是候选两两排名，例如 B 与 C 的相对排名已很清楚，二者相对组均值的位置仍可能不清楚。

G 个候选中，若第 i 个奖励的误差半径为 h_i，那么 d_i 的保守误差半径是：

```text
b_i = (1 - 1/G) × h_i + (1/G) × 其余候选的 h 之和
```

因为自己的奖励既出现在 r_i，也出现在均值中，其系数是 `1 - 1/G`。其余候选各通过均值以 `-1/G` 影响它。这是同时区间成立时的线性边界，不要求误差独立，但本身不提供区间覆盖概率。

B 的半径为 `0.75 × 0.01 + 0.25 × (0.01 + 0.01 + 0.12) = 0.0425`。所以它与均值的差可能落在 `[-0.0525, 0.0325]`，正负无法确定。C 对应 `[-0.0125, 0.0725]`，也无法确定。D 对应 `[0.0925, 0.2875]`，始终为正。

如果只关心 D 自己该不该被相对鼓励，似乎已经无需再测。但先把 D 的半径从 0.12 缩至 0.002，B、C 的半径就都降到 0.013。C 的差值区间变为 `[0.017, 0.043]`，已经稳定为正。再把 B 的半径缩至 0.002，B 的区间变为 `[-0.017, -0.003]`，稳定为负。

| 测量阶段 | A | B | C | D | 未定方向数量 |
|---|---|---|---|---|---:|
| 初始 | 负 | 未定 | 未定 | 正 | 2 |
| 只提高 D 的精度 | 负 | 未定 | 正 | 正 | 1 |
| 再提高 B 的精度 | 负 | 负 | 正 | 正 | 0 |

这才是组反馈与资源分配之间的具体联系：**D 的自身方向已经确定，但测 D 仍可能帮助别人更早得到有效反馈。** 实际测量也可能改变均值，而不只是缩小误差，所以每轮都必须重新计算。

这个例子只演示符号。标准化优势还要除以组标准差，研究验收须限制优势数值误差，不能只保护正负。组标准差很小时误差会被放大。共用参考实现还会引入相关误差，例如所有奖励共同正比例变化，在忽略分母稳定项的理想标准化公式中会抵消，但原始分数和绝对阈值可能仍改变。误差模型必须匹配真实评分方式。

配套 [CPU 脚本](../env-service-verification/scripts/command_group_objective_demo.py) 已实际运行，得到未定方向数 2、1、0。它只传播人为给出的区间，没有估计 GPU 样本、不执行测量预算算法，也不证明存在吞吐提升或训练收益。

## 方法与实现边界

先把测量预算和 GPU 执行顺序分开设计，再联合优化，不先引入新的神经网络调度器。

1. **固定反馈契约。** 固定候选代码、输入、正确性检查、组大小及奖励公式。官方最终评测保留原协议。适应性测量仅作为显式研究配置，不能把减少试验次数称作原协议等价。编译错误、正确性失败、OOM 和调度故障分别记录。
2. **可信 verifier 上报阶段。** 数据准备、正确性执行、性能测量批次和反馈汇总分开描述。不是所有编译都只使用 CPU，也不是所有非计时阶段都适合共享，必须按实际调用核实。标记来自受控 verifier，不依赖 agent 自报准确时长。
3. **先用独占样本估计不确定性。** 每个正确候选先获得小批真实 GPU 测量。传播候选、参考实现的时间区间至奖励和组优势。共享时的受污染样本最初只用于预测调度成本，不能当作无偏样本取得所谓认证。近零组方差、未知 kernel 类别或区间过宽时，退回完整独占测量。
4. **选择最有价值的下一批测量。** 比较“预计减少的组反馈不确定性 / 实际新增占卡与交接时间”，优先处理限制整组反馈就绪的候选。候选补测可能改变整个组，不能简单按当前奖励高低挑选，也不能删掉较差 rollout。这个比值是启发式起点，需与简单算法比较，不声称全局最优。
5. **决定批次大小和资源模式。** 太小的测量批次会反复加载、热身、申请与归还，太大则过度测量且阻塞别人。联合考虑下一批测量、重新初始化、物理归还及候选剩余工作。初版全部性能批次独占，正确性共享也必须先验证。进一步允许共享测量时，需要额外校准干扰偏差并验证回退成本。
6. **组级停止并全量审计。** 达到预设反馈精度才停止研究测量，所有候选都返回结果。实验期对所有候选另做独占审计，检查原分数、优势、阈值决策是否一致。在线多轮 agent 接收到中间数值也可能改变轨迹，因此第一阶段只研究最终 verifier，不假定保住末尾优势就保住整个交互过程。

普通固定样本置信区间不能被反复查看、满足条件就停止后仍自动保有原覆盖率。需要采用适合顺序观察的置信方法，或事先固定检查次数并分配误差预算。GPU 热状态、频率和缓存造成的系统偏差也不能靠多采几个样本自动消除。区间传播须处理相关性和归一化的非线性，不能仅检查几个区间端点就声称数学保证。初期只报告独立审计上的经验误差，不伪称已证明上面的概率约束。

现有 command 归还要求 CUDA 进程和设备句柄消失。因此直接把 10 次测量拆成 10 次 `exec_gpu` 可能更慢。本地还没有通用的保留 CUDA 上下文同时安全交接执行权的协议，不能在提案图里把它当成已实现功能。先测冷启动与批次收益，不以放松归还检查换性能。

Docker 提供代码、依赖和进程的运行边界，不自动提供性能隔离。真正的研究对象是测量精度、GPU 执行权、显存驻留和组反馈之间的关系，Docker 只是落地载体。

## 用现有 benchmark 做什么

具体覆盖缺口、生产算子与服务级候选、以及已完成的 FlashInfer 原生 Env command 探针，见 [AI4Infra 性能反馈 benchmark](ai4infra-performance-benchmarks.md)。该探针只验证官方任务与环境链路，不代表本节提出的调度方法已实现或有效。

| Benchmark | 用途 | 当前限制 |
|---|---|---|
| KernelBench | 首选，候选代码、正确性、延迟与加速比都能观察，且无需外部裁判 | 当前默认奖励是 correctness，必须显式建立性能奖励研究配置 |
| InferenceBench | 第二阶段，验证吞吐或延迟反馈与质量门槛的联合约束 | 需保持质量检查、计时口径和判无效条件，不能把已有避免 OOM 实验当作精度调度证据 |
| RE-Bench 本地 Qwen 任务 | 可作其他资源阶段存在时的外部验证 | 偏好裁判噪声不同于 GPU 测时误差，当前 episode 任务不能直接证明本课题收益 |
| MLE / PostTrainBench 类质量优化任务 | 将来研究质量评估预算或持久训练状态时再考虑 | 不是本轮最直接切入点，不为凑 workload 扩大实验 |

KernelBench 现状须特别注意：[evaluate](../../../examples/gpu_benchmarks/evaluate.py#L19) 采用 3 次正确性检查、10 次性能试验，返回 runtime_ms、speedup，但 [reward](../../../examples/gpu_benchmarks/evaluate.py#L31) 仍是正确性。[数据准备](../../../examples/gpu_benchmarks/prepare.py#L47) 默认选择 reward 字段。仅记录 speedup 不意味着已经用它训练。

[KernelCommandVerifier](../../../examples/kernel_bench/verifier.py#L8) 要求独立单卡 direct unit、单会话，[exec](../../../examples/kernel_bench/verifier.py#L35) 将整个 verifier shell 调用交给 exec_gpu。它提供的是保守评估边界，尚无组级精度信息或 KREX 式区域协议。不能简单把 max_containers 增大就称为研究实现。

## 选题可行性与立项判断

结论分三层：现有 bench 足以开展成本分解与冻结候选实验，当前接入不具备完整研究机制，独立课题的新颖性和实用收益都尚未成立。不建议先写复杂调度器或开始长时间训练。

**现有能力与最小补齐项。** KernelBench 已有代码输入、官方评估调用、Env command 授权与归还、奖励传递和 GRPO 的 parent_id 分组。研究原型需要四个模块：保留每次原始测量的采集器、传播组反馈误差的预算控制器、能够在受控批次边界继续评估的执行器，以及独立审计与耗时分析器。控制器可先在 driver 中实现，不必一开始修改 Router 选择算法。GPU 批次仍须经过 Env，不能在外面另建一套绕过账本的 GPU 进程。

本地固定的上游版本见 [upstream.json](../../../examples/gpu_benchmarks/upstream.json)。核查该版本的 [time_execution_with_cuda_event](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/timing.py#L201) 可见，每个计时调用有热身、CUDA 同步与 L2 缓存清理。成本不能仅用 kernel 时间乘试验次数计算。[get_timing_stats](https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda91e0c2d67e4a43bf62f96f6d104f1/src/kernelbench/timing.py#L602) 目前将统计量格式化为三位有效数字，研究原始噪声时需要额外保存未舍入的样本，不能从已有均值和标准差恢复原始序列。

当前默认只有 10 次性能试验，而且训练 reward 仍是正确性。如果目标始终只有正确性，最直接的对照是关闭非必要的性能测量，而不是为它设计复杂精度调度。使用速度奖励必须作为固定的研究配置，先保证正确性与有效计时，避免对错误结果给速度奖励。不能为这个选题悄悄改变默认 benchmark 定义。

**比前面更接近的已有方法。** 本轮追加核对以下原始资料：

| 工作 | 与本候选的关系 | 不能直接声称的贡献 |
|---|---|---|
| [OCBA 随机执行时间研究，2012](https://arxiv.org/abs/1206.5865) | 最优计算预算分配 OCBA 研究怎样把计算次数分给不同候选，并计入耗时随机性 | 把精度收益除以采样时间不自动构成新算法 |
| [LEAP，2026-08](https://arxiv.org/abs/2608.01804) | 利用任务难度和组内表现裁剪多轮 kernel 调试，并设计组内相对奖励 | “根据组反馈少用 GPU 评估”这一宽泛表述已有近邻。本候选保留固定候选集合，研究数值测量预算，仍需实证区别 |
| [VenusRL §4，2026-10](https://arxiv.org/html/2610.03286v1#S4) | 直接考虑样本组就绪时间，并对生成执行与缓存资源排序 | 组完成时间和组级优先级本身不是创新 |

连同前文 KREX、GPU Forecasters、Critter，这意味着单纯把“置信区间 + GRPO + Docker”拼在一起，贡献很可能不够。LEAP 更改调试展开与奖励的做法也不应不加说明地当作固定工作量的调度对照。

可能有研究价值的部分需要同时满足：第一，给出符合真实评分器的组反馈误差控制，而非只挑最快候选。第二，在实际容器启动、GPU 热身、物理归还和测量条件下联合选择批次与执行时机。第三，在相同反馈质量下，优于逐候选自适应、计算预算分配方法和区域独占执行器的组合。仅少测几次或仅改善模拟数字，都不足以支持这三个条件。

**如何决定继续还是停止。** 先按下节有界方案采集原始数据，冻结候选并回放，比较固定次数、逐候选精度停止、OCBA 类预算基线和组反馈预算。各种近似方案在相同原始分数与优势误差目标下比较，不能给新方法更宽松的精度。至少使用真实完整评估中的首次计时区段，重启带来的热身与初始化开销单独计量。回放若假定保留热上下文，只能作为理想上界，不能声称当前 Env 已达到。

通过离线门槛后，才实现受控批次执行，在真实 Env 下验证减少样本是否抵消交接成本。再通过这一门槛，才有必要做 PSRL 闭环质量实验。把前两阶段做成前期研究是可行的，把尚未测量的收益当作论文主线是不合适的。

本主题更接近“GPU 环境评估系统”研究，适用面集中在性能型奖励与相对反馈。对于正确性 0/1、固定训练步数、持久训练状态卸载等任务，它并不能直接替代通用资源调度研究。后文显式执行器池是另一项可复用工程机制，不是组反馈预算验证的必需前置，也不是本轮新增实现。

## 测量可靠性的已有研究与通用边界

本节于 2026-11-05 对照 `0326d46` 加主目录未提交内容局部核对，范围仅为已有评估入口、command 归还边界和本节文献。没有刷新前文历史核对范围，也没有部署新的调度器。

**结论。** 测量准确性与决策可靠性并不是临时创造的研究方向。性能评估、统计选择和自动调优已有长期积累。组级优势精度是一个窄特例，可以抽象到“在预设评估条件下，以较少资源得到足够可靠的性能结论”，但不能声称任意时间相关指标都直接适用。

下面是概念关系图，不是新增的本地调用链：

```text
程序 / 配置 + 输入 + 目标测量条件
          ↓
资源安排影响实际运行条件 → 测量样本与不确定性
                                  ↓
                  下游用途：排序 / 阈值 / 回归 / RL 反馈
                                  ↓
                  继续测量 / 改变隔离 / 接受结果
```

图例：概念与本地实现的对应边界。

| 部分 | 对应关系 |
|---|---|
| 程序、输入与性能样本 | [evaluate](../../../examples/gpu_benchmarks/evaluate.py#L19) 已调用固定上游评估，通用目标条件声明尚未实现 |
| 资源安排 | [GpuCommandScheduler.acquire](../../../psrl/workers/env_service/command_gpu.py#L58) 与 [revoke_gpu_command](../../../psrl/workers/env_service/command_gpu_node.py#L207) 提供准入与归还，不估计测量偏差 |
| 评分与 RL 反馈 | [compute_score](../../../examples/gpu_benchmarks/reward.py#L6) 读取奖励，组优势入口见 [PSRL_compute_advantage](../../../psrl/trainer/ppo/utils.py#L231) |
| 排序、阈值、置信停止与隔离选择 | 本图展示拟议的通用接口，不是现有 Env 功能。当前完整执行路径见[跟着图读源码](#跟着图读源码) |

图里的各段源码可以继续逐段追问。CPU 教学脚本见本节末尾，不能把它视为对这个控制循环的实现验收。

**已有工作及阅读用途。**

| 原始资料 | 已研究的问题 | 与本课题的联系与边界 |
|---|---|---|
| [Statistically Rigorous Java Performance Evaluation，2007](https://dri.es/files/oopsla07-georges.pdf) | 运行时非确定性下如何严谨比较性能 | 说明“看见差异不等于真实提升”是成熟问题，不局限于 GPU 或 RL |
| [Rigorous Benchmarking in Reasonable Time，2013](https://kar.kent.ac.uk/33611/) | 处理性能实验不确定性与重复运行成本，使用效应大小的置信区间呈现结果 | 为测量精度与时间成本的取舍提供直接背景 |
| [STABILIZER，ASPLOS 2013](https://people.cs.umass.edu/~emery/pubs/stabilizer-asplos13.pdf) | 代码和内存布局可能混淆优化效果，通过运行时重随机化控制布局影响 | 反复运行同一个有偏实验条件不等于消除了偏差。其具体机制面向 CPU 程序，不可直接当作 GPU 隔离方案 |
| [Duet Benchmarking，2020](https://arxiv.org/abs/2001.05811) | 在共享机器上并行比较两个版本，利用相对测量改善比较精度 | 成对比较有价值，但需要检验干扰与比较对象的关系。不能推出同卡 GPU 并发必然准确 |
| [OCBA 约束优化，2009](https://informs-sim.org/wsc09papers/056.pdf) | 在有限计算预算下分配仿真次数，提高满足约束的正确选择概率 | 资源分配直接服务决策精度已有基础，必须作为算法近邻 |
| [KREX，2026](https://arxiv.org/abs/2609.30057) | 共享 GPU 的 kernel 评估中，通过关键区域独占保护测时 | 是当前 GPU 资源效率与测量可靠性的直接系统近邻 |

这些工作说明方向有实际基础，也意味着“提高测量准确性”或者“根据需要多测少测”本身都不是新贡献。本节新增资料主要用于界定问题，不表示本地已复现这些系统。

**必须先区分三种影响。**

1. 随机波动：相同目标条件下，重复运行有一定变化。合适的重复测量可以降低估计不确定性，但相关样本、非稳定热状态和顺序观察需要相应统计处理。
2. 条件造成的系统性偏差：目标是独占性能，实际测量却持续受其他进程竞争。即使把均值测得非常稳定，得到的仍可能是另一种条件下的性能。重复不会自动消除偏差。
3. 实际任务工作量变化：固定五分钟训练，在共享条件下完成的训练步数更少，模型质量可能随之变化。这不是把同一个结果测错了，不能靠置信区间校正为本应获得的模型质量。

第二种是否叫偏差取决于目标。若任务本来要求“服务在指定负载下的 P99 延迟”，这个负载就是待测条件的一部分，不能为了干净测量把它去掉。P99 是 99% 请求延迟不超过的分位点，不能用均值的误差公式直接替代其估计方法。

教学例子：A、B 的目标独占耗时为 8、10 ms，但共享测量给 A 增加 4 ms、给 B 增加 1 ms。最终观测为 12、11 ms，错误选择 B。加入零均值小波动后，重复 2、20、200 次仍会接近 12、11。这个稳定结果可以正确描述该共享条件，不能用于未经校准地回答独占条件谁更快。

**更通用的部分是“测量用于什么决策”。** 假设已经获得同时有效的耗时区间，A 为 `[9.5, 10.5]` ms，B 为 `[9.6, 10.6]` ms：

- 要求“严格确定谁更快”，区间重叠，现有信息不足。
- 只要求“是否均低于 20 ms”，两者都可以确认通过，没有必要为了这个决策继续追求排序精度。
- 要求“计算一组标准化训练优势”，还要处理整组均值与标准差，前述判断仍不充分。

同一批测量有不同的资源需求，来源是决策不同。区间在这里是假定条件，不代表小样本实测已经拥有可靠覆盖率。若黑盒 agent 会根据任意数值细节改变后续行为，又没有明确容差，不能仅用排名或阈值一致来保证整条轨迹不变。

**通用性应分三层。**

| 层次 | 可以复用的内容 | 必须按任务适配的内容 |
|---|---|---|
| 资源执行层 | 请求身份、容量准入、结果来源、取消和物理归还 | GPU/CPU/网络的竞争机制，隔离措施与可恢复状态 |
| 评估控制流程 | 收样本、分析不确定性、选择下一批、记录成本、停止和审计 | 均值、吞吐、尾延迟、能耗各自的统计模型与测量工具 |
| 下游决策层 | 显式声明排序、阈值或数值误差要求 | 正确性门槛、参考条件、奖励函数、GRPO 优势映射 |

可考虑声明“目标条件、指标与单位、下游决策、允许误差、可重复执行边界、初始化与归还成本”作为统一接口。它是设计建议，不是已经存在的配置。接口统一不意味着每类任务使用同一个分布假设、同一套置信区间或同一条 GPU 隔离命令。

**适用范围与不能直接覆盖的任务。**

| 工作负载 | 能复用的研究问题 | 额外条件 |
|---|---|---|
| GPU kernel / 编译参数自动调优 | 多候选性能比较与测量预算 | 固定输入、精度和硬件，候选与参考可比 |
| 推理服务优化 | 延迟、吞吐与质量约束下的比较 | 固定请求负载、批处理条件与计时边界，尾延迟需专用方法 |
| 性能回归测试 | 是否出现超过容忍度的退化 | 明确基准版本、阈值、环境漂移和多次比较问题 |
| 单位任务能耗优化 | 成本与决策可靠性权衡 | 处理测量分辨率、空闲功耗和功耗归属，不能复用耗时误差公式 |
| 正确性 0/1 的功能任务 | 可复用普通资源执行机制 | 不是连续性能测量预算课题，不能省略必要正确性测试 |
| 固定墙钟训练质量 / 长驻训练状态卸载 | 只能复用少量基础设施 | 前者改变优化过程，后者涉及状态保存恢复，不被本方案直接解决 |

对于目前的接入，KernelBench 的性能奖励研究变体和 InferenceBench 是两个候选载体，不等于都已验证通用实现。RE-Bench 本地裁判的偏好噪声也需要另外的模型，不能把“会用 GPU”当作同一种测量问题。

**如何检验通用性。** 如果继续这个方向，至少在两类不同工作负载上复用同一个控制与执行框架，例如 kernel 候选评估和固定负载的推理服务评估，再覆盖排名和阈值两种决策。只在同一个 KernelBench 上更换奖励公式，不足以证明跨工作负载通用。先复用执行协议与成本记录，统计模型和评分契约允许作为插件明确替换。仍需比较独占、区域独占、固定测量次数与经典自适应预算，保持同样的可靠性要求。

这个上位问题具有跨任务价值，但若扩展后只剩“通用测量框架”，也可能只是工程整合。研究贡献仍须证明某种资源安排与测量可靠性之间的新关系及可重复收益，不能靠扩大题目名称解决新颖性不足。

## 实验顺序与停止条件

本次完成文献与源码核对、CPU 教学模拟，不启动 GPU 实验。下列为有界的后续方法验证方案。

**阶段一：先判断有没有值得优化的成本。** 选 4 个 KernelBench 题型，每题 4 个预先冻结的候选。候选来自真实生成轨迹或公开真实实现，固定输入，不拿 sleep 或空分配制造瓶颈。先在一张空闲卡验证环境，用两张卡做同卡并发或独占审计时应分别记账。第一轮上限 16 个候选，每个 3 次完整评估、单次 60 秒、整轮 60 分钟，无自动扩容重试。

采集容器准备、导入、编译、正确性、热身、纯测时、申请、排队和物理归还的耗时。若只省纯测时，则 Amdahl 上界由该部分占比 f 决定：即使将它完全消除，理想加速也只有 `1 / (1 - f)`。例如 f 为 5% 时，上界约 1.053 倍。示例是假设，不是本项目实测。测时占比很小且上下文开销很大，就停止把自适应测量预算作为主方向，不靠把性能试验次数从 10 人工抬高到几万制造收益。

**阶段二：冻结代码，分解算法与工作量变化。** 对相同候选、相同硬件，先固定测量次数比较执行顺序，再比较自适应预算。至少包括：

| 对照 | 回答的问题 |
|---|---|
| 整条 command 独占 + FIFO | 当前保守机制的组完成时间 |
| 区域独占 + 固定测量预算 | 与 KREX 类型强基线相比有没有剩余空间 |
| 每候选独立精度停止 + 相同执行器 | 收益是否仅来自经典自适应测量 |
| 组级反馈精度停止 + FIFO | 组内耦合的预算分配是否有用 |
| 组级反馈精度停止 + 联合调度 | 联合安排批次与交接是否有额外收益 |

若 KREX 无法直接复现，需说明具体限制，使用等能力的区域独占对照并明确它不是 KREX 复现。不能只打败当前串行版本就归功于新算法。GPU Forecasters 的代理预测思路也应作为后续选择性测量对照，不能认为所有省测量方法都属于本方案。

主指标是同一固定组的 T_group，报告跨独立组和重复实验的分布，辅助指标为 GPU 秒、有效候选数量、原分数误差、优势偏差、阈值判定变化及复测成本。全量审计额外成本单列，并同时报告包含审计的总实验资源。预算策略改变测量量时显式披露，不能称作严格等工作量的调度加速。

Env 功能 ON/OFF 仍以用户指定提交 `0eeead861ffafed6bf31c962d259fd847775dcf9` 为固定 baseline。当前 Env 内算法消融是另一组实验，不用 current OFF 冒充固定 baseline。

**阶段三：仅在阶段二有效后做闭环。** 冻结策略模型与题集，在有界多轮 agent 或训练实验中验证更快反馈是否保持真实结果质量。冻结代码回放只能证明执行与评分机制，不证明训练收敛、agent 质量或端到端提升。本阶段不属于本次已运行结果。

出现以下任一结果就应停止或缩小选题：性能测量不是重要瓶颈、少量样本无法可靠判断组反馈、近似优势与原始分数偏差不可接受、复测与启动抵消收益、逐候选简单策略已经达到相同效果，或者新收益完全由 KREX 已覆盖的区域并发解释。失败也能回答选题是否值得做，不应继续扩展 GPU 数量追求预设优势。

本节核对 `cd09114` 加当前工作区未提交内容。只更新研究定位和离线策略探针，生产 Router 没有动态放置补丁。本地先读了本文、[动态放置](dynamic-command-placement.md)、[五篇近期论文](recent-top-conference-papers.md)和 [benchmark 调研](gpu-workload-benchmark-survey.md)。以下区分原文事实与研究推断；未复现外部系统，不宣称穷尽论文或证明“学术界无人做过”。

因此，前文“组完成时间”“风险感知”“动态放置”应视作问题定义与必要基线，不能预设它们本身具有新颖性。尤其 VenusRL 和 CUDA Agent 是原调研需要补齐的直接相关工作。论文没有详述某个内部实现，不等于它没有实现。

### KernelBench 是否值得保留

值得，但需要改变使用方式。此前只有一次 oracle 提交和一次最终评分，适合检验设备授权与清理，无法检验“多轮返回原卡排队”的发生频率。单条 kernel 的毫秒耗时也不是一次 GPU 工具命令的总耗时，后者还含加载、编译、预热、验证和归还。

KernelBench 适合研究多轮独立执行、文件产物局部性，以及测速反馈是否可信。显存允许并发，不代表性能评分允许并发。正式测量应将候选与参考放在可比条件下；当前 PSRL 奖励取 correctness，speedup 单独记录。研究速度奖励时需单独定义实验变体，不暗改现有评分。

不建议为了避开测速难题立即换 benchmark。autoresearch 按固定墙钟预算训练，竞争会改变训练步数与质量，也有相同混淆。RE-Bench 等待裁判时仍有活的 CUDA 状态，不能直接当作可换卡 command。可另外选择正确性为主要反馈的 science GPU 工具任务，但需核验实际命令轨迹，CPU science 任务不构成证据。

### 首期机制选独立执行器，不透明搬动任意终端

下面是针对显式可重启 GPU 工具的实现提案，不是当前已经部署的调用链。

```text
[P1] 长寿命 CPU 会话：文件、终端状态、主机额度
       ↓ 提交不可变输入版本、命令、需求、反馈类型
[P2] EnvRouter：唯一等待请求 → 合格设备集合 → 全局匹配
       ↓ 原子提交短期 GPU 执行租约
[P3] 同节点 GPU 执行器：挂载本次输入、独立进程执行
       ↓ 输出写到本次 invocation 独立目录
[P4] 确认进程/句柄释放 → 撤销权限 → 归还设备承诺
       ↓ 原子发布成功输出与测量条件
[P5] 会话读取结果并继续；会话结束时清理自身资源
```

图例：图里每个部分对应的源码位置。

| 节点 | 当前可复用部分与缺口 |
|---|---|
| P1 | [EnvLease](../../../psrl/workers/env_service/types.py#L228) 当前同时携带主机和 GPU 绑定，独立主机会话租约待实现 |
| P2 | [GpuCommandScheduler.acquire](../../../psrl/workers/env_service/command_gpu.py#L58) 当前按 lease.unit_id 排队，跨设备唯一队列与执行租约待实现 |
| P3 | [KernelCommandVerifier](../../../examples/kernel_bench/verifier.py#L43) 已有显式 GPU verifier 入口，但不是新的可移动执行器池 |
| P4 | [grant_gpu_command](../../../psrl/workers/env_service/command_gpu_node.py#L192)、[revoke_gpu_command](../../../psrl/workers/env_service/command_gpu_node.py#L207) 提供授权与归还机制；新的执行身份需贯穿这些接口 |
| P5 | [EnvRouterCore.release](../../../psrl/workers/env_service/router.py#L241) 是会话释放入口；按 invocation 提交产物的协议待实现 |

跟着图读源码：当前 P1 创建的绑定在 P2 被直接复用，P3 的 verifier 命令经过原 GPU 执行链路。未来 P2 应给每次执行另建记录，P4 按执行身份和代次归还，P5 才接受对应结果。不同会话可并发准备，同一会话初期仅一个 GPU invocation；不是把多个阶段变成全局串行。具体源码有理解上的问题可以随时追问。

选择执行器路线的原因是，KernelBench 已有文件输入与独立 verifier 边界。无需把候选 GPU 全部暴露给原终端，也不必透明迁移任意 shell 状态。代价是要明确 cwd、环境变量、输入版本和产物提交，编译缓存与常驻 executor 的复用收益必须实测。这个路线本身与 CUDA Agent 相近，属于工程机制，不是创新结论。

执行租约至少包含 session_id、invocation_id、device UUID、memory budget、epoch 和 output version；主机预算仍归会话，执行器额外 CPU/主存必须单列，不能漏记。取消时先停止所属执行再确认物理释放；不确定是否已执行的命令不得自动另起副本。持久 CUDA 进程、多卡作业、跨节点迁移、MPS 与模型主动 offload 不进入首期。

候选设备首先过滤软件/硬件兼容、内存容量、清理隔离和反馈要求；仍优先独立环境 GPU。性能测量要求独占窗口，当前没有证明安全的模型共享卡不能入选。性能评分可比较的 GPU 等价类还应固定型号、运行栈、输入精度与测量协议，不能只看空闲显存。

选择顺序先实现全局 FIFO 加合格空闲卡，再比较“预计排队 + 准备 + 执行 + 归还 + 误差余量”。只在收益大于切换成本和滞回阈值时离开原卡；等待老化和每会话未完成请求上限防止饥饿。没有可校准的时长分布时，不声称概率保证，也不直接用一个预测均值承诺延迟上界。

| 换卡成本 20 s，C 在 5 s 释放 | 25 / 25 | 28 / 28 | 25 / 25 |
| GPU1 忙至 40 s，换卡成本 0.2 s | 25 / 40 | 25 / 40 | 25 / 40 |

解释：便宜换卡时，全组缩短 12%，但普通全局选择已经获得全部改善，成本策略没有额外收益。昂贵换卡时，盲目选择最早空闲设备反而使全组从 25 到 28 秒；成本策略只是避免这次退化。两卡都忙时没有收益。固定案例已提前给出 C 的释放时刻、未模拟预测错误与 GPU 干扰；它只能否证“有动态换卡收益就有算法新颖性”。

本轮停止于这个反例检查，没有启动真实 GPU 对照或改造生产 Router。原因是原先的新颖性候选出现明确已有工作重叠，当前也缺真实多轮可迁移命令的排队分布。没有把模拟收益写成 PSRL 实测收益。

### 仍值得验证的研究假设与停止门槛

更具体的候选是：**在不改变工具反馈含义的条件下，如何降低多轮 GPU 工具环境的单位有效任务成本？** 反馈含义指成功/失败、候选优劣排名或性能阈值判定。动态放置是执行手段，论文需要证明的应是可信反馈与资源效率之间的新权衡。

结合前文组内精度耦合的候选，一个机制起点是将可共享的准备/功能检查与需要独占的性能测量明确分开，允许前者填空，后者动态获得干净设备窗口；只有接近评价阈值或存在污染证据的结果才在有界预算内复测。需要比较完整 GPU 独占池、简单阶段独占池、固定卡 command、全局空闲卡、成本感知等强基线。单纯分阶段、独占或重复测量均不是新思想，只有在相同反馈可靠性下证明现有方法无法达到的成本改善，才可能形成贡献。

教学假设：两个候选真实为 10.0 和 10.1 ms，只有前者受干扰慢 10% 后变成 11.0 ms，就会错误选择后者。即使以参考耗时作比值，也不能保证不同内核受到等比例干扰。可测候选排名翻转率、阈值误判率和额外复测成本。不能用“仅 3 次没翻转”声称误判概率低于 1%；少量试验适合发现效应，不足以给出小概率保证。

优先级与门槛如下：

1. 先对已有多轮日志提取命令请求、获准、执行结束、物理归还及下轮就绪时刻，同时记录 GPU 身份、产物版本和反馈用途。若日志缺项，先补埋点；不伪造真实空窗。
2. 计算合法候选卡存在的阻塞时间，并模拟零切换成本的理想改善空间。如果即使理想换卡也几乎不改善目标，就停止动态放置主线。
3. 若空间明显，先实现上述同节点执行器池与全局 FIFO，不先写复杂预测器。小规模验收可限 2 张 GPU、每策略 6 次固定提交执行、总计 15 分钟，无策略训练。达到预算仍不足则报告不足，不自动加长。正式跑之前仍须现场预检并按归属清理。
4. 使用预先固定的真实代码与输入做机制对照，再用少量真实多轮 Agent 检查反馈是否改变后续决策。固定轨迹不能证明闭环策略质量，单次 oracle 也不能替代多轮轨迹。
5. 报告有效结果/秒、全任务完成时间、GPU 秒成本、尾部等待、失败率和排名/阈值一致性。如果简单全局队列或简单阶段独占达到同样效果，停止增加策略复杂度。

研究上的判定是：纯动态 command 放置工程价值中等且有条件，新颖性低；反馈可靠性约束下的 GPU 工具调度是尚待验证的候选，不能承诺无人做过。下一步应优先获得能否证它的真实观测，而不是先做昂贵的大规模训练。
