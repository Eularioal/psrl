# RollArt 与 DynaRL 精读：从 Agent 交互到研究选题

> **核心结论**：RollArt 解决不同阶段和轨迹互相等待的问题，DynaRL 提供随负载变化重新分配资源的运行时与调度方法。对 PSRL 而言，异步、GPU 池化、命令换卡都应视为基础能力或强基线。下一步值得验证的是：真实多轮 GPU 软件任务中，准备工作、可复用状态及 GPU 队列之间还有多少无法被简单池化消除的等待，能否在安全执行新代码的前提下联合优化。本文给出从零理解两篇论文所需的机制、算例、证据边界和研究路线。

## 1. 先看完整问题

以下是教学概念图。它先把角色串起来，不表示两篇系统的组件名称或 PSRL 的逐函数调用栈。

```text
任务输入
  ↓
模型生成动作 → 环境执行动作 → 返回观察
     ↑                         │
     └──── 下一轮继续思考 ─────┘
                 ↓ 任务结束
          完整轨迹 → 奖励评分
                        ↓
                  带奖励的样本池
                        ↓ 收够训练所需样本
                    更新模型参数
                        ↓ 发布新版本
                  后续模型生成动作
```

图例：概念与实现对应范围。

| 图中部分 | 含义 | 对应位置 |
|---|---|---|
| 模型与环境交互 | 模型发出动作，环境真正执行并返回结果 | RollArt §6.1、图 8；本地 GPU 环境执行部分见第 12 节 |
| 轨迹与奖励 | 把完整尝试评分，进入训练数据集合 | RollArt §6.1；它不等于本地 GPU 命令已经物理归还 |
| 样本池与训练 | 收集样本并更新策略参数 | RollArt §6.2、图 9；本篇不逐项映射 PSRL 训练器 |
| 运行时资源调整 | 根据负载改变各组件所占资源 | DynaRL §3 至 §5、图 6 至图 10；不能把本地 EnvRouter 等同于它 |

例如，Agent 被要求修复 GPU 推理服务的功能。它先生成补丁，在环境内安装或编译依赖，启动模型服务，发送测试请求，读取失败信息，再修改代码。模型生成用 GPU，工具测试也可能用 GPU，而编辑、下载、编译和等待又可能主要使用 CPU、磁盘或网络。

因此，任务的 GPU 使用不是连续的一整块。更棘手的是，下一步做什么取决于上一步结果，不能预先知道完整执行时间。系统不仅要让设备忙，还要保证正确版本的代码被执行、结果属于正确任务、资源确实释放。

## 2. 理解两篇论文需要的基础

**强化学习与 rollout。** 强化学习在这里指根据尝试结果的奖励更新模型行为。一次 rollout 是模型与环境交互产生的尝试轨迹。轨迹包含多轮输入、动作、观察，结束后获得奖励。训练消费的是带反馈的数据，不是仅仅一个 GPU 程序退出码。

**生成与训练。** 生成用当前参数回答问题，训练用收集到的数据修改参数。两者可以在不同设备上同时进行，但此时新收集的数据未必来自最新参数。

**参数版本与陈旧度。** 用版本号 10 的模型生成数据，直到训练器已到版本 12 才消费，这份数据就落后了两个版本。限制陈旧度可以约束新旧策略差异，但并不自动证明任何训练算法都保持相同效果。

**prefill 与 decode。** prefill 是模型读取已有输入、计算上下文表示的阶段。decode 是在这些表示上逐个生成后续 token 的阶段，token 是模型处理的文本片段。前者常有较多可并行计算，后者常受读取模型参数等内存流量限制，具体瓶颈依模型、批大小和硬件而变。

**KV cache。** 为避免每生成一个 token 都重新计算全部历史，注意力机制保留历史 token 的键和值中间结果。假设原有 1000 个 token 已算好，下一轮追加 100 个 token，命中缓存便有机会复用前 1000 个的计算。缓存被淘汰或参数更新后，则可能需要重新处理前缀。KV cache 是模型内部状态，不是容器文件，也不是 CUDA 编译缓存。

**吞吐与完成时间。** 吞吐是单位时间完成多少工作，单任务完成时间是某个任务何时完成，固定组完成时间则是最后一个指定任务何时完成。这三个目标不等价。完成大量容易任务可以提高吞吐，却不能保证指定的最慢任务提前结束。

## 3. RollArt 的贡献与执行过程

论文全名是 **RollArt: Disaggregated Multi-Task Agentic RL Training at Scale**。[官方出版页](https://www.usenix.org/conference/osdi26/presentation/gao)提供摘要与引文，[正式全文](https://www.usenix.org/system/files/osdi26-gao.pdf)中的 §3 至 §6 是机制依据。

其核心组合是四件事：按任务特征选择生成硬件、轨迹级独立交互、将奖励作为弹性调用、限制陈旧度的异步训练。它把资源绑定、执行接口和协调逻辑分层，避免所有阶段都跟着同一批最慢任务前进。

```text
[R1] 资源管理：绑定生成、环境、奖励、训练资源
                       ↓
[R2] 多个 EnvManager，各自保存本轨迹的历史与环境
         │请求动作                  ↑动作
         └────────→ LLMProxy → 生成 worker
         │执行动作 → 新观察 → 再请求动作
         ↓ 各自结束
[R3] 奖励 worker → 弹性评分服务 → SampleBuffer
                                              ↓
[R4] get_batch → suspend → 更新生成参数 → resume
                      ↓                    ↓
                  训练本批             继续采样
                      └── 后续参数同步 ────┘
```

图例：这是论文架构的教学重绘，未查阅 RollArt 本地实现，不提供伪造源码链接。

| 编号 | 谁调用谁，数据如何变化 | 原文定位 |
|---|---|---|
| R1 | 资源管理器按声明绑定 worker，执行代理按硬件偏好路由 | §4 至 §5，图 7，Listing 1/2 |
| R2 | 每个 EnvManager 循环调用生成代理与环境，积累动作和观察 | §6.1，图 8 |
| R3 | 单条轨迹结束即可触发评分，带奖励轨迹进入缓冲区 | §6.1 |
| R4 | 样本凑齐后协调参数更新，恢复采样并与训练重叠 | §6.2，图 9 |

**理解独立推进。** 一个环境慢时，不必阻止其他环境请求下一轮模型动作。但模型服务仍会合批处理请求，GPU 容量仍有限，训练仍可能等待样本。取消的是不必要的“每一轮所有环境一起走”屏障，不是取消全部数据依赖。

**理解硬件亲和。** 亲和指某类工作更适合某种资源，不表示必须永远固定在一张卡上。一个任务每轮都读入很长的新观察、只输出很短动作，和另一个任务读短题目后输出很长推导，对 prefill 与 decode 的需求不同。把二者都视为“生成任务”会掩盖这种区别。论文的基本接口允许按任务类别声明偏好，进一步的 prefill/decode 分离是阶段级扩展。二者不能混成“每个请求都已经自动预测最优硬件”。

**理解弹性评分。** “无状态”主要说一次评分请求不依赖上一个请求留下的会话状态，不表示评分模型不需要参数或显存。弹性部署将如何加载、复用和扩缩容交给服务平台，资源成本并没有消失。

**理解参数切换。** 参数变化会使旧参数算出的 KV 不能无条件继续使用。系统保留交互轨迹，并在新参数下重建需要的缓存，和重新运行全部环境操作是不同的事情。过旧轨迹可以被丢弃，这是论文训练流程的一部分，不适合偷偷用于要求固定组全部完成的实验。

## 4. 用三个例子理解 RollArt

下面均为教学假设，时间与结果可由第 13 节脚本复算。它们解释依赖与重叠，不模拟真实推理合批、通信或训练算法。

**例一：慢环境到底卡住了什么。** A、B 两条轨迹各有两轮，每轮模型生成均需 1 秒。A 每轮环境用 1 秒，B 每轮环境用 5 秒。先假定生成资源充足，两个请求能同时处理。

按轮同步时，第 1 轮模型在 0 至 1 秒执行，环境最晚第 6 秒完成，A 虽然第 2 秒就准备好了，也要等 B。第 2 轮模型在 6 至 7 秒执行，环境最晚第 12 秒完成，两条轨迹才一起结束。

独立推进时，A 的四个阶段是 0 至 1、1 至 2、2 至 3、3 至 4 秒，第 4 秒完成。B 仍在第 12 秒完成。A 可以提前评分或开始后续任务，但如果实验要求 A、B 都完成，**整组仍是 12 秒**。这说明独立推进创造的是重叠与后续工作机会，不保证每个固定组必然更快。

**例二：采样与训练重叠。** 假设每批采样 12 秒、训练 4 秒，模型同步成本暂忽略。三个批次完全串行需要 `3 × (12 + 4) = 48` 秒。允许使用稍旧参数后，第二批采样可与第一批训练重叠，第三批亦然，流水线结束于第 40 秒。长期批间隔可接近 `max(12, 4) = 12` 秒，而第一批等待和最后一批训练无法凭空消失。

这只是依赖允许时的时间模型。如果算法要求第二批必须用第一批训练完的参数，上述重叠就不合法。若权重传输与缓存重算另需 3 秒，也不能继续沿用 40 秒结论。

**例三：版本窗口。** 假设允许落后一个版本，当前生成版本为 10。由版本 9 开始的轨迹仍在窗口内，版本 8 开始的轨迹不在。把旧轨迹的下一个动作改用版本 10 生成，并不抹掉它早期动作由旧策略产生的事实。因此需要同时管理轨迹起始版本、后续生成与消费时的窗口。

“多启动四条，只收最快两条”可能减少等数据时间，但改变了工作量与入选样本。若慢任务对应更难题目，还可能改变训练数据分布。不能拿这种结果证明同一固定组的调度更优。

## 5. RollArt 的证据与限制

证据定位是全文 §7 至 §9。主评估涉及 Qwen3 8B 至 32B、H800/H20 资源和多类 Agent 任务。作者不仅对比最弱同步流程，也设置加强同步、one-off 和在自身框架内实现的 AReaL 对照。部分环境长尾消融采用注入延迟，因此不是全部来自自然负载。

| 阅读证据时的问题 | 应得到的解释 |
|---|---|
| 异构放置为什么有收益 | 特定任务对算力、带宽的偏好不同；等成本与等卡数必须分开 |
| 是否只击败最弱同步实现 | 查看 Sync+ 与异步基线，不能只引用相对 Sync 的最大提升 |
| 环境异步的效果怎么隔离 | 查看控制环境延迟分布的消融，不把它当成所有真实环境的通用倍率 |
| 是否证明学习更快 | 查看达到目标验证分数的墙钟时间，而不是只看采样吞吐 |
| 是否与原版外部系统直接比较 | 自身框架中的重实现只能支持注明条件的机制对照 |

作者讨论指出硬件亲和声明仍依赖任务类别，运行中变化的自动适配是扩展方向。生产案例也仍出现收样本等待。因此“所有环境都异步了，训练端一定无空闲”不成立。

对你最关键的限制是验收目标：论文允许陈旧数据淘汰与冗余环境策略，而你固定组实验不能通过丢慢任务来获胜。除此之外，CPU 环境上的独立推进并没有自动覆盖任意 GPU 工具进程的显存、驱动句柄与物理归还。

## 6. DynaRL 的贡献与执行过程

论文全名是 **DynaRL: Flexible and Dynamic Scheduling of Large-Scale Reinforcement Learning Training**。[官方出版页](https://www.usenix.org/conference/osdi26/presentation/wang-yuanqing)与[正式全文](https://www.usenix.org/system/files/osdi26-wang-yuanqing.pdf)提供依据，机制集中在 §4 至 §6。

其贡献组合是动态超图、组件专用的统一迁移接口、携带上下文的数据路由，以及利用过配信号进行资源重分配的策略。请求层还使用已完成工具轮次和缓存前缀信息安排优先级。

```text
[D1] worker 上报利用、进度与队列状态
                       ↓
[D2] 动态图：组件组 + 当前设备 + 依赖 + 请求亲和
                       ↓
[D3] 检测持续过配 → 预测几个重分配候选 → 选择改进方案
                       ↓ 等待或确认组件允许的中断点
[D4] 迁移管理器：重启 / 请求重分配 / 分布式状态转移
                       ↓
[D5] 路由恢复：请求送往合适 worker，按上下文安排顺序
                       └────────→ 继续执行并回到 D1
```

图例：这是外部论文机制图，没有将 DynaRL 的名称强行映射成本地类。

| 编号 | 作用 | 原文定位 |
|---|---|---|
| D1/D2 | WorkerGroup 作为逻辑组件，worker 状态和数据关联持续更新 | §3、§4.1，图 6/7 |
| D3 | 持续窗口检测、候选评估与吞吐预测 | §5.1，算法 1 |
| D4 | 由组件决定何时能中断，以及如何迁移 | §4.2，图 8/9 |
| D5 | 亲和路由与多轮请求优先级 | §4.3、§5.2，图 10、算法 2 |

**为什么需要图。** 只看一张卡利用率低，不知道原因。它可能没输入，也可能刚完成大部分任务只剩长尾，还可能等待下游。图把资源状态与依赖放在一起，调度器才能区分“少给资源也不会明显变慢”和“现在空闲但下一刻就要大量工作”。超图允许一个关系连接多个组件或参与者，比单纯设备列表更适合描述成组执行与数据交换。

**过配的实际含义。** 过配不是“GPU 空闲比例超过一个数”这么简单，而是减少部分资源后该组件损失有限、释放资源对其他组件有用。运行时指标只是判断代理，预测也可能错。

按原文 §5.1 阅读控制循环时，可以依次问四个问题。第一，低利用是否持续了足够长时间，还是瞬时波动？第二，可回收资源的候选数量有哪些，是否满足后端并行布局？第三，回收后供给方损失多少、接收方增加多少吞吐？第四，新的预计系统吞吐是否优于当前配置，组件是否已允许切换？它使用短期性能测量建立预测起点，并用运行时信息更新预测；不是训练一个强化学习调度策略。用于 rollout 的活跃 KV 比例也不等于整卡算力利用率，不能直接把该信号替换成显存剩余量。

其简化目标可读成“在总资源约束内，让最慢阶段的处理速率尽可能高”。阶段持续时间不平衡、交互轮数变化、尚未到达的数据和迁移成本会使实际调度复杂得多。下面的手算例子帮助理解这个目标，不声称该近似对所有多轮依赖都精确成立。

**三类迁移怎样理解。** 重启方式保存必要状态后重新启动，普适但可能昂贵。请求重分配将待处理和在途工作重新安排到保留的 worker，需要执行后端支持暂停与资源释放。点对点状态转移面向分布式训练，把参数和优化器等状态交给新 worker，再切换有效执行集合。它们都依赖组件协议，不是任意 CUDA 程序的透明迁移。

**安全点为什么重要。** 训练中多个 worker 可能共同完成一次参数更新。如果只停其中一半，又让另一半使用新布局继续，可能出现通信不匹配或新旧状态混用。安全点是在不破坏计算语义的位置协调切换。先建新执行集合、确认状态齐备，再替换旧集合，还需要短时资源与失败回退预算。

## 7. 用三个例子理解 DynaRL

以下继续使用独立教学假设，不是论文的性能模型参数或代码复现。

**例一：把资源给瓶颈，而不是平均分。** 假设共 8 张卡，组件 A 的速率在给 4、3、2 张卡时分别为每秒 10、9、6 个标准工作单元，组件 B 每张卡每秒处理 1 个同类单元。

| A/B 分卡 | A 速率 | B 速率 | 简化流水线有效速率 |
|---|---:|---:|---:|
| 4/4 | 10 | 4 | 4 |
| 3/5 | 9 | 5 | 5 |
| 2/6 | 6 | 6 | 6 |

对于稳定、可以重叠且工作量已归一化的流水线，瓶颈限制速率，故用两者最小值作教学近似。4/4 调整到 2/6 后，A 虽然变慢，整体反而更快。真实 RL 各阶段单位不同，必须先转成同一批样本对应的工作量，不能把 token/s 和 batch/s 直接取最小值。

若只剩 12 个工作单元，原配置需 3 秒，新配置纯执行需 2 秒，但迁移要 2 秒，合计 4 秒，反而更慢。若剩 120 个单元，则分别需 30 秒和 `2 + 20 = 22` 秒，迁移才值得。论文吞吐建模给出方向，落到短命令仍必须显式计入有限剩余工作与迁移开销。

**例二：路由与排序是两个动作。** 假设 worker X 保存 A 的长前缀，worker Y 较空，但没有缓存。把 A 送往 Y 会省排队、增加前缀重算。路由决定送到哪里，排序决定到达后先执行谁。如果 X 同时有新任务 B 和 A 的后续轮次，优先 A 可能及时复用缓存并结束整条轨迹。

论文使用工具调用轮数作为完成进度的代理。已经调用 5 次工具不等于一定只剩一次调用，尤其软件修复可能不断失败重试。理解这个启发式比记住优先级公式更重要：它利用论文负载的统计规律，不是对所有 Agent 的剩余长度预测定理。

**例三：不同状态不能混为一谈。** 假设一个训练程序包含参数 10 GiB、优化器 20 GiB、未完成更新的梯度 10 GiB。只复制参数并不能继续原优化过程。相比之下，独立测试命令结束后，如果只需要保存输出文件，下一次在另一张卡新建进程可以无需搬这些活状态。

这正是你的 command 边界的价值：明确执行对象已经结束，下一次合法新建。它与在运行中的 worker 之间搬训练状态是两种机制。把二者都叫“迁移”容易夸大实现范围。

## 8. DynaRL 的证据与限制

原文 §7 使用 H100 集群，覆盖 64/128 卡、1.5B 至 32B 模型。数学 RL 报告 token 吞吐，多轮 Agent RL 报告请求吞吐；不能把两种单位合并成一个加速排名。多轮实验分别比较资源动态分配与叠加请求优先级，便于识别两层机制的作用。

特别要检查三个条件：性能数字是预热后若干迭代的平均，不等于所有在线瞬时负载；部分外部方案是重实现，不等于直接运行其原仓库；训练曲线检查是具体配置上的经验验证，不是任意迁移协议正确性的形式化证明。

模型需要预测，资源重分配需要安全点，训练并行布局也限制了调度粒度。例如一个并行副本要 8 张卡时，零散空出 1 张卡不能任意扩出一个副本。论文 §5.1 的简化模型讨论同质资源池，也不能直接当成已解任意型号、拓扑及 GPU 工具程序的统一放置。

两处原文表达应谨慎阅读：算法 2 的排序伪码没有清楚写升降序，正文才说明更多工具轮次和更长缓存前缀优先；§7.5 对阈值极端行为的文字解释与 §5.1 的低利用触发条件表面上存在方向疑点。本篇采用机制正文理解，不根据这些表述推出通用阈值规律，复现时应核验具体实现。

最关键的研究边界是：论文已经把工具调用、上下文亲和和组件状态纳入系统。不能把它简化成“只调训练、不管 Agent”，再以此制造自己工作的差异。真正需要比较的是具体状态、可中断条件和目标函数。

## 9. 两篇论文真正的区别

| 维度 | RollArt | DynaRL |
|---|---|---|
| 首要矛盾 | 阶段资源特征不同，轨迹互相等待 | 固定分配不能跟随瓶颈变化 |
| 主要控制对象 | 阶段部署、轨迹推进、评分和参数版本 | 组件资源、worker 布局、请求路由与顺序 |
| 状态问题 | 环境历史与模型版本如何跨异步过程衔接 | 如何安全搬状态，并保持数据亲和 |
| 借鉴价值 | 看见完整数据流和真实等待来源 | 把可观测性、决策、执行协议分开 |
| 不可直接套用处 | 可淘汰过旧或冗余轨迹，不适合固定组全部完成目标 | 已支持组件的迁移接口，不等于任意用户进程透明迁移 |

可以把两者理解为互补层次，但不能宣称把两个系统接起来必然更快。独立采样改变队列负载，动态资源收缩改变生成能力，二者共同运行可能相互振荡。先统一观测单位、模型版本语义与资源归属，才有意义讨论组合。

## 10. 对你的课题意味着什么

本篇延续已有[非计时评分场景](non-timing-gpu-scheduling-scenarios.md)和[command 调度研究](command-scheduling-research.md)，不重新创建相互冲突的研究现状入口。

你目前的工程基础包括命令借还、显存准入、物理归还、同机显式命令池，以及协作式 CPU 准备前移。同机池已能在下一条 direct 命令时重新选卡，未配置池仍按原绑定运行。它不包含跨节点活状态迁移，不自动覆盖 MPS 或模型共享卡。

因此以下表述都不足以单独形成论文贡献：支持 Docker GPU 工具、让轨迹异步执行、使用空闲卡、在命令边界归还、按任务亲和放置、把准备放到 GPU 准入前。它们是重要工程能力，但已有论文和本地实现都已覆盖其中大量内容。

更值得追问的是：**在这些强基础能力已经存在后，真实负载还留下什么稳定、显著、可解释的低效？** 本地 SGLang 算子实验已有证据表明，同机编译缓存可以跨兼容设备复用，无关代码修改不必让它全部失效。因此不能以“每换卡必重编译”或“整个仓库 hash 改变便全部冷启动”的弱基线证明新策略。

这也修正了上次短调研的定位：GPU 环境确实重要，但“环境使用 GPU”本身不足以证明与 RollArt/DynaRL 存在新的研究问题。要说明它改变了什么约束，以及已有机制为什么无法处理。

## 11. 建议研究的问题与否证路线

**主候选：面向多轮 GPU 软件任务的准备、驻留与执行联合调度。** 更具体地说，面对多个不断修改程序的 Agent，决定哪些准备工作提前做、保留哪些仍有效的主机状态、何时申请 GPU、选择哪个合法设备，让固定组的所有有效结果尽早返回。

这里的驻留是保留在内存或存储中的准备结果，不默认保留活 CUDA context。程序变更下的状态有效性是约束，是否能形成创新取决于它与排队、内存压力和准备重叠之间有没有新权衡。首期优先功能测试评分，避免把另一个研究方向中的测速精度问题混入。

**一个说明因果的例子。** 教学假设：A 在原节点有有效模型文件和主存准备，原 GPU 等待 12 秒，获准后执行加归还 4 秒。另一候选 GPU 等待 2 秒。若同机可直接复用准备，换卡总计 6 秒，原卡 16 秒，简单池化就已经解决问题。如果另一候选在不同节点，需新增 20 秒准备，且准备与等待可重叠，则总计 `max(2,20)+4=24` 秒，应留在原节点。如果准备必须等另一依赖完成后才能开始，公式又应改变。研究点不在把四个时间机械相加，而在合法状态和实际依赖决定哪些工作能重叠。

**与论文的关系。** RollArt 提醒你解除多余屏障并分别测量环境准备；DynaRL 提醒你显式描述状态与可切换点。你拟增加的是迭代 GPU 程序的准备状态、主机资源与 GPU 准入之间的联合决策。这个扩展需要与原生内容缓存、预热服务、增量构建、局部性感知服务调度比较，不能仅凭两篇没有展开某细节便声称首创。

| 研究问题 | 必要观察 | 可实现的第一步 | 否证条件 |
|---|---|---|---|
| GPU 等待能否与合法准备重叠 | 准备依赖、就绪时刻、实际占卡区间 | 记录阶段时间，使用现有 prepared 接口 | 准备已被隐藏，进一步重叠空间很小 |
| 有效主机状态是否值得保留 | 状态大小、下一次使用、加载和重建耗时 | 明确内容键和内存预算，先用简单保留策略 | 原生文件缓存或简单淘汰已达到相同效果 |
| 换节点是否胜过等原节点 | 合法设备、队列、数据与初始化成本 | 先做离线决策回放，不先开发跨节点迁移 | 即使理想预测也没有明显收益 |
| 联合决策是否优于分别优化 | 多任务共享主存、CPU、GPU 的真实竞争 | 与全局池化加准备前移对比 | 收益全部来自已有池化或去掉冗余启动 |

**优化目标。** 对固定 G 条 rollout，定义 `T_group = max(C_i) - t0`，其中 t0 为整组释放时刻，C_i 为第 i 条有效反馈返回时刻。保持 G、代码版本、任务输入与评分协议一致。失败不能当成功，也不能丢弃慢样本。GPU 秒、主存峰值、重建次数是辅助成本，不另加与此目标冲突的公平性主目标。

**最小验证路线，属于提案，本次不执行 GPU。**

1. 从 2 个已审核的真实 GPU 功能任务，各选 2 条真实代码修改轨迹，每条最多 3 次工具调用，总计最多 12 次调用。先冻结补丁和输入，避免 Agent 随机性掩盖机制。先确认任务许可证和评分协议允许该评测用途，不默认用于训练语料。
2. 预算上限为两张独立环境 GPU、30 分钟、每调用最多 120 秒。现场预检失败则停止。资源不满足时不自动借训推 GPU，不自动扩大规模。
3. 记录 CPU 准备、文件/主存命中、请求、准入、启动、执行、归还、反馈时刻以及输入与代码身份。缺失某阶段就报告缺失，不补成零。
4. 先算理想上界。如果可优化准备只占总关键路径的 5%，即使完全消除，理想加速约为 `1/(1-0.05)=1.053`，通常不值得先造复杂调度器。这是教学阈值示例，实际门槛应在实验前约定。
5. 对比固定卡、当前同机池、同机池加已有 prepared/原生缓存、简单成本模型、候选联合策略。保留上游已有 fixture 和服务复用。只胜过固定卡不能证明新算法有效。
6. 对合法依赖做消融：固定放置只改准备、固定准备只改放置，再测联合方案。分别计入控制、重新初始化和清理成本。若简单基线已取得全部收益，停止此选题，而非继续加预测网络。
7. 冻结轨迹只证明执行机制。只有机制成立后，才另外预算少量真实多轮 Agent，检查更快反馈是否保持功能结果与任务完成率。最后才考虑训练收益。

**备选方向**是[组反馈精度与测量预算](command-scheduling-research.md)，它需要受控评分器和独立的误差验证，不是本篇非计时主线的一个小补丁。已有文档已列 KREX、GPU Forecasters 等近邻，不能跳过它们只与 RollArt/DynaRL 比较。

## 12. 本地源码映射与阅读路径

以下图与源码在 2026-11-06 局部核对，包含当前未提交实现。研究中的准备状态目录和联合优化器尚未实现。

```text
[L1] runner 申请会话，保留主机资源和容器
       ↓
[L2] 普通 exec_gpu，或 execute_prepared 先完成协作式 CPU 准备
       ↓
[L3] command acquire：固定绑定或显式同机池，选合法单卡
       ↓
[L4] 授权并执行新进程，返回输出
       ↓
[L5] 物理归还确认 → 清 GPU 记账 → 下一轮回 L2
       ↓ 整任务结束
[L6] 汇合作业、清理所属容器、释放会话
```

图例：图里每个部分对应的源码位置，也是“跟着图读源码”的顺序。

|---|---|---|---|
| 1 | L1 `run_harbor_episode` | 任务需求变为会话租约 | [runner.py:372](../../../examples/sciaccel_rl/runner.py#L372) |
