### 哪些运行失败了，补跑改变了什么

先展开计数：PSRL step 是一次策略训练迭代；每步使用若干题目组，每组包含多条 rollout，也叫轨迹或 episode。本组任务每条轨迹包含两次环境 GPU 命令、三次模型请求。因此六卡两步的目标是 **2 step × 6 组/step × 2 轨迹/组＝24 轨迹＝48 命令＝72 请求**；八卡普通 AIME 十步是 **10 × 10 × 2＝200 轨迹＝400 命令＝600 请求**。这是累计工作量，不是同时运行数量；环境命令内部的参数更新次数也不等于 PSRL step。高显存短档每步六组，不能套用普通 AIME 每步十组。

### 同样叫超时，实际阻塞位置不同

先看真实 Episode 例子。这张图从各条轨迹开始计时，画的是 11-23 历史运行，不是新的实验。

[![历史Episode基线的三批准入、持卡与720秒超时](../../experiments/episode-partition-queue.png)](../../experiments/episode-partition-queue.svg)

两张环境卡各允许五个会话持有预算，24 条轨迹分成 10、10、4 三批准入。轨迹 12 第 15.92 秒得到第一次模型回复，随后等了 541.69 秒，第 557.61 秒拿到资源。它此时只剩 **720−557.61＝162.39 秒**，需要完成环境适配、模型回复、环境验证与收尾。实际适配在第 562.69～668.79 秒执行，结束后剩下 **720−668.79＝51.21 秒**；随后验证没有在总期限内结束。清理继续到约第 732.49 秒。这里的限制从轨迹开始就计时，不会在获准 GPU 时重新给 720 秒。[完整时间线与条件](../../experiments/09-资源分区_静态卡池与推理余量共享.md#720秒历史尝试后排拿到卡时只剩不足三分钟)

Command 十步失败则发生在另一位置：**进入 GPU 执行入口 → 查询所属容器 ID → 申请 GPU → 启动和执行命令 → 物理归还**。失败停在第二步，此时尚未发出该条命令的 GPU 准入申请。[历史冻结源码](../../env-service-verification/results/partition-three-way-20261125/three-way-10/command_static/source/psrl/workers/env_service/docker.py#L69)每次调用 `docker compose ps -q main`，内部期限固定 10 秒。[完整调用栈](../../env-service-verification/results/partition-three-way-20261125/three-way-10/command_static/fixed/launcher.log#L3037)指向这条路径；提高 GPU 排队期限不会改变它的内部查询上限。主目录的新路径见下一节。

重叠交接失败是拿到 GPU 之后的执行期限。在同波正常返回的一个命令中，**239.98 秒总耗时＝169.59 秒准备＋37.10 秒迭代与保存＋33.29 秒未细分边界开销**。准备包含导入、模型加载与数据编码，已经消耗约 71% 的执行预算。失败的两条命令缺少相同粒度的阶段耗时，不能直接套用正常命令的分解，更不能把全部耗时都解释成 GPU 计算竞争。

历史 Agent 包装层虽在日志文字提醒“可能来自下游调用”，但仍统一返回 `TRAJECTORY_TIMEOUT`；当前[超时处理](../../../../psrl/workers/agent_loop/loops/base_agent_loop.py#L731)检查外层期限是否真的到期，分别返回 `trajectory_timeout` 和 `operation_timeout`。原 Docker 10 秒查询抛出的是 `RuntimeError`，走普通异常路径；它与上述分类问题不是同一异常分支。已有个别任务循环自行返回超时原因，本轮没有改写这些任务特有语义。

### 容器查询修复与 trace 能回答的问题

**10 秒没有返回是明显长尾，但现有证据不足以断言 Docker 有确定的程序缺陷。** 历史 Python traceback（异常调用栈）显示子进程已创建，Harbor 在 `_collect_buffered_output → process.communicate()` 等待。`communicate` 同时等待输出读取与进程退出；内部 10 秒期限从这段等待开始，不含它之前的 Python 构建命令和创建子进程耗时。该栈无法继续区分 Compose 插件启动、子进程读配置、Docker 服务响应、输出管道关闭或调度延迟。失败轨迹 uid=130 的记录尚无成功 GPU 命令返回。当前可见环境查询对应时段 Docker journal 没有日志，不能用今天的成功 trace 补成昨天的故障现场。

[![成功查询耗时与历史trace的可见边界](../../experiments/container-lookup-trace.png)](../../experiments/container-lookup-trace.svg)

图上半部是本次同一个 CPU 容器的三组顺序查询：Compose 为 **173.88／161.25／437.28 毫秒**，直接 API 为 **1.29／1.14／1.07 毫秒**。这是最小配置、单节点、单次三对的控制路径测量，不是训练加速比。另一次只跟踪自建查询进程的 `strace`（系统调用轨迹）看到 Docker CLI 启动 Compose 插件、读取配置文件、连接 `/var/run/docker.sock`；有 trace 的那次不计入上述时间，避免混入跟踪开销。[原始结果](../../env-service-verification/results/container-query-20261126/result.json) · [新抓的成功系统调用轨迹](../../env-service-verification/results/container-query-20261126/compose.strace)

主目录使用已有 `docker_api` 模块直接调用本机 Unix socket，通过 Compose 项目、`main` 服务和租约标签筛选容器；调用方提供 actor 身份时也核对它。只接受唯一、正在运行且归属匹配的完整容器 ID。**每条命令重新查当前容器，不缓存 ID**，因此容器重建后不需要猜测旧缓存是否失效。后续节点准入仍会检查容器状态和设备归属。参见[提供者入口](../../../../psrl/workers/env_service/docker.py#L70)和[查询与重试](../../../../psrl/workers/env_service/docker_api.py#L52)。

查询最多两次，每次 10 秒，中间间隔 0.25 秒；请求耗时与重试间隔都仍受上层剩余准入时间和整轨迹期限约束。只重试读请求的超时、连接异常及指定的服务端临时错误。归属不符、容器缺失、结果不唯一等情况直接拒绝；取消会停止重试。**不重放环境 GPU 命令，不放宽显存预算，也不自动重跑训练。** 本机 API 路径沿用既有本机设备控制约束，不支持把远程 Docker context 当成本机 daemon。

| 新增记录 | 发生失败后能回答什么 | 仍不能单靠它回答什么 |
|---|---|---|
| 查询连接、等响应头、读响应体、身份校验及每次尝试耗时 | 请求在哪个边界停住，是否重试，返回的是哪个容器 | daemon 内部为什么慢，需要对应服务端日志或进一步诊断 |
| 本地命令队列、上次物理归还、容器查询、GPU 准入、执行、归还请求、取消清理 | 原始失败阶段、请求身份、各阶段时间与准入剩余预算；清理不能覆盖首次失败 | 命令内部的模型读取、CPU 等待、GPU 计算细分仍需任务自身打点 |
| `trajectory_timeout` 与 `operation_timeout` | 公共 Agent 包装层自己的总期限到期，还是下游操作先超时 | 任务循环主动吞掉错误或自行返回原因的内部细节 |

执行阶段记录随异常、`last_gpu_command` 或作业 reservation 暴露，失败阶段同时写日志，不额外为每条命令执行同步文件写入；实验调用方可将这些结构化字段纳入自己的结果。源码见[公共执行阶段](../../../../psrl/workers/env_service/gpu_execution.py#L27)。异常本身也保留记录，因此本地排队尚未获得执行锁时，不需要覆盖正在执行的另一条命令的后端记录。

**验证结果与边界。** 第一轮 50 项测试通过，覆盖 Unix socket 故障注入、身份变化、超时归因、GPU 执行取消与物理归还顺序。补充无 actor 的合法独立租约调用、精确请求期限后，相关 17 项复核通过，其中 16 项与首轮重叠，合计 51 个不同测试，不是 67 个不同测试。真实容器验证位于用户私有节点，只创建一个限制 CPU、主存且不挂 GPU 的容器，三对查询身份一致，强制重建后 ID 改变，停止后拒绝，最终按项目核实容器全部删除。没有重现历史 10 秒卡顿，没有运行新的 science／AIME 策略训练，也没有把补丁写进已运行的冻结实验目录。

复现脚本为 [verify_container_lookup.py](../../env-service-verification/scripts/verify_container_lookup.py)，需要已激活项目环境、本机 Docker socket、已有包含 `sleep` 的镜像及 `strace`；参数为 `--image <本地镜像> --output <新的结果目录>`。本次外层预算 150 秒，正常完成约 16 秒。它只处理本次生成的 Compose 项目。绘图脚本为 [draw_container_lookup.py](../../env-service-verification/scripts/draw_container_lookup.py)。

异常序列化补充验证后，执行层 10 项再次通过，仍属于上述 51 个不同测试。各轮日志、最终源码哈希及实机测量与后续小幅完善的版本边界保存在[验证清单](../../env-service-verification/results/container-query-20261126/verification.json)中。

| **P1：冻结配置与训练兼容检查** | 持卡参数传错可早发现，融合算子错误却在整批采样后才暴露 | 对每个策略生成并校验最终配置；保留实际依赖来源和补丁哈希。当前测试组合显式关闭不兼容融合路径；换模型／分布式配置时先做最小前向兼容检查，不能只靠 `py_compile` 或导入成功 |
| **P1：准备阶段与启动长尾** | 169.59 秒准备会用尽命令预算，注册失败也会拉高初始化 | 先补导入、文件读取、模型搬运、CPU 等待和退出阶段的低开销记录，再决定本地依赖缓存、预热或限制同时准备数量。失败进程退出前保存有界诊断；不先把所有准备任务提并发，也不未经核验复用旧模型／代码状态 |
| **P1：汇总失败与重跑成本** | 只展示补跑成功时间会隐藏完成作业所需的额外投入 | 汇总关联原 attempt、补跑原因、修改项、每次时长与清理。分别报告成功尝试的性能、所有尝试的完成性和累计成本；单次失败不能推导稳定故障率 |

“查询恢复＋阶段记录”小修复包已经完成本地针对性验证，后续正式对照应在三种策略上冻结同一补丁，并保留新阶段记录；不能只给动态组打补丁。下一步优先使用记录定位准备长尾、完善期限和兼容预检。R3 所有权和 R4 MPS 故障仍是扩展部署门槛，不能拿它们解释本次缺少对应证据的失败。

### 证据范围与结果使用规则

- **性能结果与失败记录并列保存。** 八卡 Command 静态首次完成六步，不能和其他组的十步完整耗时计算加速比；补跑完成十步后才能比较同工作量，同时标注跨运行窗口。原失败和补跑监督记录均确认物理释放。
- **修复、规避和重跑成功分开。** 错误模式配置已纠正；融合算子通过共同配置绕开；Docker 历史补跑未修改查询，当前主目录才完成查询与诊断修复；准备长尾和历史查询慢因仍待定位。增加期限只改变终止条件。
- **较慢不等于失败。** 单步视觉完整方案较 Command 静态慢 4.62%，普通 AIME 最新两步 Command 静态也比 Episode 慢，二者都是完整完成的结果；前者未借卡，后者差异尚未分解。不能据此宣称已出现正确性故障或稳定性能回归。
- **这些不是所有历史运行的故障率统计。** 本次聚焦 11-23～26 的主基线、十步消融、交接补跑，并引用 11-19／23 启动审计；旧 science、MPS 与状态复用实验仍按[实验总览](../../experiments/01-实验总览_调度收益与证据范围.md)各自版本解释。本节不把不同持卡方式、CPU 故障注入和真实 GPU 训练汇成一个成功率。
- **成功范围不扩大。** 当前训练对照证明真实采样、训练调用、调度和清理链路完成；已报告的零组内奖励方差／零策略梯度不等于运行崩溃，也不构成模型学习效果提升的证据。完整方案在负载回升时取回推理卡的真实闭环仍缺验收，见[研究优先级](../../milestones/05-调度研究_研究全景与证据详解.md#接下来可以做什么优先级与验收边界)。

## 3. 优先解决的工程问题

优先级是本次建议：P1 表示扩大使用范围前应补齐，P2 表示在现有受控范围内可继续使用但会限制效率或长会话。没有将本次未复现的风险写成线上事故。

### R1：同名 Router 复用配置核对，已实现并完成隔离验证

`create_env_router` 创建或复用命名 actor 后，先读取服务启动时保存的配置契约，再与本次预期比较。契约包含声明配置、训推节点身份和协议版本，同时比较规范化结构与 SHA-256 指纹。不一致或旧服务没有契约接口时明确拒绝，不继续预热、不热改活动服务。

这里采用严格声明配置比较，字典键顺序被规范化，训练节点集合排序去重。省略默认项与显式默认值可能仍被拒绝，不宣称支持任意语义等价配置。应从同一份解析配置启动复用客户端。

源码见 [router_contract](../../../../psrl/workers/env_service/router_contract.py#L10) 和 [创建入口](../../../../psrl/workers/env_service/router.py#L752)。CPU 测试覆盖同配置复用、预算、后端、设备、节点身份、协议差异，以及缺契约接口和预热前拒绝。2026-11-11 隔离真实 Ray 命名 actor 的同配置复用、异配置拒绝通过。双 driver 和共享长期服务部署仍待验收。

### R2：节点只读诊断与受控恢复，已实现并完成隔离验证

新增 [node_diagnostics](../../../../psrl/workers/env_service/router.py#L581)，列出健康错误、重试耗尽、活动租约、退休待清理租约、阻断 unit、GPU 命令及旧借卡阶段。新增 [recover_node](../../../../psrl/workers/env_service/router.py#L605)，允许管理员在耗尽后重新发起一次有超时的物理检查，并共享已在途探测。重试次数重开后，常规路径仍受原自动预算限制。

恢复不会直接清空资源字典或 GPU 隔离。节点查询成功和物理清理确认仍为不同条件，`healthy` 不保证全部任务获准。死节点仍有活动归属时保留旧句柄，孤儿 MPS 服务仍需人工处理。CPU 回归覆盖继续失败、超时、待清理、并发调用和活动归属保护。2026-11-11 隔离服务验证使用真实 Docker 探测链，在专属节点 actor 内注入失败、超时和待清理标志，阻断与故障解除后的恢复均通过。活动 GPU 任务故障仍需单独验收。

两个问题的初学者背景、完整例子、调用图和可运行实验见[配置复用与节点恢复](05-EnvRouter_配置恢复与Worker重试.md)。R3 的重启持久化和跨控制器所有权不属于这两个入口的修复范围。

### R3：Router 重启与跨 Router 设备唯一所有权，扩展部署前 P1

**确认的架构边界。** 账本的租约、待清理记录、预算和测量保存在内存字典，见 [EnvUnitLedger.__init__](../../../../psrl/workers/env_service/ledger.py#L66)。一个账本内校验配置，不等于不同 Router、不同 Ray 集群之间有统一设备所有权。

教学例子：A、B 两个独立 Router 都配置同一张 80 GiB GPU，各自在尚未实际分配显存时承诺 60 GiB。单个账本均未超额，但总承诺达 120 GiB。实测显存不能替代跨控制器的预约协调。本次未运行双 Router GPU 竞争实验。

如果仍是一套受控实验独占资源，可先明确单控制器部署约束。若要支持多用户或长期服务，则需要设备所有权协调、可恢复的租约状态，以及防止旧控制器在失去所有权后继续授权的代际凭据。自动重启需要与这些归属检查一起设计。

### R4：MPS 服务故障与真实接入证明仍缺验收，P1 验证项

`launch` 检查容器身份、IPC 和管道挂载，配置 MPS 环境后放行作业。它没有在运行期间持续证明该客户端仍由目标 MPS 服务管理。参见图中 4 和 [MPS 的故障边界](../02-资源与调度/04-GPU并行_MPS执行后端.md#8-原理与当前效果应该怎样理解)。这是已知验证缺口，不能写成“已经测出静默退回普通 CUDA”。

建议先限定环境专用卡，覆盖服务在启动前消失、连接过程中失联、执行中退出、取消回执缺失四类故障。验收看作业是否明确失败、预算是否保留、相邻作业是否受影响、最终物理释放是否确认。还要保留 cgroup v1、可信任务域、客户端显存限额按进程生效等限制，不把该实现当作恶意多租户隔离。

### R5：严格队首准入会闲置可用资源，P2

direct 的 [acquire](../../../../psrl/workers/env_service/command_gpu.py#L106) 和 MPS 的 [admit](../../../../psrl/workers/env_service/parallel_gpu.py#L208) 都先找队首，后来的请求不能越过它。同机命令池共用一个 FIFO，并不是每张卡独立队列。FIFO 指先进先出，这是确定的策略，不是竞态或账本错误。

教学例子：unit 总预算 80 GiB，活动作业占 50 GiB。队首先来一个需要 40 GiB 的 A，后面 B 只需要 10 GiB。A 放不下，B 虽然放得下也要等，30 GiB 余量暂时闲置。MPS 并发机制无法自动解决这个上层排队问题。

建议考虑有限回填：允许能放下的小任务先运行，同时限制绕过次数、等待年龄或为队首保留容量，避免大任务一直等不到。是否缩短整组完成时间必须用相同工作量验证，不能仅看瞬时 GPU 占用。目标仍可保持整组反馈完成时间，不必另引入公平性优化目标。

### R6：作业数量上限是会话累计值，P2

[GpuJobManager.start](../../../../psrl/workers/env_service/gpu_jobs.py#L61) 根据 `len(self.jobs)` 限制默认 128 项，已完成作业仍保留。MPS `submit` 也按同 lease 的累计记录数限制 128 项，见 [submit](../../../../psrl/workers/env_service/parallel_gpu.py#L133)。所以即使每次只跑一条，第 129 次提交也会被拒绝。这是有意的有界保护，不是已确认内存泄漏。

短 episode 通常不会触发，但长会话或持久执行器池需要明确产品契约。若支持更长会话，应把活动上限与历史保留上限分开，提供终态确认和有界归档，保留去重与取消所需身份，不能直接删除所有完成记录或无限调高上限。

## 4. 后续能力与验证缺口

| 方向 | 当前状态 | 建议 |
|---|---|---|
| 自动 command/episode | 静态配置，部分任务有显式 command 接入 | 先建立任务能力声明，说明是否常驻 GPU、命令边界是否可靠、是否可重跑 |

| 性能评分与并发干扰 | KernelBench command 已限制为专用 direct | 不为提高吞吐拆掉评分隔离，正确性评分和计时评分分开处理 |
| vLLM 共卡 | 有显式共享和睡眠借卡分支 | 环境专用 MPS 验证不能替代真实训推共存与模型性能边界验证 |
| 原请求跨 worker 重派发 | 有重试与补采，缺完整转移协议 | 先确认旧执行终止，再引入尝试身份、旧结果隔离和有界重跑 |
| 多节点派发吞吐与长期运行 | 有健康过滤、容量与负载偏好 | 不能将源码接入或单卡组件验收等同于长期多节点收益 |

已有 MPS 真实训练证据是训练段约一成收益，短流程整体不一定更快。高显存压力下减少 OOM、MPS 计算共享、完整训练提速是三个不同结论。具体数字继续以[实验报告](../../experiments/04-MPS训练_并行执行与控制修复对照.md)为准，不为 review 追加训练。

## 5. 建议修复包与验收条件

近期实验可靠性的小修复包已完成[第 0 节的定向验证](#容器查询修复与-trace-能回答的问题)：容器查询有界恢复、超时分段记录。后续优先处理期限预检、训练兼容和准备长尾。以下 R1–R6 是按部署范围选择的服务工作，不替代近期失败复盘的优先级。

1. **配置与恢复入口**：R1、R2 本地实现已完成。配置不一致明确报错，节点故障有可读原因，恢复经过新的物理核对。下一步在真实部署中按相同边界验收。范围有限、能直接降低下一次实验误判和人工排障成本。
2. **MPS 故障矩阵**：处理 R4。先补服务失联和清理回执缺失验证，再根据失败点修改实现。先确认异常下的回收，再扩大并发。
3. **长会话与队列效率**：有实际需求时做 R5、R6。保护大任务，同时验证整组完成时间和有界历史存储。
4. **长期或多用户部署基础**：启用该部署目标前必须完成 R3，不能排在跨节点大规模实验之后。
5. **动态调度研究**：建立能力声明和分段成本数据之后，再推进自动模式、动态放置和卸载预测。把新策略与故障恢复分开验收。

单控制器实验与多用户服务的前置条件不同，按近期部署目标选择修复包即可。

## 9. 从训练执行链理解剩余工作

把一次训练中的环境执行拆开，剩余问题就容易定位：

| 执行位置 | 对应问题 | 读者要检查什么 |
|---|---|---|
| 训练启动方找到 Router | R1 配置一致性 | 找到的服务是否使用本次预期预算、设备和后端 |
| Router 选择节点和批准资源 | R2 恢复、R3 所有权 | 节点故障解除是否经过物理检查；是否只有一个控制器有权授权设备 |
| GPU 命令进入队列 | R5 队首阻塞 | 大请求等待时，较小请求能否安全使用余量 |
| 多个 CUDA 程序通过 MPS 执行 | R4 服务异常 | 服务失联后，预算是否保留，所属作业是否清理，相邻作业是否正常 |
| 同一容器不断提交命令 | R6 累计记录上限 | 活动作业数与历史记录数是否分别受控 |

CUDA 是程序使用 NVIDIA GPU 的运行接口，MPS 是协调多个 CUDA 客户程序的服务。上表的“服务恢复”既包含进程能回答请求，也包含它管理的物理资源归属已经核实。相关手算例子见 R3、R5、R6。

运行 [CPU 教学算例](../../env-service-verification/scripts/model_engineering_backlog.py)：

```bash
python docs/env-worker-deep-dive/env-service-verification/scripts/model_engineering_backlog.py
```

先激活项目环境，并从仓库根目录执行。脚本使用标准库和教学数字，展示三个具体结果：

1. 两本账各登记 60 GiB，总承诺 120 GiB 超过物理容量 80 GiB；重建空账本也会丢失旧预约。
2. 容量 80 GiB、已用 50 GiB，队首需要 40 GiB 时，后面只需 10 GiB 的任务一起等待，30 GiB 余量暂时闲置。
3. 保留 128 条完成记录后，活动数为零，但下一次提交仍触及累计上限。

2026-11-11 的实际 CPU 输出与这三个例子一致。这个脚本解释内存账本、队列和计数的行为；真实 GPU 归属与 MPS 服务异常继续使用第 6 节列出的独立验收。
