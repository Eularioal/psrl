# 从 YARN 到 GPU 工具调度：哪些启发可能形成研究贡献

> **核心结论**：按 Hadoop YARN 理解。最值得借鉴的是应用级协调与资源级调度分离，以及执行保障可以随阶段改变。当前首选研究候选是“比较关系感知的 GPU 测量调度”：评分器声明候选之间要解决的比较问题，Env 联合决定测量批次、设备与保护窗口，目标是在反馈误差约束下缩短整组完成时间。第二候选是跨工具等待的状态保留与计算租约分离。两者均为提案，分层、独占、共享、状态驻留本身都不是新贡献。

## 先理解 YARN 提供的分工

YARN 是 Hadoop 的资源管理体系，名字展开为 Yet Another Resource Negotiator。它把集群资源管理和具体应用的执行逻辑分开。先看完整关系，图的左侧是外部机制，右侧是本项目的对应关系与提案，不表示一一等价。

```text
YARN                                     Env 研究设计
ApplicationMaster 应用协调者               [1] 同题组与评分协调者（新策略待实现）
    │ 知道应用任务及其依赖                     │ 哪些候选要比较、何时需要可信结果
    ▼                                         ▼
ResourceManager 集群资源管理者              [2] EnvRouter 与资源账本（已有）
    │ 按集群资源约束分配                       │ 选择设备与测量窗口（后者是提案）
    ▼                                         ▼
NodeManager 节点执行管理者                  [3] Env 节点服务与 EnvWorker（已有）
    │ 启动、监控、回收                         │ 创建容器、执行、观察、回收
    ▼                                         ▼
Container 获配资源下的执行单元              [4] GPU command 与评估器（已有执行接口）
    │ 状态反馈                                 │ 数值结果 + 条件记录 + 有效性检查（待补）
    └─────────→ ApplicationMaster              └─────────→ [1]
```

图例：图里每个部分对应的源码位置。

| 编号 | 对应关系和边界 | 本地入口 |
|---|---|---|
| 1 | 现有 Harbor runner 编排单个任务，尚无本文所述跨候选比较协调策略 | [run_harbor_episode](../../../examples/sciaccel_rl/runner.py#L369) 申请会话租约，完整组级协议为提案 |
| 2 | 会话准入和 command 准入已有，反馈误差预算尚未加入 | [EnvUnitLedger.try_admit](../../../psrl/workers/env_service/ledger.py#L113)、[GpuCommandScheduler.acquire](../../../psrl/workers/env_service/command_gpu.py#L82) |
| 3 | 执行环境创建和销毁 | [EnvWorkerEnvironment.start](../../../psrl/workers/env_worker/harbor.py#L146)、[stop](../../../psrl/workers/env_worker/harbor.py#L182) |
| 4 | 统一 GPU 执行与已验证的官方评估调用 | [exec_gpu](../../../psrl/workers/env_service/managed_execution.py#L53)、[FlashInfer 评估 main](../env-service-verification/scripts/flashinfer_official_eval.py#L8) |

ResourceManager，简称 RM，回答集群资源怎样分。NodeManager，简称 NM，负责单节点上的执行。ApplicationMaster，简称 AM，知道某个应用的任务依赖、完成条件和下一步需求。AM 是应用框架中的协调程序，不等同于“大模型 agent”。YARN container 首先是资源分配与执行抽象，并不必然是 Docker 容器。[官方架构](https://hadoop.apache.org/docs/current/hadoop-yarn/hadoop-yarn-site/YARN.html)

把这个思路用于当前问题：Env 不必理解每个算子的数学意义，评分器也不必自己扫描集群抢卡。前者提供资源条件和成本，后者提供哪些测量能够帮助应用完成，两者通过显式协议交换信息。给程序起一个 AM 的名字没有创新，关键在协议额外表达了什么，以及联合决策是否有可测收益。

## 哪些机制能借鉴但不能直接当创新

| YARN 思路 | 可以怎样借鉴 | 容易误解的边界 |
|---|---|---|
| 应用协调与集群调度分开 | 评分器报告候选差距、依赖和剩余测量需求，Env 报告资源与切换成本 | 层次化调度是已有体系，不是论文贡献本身 |
| GUARANTEED / OPPORTUNISTIC | 普通工作利用可借用资源，关键测量申请更强保护 | YARN 的保障主要是资源分配、启动与抢占语义，不是 GPU 性能或统计准确性保证 |
| 运行时升级、降级执行类型 | 一个任务不同阶段可以改变保障需求 | 修改优先级不会自动排空已提交 CUDA 工作，也不会自动释放显存 |
| 节点本地机会队列 | 对很短的 GPU 工作减少重复远程调度往返 | 只有实际瓶颈在控制面时才有价值，并且要保证授权不会重复消费 |
| 资源本地性 | 把环境、编译缓存、模型状态和待比较候选的放置一起考虑 | 最近或缓存命中不一定最优，等待与测量可比性也要计入 |

官方 opportunistic container 可以先在节点排队，必要时为 guaranteed container 让路，也支持申请提升执行类型。这里借鉴的是按阶段改变保障的思路，不能把 YARN 的“guaranteed”翻译成“计时准确”。本项目若要实现可靠测量，需要另行定义保护边界、条件记录和统计验证。[官方执行类型文档](https://hadoop.apache.org/docs/stable/hadoop-yarn/hadoop-yarn-site/OpportunisticContainers.html)

## 首选课题：比较关系感知的测量调度

用户真正想知道的常常不是“每个 command 多快完成”，而是“这几个实现谁更好，是否足够好，下一轮该保留谁”。因此调度对象可以扩展为一个有比较关系的测量请求。

比如评分器提交 A、B 两个候选及同一个 workload，声明当前需要分辨它们的性能差距。请求还携带候选代码哈希、设备类型、计时后端、缓存协议、容许误差与截止预算。它不直接给 Env 一个看似准确的概率，误差模型必须来自测量和校准。

拟议过程是：

1. 应用协调者汇集同题候选和已有结果，决定尚未解决的是排名、阈值判断，还是完整数值奖励。
2. Env 根据可用 GPU、冷启动、排空竞争作业的成本和缓存状态，决定下一批测哪些候选、在哪里测、是否需要保护窗口。
3. 节点在实际满足协议条件后才开始计时，记录设备身份、版本、计时方式、顺序和竞争状态。记录本身不等于统计正确证明。
4. 评估器返回数据，协调者检查条件是否一致、结果是否足够。若代码、设备条件或协议改变，受影响结果要失效或重新校准。
5. 达到任务规定的反馈精度后返回，其余测量停止。若预算耗尽，明确报告不确定，不能将未认证结果静默写成高精度奖励。

若训练仍需要所有候选的数值奖励，不能因为确定了最优候选就删掉其余 rollout。选择最优、过阈值和 GRPO 组内优势各有不同的停止条件，须由应用声明。GRPO 是按同题组的相对奖励构造训练信号的方法，完整说明见[已有研究文档](command-scheduling-research.md)。

**教学例子**：A 在既定独占协议下为 10 微秒，B 为 10.2 微秒。若 A 测量时受竞争影响增加 10%，B 在空闲时测，返回 11 与 10.2，就会选错 B。反复测 A 所处的污染状态，只可能更确信这个错误。

可以把 A、B 放入同一受控测量批次，在一致的缓存协议下交错测量。教学模型中，假设线性漂移每次增加 0.1 微秒，按 A、B、B、A 顺序得到 10、10.3、10.4、10.3。均值是 A=10.15、B=10.35，差值仍为 0.2。ABBA 顺序让两候选的平均测量位置相同，因此抵消了这个**特定的线性漂移模型**。

这不是通用校正算法。候选特异的带宽竞争、不同热状态和相互影响不一定抵消，必要时仍要独占、重置缓存或采用其他实验设计。ABBA、配对测量与批处理本身都不是新的贡献。

另一笔账是切换成本。假设进入一次保护窗口需 8 ms，每个采样块需 1 ms，四次单独进出需 36 ms，合为一个四采样块的窗口需 12 ms。但是等齐候选和占用更长连续窗口可能延迟其他关键轨迹。真正的问题是**何时值得一起测、何时应立即测、何时追加证据**，而不是永远批量化。

拟议目标仍为最小化固定组完成时间，约束具体应用所需的反馈错误或偏差。在目前未实测误差分布的阶段，不承诺诸如“99% 可靠”之类的概率。若并发改变实际训练工作量，分数变化属于结果改变，不属于本课题可以用配对测速消除的测量误差。

## 第二课题：状态保留与计算租约分离

当前 command 将资源持有边界放在命令上。另一个值得研究的问题是：工具等待期间，是否可以保留昂贵的 GPU 状态，同时让出计算机会，何时才值得卸载。

**教学例子**：一张 96 GiB 卡，A 有 60 GiB 常驻状态，进入等待，B 需要 40 GiB、执行 1 秒。A 即使不计算，空闲显存也只有 36 GiB，B 仍放不下。若 A 卸载加恢复需 6 秒，B 提前执行的 1 秒并不自动带来整组收益。必须考虑 A 何时返回、B 是否在关键路径，以及是否有别的空闲设备。

设计上可分为：容器及主存会话预算、仍占据的 GPU 状态预算、实际执行预算。状态预算必须持续记账，计算让出不能把显存占用清零。进程暂停不意味着显存释放，也不保证先前提交的 kernel 已执行完。

可研究按任务返回时间的不确定性和状态重建成本，联合选择保留、显式卸载、等待或换卡。这里的返回时间包括 agent 思考、CPU 工具和外部评估，可能不规则。执行协议需要可合作的安全点、准确归属和恢复验证，不能把任意 CUDA 进程当作可无损抢占。

这是第二优先级。它更接近用户先前关注的 episode offload，但实现面和已有工作的重合都更大。当前并未实现任意 GPU 状态自动卸载，此处也没有据此修改生产路径。

## 已有工作与创新边界

| 已有工作 | 已经覆盖的部分 | 候选课题仍须证明什么 |
|---|---|---|
| [KREX](https://arxiv.org/abs/2609.30057)，2026 预印本 | 命令内关键区域独占，排空竞争工作并保护测量过程 | 相比区域隔离加独立自适应测量，比较关系与测量批次的联合决策是否进一步改善可靠反馈完成时间 |
| [GPU Forecasters](https://arxiv.org/abs/2605.31464)，2026 预印本 | 用模型选择性预测 kernel 性能，减少昂贵 GPU 评估 | 不能把“不确定才上 GPU”当新意。要验证物理调度条件与反馈协议耦合的额外收益 |
| [Salus](https://proceedings.mlsys.org/paper_files/paper/2020/hash/d9cd83bc91b8c36a0c7c0fcca59228f2-Abstract.html)，MLSys 2020 | 细粒度 GPU 共享、切换与显存管理 | 状态常驻加计算复用本身不新。要证明 agent 工具返回不确定性下的决策优于现有保留和驱逐策略 |
| [Gandiva](https://www.usenix.org/conference/osdi18/presentation/xiao)，OSDI 2018 | 利用迭代行为进行 GPU 时间共享 | 与规则训练迭代相比，开放式工具阶段带来的新困难必须实测而不是假定 |
| [Sparrow](https://amplab.cs.berkeley.edu/projects/sparrow-low-latency-scheduling-for-interactive-cluster-services/) | 分布式低延迟调度 | 本地队列、减少中央往返不单独构成新贡献 |

2026-11-06 核查以上官方说明与论文摘要，属于选题初筛，不是完整系统综述，也不足以证明没有其他重合工作。更完整的近邻清单见[command 研究的新颖性复核](command-scheduling-research.md#2026-11-05-新颖性复核与实现取舍)。

首选课题的贡献假设应写成：“应用声明需要解决的比较关系，系统基于执行条件和切换成本，联合安排证据采集与 GPU 放置。”论文必须把新增机制和成熟实验设计、成熟隔离技术各自贡献拆开。若给 KREX 加一个简单批处理队列就取得相同效果，应当缩小或放弃创新主张。

## 如何用当前 benchmark 验证

第一课题先用 KernelBench 和 FlashInfer-Bench，固定多个正确候选，包含明显快慢和非常接近的候选。覆盖计算、带宽及短 kernel，不把单个 RMSNorm 的功能通过当作研究证据。然后用 SWE-Serve 的 speedup 子集或正式 InferenceBench 服务任务验证跨层次适用性。具体接入状态见[benchmark 选型与结果](ai4infra-performance-benchmarks.md)。

第二课题需要显式保留跨命令状态的真实任务。可从现有 InferenceBench 常驻服务入手，再考虑 RE-Bench，但必须确认选定任务确实有 GPU 状态和外部等待，不能为了制造收益人为延长空窗。继续优先使用独立空闲设备。

第一课题至少设五个对照：全程独占、朴素共享、区域独占、区域独占加每候选独立自适应测量、再加简单批处理的强基线。拟议方法要在最后一个基础上证明收益，不能只打赢前两个。

主指标包括相同候选与工作量下的整组完成时间、反馈错误率或奖励偏差、总 GPU 时间和重测成本。记录冷启动、排队、保护窗口切换与清理。按实际反馈用途另报选择质量或 GRPO 优势偏差，不强迫所有任务采用同一种准确性指标。

立项停止条件：若性能误差不足以影响真实反馈、可节省的测量预算很小、批处理等待抵消收益，或者成熟基线已达到同等结果，就不继续扩大实验。现有三个 workload 的成功只证明执行链路可用，不能回答这些问题。
