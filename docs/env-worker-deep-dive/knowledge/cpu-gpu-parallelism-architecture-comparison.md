# CPU 与 GPU 在多任务并行上的架构设计对比：为什么调度粒度天生不一样

> **核心结论**：CPU 的核心和 GPU 的 SM 数量级看起来相似（都是几十到上百个），容易让人类比成"同一种东西，只是数量更多"，但两者是为完全不同的工作负载设计的硬件，调度粒度因此天生不同——CPU 核心是"按进程/线程独立分配"的通用单位，GPU SM 是"当前被选中的那一个 context 内部"的吞吐量资源池。这不是某一方"没做好"，而是各自面对的任务特征决定的必然结果。本文讲清楚这组差异从哪来、设计之初各自在优化什么，以及 GPU 后来为了补上"多租户"这块短板，用软件（MPS）和硬件（MIG）分别做了什么。具体到 PSRL vLLM + 环境共享这个场景意味着什么，见[CUDA 上下文开销与计算竞争](cuda-context-and-compute-contention.md)第 4 节。

## 1. 先看结论：一张对照表

| 维度 | CPU（多核） | GPU（多 SM） |
|---|---|---|
| 最初设计要服务的任务 | 少量、彼此无关、随时可能要切换的独立程序（操作系统上跑的各种进程） | 海量、彼此相似、可以批量处理的同构任务（最初是像素/顶点着色，后来扩展到矩阵运算） |
| 调度的基本单位 | 核心，操作系统可以把任意进程调度到任意核心 | SM 不直接对应"进程"，而是由硬件在**整张卡**粒度先选定一个 context，再把这个 context 内的线程块分发给空闲 SM |
| 核心/SM 之间能否各自服务不同进程 | 能，这是硬件默认就给的能力 | 不能（没有 MPS/MIG 时），没被选中的 context 整体挂起，不会有"匀一部分 SM 给它" |
| 切换到另一个任务的成本 | 低（切寄存器和页表基址，微秒级） | 高（涉及更大的地址空间重映射和驱动侧簿记，且设计初期几乎不考虑频繁切换） |
| 对"多租户同时用"的原生支持 | 原生支持，是操作系统最基本的职责 | 原生不支持，要靠后加的软件代理（MPS）或硬件分区（MIG）补上 |

接下来逐条说清楚这些差异从哪来。

## 2. CPU 的设计出发点：为什么核心天生能"独立分配给任意进程"

### 2.1 CPU 面对的任务特征：少量、异构、随时可能要切换

CPU 从诞生起，要服务的场景就是"一台机器上同时运行很多个互不相关的程序"——操作系统本身、你打开的编辑器、后台的网络服务，这些程序彼此做的事情完全不同，谁也不知道下一刻哪个程序会需要被唤醒、哪个会要等 I/O。这种任务特征要求硬件必须能**随时把任意一个核心让给任意一个进程**，而且切换要快，因为任务粒度很碎（一次系统调用、一次中断，都可能触发切换）。

### 2.2 核心天生具备切换到任意进程所需的全部状态

要做到"随时可以切到任意进程"，每个核心必须**自带一份完整、独立的执行状态**：寄存器组、程序计数器、栈指针等等。操作系统做的事情只是把"当前该跑哪个进程"的决策结果（一组寄存器值 + 页表基址）灌进某个核心，核心本身不关心这组值从哪来、下一刻会不会被换成另一个进程的值。正因为核心和核心之间天生互不依赖、天生能装入任意进程的状态，多核之后，"进程 A 在核心 1、进程 B 在核心 2 同时跑"才是硬件免费送的能力——不需要操作系统额外去"协调"两个核心变成一伙，两者本来就是独立的。

## 3. GPU 的设计出发点：为什么 SM 天生不是按进程分配的

### 3.1 GPU 面对的任务特征：海量、同构、批量吞吐优先

GPU 最初是为图形渲染设计的：一帧画面里有几百万个像素，每个像素都要跑**同一段**着色器代码，只是输入数据（这个像素的坐标、颜色）不同。这种任务的特征和 CPU 服务的场景完全相反——不是"少量互不相关的程序随时切换"，而是"海量彼此相似的数据，一次性批量跑完同一份代码"。GPU 的硬件设计从一开始就是为了最大化这种场景下的**吞吐量**（单位时间处理完多少数据），而不是 CPU 在意的**延迟**（单个任务多快有响应）。这个设计目标后来扩展到了通用计算（矩阵乘法、深度学习训练推理这类工作负载恰好也是"海量数据、同一份计算逻辑"），但底层硬件的取向没有变。

### 3.2 SM 面向的是"同一程序的海量线程"，不是"任意进程"

因为目标场景是"同一份代码、海量线程"，GPU 把执行单元设计成了 SIMT（Single Instruction, Multiple Threads）风格：一个 SM 同一时刻让一大批线程执行**相同的指令**，只是各自操作不同的数据，这样硬件可以用更少的指令调度逻辑换来更高的线程密度。但这个设计有个代价：SM 不像 CPU 核心那样天生具备"装入任意一个互不相关程序的独立状态"的能力，它更擅长的是"在已经选定的这一份程序（这一个 context）内部，调度海量相似的线程"。换句话说，GPU 硬件在分发线程块给 SM 之前，要先在**整张卡**的粒度确定"现在服务的是哪个 context"，这个判断不是按 SM 逐个做的，而是对整张卡统一生效——这正是第 4 节那句"没被选中的 context 整体挂起"的根源：GPU 的硬件设计压根没有为"两个完全不相关的程序同时各占一部分 SM"这件事做过优化，因为它最初要服务的场景里根本不存在"两个不相关的程序"，只有"一个程序、海量相似线程"。

## 4. 上下文切换成本：为什么 CPU 便宜、GPU 贵

CPU 切换进程的成本，本质上只是换一套寄存器值和页表基址，现代 CPU 对这件事做了大量硬件加速（比如硬件支持的快速上下文切换、TLB 的进程标签避免整表刷新），微秒级就能完成——这是因为 CPU 的设计前提就是"切换会频繁发生"，所以必须把它做得便宜。

GPU 的上下文切换天生更重：一个 context 要恢复的不只是几个寄存器，还包括整个地址空间映射、已加载到 GPU 上的代码（cubin）、驱动侧为这个进程维护的簿记结构（这些正是[CUDA 上下文开销与计算竞争](cuda-context-and-compute-contention.md#2-cuda-上下文是什么)第 2 节列出的那几块）。更关键的是，GPU 最初的设计前提是"一次把一大批相似任务交给 GPU，让它尽量不被打断地跑完"，频繁切换 context 完全不在最初的优化目标里——这是设计取向的必然结果，不是实现上的疏忽。

## 5. 当 GPU 也要面对多租户：MPS 和 MIG 分别补的是哪一层

数据中心场景出现之后，"一张 GPU 卡被多个不相关的进程/用户共享"这个需求，恰好是 GPU 最初设计时没有考虑过的场景——这也是为什么 NVIDIA 要在驱动和硬件两个层面分别打补丁，而不是"GPU 本来就支持，只是没开"。

### 5.1 MPS：软件层代理，没有改变硬件调度粒度

[CUDA 上下文开销与计算竞争](cuda-context-and-compute-contention.md#43-mps-在修哪一层不是事后合并是从源头上就只建一个)第 4.3 节已经讲过 MPS 具体怎么工作：它让多个进程的提交都转发给同一个 MPS server 进程持有的那一个 context，伪装成"同 context 下的不同 stream"，从而借到硬件本来就支持的"同 context 内不同 stream 可并发分发到不同 SM"这条路。**MPS 是纯软件层的代理，没有给硬件增加任何"按进程切分 SM"的新能力**——它解决的是"让多个进程看起来像一个进程"，不是"让 SM 真正具备像 CPU 核心那样的独立分配能力"。这也是为什么 MPS 无法提供硬件级别的故障隔离：如果某个客户端进程的提交导致了 GPU 异常，MPS server 和所有共享它的客户端都会受影响，因为大家本质上共享的是同一个 context。

### 5.2 MIG：真正的硬件分区，向 CPU 的"核心独立"模型靠拢，但要付出代价

比 MPS 更彻底的方案是 **MIG（Multi-Instance GPU）**——这是 NVIDIA 从 Ampere 架构（A100 及之后）开始在硬件层提供的能力，可以把一张物理 GPU **真正切分**成几个相互隔离的实例，每个实例有自己专属的一份 SM、显存、显存带宽、缓存，不同实例之间是硬件级隔离，一个实例崩溃不会影响另一个。这个模型在"调度粒度"这件事上，才是真正向 CPU 的"核心独立分配"靠拢了——每个 MIG 实例更接近"几个专属核心"，而不再是"同一个 context 下的不同 stream"。但代价也很明显：切分之后各实例的资源是静态固定的，不能像 MPS 那样按需弹性共享同一份资源池，总吞吐量上限因为分区边界而无法互相借用——这正好印证了第 3 节的结论：GPU 要做到和 CPU 一样的"独立分配"，必须从硬件层面真的切出边界，不是免费的。

> MIG 的硬件分区机制是 CUDA 生态的通用常识，不是 PSRL 仓库源码或实验验证出的内容，这里特意说明清楚，PSRL 当前也没有部署 MIG。

## 6. 回到 PSRL 的场景：这组差异意味着什么

vLLM 进程和环境容器进程，在 PSRL 里就是第 3 节说的"两个彼此不相关的程序"——这正是 GPU 硬件最初完全没有为之优化的场景。没有 MPS、没有 MIG 的情况下，两者只能退回到 GPU 原生支持的"按 context 整体轮转"，这不是 PSRL 代码可以绕过的限制，而是第 3-4 节讲的硬件设计取向决定的。具体这组限制在 PSRL 代码里的体现——`GpuControlGate`、共享票据、时间片轮转的调用链——见[CUDA 上下文开销与计算竞争](cuda-context-and-compute-contention.md#4-计算层面没有-mps-时gpu-在两个上下文之间怎么调度)第 4-5 节。
