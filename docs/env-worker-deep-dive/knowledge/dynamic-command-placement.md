# GPU 命令动态放置：从固定 unit 到会话与执行分离

> **核心结论**：用户提出的“上一条命令归还后，下一条命令能否避开原 unit 的拥堵”是当前结构值得优化的方向。普通 direct command 路径释放 GPU 活动预算，但不改变会话的 unit、节点或设备集合。建议保留 EnvRouter，分离长期会话资源与短期 GPU 执行租约，先支持同节点、无存活 GPU 状态的命令边界换卡，再考虑远程执行。
>
> 本文是设计分析，不是已完成的动态调度实现。当前源码也有 MPS 并行路径，其作业仍进入租约指定的节点和 unit，不能把同卡并行等同于跨卡改派。本次只运行 CPU 教学模拟，不宣称真实 science 或训练提速。

## 1. 当前调用链与绑定位置

下面先画当前 direct command 路径，再画提案。当前路径沿用已有[unit 共享与跨机器边界](env-router-current-flow.md#14-unit-如何共享及命令能否跨机器)和[容器提供者分层](unified-gpu-execution.md#10-当前结构与前两阶段的对照)。

```text
当前实现
[C1] 派发器选 AgentLoopWorker 所在节点
       ↓
[C2] Client → EnvRouter / Ledger → EnvLease
       固定 node_ip、unit_id、gpu_indices
       ↓
[C3] 创建容器，映射这份租约里的设备
       ↓
[C4] 下一条 GPU command → 原 unit 的命令队列
       预算不足 → 等待，其他 unit 空闲也不会改派
       获准     → 原节点服务授权 → 原容器执行
       ↓
[C5] 撤权、确认无所属句柄及计算进程 → GPU 活动预算归还
       会话、文件、CPU/主存额度和原 GPU 绑定继续存在
       └──────────────────────────→ 下一条命令回到 C4
       ↓
[C6] 整个任务结束 → 清理所属环境 → 释放会话

设计提案，尚未实现
[P1] 会话租约：固定容器所在节点、文件、CPU/主存/名额
       ↓ 命令准备就绪并声明需求
[P2] EnvRouter 命令调度：检查可执行候选 → 公平排队 → 动态选卡
       ├→ 本节点 GPU0 的短期执行租约
       └→ 本节点 GPU1 的短期执行租约
              ↓
[P3] 节点按本次执行租约授权设备 → 启动新的 GPU 程序
              ↓
[P4] 撤权并确认归还 → 只释放本次执行租约 → 回到 P1
```

这些代码如果有理解上的问题，可以随时追问。

**跟着图读源码。** C1 的容量选择仅决定把任务派到哪个 worker，C2 才是真正的资源准入。C2 创建会话后，C3 把选择固化为实际 Docker 设备配置。每次进入 C4，调度器都从同一份 lease 读取 unit_id，构造请求并在该 unit 内等待。C5 的物理检查在后台进行，输出就绪不等于预算已经归还。确认后只清除活动 GPU 记账，原 lease 不迁移。任务再次要 GPU 时重复 C4，最终才进入 C6。不同会话可以并行，unit 的短期准入锁不代表整张 GPU 永远只能跑一条命令。

当前工作区新增的 MPS 路径用于多进程共享 GPU 执行，参见 [MpsDomain.admit](../../../psrl/workers/env_service/parallel_gpu.py#L219)。它有作业级显存请求，但仍使用域绑定的 self.unit，且 unit 配置要求单张独立环境 GPU。本文没有重新验收该分支，普通 direct 路径的租约级显存需求不能笼统推广为所有执行后端都只能这么申报。

## 2. 用户担忧成立的条件

担忧成立，但需要区分三个动作。

1. A 的命令完成物理归还，A 的活动 GPU 预算释放。
2. 新会话 B 获准，首先消耗 CPU、主存和会话名额。在 command 模式下，仅创建 B 不会占用活动 GPU 预算。
3. B 的 GPU 命令随后获准运行，才会与 A 的下一条命令争用 GPU。若没有足够余量并行，A 需要等。

实际上 B 的会话甚至可能在 A 尚未归还时就被准入，只要主机额度和名额足够、其 GPU 需求在这个 unit 上理论可满足。[Ledger._fits_now](../../../psrl/workers/env_service/ledger.py#L463) 对 command 会话不要求当前 GPU 立即可用。若 max_containers 已满或主机资源不足，新会话仍不能进入。因此不是“GPU 一释放就必然多收一个 session”。

还有两个不同问题。

- **局部拥堵**：A 被固定在 GPU0，GPU1 已空闲，但 A 不能使用它。动态选卡可以解决符合条件的这类等待。
- **总容量不足或公平性**：所有兼容 GPU 都忙，或者短任务不断插队。动态选卡无法创造容量，需要公平排队、队列上限和有界等待。

当前 direct 队列是按请求先后顺序尝试准入。已经等待的 A 命令不会仅因 B 是新会话就被 B 直接越过。问题在于 A 的下一条命令尚未提交时，调度器不能知道它马上会回来，B 可以合理地先开始。永久给老会话保留空闲 GPU 会损失其他任务的机会。

“当前总是选择队列最短、压力最小的节点”也需要收紧。现有派发器主要检查能否容纳请求组、资源优先级及节点 CPU 负载。Ledger 优先选当前 GPU 需求可满足的候选，再看资源优先级及 CPU/主存/名额等占用比例，见 [_load](../../../psrl/workers/env_service/ledger.py#L500)。目前没有根据每条 GPU 命令剩余执行时间预测完成时刻的调度器。

## 3. PD 分离能借鉴什么

PD 指 Prefill 与 Decode。Prefill 是模型处理输入上下文的阶段，Decode 是逐步生成后续 token 的阶段。二者计算特征不同，PD 分离把它们放在不同资源上执行，并处理阶段之间的状态传递。DistServe 还把通信带宽纳入资源放置，优化的是满足延迟目标的有效吞吐，并非单看空闲卡数量。[DistServe 原论文](https://arxiv.org/abs/2401.09670)

Mooncake 进一步围绕 KV cache，即模型注意力机制保存的键和值中间状态，组织分离的存储与调度。缓存的位置和转移成本影响请求执行位置，同时需要在吞吐与延迟要求之间权衡。[Mooncake 原论文](https://arxiv.org/abs/2407.00079)

对环境任务有用的是这些原则，下面的映射是设计推论，不是两篇论文直接给出的 EnvRouter 方案。

| PD 分离的原则 | 环境执行中的对应设计 |
|---|---|
| 不同阶段独立决定执行资源 | 会话保持文件与主机状态，GPU 命令就绪时另选设备 |
| 状态有明确位置与传输方式 | 明确源码、数据、checkpoint、GPU 常驻状态分别在哪里 |
| 调度考虑传输与计算成本 | 比较排队、设备授权、数据准备、执行及模型干扰成本 |
| 为延迟目标控制负载 | 防止过量接收将很快请求 GPU 的会话，记录等待分位数与超时 |

不能直接把“环境 CPU 阶段”叫 prefill，把“环境 GPU 阶段”叫 decode。两者语义不同。模型 KV cache 的形态相对规则，而任意 Docker 命令可能依赖进程内变量、打开的文件、网络连接、后台服务甚至未保存的 GPU 张量，不能假设都能搬到另一张卡或机器。

## 4. unit 细化与两层租约提案

建议把“细粒度”分成物理资源粒度和调度时间粒度。

**物理资源粒度。** 对普通单卡任务，单 GPU unit 比把多张卡固定打包更容易独立装入请求。目前已有单卡 unit 配置能力。把一张物理 GPU 重复声明为几个 unit 则不合适，会让同一物理容量面临重复承诺，现有配置校验也不允许这种重叠。未来可以有逻辑候选池包含多个设备，但设备应只有一份权威容量账本。多卡任务还需要同时取得满足拓扑与逐卡显存条件的完整设备组，不能把多张卡的显存简单相加当成单卡容量。

**调度时间粒度。** 真正需要改变的是从“会话创建时固定 GPU”变为“每次可独立执行的 GPU 命令选择设备”。建议保留 EnvRouter 这个协调者，拆出以下概念。名称是设计描述，不是已经存在的接口。

| 对象 | 持有时间 | 记录内容 |
|---|---|---|
| SessionLease，会话租约 | 整次环境会话 | 容器节点、CPU、主存、容器集合、工作目录、允许使用的 GPU 候选池 |
| GpuInvocationLease，单次执行租约 | 一次 GPU 作业至物理归还确认 | 父会话、job_id、设备 UUID 集合、逐卡显存承诺、执行节点、授权代次、后端能力 |
| 设备账本 | 服务运行期间 | 物理容量、现有承诺、真实占用、清理隔离状态、训推保护余量 |

CPU 和主存按容器实际所在节点记账，GPU 按实际执行设备记账。这样迁移命令时，不会把 A 的主存额度从 unit0 错误转到 unit1，也不会因为重新计主机资源而重复扣费。

租约中的授权代次可理解为单调增加的“第几次授权”。例如旧执行是第 7 次，新执行是第 8 次，第 7 次延迟到达的归还消息必须被拒绝，不能撤销第 8 次授权。跨设备时还应把执行租约身份、容器身份及设备身份一起校验，不能只换 unit_id 就继续使用旧清理回调。

## 5. 同节点换卡为何也需要改造

目前容器创建时，overlay 只映射原租约的 GPU。DeviceCgroupFence 还要求实际映射集合与租约集合一致，见第 1 节 C3/C4。cgroup 是 Linux 内核用于控制一组进程资源与设备访问的机制，当前代码依靠其设备访问规则阻止未获准的命令使用 GPU。

所以，简单修改 CUDA_VISIBLE_DEVICES 不够。它用于影响 CUDA 程序看到和选择哪些 GPU，不会凭空增加容器设备，也不替代内核访问权限。

首期同节点方案可采用“候选设备可发现，但默认不能访问，执行时仅开放本次子集”。这需要明确的候选映射契约，以及与之匹配的设备白名单校验，不能直接删除当前集合相等检查。也可以在受控执行容器中运行命令并挂载会话工作目录，但该方案对终端状态和文件同步的要求更高。

允许换卡的首期条件应包括：

- 上一条 GPU 程序及其子进程已退出，所属 GPU 句柄和计算活动确认清空。
- 下一条 GPU 程序从文件或明确输入启动，不依赖旧进程中的 CUDA 上下文和未保存张量。
- 目标 GPU 的软件、硬件、镜像和权限能力兼容，逐卡显存预算满足。
- 同一容器暂时只允许一个可重绑定执行，避免一条命令撤权时影响另一条命令。

生产授权仍需由同一个 Router 在检查后原子承诺目标容量，防止两个并发请求都看到“这张卡空闲”。异步设备启用和回收期间保留相应承诺，启用失败且撤权未确认则隔离目标设备，不能直接尝试下一张卡并留下旧授权。

MPS 域还有特定设备、服务进程和通信端点绑定，首期可显式固定在原域。将来扩展时以执行后端能力声明加入候选，不能宣称普通设备换绑自然覆盖 MPS。

跨节点再增加工作目录同步、镜像可用性、临时文件、输出提交和取消确认问题。共享文件系统只解决部分文件可见性，不会迁移活进程和打开的连接。任务已经开始后，控制连接丢失也不能自动在另一节点重试任意命令，否则可能重复产生副作用。

## 6. 选卡成本与公平性

首先过滤不安全或不可执行的资源，然后再比较收益。用户指定的偏好继续生效：优先未被训推占用且可用的独立 GPU，包括同节点另一张卡。只有这些实际可执行候选紧张，才考虑显式获准共享的模型 GPU，而且必须保留模型显存与性能余量。尚未实现远端执行的空闲卡不能被当成当前命令可直接使用的候选。

对合格候选 g，可以估计：

```text
预计完成延迟(g)
  = 预计排队等待(g)
  + 数据与运行状态准备(g)
  + 设备授权及切换开销(g)
  + 本次命令预计执行时间(g)
  + 不确定性余量(g)
```

对模型或其他任务的影响还应通过硬性延迟边界或明确权重纳入目标，不能用几个 MiB 余量代替计算性能判断。此公式是候选比较框架，不是声称可以精确预测任意用户程序。

“队列最短”不等于“最快”。假设 GPU0 前面只有一个 20 秒任务，GPU1 前面有四个各 1 秒任务，新任务需要 3 秒，无切换成本且串行执行时，完成时间分别是 23 秒和 7 秒。只数排队条数会选错。真实环境允许显存足够时并行，此时还要估计并发造成的执行变慢，不能总把持续时间直接相加。

首期可以用已知任务类别的近期耗时和保守上界，不要求先做复杂机器学习预测。运行时间上限不是实际耗时估计，两者需分开记录。对未知命令使用保守策略，并观察预测误差。

**公平性不能靠“老 session 永远优先”。** 建议以已经准备好执行的命令为排队对象，限制每个 session 的未完成请求数，累计实际服务额度，并让等待越久的请求获得更高机会。这里的等待老化指随着等待时间增长逐步提高优先级，用来避免大任务或新会话一直得不到服务。下一条尚未提交的命令不能无限占住卡。

可以给连续命令短时、有限的亲和偏好，但只在不破坏等待上限时使用。不要默认引入固定空等窗口。若 A 还在调用模型，而 B 已准备执行，空着卡等 A 未必缩短总时长。改派也应有最小收益阈值，例如只有预计节省超过切换成本及误差余量才换，避免几张卡之间反复摇摆。等待者在候选池中保留唯一请求身份，设备归还时重新匹配，不能向多个队列复制同一请求并各占一份预约。

## 7. 教学模拟与结果

**全部数字均为教学假设。** 两张 GPU，每条命令的预算占满单卡允许容量，故每张卡一次只能运行一条。会话文件仍在同一个节点，没有常驻 CUDA 状态。A1 在 GPU0 上从 0 秒执行到 2 秒，A 随后规划到 4 秒。C 占用 GPU1 至 5 秒。B 在 2 秒准备好，运行 20 秒，因此选择刚空闲的 GPU0，从 2 秒运行到 22 秒。

在 B 开始时使用 GPU0 并不荒谬，GPU1 尚忙。4 秒时 A2 准备好，只需 3 秒，但 A 的原绑定仍是 GPU0。

| 方案 | A2 的执行 | A2 从就绪到开始的延迟 | A 完成 | 全部任务完成 |
|---|---|---:|---:|---:|
| 当前固定绑定的简化模型 | 等 GPU0 到 22 秒，执行到 25 秒 | 18 秒 | 25 秒 | 25 秒 |
| 动态候选，换卡成本 0.2 秒 | GPU1 在 5 秒释放，5.2 秒开始，8.2 秒结束 | 1.2 秒，含准备 | 8.2 秒 | 22 秒 |
| 动态候选，换卡成本 20 秒 | 换卡反而更慢，继续选 GPU0 | 18 秒 | 25 秒 | 25 秒 |

A 完成时间改善 16.8 秒，而全组总时长只改善 3 秒，因为 B 仍到 22 秒才结束。必须分别报告单会话延迟与全组完成时间，不能把前者直接写成训练总时间收益。如果 A 后面还有必须串行的模型调用和 GPU 阶段，提前完成 A2 可能进一步影响关键路径，但本模拟没有这些阶段，不能推算为实测收益。

[dynamic_command_placement_demo.py](../env-service-verification/scripts/dynamic_command_placement_demo.py) 可在仓库根目录使用 Python 标准库运行：

```bash
python docs/env-worker-deep-dive/env-service-verification/scripts/dynamic_command_placement_demo.py
```

脚本中 simulate 的 available 是每张卡未来可用时间，Job.ready 是命令已经准备完成的时刻，switch_cost 表示换卡准备时间。它先枚举候选，再比较预计结束时间。另有两卡都忙的场景，结果仍留在 GPU0，说明动态选择不能消除真实资源不足。

**Results。** 本次实际运行脚本，固定、低成本动态、高成本动态三组分别得到 A2 完成时刻 25、8.2、25 秒，全组完成时刻 25、22、25 秒。模拟假定精确已知持续时间，没有真实授权、迁移、预测误差、公平排队或 science 训练。这些数字只验证例子的算术和设计取舍，不能作为 PSRL 性能结果。

## 8. 实施优先级与有界验收

建议按下面顺序推进。本文只整理设计，没有修改生产调度器。

| 优先级 | 改造内容 | 解决的问题 |
|---|---|---|
| 第一阶段 | 记录命令就绪、等待、授权、执行、归还时间，以及候选设备拒绝原因 | 分清 GPU 真忙、预算不足、控制等待和固定绑定造成的闲卡 |
| 第一阶段 | 主机会话与 GPU 执行租约分离，同节点 command 边界重新选卡 | 直接解决原卡排队、另一张卡可用的问题 |
| 第一阶段 | 有界公平等待、唯一请求身份、明确后端能力及设备子集授权 | 防止改派导致饥饿、重复承诺或旧回调误撤新授权 |
| 第二阶段 | 结合耗时、并发干扰和预测误差的预计完成时间调度 | 比队列条数和瞬时显存更接近最终时长 |
| 第二阶段 | 根据 GPU 待执行工作量限制新会话的提前进入 | 避免 CPU 环境大量存活、GPU 队列持续累积 |
| 后续阶段 | 显式输入输出的远端 GPU 执行 | 利用其他节点，先解决文件与执行语义 |
| 更后阶段 | 有 checkpoint 协议的状态迁移与恢复 | 承接常驻 CUDA 状态，不尝试透明搬迁任意活进程 |

原型验收应先使用同一节点两张空闲环境 GPU，保持相同命令、输入、显存预算和控制开销统计，构造原卡繁忙、另一张卡稍后空闲的情况。总预算例如不超过 5 分钟，每组有限命令，无模型训练。必要证据是 A 的第二条命令实际使用另一张 GPU 的 UUID、工作文件保留、未授权设备不可用、旧执行回调不能释放新授权、最终物理资源清空。换卡开销、单会话延迟、全组时长分别统计。

只有上述路径完成后才接一次最小真实 science 验证，不自动追加长训练。若验证的是同节点动态路由，修复前后使用同一当前版本仅改变路由策略，以隔离机制。若进一步声称相对历史 OFF 的训练收益，固定 baseline 仍必须使用 `0eeead861ffafed6bf31c962d259fd847775dcf9`，另列实际版本和补丁，不用当前 OFF 替代。
