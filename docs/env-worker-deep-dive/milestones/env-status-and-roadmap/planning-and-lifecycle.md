## 未来规划与验收标准

以下是**建议的推进顺序，不是已实现能力或排期承诺**。先让最新能力在一个真实任务闭环，再扩大可接入任务范围。自动选择 episode / command 需要资源画像和安全释放边界，适合放在这些基础之后。

| 优先级 | 工作内容 | 完成时应拿到的证据 |
|---|---|---|
| P0：原生任务与最新版本闭环 | 选一个原生 science GPU 任务，将显式 GPU 执行、可信归属、任务评分、取消和清理串起来。冻结包含最新修复的代码版本 | Docker 内真实 CUDA 工作得到本任务的活动证据。CPU 假工作不能借用别人的 GPU 活动通过严格评分。取消或正常结束后核实进程、容器及显存释放 |
| P0：补齐新修复实机验收 | 小规模核验逐卡预算、主容器 / verifier / sidecar 限额、节点失效停止派发和恢复清理 | 真实两卡中单卡放不下时拒绝或等待。全部容器限制与账本一致。故障下有界结束，不遗留全局暂停，不在清理未完成时放行 |
| P1：当前版本低压力基准 | 用相同成功工作量、固定 OFF 和冻结 ON，做少量顺序平衡对照 | 同时记录冷启动、工作阶段、总时间、等待、OOM 和有效 token，明确额外开销及适用负载。达到预设结论后停止，不自动拉长训练 |
| P1：通用任务接入与可观测性 | CPU 单容器共用后端已通过验证，继续接 GPU 租约、远程 worker 生命周期和明确适配契约 | 原生 science 验证执行、评分和清理，补齐能力后再考虑替换默认路径。日志能区分准备、排队、执行和清理 |
| P1：服务故障恢复 | 持久化或可重建的租约、跨控制器设备所有权、清理确认后再调度 | 控制器退出重启或通信中断不会重复授权，不会把遗留工作当作已释放 |
| P2：提高剩余容量利用率 | 改善 FIFO，即先进先出队列中大任务挡住后续小任务的情况。允许能放下的小任务使用余量，并限制大任务的等待时间，完善多卡逐任务归属 | 在相同混合负载下减少空闲和等待，同时大任务有等待上界。不能只报告小任务变快 |
| P2：同容器多作业并发 | 按作业建立独立预算和进程归属，设备权限按活动作业生命周期管理 | 容量够时 A/B 重叠，不够时 C 等待。取消 A 不杀 B、不撤掉 B 所需权限，不错误归还 B 的预算 |
| P3：自动持有和卸载策略 | 基于任务能力、峰值、等待时长及释放恢复成本选择持续占用、command 或协作式卸载 | 比较释放加恢复成本与可利用等待窗口，只在有安全恢复方法且净收益为正时切换。不能通过检测“模型在生成”就强制撤走 CUDA 状态 |
| P3：完整训推与环境共享 | 在已验证的显式 command 共享和旧互斥借卡之上，补齐完整训练的峰值预算、权重有效性与传输登记 | 模型正确恢复，测量持续计算干扰、控制等待和完整训练总收益，不能将小型共存探针当作吞吐验收 |

本阶段不把运行中活容器跨机迁移、任意 CUDA 程序强制抢占或最优调度器作为已有承诺。它们需要额外的任务恢复协议或系统支持。

## 专项设计：自动选择模式与预测式卸载

**本节是后续设计提案，不是已经实现或已经测出收益的功能。** 目标是新任务接入后，系统根据它的 GPU 状态、可释放边界、实际资源压力和预计等待时间，选择合适的持有策略，减少人工指定模式的负担。下面的数字全部是教学假设，与前文真实实验数字分开。

先看完整决策链。图中“任务适配器”是任务与资源服务之间的接口，负责说明如何安全停止 GPU 工作、保存状态和恢复执行。预测器负责估算时间，最终授权仍由资源账本和执行节点完成。

```text
[A1] 任务适配器：声明命令边界、持久状态、可卸载能力
         + 运行观测：任务进程、显存、阶段耗时、模型等待
                             ↓
[A2] 能力识别：无跨命令 GPU 状态 / 可恢复状态 / 未知或不可恢复
                             ↓
[A3] 选择持有方式
     无跨命令状态 → command，在命令边界确认归还
     有持久状态   → episode，再决定常驻或临时卸载
                             ↓
[A4] 检查是否有必要让位
     已有空闲容量够用 → 正常准入其他任务
     没有等待者       → 保持当前状态
     容量不足且有等待者 → 进入预测评估
                             ↓
[A5] 预测：剩余等待、卸载、借用者占卡、恢复、完成时间
     检查能力、逐卡容量、主存、期限与预计净收益
                ├─ 不满足 → 保持常驻，等待者排队
                └─ 满足   ↓
[A6] 安全点 → 卸载 → 确认释放 → 授权借用者
     → 借用者确认归还 → 原任务重新准入、恢复、校验
                             ↓
[A7] 记录实际成本和预测误差，调整后续策略
```

图例：A1 是任务能力接口，A2 / A3 是模式选择，A4 是实时压力判断，A5 是成本与收益估算，A6 是执行和资源交接，A7 是观测反馈。A2 至 A7 中的自动策略尚待实现。现有统一执行后端、资源账本、进程归属与受控借卡能力可以成为基础，但不能把它们等同于已经有了这套自动决策器。

**一、先区分“持有范围”和“状态是否常驻”。**

episode / command 回答的是“GPU 预算按整个会话还是按命令申请”。offload / reload 回答的是“已经存在的 GPU 状态怎样临时移出、之后怎样恢复”。offload 指把恢复执行所需的数据移到主机内存等位置并释放可归还的显存，reload 指重新申请资源、恢复数据和运行状态。暂停一个进程通常不等于释放显存，不能只停进程就给其他任务放行。

| 识别出的任务形态 | 建议模式 | 等待期间的行为 |
|---|---|---|
| 每条 GPU 命令独立，结束后没有后续必需的 GPU 状态 | 优先 command | 命令结束并确认归还后，其他任务可使用容量，不需要额外卸载上下文 |
| 一个长生命周期进程保存 GPU 模型或仿真状态，能够安全卸载并恢复 | episode，加可选卸载策略 | 会话、文件和恢复信息保留，只有满足成本与容量条件时才临时归还一部分 GPU 预算 |
| 有常驻 GPU 状态，但没有可靠恢复接口 | episode，保持常驻 | 不自动撤销仍被使用的容量，其他任务排队或选择别的资源 |
| 新任务行为未知，只有普通 shell 命令 | 先用保守的 episode 管理并采集画像 | 遥测用于提出模式建议，不凭低利用率直接卸载或切换 |

“episode 加可选卸载”需要新增阶段状态和预算交接协议。当前 episode 策略并没有这个通用能力，而且模式目前绑定在 unit 配置中。后续应把节点资源池的设备能力与每个会话的持有策略分开，让同一个受支持资源池能够管理不同类型的租约。不能只运行时修改一个 `gpu_reservation` 字符串，就认为原有预约、设备权限和状态已经完成转换。

例如，一个 science 程序在多轮交互之间保留 GPU 上的数值网格，它仍是一条完整 episode。等待模型时，可以在明确的迭代边界保存网格、卸载显存，之后恢复同一网格继续运行。这不是结束该 episode，也不是丢弃状态后重新开始一条 command。反之，如果每条命令都会自行加载输入、计算并退出，就适合按命令管理。密集短命令也可考虑合并为一个受控批次，避免反复准备的成本，但必须保留真实的安全释放边界。

**二、自动识别依赖“能力声明加运行验证”。**

系统可以自动选择策略，但不能仅凭程序名、GPU 利用率降到零或一次显存下降，就推断任意程序能够安全恢复。自动化的对象是选择过程，恢复能力仍需要任务框架或适配器提供。

| 输入信息 | 如何取得 | 用于什么决策 |
|---|---|---|
| GPU 工作入口与完成边界 | 受控工具调用、任务阶段事件、命令及其子进程完成确认 | 确定何时能申请、停止新增工作和检查归还 |
| 跨命令保留的状态 | 适配器说明，结合多轮进程和显存观察 | 区分无状态命令与常驻任务。显存回落本身不能证明后续不会使用旧状态 |
| 卸载与恢复能力 | 适配器提供停止新工作、等待当前计算完成、保存、释放、恢复和校验接口 | 作为允许卸载的前置条件，不由预测器凭空补出 |
| 可释放量与残留量 | 可信任务归属、逐卡实际测量 | 判断卸载后到底能容纳谁，不能把申报总量当作必然可释放量 |
| 时间和状态规模 | 记录每阶段开始结束、待保存数据量、恢复开销、模型请求状态 | 学习相似任务的卸载、借用和恢复时间 |
| 等待者与资源约束 | 调度队列、优先级、期限、主存和逐卡容量 | 判断让给谁，以及对原任务造成的等待是否可接受 |

初次接入时，已经由适配器保证独立命令语义的任务可以直接选择 command。其余任务先保持保守策略，经过有界的观察和恢复验证后再开放更积极的选择。多次观测只是增加时间预测的可信度，不能取代安全恢复契约。模式变化只在安全点或下一次会话开始时提交，旧预算与新预算必须一致交接。

如果一个被声明为独立命令的任务实际上留下后台 CUDA 子进程，系统应保留其占用、阻止错误归还并报告契约不符合，而不是先释放预算，再把“自动识别成 episode”当作补救。

**三、episode 是否卸载，先判断能否释放，再判断是否值得。**

第一步是确认卸载有必要。如果其他任务在现有余量里已经放得下，就按正常准入共享，不必搬运常驻任务。如果没有可执行的等待者，也不应为了追求更低的显存曲线反复卸载。

第二步是容量与恢复可行性。教学假设一张卡预算 80 GiB，A 常驻占 48 GiB，B 峰值需 40 GiB，GPU 安全余量 4 GiB。两者常驻合计 `48 + 40 + 4 = 92 GiB`，放不下。若 A 卸载后仅残留 4 GiB，则借出期间为 `4 + 40 + 4 = 48 GiB`，可以容纳 B。还必须给 A 的主机内存副本及额外缓冲预留空间，确认 B 归还后 A 能恢复。多卡任务逐卡检查，不能用另一张卡的空闲抵消本卡超量。

第三步才是时间预测。建议记录以下五个量，全部采用同一时间起点：

| 符号 | 含义 | 需要包含的实际开销 |
|---|---|---|
| W | 从现在到 A 再次需要 GPU 的剩余等待时间 | 模型请求的剩余排队和生成、CPU 阶段，不能照搬上一次完整等待时间 |
| O | A 从决定卸载到资源确认可借出的时间 | 等待当前计算安全结束、保存状态、传输、释放和节点确认 |
| B | 借用者获得资源到确认归还所占的时间 | 模型加载或唤醒、GPU 计算、可能的再次卸载以及归还检查 |
| R | A 从可恢复到重新可执行的时间 | 资源重新准入、reload、状态校验、必要的运行时重建和同步 |
| G | 留给预测误差的保护时间 | 避免实际稍慢或模型稍早返回就立刻冲突 |

不能只按“状态字节数除以传输带宽”估算 O 和 R，等待安全点、内存分配、重新初始化和通信竞争也会花时间。预测应按任务类型、状态规模、设备和当前竞争情况分类统计，采用偏短的可用等待窗口、偏长的交接耗时。没有可靠样本时，先保持常驻或进行有界的成本测量，不把未知成本当作零。

第一版预测器可以从简单统计开始：O / R 使用同类任务近期真实卸载恢复的分布，B 使用相同模型、输入规模和执行批次的占卡记录，W 结合当前请求排队情况、已生成长度、历史生成长度与速度估计剩余时间。生成可能提前结束，未来长度并不已知，所以 W 应给出范围和可信程度，不能把回复长度上限直接当作必然等待时长。例如 W 估计为 30 至 60 秒，就先按较短的 30 秒判断能否放入，而不是按 60 秒填满。每次阶段事件到达后更新预测，记录“预计”和“实际”的差异，持续偏乐观时提高余量或停用自动卸载。

对于“A 等待另一个设备上的模型返回，B 是独立等待者”的情况，第一版可采用保守窗口规则：

```text
O + B + R + G <= W

即：A 卸载、B 完成并归还、A 恢复，再加保护时间，
都应能放进 A 原本的等待窗口。
```

这是一条尽量不推迟 A 的策略，不是所有有收益调度的必要条件。后续若允许 A 增加少量延迟，可以在明确的延迟预算内放宽，但必须比较两边的收益和损失。

**四、“卸载加恢复小于别人省下的时间”是有用信号，还需要检查整体收益。**

首先明确优化目标：是尽快完成所有任务，还是让高优先级任务更快完成。不能把某个 GPU 多忙了几十秒，直接当成训练少用了几十秒。若借出的任务不在训练等待的关键路径上，它提前完成也可能不缩短这一步训练。

一种可解释的比较方式，是预测保持现状和执行让位这两套方案的完成时间。设 F 表示完成时刻，w 是体现优先级的权重，可以比较：

```text
预计完成时间净收益 = Σ w_i × (F_i_保持现状 - F_i_让位)

只在安全条件满足、净收益为正且超过误差余量时考虑让位，
同时约束原任务和其他任务的最大延迟。
```

如果目标是整批任务尽快结束，就直接比较两种方案中最后一个任务的完成时间，或训练数据汇合点的就绪时间。各任务等待时间的减少不能直接相加当作整批墙钟收益。让位方案的时间线上已经包含 O、B、R 时，也不能再把卸载恢复成本扣一遍，否则会重复计算。

下面用两组可手算例子说明。假设 A 的状态安全可卸载，B 是另一模型的一批有界请求，B 的占卡时间已经包含加载、执行和归还。两者不能同时放入当前 GPU，A 等待的模型运行在另一张卡上，不依赖 B。A 收到结果后还需 10 秒 GPU 工作，然后结束并释放资源。

固定 `O = 4 秒，B = 20 秒，R = 6 秒，G = 4 秒`，两个任务的完成时间权重均为一。以下均为教学假设，不是实测。

| 情况 | 保持 A 常驻 | 让 A 卸载后运行 B | 判断 |
|---|---|---|---|
| 长等待，W = 60 秒 | A 在 60 秒恢复计算，70 秒完成。B 随后运行，在 90 秒完成 | A 在 0 至 4 秒卸载，B 在 4 至 24 秒运行并归还，A 在 24 至 30 秒恢复。A 仍在 60 至 70 秒计算 | 窗口 `4 + 20 + 6 + 4 = 34 <= 60`。A 无延迟，B 提前 66 秒，整批从 90 秒降到 70 秒，节省 20 秒 |
| 短等待，W = 8 秒 | A 在 8 至 18 秒计算，B 在 18 至 38 秒运行 | B 仍到 24 秒才归还，A 到 30 秒才恢复，在 30 至 40 秒计算 | B 提前 14 秒，看似超过卸载恢复的 10 秒，但 A 推迟 22 秒，整批从 38 秒变成 40 秒。窗口也不满足，应保持常驻 |

这说明，用户提出的 `offload + reload < 让位节省的时间` 可以作为候选筛选条件，但不能只看受益的 B。原任务 A 的恢复延迟、其他受影响任务及完整完成时间必须一起考虑。长等待例子里，搬运成本被 A 原本就存在的等待隐藏，B 的计算提前完成，才带来实际整体收益。

**五、如果被让位的模型正是 A 等待的 vLLM，需要按依赖关系调度。**

前面的 W 假设模型在其他设备上生成。若 A 正等着同一张卡上的 vLLM 生成下一条指令，而 A 又占着使 vLLM 无法恢复的显存，那么“等待 vLLM 完成再决定是否卸载”可能形成循环等待。

这种情况不应把 vLLM 被阻塞的时间预测成一个可自由利用的空闲窗口。应显式标记依赖：A 要继续，必须先让 vLLM 获得 GPU。合法路径为“A 到达安全点并卸载 → vLLM 唤醒并生成结果 → vLLM 按协议归还所需容量 → A 重新准入并恢复”。预测目标是整条链的完成时间，需要计入两边的加载、卸载和模型权重有效性检查。

如果 A 无法安全卸载、两者又无法共存，就应在准入时避免这种组合，改用其他可服务副本或其他设备。自动选择器不能通过猜测未来会空闲来解决资源依赖冲突。现有受控 vLLM 借卡与 command 模式也尚未合成这套通用协议。

**六、预测只决定是否尝试，实际交接必须有确认。**

建议为可卸载 episode 增加以下状态。状态变化属于提案，不能认为当前已有同名完整状态机：

```text
常驻 → 停止新增 GPU 工作 → 到达安全点 → 卸载中
     → 已确认释放 → 借用者持有 → 借用者已确认归还
     → 原任务重新准入 → 恢复中 → 校验通过 → 常驻

任何阶段结果不确定 → 保留对应资源的占用或隔离状态
                    → 有界恢复或清理，不能直接重复授权
```

CPU 会话租约和恢复数据在卸载期间保留。GPU 账本只归还已经确认释放的部分，残留显存仍然计费。应记录恢复需求与恢复优先权，停止接纳会越过约定归还时间的新借用任务，但不能把同一份容量同时承诺给借用者和正在恢复的原任务。

预测 A 还会等待 60 秒，实际却在 15 秒返回时，应停止继续放入新借用者，等当前借用者在约定的安全边界归还，再恢复 A。不能为了兑现预测结果直接杀死一个没有恢复能力的任意 CUDA 程序。首版只接纳执行时间有上界或具备协作归还能力的借用者，超时按任务契约终止或隔离，确认物理释放后才能让 A 进入。

为避免短时间内反复搬运，还应设置最短驻留时间、两次卸载之间的冷却时间、连续错误后的退回常驻策略，以及每个任务的累计额外延迟上限。这些阈值需要通过实际负载校准，不在本提案中编造默认实测值。

**七、怎样逐步实现并验证。**

1. 先增加能力描述和时间观测，只生成“建议 command / episode / 可卸载”的记录，不改变任务行为。检查建议是否与真实命令、状态和释放边界一致。
2. 对已声明且验证过独立命令语义的任务，在会话开始时自动选择 command。对常驻任务保持 episode，补齐按租约记录策略与阶段的账本结构。
3. 选一个支持保存恢复的真实 science GPU 任务，先显式控制一次卸载和恢复。核验状态连续性、任务正确性、主机内存预算、物理释放以及恢复成本，再启用预测。
4. 用常驻方案与预测卸载方案做相同工作量的有界对照。同时记录 A 延迟、B 完成时间、整批耗时、搬运次数、主存峰值、预测误差和清理结果。必须包含“窗口长应该借出”“窗口短应该保持”“没有恢复能力不得卸载”“容量够无需卸载”四类输入。
5. 最后扩展到同卡 vLLM 依赖链、混合任务优先级和多个借用者。跨任务自动选择与物理交接通过之前，不追加大规模长时间训练来追求更大的提速数字。

下面是完全内嵌的 Python 教学模型，直接复制运行即可。它对应 A5 的时间线比较，不会加载模型、移动真实数据或操作 GPU，也不替代能力、显存和交接检查。它假设 A 等待的模型在另一张卡上，且等待时间不受本次搬运影响。

```bash
python3 - <<'PY'
def evaluate(wait, *, can_offload=True, has_waiter=True, already_fits=False):
    if already_fits:
        return "share", "已有容量足够，正常准入，不卸载"
    if not has_waiter:
        return "resident", "没有等待者"
    if not can_offload:
        return "resident", "缺少安全恢复能力"

    offload, borrow, reload, guard, a_tail = 4, 20, 6, 4, 10
    # A5：保持常驻时，B 必须等待 A 完成。
    keep_a = wait + a_tail
    keep_b = keep_a + borrow
    # A5：让位方案显式计入卸载、B 占卡和 A 恢复。
    yield_b = offload + borrow
    ready_a = yield_b + reload
    yield_a = max(wait, ready_a) + a_tail
    window_ok = ready_a + guard <= wait
    completion_gain = (keep_a - yield_a) + (keep_b - yield_b)
    batch_gain = max(keep_a, keep_b) - max(yield_a, yield_b)
    decision = "offload" if window_ok and completion_gain > 0 else "resident"
    detail = (
        f"A {keep_a}->{yield_a}s, B {keep_b}->{yield_b}s, "
        f"sum_gain={completion_gain}s, batch_gain={batch_gain}s"
    )
    return decision, detail

cases = [
    ("long_wait", 60, {}),
    ("short_wait", 8, {}),
    ("no_restore", 60, {"can_offload": False}),
    ("enough_capacity", 60, {"already_fits": True}),
    ("no_waiter", 60, {"has_waiter": False}),
]
for name, wait, options in cases:
    decision, detail = evaluate(wait, **options)
    print(f"{name}: {decision}, {detail}")
PY
```

预期输出：

```text
long_wait: offload, A 70->70s, B 90->24s, sum_gain=66s, batch_gain=20s
short_wait: resident, A 18->40s, B 38->24s, sum_gain=-8s, batch_gain=-2s
no_restore: resident, 缺少安全恢复能力
enough_capacity: share, 已有容量足够，正常准入，不卸载
no_waiter: resident, 没有等待者
```

`sum_gain` 是两任务完成时间改善的合计，`batch_gain` 是整批结束时间的改善。短等待行展示的是被拒绝的让位方案会造成什么后果，实际决策保持常驻，并不真的把 A 延迟到 40 秒。这些结果只验证教学模型的算术和决策，不是自动策略已进入框架或取得性能收益的证据。

## 完整生命周期与独立可运行演示

| 步骤 | 图中编号 | 输入与状态变化 |
|---|---|---|
| 1. 放置 | 1 → 2 | 按实际组大小读取需求和健康容量，选择 worker。此时尚未取得最终执行许可 |
| 2. 会话准入 | 2 → 3 | 提交资源需求，等待节点探活和清理确认后返回允许、等待或拒绝 |
| 3. 容器创建 | 3 → 4 | 运行器将租约配置交给 Harbor，在最终容器集合施加标签和限制 |
| 4. GPU 工作 | 4 → 5 → 6 | 统一后端选择持有策略。command 经命令排队和预算检查，节点授权后才执行 |
| 5. 并行收尾 | 6 → 7 | 等待撤权和归还确认。采用后台归还时，CPU / 模型规划可继续，下一条 GPU 工作仍必须服从归还状态 |
| 6. 结束与异常 | 7 → 3 | 评分后释放会话，异常进入按归属清理。待清理资源不能因为租约计时到期就直接重新使用 |
| 独立分支 | 8 | 借卡状态机在模型和环境阶段交替，不能将其伪装成 command 路径里的一个无条件步骤 |

下面的演示直接包含全部代码，安装 Python 3 的机器即可运行，不需要 PSRL 仓库、其他脚本、Docker 或 GPU。复制整个命令块到终端执行即可。

**这是教学模拟，不是生产调度器。** 它用简化账本模拟图中 3、5、7 的申请、等待和确认归还，假设外部占用一直为 70 GiB，已获准任务还没实际分配。实际系统还需检查进程身份、设备权限、节点健康、并发请求和真实释放状态。脚本最后还用本文表格中的数值生成上面的文本条形图，图表数据无需外部文件。

```bash
python3 - <<'PY'
capacity = 90
measured = 70
reservations = {}

def request(name, amount):
    # 图中 3、5：把已承诺但尚未分配的额度计入准入。
    projected = measured + sum(reservations.values()) + amount
    allowed = projected <= capacity
    if allowed:
        reservations[name] = amount
    state = "granted" if allowed else "wait"
    print(f"{name}: {state}, candidate={projected} GiB")

request("A", 15)
request("B", 15)
request("C", 15)

# 图中 7：教学中假设 A 已经物理释放，再删除预约。
del reservations["A"]
print("A: return confirmed (simulated)")
request("B", 15)

groups = [
    ("三步训练累计，越短越好", 1100.80, 503.69),
    ("含初始化和清理的总时间，越短越好", 1954.11, 1415.01),
]
for title, off, on in groups:
    print(f"\n{title}")
    for label, value in (("OFF", off), ("ON", on)):
        bar = "#" * round(40 * value / off)
        print(f"{label:<3} |{bar:<40}| {value:7.2f} 秒  {value / off:6.2%}")
PY
```

申请部分的预期输出如下，后面会打印本文所列条形图：

```text
A: granted, candidate=85 GiB
B: wait, candidate=100 GiB
C: wait, candidate=100 GiB
A: return confirmed (simulated)
B: granted, candidate=85 GiB
```

`candidate` 表示“若现在批准这条申请，需要承担多少显存”，不是实测显存。B、C 显示 100 GiB 时都没有真的分配。A 确认归还后，B 的候选总量重新降到 85 GiB，因此获准。这个例子展示为什么先等待可以避免已经知道会超额的申请，但不能用它证明实际吞吐或不会发生任何 OOM。

## 设计演进与交付边界

从设计目标看，Env 的工作分为三层。三层的实现和验收进度不同，不应统一标成“已经完成”。

| 层次 | 要解决的问题 | 当前交付程度 |
|---|---|---|
| 第一层：统一管理环境 | 把分散的容器启动、容量检查、归属和清理纳入同一资源服务，避免各执行进程独立竞争 | science / Harbor 主路径已有实现和真实运行证据，全部环境后端统一仍未完成 |
| 第二层：缩短 GPU 持有范围 | GPU 阶段结束后允许别的任务使用容量，同时保留当前任务容器、文件和 CPU 状态 | 显式 command 模式已实现，具有本文高压力三步训练证据。任意任务自动接入和同容器并发仍未完成 |
| 第三层：跨角色动态共享 | 按实际任务特征，在环境、推理和其他工作之间自动选择资源持有、卸载和恢复策略 | 有受控模型借卡组件实现，自动模式选择、通用上下文卸载和完整训练共享验收仍属于后续工作 |

下一次可以明确交付的目标是：冻结一份包含新修复的版本，在一个原生 science GPU 任务上完成执行、归属、严格评分和清理验收，再对这个冻结版本测量低压力开销。这样可以把“单个组件能工作”推进到“同一个真实任务能完整使用这一套能力”，同时保持收益数字与代码版本一致。
