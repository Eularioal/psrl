## 目标和全景

Agent 在研究工程任务里会反复写代码、训练、推理、自测，最后提交给独立评分器。同题的多次探索需要比较反馈，才能更新外层 Agent。这里希望缩短的是**获得可信反馈的完成时间**，同时守住资源与候选版本正确性。

```text
Agent 探索 → GPU 训练／推理／自测 → 提交 → 独立评分 → 组内比较与学习
                 │                         │
                 └────── Env 调度研究 ──────┘
                   ├ 资源：能否安全放入、借还、共享
                   ├ 状态：保留什么、放哪张卡、等还是重建
                   └ 反馈：怎样测得准、减少整组等待
```

这是问题分类图。实际任务接线、命令执行、评分与 Actor 更新的[源码映射](env-scheduling-big-map.md#全局地图与问题背景)已在详细版核对。

## 探索方向与当前判断

| 分支 | 尝试的想法 | 得到了什么、卡在哪里 |
|---|---|---|
| 显存准入与可信归属 | 实际占用加未兑现承诺共同准入 | 压力下减少显存不足失败；作为安全底座保留 |
| 命令借还、同机池与准备前移 | 保留环境，GPU 按阶段使用，下一命令可重新选卡 | 机制可用；预算缩短后仍需验证关键路径收益 |
| MPS 与训推借还 | 同卡计算共享，或显式让出推理 GPU 窗口 | 有组件验证；独立 GPU 优先，完整训推影响单独验证 |
| 批量、常驻进程与模型复用 | 省掉重复导入、CUDA 上下文和模型加载 | 简单复用很强；模型更热不必然使整批更快 |
| 版本与主存缓存 | 只保留有效状态，按容量淘汰 | 发现并修复候选入口旧字节码；人工四会话 CPU 缓存场景收缩 |
| 模型亲和与联合放置 | 同模型连续运行，少加载，再考虑跨卡优化 | 亲和收益明显，复杂联合搜索未稳定超过它 |
| 等待／重建与可预测性 | 比较等待、加载、执行；有依据才允许预测换卡 | 系统矩阵有重复收益，新增预测门控默认关闭、尚需实机验证 |
| 测量保护与采样预算 | 防止 GPU 竞争导致快慢判断错误 | 简单保护有效，复杂自适应未胜固定少轮数 |
| 整组长尾与可分段评估 | 优化一组探索拿齐反馈，兼顾交接与复用 | 当前短 verifier 剩余太少；等待更自然、足够长的任务 |

## Results：最值得讨论的证据

**等待还是重建已形成较完整机制证据。** 两张同型 H20，固定模型与输入、已知更新步数，四种核心场景各三次。主指标是目标与阻塞命令都完成的时间，启动与画像单列。

| 场景，秒 | 固定旧 runner | 模型亲和 | 始终复制 | 预测选择 |
|---|---:|---:|---:|---:|
| 小目标 | 3.58 | 3.54 | 13.30 | 3.54 |
| 短等待 | 36.46 | 37.03 | 48.04 | 36.80 |
| 临界等待 | 46.17 | 46.64 | 46.61 | 47.02 |
| 长等待 | 85.29 | 86.11 | 52.75 | 52.80 |

长等待相对亲和减少 **38.69%**，包含冷副本清理仍减少 **37.31%**。预测的意义在于跨场景取舍：长等复制、短等复用；临界条件慢 0.81%。48 个核心单元全部完成，故障单元完成 5/9，整体 53/57。研究驱动使用真实 EnvRouter／EnvWorker，尚未验证自然 Agent 或完整策略训练。

例如一次真实决策：热卡阻塞剩余预测 51.211 秒，目标执行画像 33.289 秒；冷卡加载 11.007 秒。等待预计 84.500 秒，冷卡预计 44.296 秒，计入两秒切换门槛且容量合格后选择复制。目标实际延迟 43.740 秒，整组 53.000 秒。收益来自另一卡并行，阻塞命令继续留在原卡。详见[系统矩阵](../experiments/gpu-benchmarks/warm-placement-matrix.md)。

**负结果明确了强基线。** 模型亲和已经能减少大量加载，复杂联合枚举未稳定更好；PostTrain 保留模型让暖请求约 9.5 → 4.4 秒，但整批 113.84 秒仍慢于常驻进程重载的 91.96 秒；反馈自适应在 27 对实验中都慢于固定保护两轮。详细证据见[结果表](env-scheduling-big-map.md#results主要证据怎样解读)。

**预测准确性会改变结论。** 人为十倍高估使短等待错误复制、耗时增加 27.48%；报告过期与预算不足均回退等待。新增可预测性模块检查身份、进度与完成校准，off／observe／auto 默认 off，新增接线的 GPU 复验仍是缺口。

## 下一步建议与请教问题

建议优先研究：**真实可复用请求中，在线进度预测能否胜过简单亲和与静态画像阈值，并在额外副本占用显存后仍改善整组完成时间？** 原型首先采用能够报告进度的有界训练／评估命令，下一步收集自然 checkpoint 与评估循环。

备选方向是**资源竞争下的反馈保真**：保留固定两轮和全程保护的强基线，比较相同反馈质量下的整组时间，并校验完整训练奖励关系。四会话人工 CPU 缓存和极短 verifier 尾部暂缓扩大。

希望师兄帮助判断：

1. 主指标优先选关键反馈延迟、同题组完成时间，还是整批吞吐？
2. 优先切 PostTrain 的 checkpoint 训练／评估循环，还是性能算子题的测量可靠性？
3. 在亲和、原生缓存、常驻进程与静态画像都纳入后，什么增量值得发展成研究贡献？
4. 是否先用少量自然 Agent 轨迹确认复用频率、状态寿命与可预测覆盖，再扩展算法？
