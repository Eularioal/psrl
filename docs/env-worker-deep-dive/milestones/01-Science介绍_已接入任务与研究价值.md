# Science介绍：已接入任务与研究价值

> **核心结论**：PSRL 已能让语言模型智能体执行多类真实 GPU 任务，接收独立评分，并用交互记录完成一次策略训练与更新后采样。现有任务覆盖算子优化、机器学习训练、模型权重交付和推理服务，足以支持下一阶段的资源调度研究。各题库的完成范围不同，当前成果主要是固定本地条件下的功能验证。

本文面向第一次了解这项工作的读者。最新核对：**2026-11-16**，本轮新增真实 GPU 快检与策略训练验证，既有任务沿用固定证据。接入仍处于本地开发验证阶段。

本篇负责解释任务场景和接入覆盖。回顾整个Env时，分别看[架构现状](../knowledge/01-架构与执行/01-Env架构_现状与完整执行流程.md)、[当前基线与实验效果](../experiments/01-实验总览_调度收益与证据范围.md)和[下一步研究优先级](05-调度研究_研究全景与证据详解.md#接下来可以做什么优先级与验收边界)，不把任务题库覆盖当成调度收益。

## 这项工作解决什么问题

agent 完成“训练分类器”“优化 GPU 算子”或“修复推理服务”这类任务时，需要反复操作真实软件：读取数据、修改程序、运行实验，再根据结果决定下一步。

PSRL 需要把这整个过程接起来：为任务准备运行环境、安排 GPU、收集模型的操作记录、获得可信评分，再用这些记录训练 agent。独立评分器（verifier）根据提交的代码、预测或模型权重计算结果。

因此，这项工作的价值有两部分：一是把不同类型的真实 GPU 工作接进同一个训练框架；二是提供可重复的任务和评分，方便研究怎样让多个任务更快获得反馈。

## 用一道手写数字题看完整过程

以已经验证的 MLE 本地手写数字题为例。任务共有 **1797 张真实的 8×8 数字图像**，固定划分为 1347 张训练图像和 450 张测试图像。

[![两个模型、两层训练：工具里的模型与Agent策略分开更新（2/2）](../../_static/img/document-figures/two-model-training-loops-screen-02.png)](../../_static/img/document-figures/two-model-training-loops.png)

策略模型 θ 提出训练方案，环境任务模型 φ 执行更新并保存产物，评分器返回质量。 φ 的内部训练次数与 θ 的策略 step 属于两层循环。任务产物不会自动成为下一轮 Agent。 θ、φ 是教学符号。任务模型接管 Agent 是额外设计，需要能力评估与发布协议。 [查看矢量图](../../_static/img/document-figures/two-model-training-loops.svg)。
<!-- /figure:two-model-training-loops -->

1. **拿到问题。** agent 能看到训练图像及其数字标签，也能看到测试图像和各自的 ID；测试标签只交给独立评分器。
2. **训练并预测。** agent 编写或运行分类程序，调用 GPU 训练分类器，再为 450 张测试图像分别预测 0 至 9 中的一个数字。
3. **交付结果。** agent 提交 CSV 表格，包含每个测试 ID 和预测类别。评分器先检查是否缺行、重复或出现非法类别，再对照隐藏标签计算准确率。
4. **得到任务反馈。** 固定实验的参考实现答对 437 张，准确率为 `437/450≈97.11%`。这说明这一份提交的分类效果。
5. **验证 PSRL 训练链路。** PSRL 收集 agent 生成命令、调用工具和读取结果的过程，结合评分执行一次策略训练。新策略版本发布后，再用它生成下一次任务交互，并完成独立评分。

这里有两份模型：**任务内的数字分类器**负责识别图像，**PSRL 的策略语言模型**负责决定怎样操作工具。第 2 步训练前者，第 5 步训练后者。97.11% 来自固定参考提交；策略训练带来了多少能力提升，需要另做效果对照。

## 已经接入哪些任务

不同任务会以不同方式使用 GPU。下面先说明 agent 实际要做的工作，详细数量放在下一节。

| 任务类型 | 对应 benchmark | agent 做什么，提交什么 |
|---|---|---|
| 优化 GPU 计算 | KernelBench、FlashInfer-Bench、FastKernels | 把给定计算改写为更合适的 GPU 实现，提交代码。评分器比较数值结果，按协议记录耗时 |
| 从数据训练预测模型 | MLE 本地任务、AIRS-Bench | 读取公开训练数据，训练分类、检索或预测程序，提交预测表格。评分器对照隐藏结果计算指标 |
| 训练后交付模型 | MLGym、PostTrainBench、autoresearch | 训练游戏策略、图像或文本模型，或修改固定训练程序；提交权重或训练代码，由评分器重载或重跑 |
| 运行与修改推理服务 | InferenceBench、SWE-Serve | 启动语言模型服务，或修改真实服务源码；提交启动方案或代码修改，评分器独立测试 |
| 研究工程综合题 | RE-Bench | 完成偏好训练、算子实现、模型修复、训练脚本优化等不同任务，按题提交代码、权重或预测 |

这些差异会直接影响调度。例如，算子测试可能只短暂计算，训练会持续占用 GPU，服务则可能在没有请求时仍把模型留在显存里。

## 目前验证到了哪一步

**GPU 快检**是用真实 GPU 执行任务、提交结果并获得独立评分；**策略闭环**是在此基础上，完成真实语言模型交互、一次 PSRL 优化器步骤、策略版本发布，以及新版本继续交互和评分。完成优化器步骤、获得非零梯度与策略能力提升分别验证。

| 范围 | 已有 GPU 任务证据 | 已有策略闭环证据 |
|---|---|---|
| 六类公共任务与 AIRS | Harbor 执行的六类共 476 项，加 AIRS 19 项，共 **495 项**，均有逐题或逐定义快检 | 公共六类和 AIRS 各选代表题 |
| MLGym | **9 个 GPU 任务身份**快检通过 | 全部 9 个任务身份 |
| PostTrainBench | **15/24 个模型与目标组合**快检通过，包含真实生成与本地裁判评分 | 全部 15 个已快检组合 |
| FastKernels | **77/458 个目标**快检通过，涵盖单算子、模块、网络阶段与整模型 | Linear 与 SigLIP2 整模型代表题 |
| SWE-Serve | 已导入 41 题，原测试和本地快速协议去重后 **21 题测试全过**，其中 **17 题观测到 GPU 工作** | score 本地服务题、DSv32 cache、dLLM 采样协议 |
| 官方 Kaggle 竞赛 | 等待凭据、竞赛授权和逐竞赛准备 | 待接入 |

这里按题目、算子定义或模型组合计数，计数单位随题库而异。已通过的本地协议常用小数据、短训练或缩小输入，目标是把执行、评分和训练链路跑通。部分策略轨迹达到轮数或输出预算后对已有产物评分；dLLM 的参考补丁快检全过，策略模型自行修复则得零分。官方完整规模、长期稳定性、策略能力提升和调度性能收益，仍各自需要专门实验。任务中的公开起始程序或参考补丁用于功能验收，便于把接入故障与解题困难分开。

例如新增的写作题：agent 用两条公开记录做短训练并提交权重，评分器重载该模型，为两条隐藏问题实际生成回答，再与冻结参考答案比较。本地裁判是另一份只读模型，负责给出偏好分数。健康题则按原数据中的正分、负分标准评价回答。这样的任务覆盖“训练、交权重、生成、裁判评分”的 GPU 使用过程。

依赖放在任务镜像、专用虚拟环境或独立目录中，部分任务只读复用已有 Python 环境。已有安装路径和包元数据审计未发现本次接入修改主环境安装；长期复现仍需继续固化这些依赖。相关机制见[接入详情的环境说明](03-Science验收_接入流程与环境隔离.md#环境与依赖怎样隔离)。

## 下一步可以研究什么

**首先研究“怎样更快拿到可靠反馈”。** agent 常常要比较多个候选程序，再选择下一步。并行评分能减少等待，但 GPU 争用也可能影响计时，让候选的快慢顺序发生变化。可以从 KernelBench 和 FlashInfer 开始，同时比较整组评估耗时、正确性与排名稳定性。

**其次研究“任务哪个阶段需要 GPU”。** 数据处理、代码编译、GPU 训练和评分的资源需求不同。调度器若能识别这些阶段，就有机会把空闲资源交给其他任务。比较时需要保持训练步数、输入和评分标准一致，才能解释时间节省来自哪里。

**最后研究“保留模型还是释放重载”。** 例如推理服务完成测试后，agent 开始改代码。GPU 此时可能没有计算，但模型仍占显存。结束服务可以让其他任务使用这部分资源，下一次测试又要重新加载模型。应比较等待时间、重载成本和整组任务完成时间，再决定是否值得释放。

现有接入提供了上述研究的任务基础。下一步需要与独占执行、静态分配、进程复用等基线做同工作量对照，用结果判断调度方案的收益。

**任务内容的多样性已经较好，GPU 使用方式仍有值得补充的场景。** 当前题量集中在程序优化，短协议对运行中显存增长、释放后恢复、任务内多卡协同，以及 agent 根据结果发起并行实验的覆盖较浅。已有显存压力与同卡共享实测，可以在此基础上补这些任务形态。覆盖矩阵、具体例子和推进顺序见[路线图的多样性评估](02-Science现状_任务覆盖与接入路线.md#多样性覆盖与缺口)。
