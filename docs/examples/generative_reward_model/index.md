# Generative Reward Model

> **Status:** these planned recipes describe the intended learning signals. Launch scripts and complete configs are not yet published.

Open-ended tasks such as creative writing, dialogue and instruction following often
lack a programmatic checker that covers all aspects of answer quality. **Generative
Reward Models (GRMs)** address this gap by having another language model produce a reward signal
itself, either by *judging* the response or by *teaching* the policy what a better
response would have looked like.

PSRL groups two complementary recipes under this umbrella:

| Recipe | One-line summary | Status |
|---|---|---|
| [LLM-as-a-Judge](#llm-as-a-judge) | A frozen / fine-tuned LLM scores each rollout, the score is used as the RL reward | TBD |
| [On-Policy Distillation](#on-policy-distillation) | A stronger teacher model emits token-level targets on the policy's own rollouts, the policy distills against those targets | TBD |

The proposed recipes would reuse the rollout and parameter-transfer infrastructure
used by the RLVR examples, with model-derived feedback supplying the learning signal.
The integration details remain part of the planned work.

> **Idea:** a separate model scores an answer using a rubric. For example, it may rate a summary from 1 to 5 for factual accuracy and coverage. The chosen score becomes task feedback; judge quality and rubric design still need evaluation. This recipe remains planned.

### What it is

**LLM-as-a-Judge** turns a separate language model into the reward function. For every
rollout produced by the policy, a *judge* LLM reads the prompt together with the
response (and optionally a rubric, reference answer, or multiple candidates) and emits
a score, typically a scalar in `[0, 1]`, a discrete rating, or a pairwise preference.
That score is then used as the reinforcement-learning (RL) reward signal. Algorithms
used in the [RLVR examples](../rlvr/index.md), such as PPO, GRPO and DAPO, can in
principle consume such scores; this planned recipe still needs its own integration
and validation.

This supports RL on tasks where programmatic checks provide incomplete feedback: instruction following,
creative writing, dialogue, summarization, safety alignment, and so on.


## On-Policy Distillation

> **Idea:** the student generates its own answer prefix, and a teacher supplies target probabilities for what should come next. For example, after the student writes “2 + 3 =”, the teacher can assign high probability to “5”. Training reduces the mismatch on prefixes the student actually visits. This recipe remains planned.

### What it is

**On-Policy Distillation** uses a stronger **teacher** LLM as the supervision signal
for the **student** policy, but, unlike classical offline distillation, the
trajectories being distilled are sampled from the *student's own* current policy. For
every rollout the student produces, the teacher provides token-level targets (full
distributions or log-probs), and the student is trained to match them via a KL-style
loss.

The training examples follow prefixes generated by the student: the teacher tells
the student "given *your* prefix, *here* is what a
stronger model would have said next", which reduces the context mismatch between student-generated trajectories and
a fixed set of offline teacher examples. The benefit depends on the task and
training setup. In an asynchronous system, the delay between generation and training
also determines how closely those samples match the student's latest parameters.
