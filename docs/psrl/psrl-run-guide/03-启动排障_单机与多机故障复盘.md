## 近期Env实验：Ray启动失败与导入阻塞

### 先分清进程存在、注册成功和Actor可用

Ray中的actor是由Python进程承载、可以远程调用的对象。Raylet是节点上负责启动和管理这些worker进程的服务。看到一个PID，只能说明操作系统创建了进程，还要依次完成Python和Ray库加载、向Raylet注册、导入actor类及其依赖，才可能运行PSRL初始化。模型权重加载和环境GPU调度位于后面的阶段。

[![Ray启动阶段与11月23日三次注册超时的真实时间线](../../env-worker-deep-dive/experiments/ray-startup-stages.png)](../../env-worker-deep-dive/experiments/ray-startup-stages.svg)

先看上方四个阶段，再沿下方同一时间轴读三个失败进程。红条结束只证明注册期限到了，不能凭它判断具体卡在哪个import。绿色进程进入CoreWorker后，又经过业务加载才完成actor创建，说明注册期限不是整个训练初始化期限。

本次按安装环境报告的Ray **2.49.1**、提交 `c057f1e` 核对上游代码。注册超时分支会记录进程是否仍活着，随后终止仍未注册的活进程，并处理后续待启动请求。因此“进程还活着”与“最后被终止”可以同时成立，不必先有Python崩溃。[Ray对应版本的超时处理](https://github.com/ray-project/ray/blob/c057f1ea836f3e93f110e895029caa32136fc156/src/ray/raylet/worker_pool.cc#L534)

### 两次真实注册故障，分别卡在哪里

| 实验 | 原始观测 | 可以确认 | 仍不能确认 |
|---|---|---|---|
| 11月19日容量实验预启动 | 48个worker在0.132秒内启动，48个都在约30秒时注册超时，driver栈停在CoreWorker连接 | 批量预启动的注册阶段失败，训练尚未开始 | 为什么48个进程都没及时注册，缺当时worker栈 |
| 11月23日整卡组 | 三个worker各30秒未注册，日志均说进程仍活着，第四个成功，最后实验完成 | 注册失败带来重复启动和额外等待，不是该组训练最终失败 | 三个失败PID各自卡在哪一行，没有对应Python日志或栈 |

11月19日的具体过程是：12:52:58.438开始拉起第一批worker，12:52:58.570已拉到第48个，12:53:28.438～28.570逐个报注册超时。同期driver栈是 `ray.init → connect`，没有轨迹开始。Ray该版本的driver注册流程确实可能等预启动worker到齐，这和“worker全部超时、driver仍卡在连接”吻合。它定位了启动阻塞机制，底层加载慢的具体原因仍缺证据。[Ray预启动等待代码](https://github.com/ray-project/ray/blob/c057f1ea836f3e93f110e895029caa32136fc156/src/ray/raylet/worker_pool.cc#L798)

11月23日以15:32:13.426为起点，实际时间如下：

| 进程 | 启动时刻 | 结果 |
|---|---|---|
| 1351900 | 15:32:13.426 | 15:32:43.426未注册，耗时30.000秒 |
| 1353994 | 15:32:43.529 | 15:33:13.529未注册，耗时30.000秒 |
| 1355419 | 15:33:13.537 | 15:33:43.537未注册，耗时30.000秒 |
| 1357325 | 15:33:43.544 | 约8.186秒后开始构建CoreWorker，约87.745秒后actor创建完成 |

前三次明确花掉约 `30＋30＋30＝90` 秒等待。这里重试的是承载actor的worker进程，尚未开始环境轨迹，不是已经跑了三次训练，也不是EnvWorker把三个episode重派发。第四个从进程启动到actor创建完成用了约87.75秒，其中进入CoreWorker后的区间约79.56秒。**这不能理解成它超过30秒也不该被允许**，因为注册阶段和后续actor加载属于不同阶段，而且CoreWorker构建时刻也不等于精确的注册完成时刻。

该整卡组成功主控进程出现前，比同轮静态组多172.52秒。90秒注册失败解释其中一部分，剩余差异缺细分证据，不能把172.52秒全部归给三次超时，也不能承诺加大期限会恰好省下90秒。

证据：[本次只读汇总](../../env-worker-deep-dive/env-service-verification/results/ray-startup-review-20261125/evidence.json)、[48个预启动worker日志摘录](../../env-worker-deep-dive/env-service-verification/results/ray-startup-review-20261125/prestart-registration-20261119.log)、[三次历史注册日志](../../env-worker-deep-dive/env-service-verification/results/live-partition-20261123/elastic/resident/startup-raylet.log)、[第四个worker的CoreWorker日志](../../env-worker-deep-dive/env-service-verification/results/ray-startup-review-20261125/successful-worker-excerpt.log)、[当时driver栈](../../env-worker-deep-dive/env-service-verification/results/capacity-design-20261119/resident-startup-stack.txt)。

### 为什么优先怀疑共享目录上的Python依赖加载

11月24日采到另一个worker的有效栈时，进程已存在约9.40秒，栈顶是Python寻找模块文件时的 `_path_stat`。调用链为 `import ray → 硬件支持模块 → requests → charset_normalizer → 编码模块查询`，当时CPU用户态与内核态累计约0.61秒。它说明启动期确实可能主要在等待，不是在持续做模型计算。

这里Ray连带加载TPU支持模块，只是导入链的一环，并不表示H20任务在使用TPU。真正值得看的是：为了完成一个看似简单的 `import ray`，进程已经查询了多层依赖及编码模块文件。

另一次配置预检的栈停在Transformers递归扫描模型包目录，安装源码在该处使用 `os.scandir`，递归处理子目录。本次核对依赖所在挂载类型为 `fuse.dop-fuse`。这些证据共同支持：**共享文件目录中的大量模块查找、目录枚举和小文件访问，是启动抖动的优先排查对象。** 当前挂载类型不是历史存储故障证明，也不能仅凭路径名把底层认定为Ceph。

“文件元数据查询”是在问文件是否存在、是什么类型、目录里有哪些文件，和读取模型权重的大块数据不同。即使总带宽尚未打满，每次小查询的等待叠加起来，也会让Python启动变慢。48个进程集中加载同一批依赖，可能放大这种成本，也可能叠加CPU调度竞争，现有证据还不能分离各自比例。

**证据限制尤其重要：** 现有worker采样文件有123条记录，但仅1条有效worker栈，其他记录多为进程已退出或已成为僵尸。该有效样本来自11月24日成功实验，并非11月23日那三个失败PID，本轮也没有注册超时。它是具体线索，不能代替历史失败栈或证明唯一根因。配置预检的Transformers扫描同样只是另一个进程的样本。

原始采样见[worker栈](../../env-worker-deep-dive/env-service-verification/results/episode-static-1200-20261124/startup-stacks.jsonl)和[配置预检栈](../../env-worker-deep-dive/env-service-verification/results/episode-static-1200-20261124/preflight-stacks.jsonl)。本次只读汇总同时保留采样数量和边界。

### 180 秒导入预检的排查与修复

这次超时发生在私有 Ray 已建立、探针 worker 已返回模块来源之后。启动器另开 Python 进程，接连导入训练器、PostTrain Agent 和参数服务，再启动真正的训练 driver。11 月 24 日同一个独立预检曾用 85.77 秒，随后一次超过 180 秒被终止。两条日志把问题定位到额外的导入子进程，Ray 注册和 GPU 调度属于另外的阶段。 [超时状态及分段证据](../../env-worker-deep-dive/env-service-verification/results/handover-overlap-20261125/gated/resident/status.json)

训练器会间接导入 veRL、Torch、Transformers 和其他训练组件。Transformers 5.10.1 初始化时递归枚举模型目录并读取 Python 源文件，用来建立后续按需加载的索引。旧诊断在第 20、40、60 秒分别采到读取模块、建立 Transformers 索引和查询模块路径。新诊断再采到目录扫描，但随后以信号 11 退出，属于另一次启动失败。 [旧诊断](../../env-worker-deep-dive/env-service-verification/results/handover-overlap-20261125/import-diagnostic.log) · [本次诊断](../../env-worker-deep-dive/env-service-verification/results/handover-rerun-20261125/import-shared.log)

下图固定解释器、包版本及其他依赖，每次使用新进程，只把经过内容核对的 2434 个 Transformers 文件移到节点本地。四次顺序为共享、本地、本地、共享。

### 另外三次是确定的配置或依赖异常

这几次需要补齐配置和依赖，延长注册期限不能解决它们：

| 11月18日记录 | 真正报错 | 发生位置与原因 |
|---|---|---|
| config-failure | `Could not find 'data/data'` | 训练driver解析Hydra配置失败，还没提交TaskRunner。配置搜索范围或快照内容不完整 |
| import-failure | `No module named 'examples.airs_bench.grading'` | TaskRunner运行阶段，间接导入AIRS评分模块失败，worker可见的模块集合不完整 |
| grpc-version-failure | 安装grpc为1.83.0，生成代码要求至少1.85.0 | 参数服务初始化时抛出明确版本异常，运行库和生成协议代码不匹配 |

当前保存的最终源码已包含一些修复，不能只看今天文件存在就否认当时日志。反过来，只有ModuleNotFoundError也不能进一步认定究竟是当时没复制文件、路径被遮蔽还是某个包导入来源不对，这一层需要当时快照才能确认。

这类错误可能被Ray包装后传回driver，但不等于worker未向Raylet注册。应该保留最里面的异常及其导入文件，而不是只看最外层的actor或任务失败提示。修复时使用本次隔离依赖和完整源码，分别核对driver及真实worker的导入来源，不向共享环境随意安装或升级包。

证据：[配置失败日志](../../env-worker-deep-dive/env-service-verification/results/integrated-partition-20261118-02/config-failure/launcher.log#L141)、[模块导入失败日志](../../env-worker-deep-dive/env-service-verification/results/integrated-partition-20261118-02/import-failure/launcher.log#L1967)、[gRPC异常](../../env-worker-deep-dive/env-service-verification/results/integrated-partition-20261118-02/grpc-version-failure/launcher.log#L1967)。

### 哪些失败记录不应归到Actor启动

11月19日另一次 `stopped_initialization_budget` 已有训练worker的FSDP、NCCL、NIXL初始化记录，最后是监督器期限到期后SIGTERM清理。这里应查完整初始化用了多久、外层还剩多少预算，不能把收尾时进程被终止当作最初的注册故障。

11月23日episode静态组在任务运行后触发720秒轨迹期限，属于资源排队和任务预算问题，不是actor启动。整卡实验静态组还有一次外层清理探针导入错误，但内层两步训练已经成功，同样不能算训练actor没起来。相同 `failed` 状态字段可能来自这些不同阶段，必须结合内层退出码、首条轨迹和最后一段日志判断。

没有发现上述两次注册失败可直接归因于CUDA OOM的证据。部分成功主控worker的日志出现CPU-only actor看不到GPU的警告，但后续训练成功，警告本身不是根因。Ray的CPU/GPU逻辑资源、环境账本预约和真实显存也属于不同层次，worker尚未注册时不能先归因于Env的GPU准入策略。

### 已有缓解措施与下一步最有价值的证据

| 措施 | 当前代码或结果 | 能解决什么、还缺什么 |
|---|---|---|
| 关闭批量预启动 | 恢复脚本明确设置 `RAY_enable_worker_prestart=0`、`RAY_prestart_worker_first_driver=0` | 避免第一批48个worker集中启动及driver等它们的路径。正常需要的worker仍需启动，30秒失败并未因此绝迹 |
| 注册期限30→90秒 | 当前实验runner的私有Ray配置，整体初始化仍受1200秒约束 | 让正常但较慢的进程有机会完成，不能修复缺模块或真正挂死 |
| 延迟PSRL业务依赖导入 | `main_ppo`将模型和训练辅助依赖移入真实训练入口 | 配置打印CPU对照96.59→37.72秒，证明该次预检成本变化，不保证每个Ray worker都少加载同样的库 |
| 持久化启动阶段与采样 | Ray建立、导入预检、配置预检、driver和首轨迹分开计时 | 有助定位时间去了哪，现有失败前有效栈仍不足 |

11月24日应用启动修改的完整复测没有观察到注册超时，初始化为725.73秒，历史整卡组为978.98秒。它说明这套路径可以成功启动，不能证明历史根因已根治：这是顺序单次，缓存、文件服务负载和多项修改未分离，且该轮没有实际发生整卡借出。更早的独立零GPU注册验证也只是链路通过，未复现30秒故障。

关闭预启动的环境变量目前可明确定位到外层恢复和后续运行脚本，`run_arm`本体主要设置注册期限。不能只检查一个脚本就认为所有实验入口都继承同样配置，下一次应保存最终Raylet的有效参数和进程环境来源。相关代码见[恢复启动环境](../../env-worker-deep-dive/env-service-verification/scripts/resume_capacity_validation.py#L65)、[当前私有Ray建立](../../env-worker-deep-dive/env-service-verification/scripts/integrated_partition_training.py#L180)和[配置检查入口](../../../psrl/trainer/main_ppo.py#L32)。

### 启动全流程（跑通之后回看）

1. 探测 `LOCAL_IP` → 本地起 Ray（`ray_init.address=local`）→ Hydra 把脚本参数覆盖进 `ppo_trainer.yaml`。
2. `TaskRunner` 建 worker pool：2 卡跑 `PSRL_vLLMHttpServer`（rollout，显存占用高，因为 `gpu_memory_utilization=0.9`），2 卡跑 `FusedWorker_actor_dummy`（FSDP2 训练）。
3. 加载 GSM8K parquet 数据集，建 DataLoader。
4. 训练侧 FSDP 初始化完成后，通过 **NIXL** 把权重写入 PS Worker，由 `PSManager` 协调版本，rollout 侧的 vLLM 实例再拉取对齐。
5. 训练循环 `trainer.total_training_steps=3`：rollout 生成 → reward → GRPO advantage → FSDP 反向更新 actor → NIXL 把新权重推给 rollout。第 3 步夹一次验证。
6. 3 步跑完，停 PSManager/NIXL，打印 `Training completed successfully!`，退出码 0。

### 报错一：`AssertionError: PSManager IP xxx not found in ray nodes`

- **现象**：`ray_trainer.py` 里 `assert self.config.psrl.ps_manager_ip in ip_to_node_id` 断言失败。
- **根因**：脚本用 `LOCAL_IP=$(hostname -I | awk '{print $1}')` 取本机 IP，依赖 `hostname -I` 输出顺序。这台机器有上百个虚拟/桥接网卡，真实可路由 IP 没有排在最前面，导致取到了一个虚拟网卡 IP，而 Ray 节点注册用的是真实可路由 IP，两者对不上。
- **修复**：改用不依赖网卡枚举顺序的路由查询法——建一个 UDP socket "连"外部地址（这个 UDP connect 用于内核路由选择），读出内核选定的本地出口 IP：
  ```bash
  LOCAL_IP=$(python3 -c "import socket; s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.connect(('8.8.8.8', 80)); print(s.getsockname()[0]); s.close()")
  ```

### 报错二：DataLoader worker 里 `AttributeError: 'str' object has no attribute 'get'`

- **现象**：`verl` 的 `rl_dataset.py` 里 `row_dict.get("extra_info", {}).get("index", 0)` 对着字符串调 `.get()` 报错，且发生在 DataLoader 子进程里被上层重试吞掉，刷出几千万行日志。
- **根因**：`psrl_demo/data/gsm8k/{train,test}.parquet` 的 `prompt`/`reward_model`/`extra_info` 三列本该是 Arrow 原生 struct/list，实际存成了 JSON 字符串，`datasets.load_dataset` 读出来仍是字符串，与 veRL 期望的 dict/list 契约不符。
- **修复**：不改第三方 `verl` 代码加防御判断，而是修数据源——用 pandas 把这三列 `json.loads` 解码回原生类型再落盘（原文件备份到 `.bak/`）。

### 教训

两处都属于"环境/数据契约"层面的坑，而不是训练算法逻辑问题：
- 依赖 `hostname -I`/`ip addr` 之类会受网卡数量和顺序影响的命令来定位"本机 IP"不可靠，应该用路由表查询（`ip route get` 或 socket connect 技巧）。
- 用第三方框架的数据 loader 时，数据文件的列类型必须严格匹配其假设（这里是"嵌套字段必须是原生 Arrow 类型，不能是 JSON 字符串"），生成数据集的脏活最好在预处理脚本里保证类型，而不是等运行时报错才发现。

## 让 `qwen2.5_3b_fsdp.sh` 跑通 2 节点实验：脚本改了什么

### 一句话结论

脚本原本要求调用者自己导出一堆环境变量才能跑（`PSRL_WORKSPACE`、`LOCAL_IP` 等），且这些变量会被脚本内部 `source` 的公共环境脚本悄悄覆盖；改成脚本自身负责计算和保护这些变量后，调用方只需要设置 `PSRL_WORKSPACE` 一个变量即可运行。

### 根因

脚本里 `source ${PSRL_WORKSPACE}/env/psrl.sh` 会连带 source 到上级的公共 `activate` 脚本，而那个脚本会无条件地把 `PSRL_WORKSPACE` 重新导出成它自己默认的工作区路径，覆盖掉调用者原本设置的值。脚本后面所有依赖 `PSRL_WORKSPACE` 算出来的路径（模型路径、训练/测试数据路径、日志路径）都因此指向了错误的目录，报 `FileNotFoundError`。

### 三处修改

1. **保护 `PSRL_WORKSPACE` 不被 `source` 链路覆盖**：
   ```bash
   : "${PSRL_WORKSPACE:?PSRL_WORKSPACE must be set...}"
   _psrl_workspace=${PSRL_WORKSPACE}
   source ${PSRL_WORKSPACE}/env/psrl.sh
   export PSRL_WORKSPACE=${_psrl_workspace}   # 恢复被覆盖的值
   ```
   `source` 前把值存进临时变量，`source` 后立刻恢复；同时用 `:${VAR:?msg}` 强制要求调用者显式传入，缺失时给出清晰报错而不是静默用错路径。

2. **`LOCAL_IP` 改为脚本内自计算**，复用单机 demo 脚本的做法（见[单机启动故障复盘](#单机-demo-踩坑记录两处根因与修复)报错一）：
   ```bash
   LOCAL_IP=$(python3 -c "import socket; s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.connect(('8.8.8.8', 80)); print(s.getsockname()[0]); s.close()")
   ```
   这是当时修改的记录；当前仓库 DAPO 脚本仍使用外部 `LOCAL_IP`，需要按目标节点路由并核对 Ray 注册地址。

3. **日志/checkpoint 路径改为跟着 `PSRL_WORKSPACE` 走，而不是跟着 Python 包安装路径走**：删掉了通过 `python -c "import psrl..."` 反推安装目录的写法（以及从未真正生效的 `HOME=` 赋值），`logging_path`、最终 `tee` 的日志文件、`CKPT_ROOT` 默认值统一改成基于 `${PSRL_WORKSPACE}`，并补上 `mkdir -p ${PSRL_WORKSPACE}/logs`。

### 验证

原记录报告：当时修改后的 2 节点、16 GPU 脚本完成训练并正常退出。原始完整日志未随本页发布，当前脚本也未保留本节全部修改，因此该结果作为历史记录保存。

### 教训

和[单机启动故障复盘](#单机-demo-踩坑记录两处根因与修复)的单机坑同一类问题：多层 `source` 链路里，下游脚本对"某个环境变量已经是我要的值"的假设很容易被上游脚本悄悄打破。凡是脚本要 `source` 一个不受自己控制的公共环境脚本，且自身行为依赖某个变量的具体值时，都应该在 `source` 前后做保存/恢复，不能假设 `source` 只会新增变量、不会覆盖变量。

## laps/repair_easy 多机训练踩坑复盘：从 `max_model_len` 崩溃到重启，给下一次训练任务的检查清单

### 一句话结论

`examples/sciaccel_rl/fsdp_qwen2.5_3b_laps.sh` 是从另一个模型的脚本（`fsdp_qwen35_4b.sh`）改造来的，改造时只调了模型路径，没有重新核对**目标模型自己的上下文窗口上限**，导致 `max_prompt_length + max_response_length`（67584）超过 Qwen2.5-3B 的 `max_position_embeddings`（32768），8 个 vLLM server 在启动阶段全部 `ValueError` 崩溃；修复只用脚本本身已经预留的 `MAX_RESPONSE_LENGTH` 环境变量覆盖（改成 `30720`，使 `2048+30720=32768` 刚好等于上限），不改脚本默认值，重新以相同拓扑重启后 `[validate_config] All configuration checks passed successfully!`，顺利通过了此前崩溃的那一步。详细的字段含义和 RoPE 原理见 [模型配置：上下文长度与生成限制](../03-模型配置_上下文长度与生成限制.md)。

### 时间线

| 时刻 | 事件 |
|---|---|
| 2026-09-17 | 首次启动，`max_response_length=65536`（继承自 `fsdp_qwen35_4b.sh` 的默认值），8 个 vLLM rollout/validate server 在 `__init__` 阶段全部抛出 `ValueError: max_model_len (67584) should be less than or equal to max_position_embeddings (32768)`，级联触发 `ActorDiedError`，训练 driver 退出 |
| 2026-09-18 | 确认 Ray 集群仍空闲（`ray status` 显示 3 节点 24 GPU 全部 0 占用，`main_ppo` 无残留进程）后，用 `MAX_RESPONSE_LENGTH=30720` 覆盖重启，`validate_config` 通过，进程正常拉起 rollout/validate/PS 各角色 |

### 改脚本 vs. 改调用参数：为什么选后者

`fsdp_qwen2.5_3b_laps.sh` 里 `max_response_length` 本来就写成了 `${MAX_RESPONSE_LENGTH:-65536}`——脚本作者已经预留了外部覆盖的口子，只是默认值是从别的模型抄过来的、没人替 Qwen2.5-3B 校正过。既然口子已经在，就没必要改脚本本身（改了会影响这份脚本以后被用在别的、真的需要大 `max_response_length` 的模型上），直接在调用时传 `MAX_RESPONSE_LENGTH=30720` 即可——这也是当时"能用参数覆盖就不碰脚本默认值"的一贯做法（同一份脚本很多变量都是 `${VAR:-default}` 形式）。

### 检查清单：下次启动一个新的训练任务前

1. **核对上下文窗口预算，尤其是"照抄别的模型脚本"时**：`max_prompt_length + max_response_length`（进而 `max_model_len`）必须 `≤` 目标模型 `config.json` 里的 `max_position_embeddings`（没有配 `rope_scaling` 时是硬上限）。换模型 = 重新核对这一项，不能假设别的模型脚本里的默认值天然适用。
2. **改脚本前先看有没有现成的环境变量覆盖口子**（`grep '\${.*:-' script.sh`）；有就传参数，没有再考虑改默认值——改默认值会影响脚本对其他场景的复用性。
3. **复用集群前先确认它真的空闲**：`ray status`（3 节点/GPU 数是否符合预期、`Total Usage` 是否接近 0）+ `ps aux | grep main_ppo`（确认没有残留进程）+ `nvidia-smi`（两台机器 GPU 利用率/显存是否都是 0），三者都确认了再重用，不要凭"看起来没人用"就直接抢占共享集群资源。
4. **`LOCAL_IP` 多机场景必须显式传**：单机脚本能自动探测（见[单机启动故障复盘](#单机-demo-踩坑记录两处根因与修复) UDP socket 技巧），但 `fsdp_qwen2.5_3b_laps.sh` 这类多机脚本默认 `LOCAL_IP=127.0.0.1`，必须显式传成头节点的真实可路由 IP，否则 worker 节点连不上 `ps_manager`（`PSManager IP xxx not found` 类报错，见[多机启动脚本修复](#让-qwen25_3b_fsdpsh-跑通-2-节点实验脚本改了什么)同源问题)。
5. **后台启动用 `nohup setsid ... & disown` 三件套**，并把 stdout/stderr 重定向到固定路径的日志文件，这样断开 SSH 连接、甚至当前 Claude 会话结束都不影响训练进程存活；重启前记得把旧崩溃日志 `mv` 走而不是覆盖（`tee` 不是 `tee -a`，直接重跑会连崩溃现场一起冲掉）。
6. **别只看"进程还活着"就判定训练健康**：这次崩溃发生在启动阶段（`validate_config`/vLLM 初始化），下一类常见故障发生在训练中途——[训练排障：DAPO退化诊断](../05-训练排障_DAPO退化诊断.md) 记录过一次 DAPO+Qwen2.5-3B 训练约 step 115 后的持续训练退化（`entropy`→0、`response_length` 打满、`reward`→-1、`grad_norm` 爆炸），过程中进程本身没有退出、只是指标全废。所以监控除了"进程存活 + GPU 利用率"，还必须盯 `actor/entropy`、`response_length/clip_ratio`、`group/zero_variance_fraction`、`grad_norm` 这几个指标（见[训练日志与指标](01-PSRL运行_准备启动与监控.md#如何阅读训练日志抓取每步指标)指标表），以预先定义的异常阈值及时保存并结束。
7. **建立自动化的定期巡检**，不要指望自己全程盯着：历史执行曾每 20 分钟巡检日志、GPU 与进程；后续可用实际支持的监控系统，并按进程归属与退出状态决定清理，单次遥测失败单独记录。

### 记忆点

崩溃分两大类，排查思路不一样：**启动期崩溃**（配置/资源不匹配，比如这次的 `max_model_len`，或第八/十二节的 IP/数据类型问题）通常几秒内就能从日志报错定位到根因，修好参数重启即可；**训练中期崩溃**（熵崩溃、reward 坍缩这类）不会报错、进程也不退出，只能靠持续盯几个关键指标的变化趋势发现，可根据预设阈值停止、保全证据，再决定从健康 checkpoint 做有界对照。
