# 从一道代码题理解 PSRL 的 EnvWorker

EnvWorker 是做题环境的本地管理员：它跟踪任务容器的启动、运行和清理，报告资源占用，让 PSRL 能同时运行很多任务。

> 本文解释的是 2026-09-21 Env Service 设计提案（本地资料，未随仓库发布）。原文标注为待批准；本文提到的新 EnvRouter、新版 EnvWorker 和两个 Gate 是目标设计。
>
> 现有代码中也有一个叫 EnvWorker 的组件，但职责与新版不同。本文先讲新设计为什么需要这些组件，再在第 9 节对照现有实现。实现状态依据 2026-09-22 的源码检查；例子中的机器配置和资源数字均为教学示例。

## 1. 先看模型怎样修一道代码题

假设我们给模型一道题：

> 修复 `solver.py`，让它通过测试。

文件里有一个错误：

```python
def add(a, b):
    return a - b
```

测试要求 `add(2, 3)` 返回 `5`。模型要查看代码、修改代码、运行测试，再根据结果决定是否继续修改。

这个过程可以写成：

```text
读题 → 查看文件 → 修改代码 → 运行测试 → 得到评分
                              │
                              └─ 测试失败，就继续修改
```

这里有一个关键区别：模型能生成“运行测试”的指令，但还需要另一个程序真正执行它。

例如，模型通过工具调用提出：

```bash
python -m pytest tests/test_solver.py -q
```

系统必须在某个地方运行这条命令，再把测试输出交给模型。这个地方就是任务的“环境”：里面有 Python、依赖、题目文件和可以修改的目录。

### 做题环境为什么通常用 Docker 容器

可以把容器理解成给任务准备的独立工作间。任务 A 修改自己的文件，不应把任务 B 的文件也改了。

容器不是新建的一台物理机器。多个容器可以在同一台机器上运行，共享这台机器的 CPU、内存等硬件，因此还需要配置资源限制。

本文会反复用到三个词：

| 词 | 通俗解释 | 本例中的含义 |
|---|---|---|
| sandbox，沙箱 | 执行任务的隔离环境 | 放着 `solver.py` 和测试文件的容器 |
| episode | 从开始到评分的一次完整尝试 | 这次修代码的全过程 |
| turn，轮次 | episode 中的一次模型交互 | 模型看完测试失败信息，再生成下一步操作 |

一个 episode 通常会有很多轮，但共用同一个任务容器。否则模型刚改好的文件，下一轮就找不到了。容器持续存在也不代表所有 shell 变量一定跨调用保留；那取决于具体的命令执行方式。

### 这跟训练有什么关系

PSRL 需要收集大量这样的尝试。每次尝试有模型生成的操作、环境返回的结果和最后的评分，系统再将这些信息整理成训练样本。

因此，做题环境是训练数据产生的一环。如果容器起不来、测试没跑完、评分被其他任务干扰，即使模型服务正常，也可能收不到有效样本。

Env Service 就是文档对“统一管理这些做题环境”的整套方案的称呼，EnvWorker 是其中一个组件。

## 2. EnvWorker、Harbor、EnvRouter 分别管什么

先只记住这三个名字：

- **Harbor：把一题实际跑完。** 准备环境、执行命令、运行评分程序、停止环境。
- **EnvRouter：决定任务在哪里启动，以及现在能不能启动。**
- **EnvWorker：管理自己负责的那份资源上的环境，跟踪容器和负载，配合清理。**

用一条具体请求来理解：

> “我想启动一个需要 4 核 CPU、12 GiB 内存的任务。”

EnvRouter 查看各处剩余容量，决定：“节点 B 有空位，放到那里。”

负责这份资源的 EnvWorker 跟踪新任务环境，记录它的容器和运行情况。具体创建容器、执行 `pytest` 等操作由 Harbor 完成。

如果任务异常退出，系统还要能找到它留下的容器并清理。EnvWorker 提供本地的环境状态和生命周期管理，EnvRouter 管理全局占用记录与回收安排。

这里描述的是职责分工。提案中的包装方式和调用接口仍需在实现时统一，不要把这段话理解成已经存在的一组固定函数调用。

### Harbor 已经能开关容器，EnvWorker 是否重复了

区别在于管理范围。

Harbor 可以知道“这一题的容器怎么创建、命令怎么执行、怎样评分”。但这不等于整个 PSRL 已经知道：

> 同一节点上的其他任务占了多少资源？  
> 哪些调用方已经退出，却留下了容器？  
> 这张 GPU 能不能再分给下一批任务？

新 EnvWorker 的目标，是围绕 Harbor 提供这些本地管理能力，复用 Harbor 的具体执行功能。它不需要再写一套自己的终端协议。

### AgentLoopWorker 又是什么

Agent loop 是“调用模型—执行工具—把结果交回模型”的循环。AgentLoopWorker 是运行这段流程的 PSRL 组件，SciAccel 路径会由它驱动 Harbor 流程。

用本例区分两个名字：

| 组件 | 它关心的事情 |
|---|---|
| AgentLoopWorker | 模型刚改完代码，现在该跑测试；测试失败后还要继续问模型 |
| EnvWorker | 这个任务容器仍在运行，占用了多少资源，结束后是否清理干净 |

“做题进行到哪一步”和“做题环境是否正常”，是两种不同职责。

## 3. 为什么需要统一管理：两个进程各开 8 个任务的例子

假设一台机器最多适合同时运行 8 个任务。你给每个 AgentLoopWorker 都设置“最多同时运行 8 个”。

如果这台机器上恰好有两个这样的进程，会发生什么？

```text
进程 A：我的上限是 8 个 → 启动 8 个
进程 B：我的上限也是 8 个 → 再启动 8 个

整台机器：16 个任务
```

两个进程都遵守了自己的规则，但机器超载了。

当前 SciAccel 使用的 `asyncio.Semaphore` 可以理解成进程内的名额计数器。它能控制这个进程同时放行多少任务，却不会自动与另一进程共享计数。

新方案要补上的，是一份大家共同遵守的容量账本：

```text
节点总上限：8
A 已申请：5
B 最多还能申请：3
```

另外，如果节点 A 已满、节点 B 空闲，也应该在任务开始前选 B。若先把任务发给 A，再在 A 上等，B 的空位就可能利用不上。

这解释了两个组件为什么需要合作：EnvWorker 报告本地运行情况，EnvRouter 根据全局信息选择位置和控制启动数量。

> 提案第一步也考虑使用现有的 SlotManager，通过文件锁共享名额。它要真正形成共同限制，相关进程必须使用同一锁目录、锁命名空间和池标识；换一个类名不会自动让所有进程共享容量。

## 4. unit 是什么：用一份资源清单理解

文档没有直接说“每台机器一个 EnvWorker”，而是说“每个 unit 一个”。

unit 可以理解成登记好的一份资源额度。例如：

```text
名称：cpu-unit-b
位置：节点 B
CPU 预算：16 核
内存预算：64 GiB
最大容器数：4
GPU：无
```

假设每个任务申请 4 核 CPU、12 GiB 内存：

| 已启动任务数 | CPU 额度占用 | 内存额度占用 | 能否再启动一个同样的任务 |
|---|---:|---:|---|
| 1 | 4 核 | 12 GiB | 可以 |
| 3 | 12 核 | 36 GiB | 可以 |
| 4 | 16 核 | 48 GiB | 不可以 |

最后一行还有 16 GiB 内存，但 CPU 额度已经用完，容器数也到上限了。申请必须同时满足所有限制。

unit 是管理资源的方式，不是一个容器，也不一定等于整台机器：

```text
节点 B
├─ CPU unit：由一个 EnvWorker 管理
│  ├─ 任务容器 1
│  ├─ 任务容器 2
│  └─ ……
└─ GPU unit：由另一个 EnvWorker 管理
   ├─ 任务容器 3
   └─ ……
```

这个图表示管理归属，不表示 EnvWorker 进程里面嵌套了容器。

GPU unit 还需要登记允许使用的 GPU 编号和显存预算。不同 unit 不能把同一张 GPU 重复分配，也要避开仍归训练或模型推理使用的设备。

登记预算只是第一步。实际执行时还得配置容器资源限制、映射正确设备，并监测真实用量。任务申报需要 12 GiB，不代表运行峰值一定不会超过它。

文档把 EnvWorker 实现为 Ray actor。初读时可以将它理解为集群里长期运行的 Python 服务对象：其他组件可以调用它，它也能记住自己管理着哪些环境。

## 5. 把组件串起来：一次任务从申请到结束

继续用修复 `solver.py` 的例子，按目标设计走一遍。

### 第一步：先申请资源，没空位就等

PSRL 准备启动一次尝试，先检查有没有满足需求的 unit。

文档把这一步叫 **Gate A**。“Gate”就是一道关卡，Gate A 检查的是：

> 现在启动这个新环境，会不会让 CPU、内存、显存或容器数量超出预算？

通过检查后才允许创建容器。这道检查放在 Harbor 的 `Job.create` 之前。

顺序很重要，因为 Harbor 会在第一次模型调用前就启动环境。如果先开 100 个容器、再让其中 90 个排队，那些排队的容器也可能已经占着内存了。

在 Gate A 等待时，任务容器尚未创建，因此没有这份沙箱开销；调用方本身仍有少量开销，也仍可能被取消或受其他超时限制。

### 第二步：在选定的位置创建环境

假设选择了节点 B 的 CPU unit，就把这次尝试交给合适的 B 节点上的 AgentLoopWorker，按分配结果运行 Harbor。

提案的第一层接入方式仍使用本地 Docker。这意味着运行 Harbor 的位置决定了容器所在位置：要把容器放到 B，就需要把任务派给 B 上的 worker。

这里暂时没有“agent 在 A，容器可以透明地放在任意远端 B”的新远程执行服务。

### 第三步：在同一个环境中反复做题

Harbor 启动容器，agent 开始与模型交互：

```text
第 1 轮：模型要求查看 solver.py → 工具返回文件内容
第 2 轮：模型修改减号为加号 → 文件在容器中更新
第 3 轮：模型要求运行测试 → 工具返回测试结果
```

EnvWorker 跟踪环境和负载。它不会决定将减号改成加号，也不需要让 EnvRouter 转发每一条 shell 命令。

### 第四步：评分并收集样本

Harbor 运行任务的 verifier，也就是评分程序。评分规则由任务定义，可能检查答案、测试通过情况或其他要求。

PSRL 将评分和这次尝试的模型调用记录对应起来，整理为后续训练数据。EnvWorker 负责执行条件，不负责计算训练梯度。

### 第五步：清理之后再归还名额

Harbor 停止环境，服务检查是否还有残留容器或进程，然后更新资源占用记录。

正常完成、执行失败、主动取消都需要走清理流程。如果发起任务的进程突然退出，还需要其他组件接手处理遗留环境。

下面的顺序表达了这套设计要保证的事情：

```text
申请资源 → 获得名额 → 创建环境 → 多轮做题 → 评分 → 清理核验 → 归还资源
```

具体故障处理和调用顺序仍需要实现与测试，不能仅靠流程图就认为已经有了保证。

## 6. GPU 任务为什么更难：显存、计算和评分是三件事

### 模型用的 GPU，和任务用的 GPU，用途不同

前面的 `pytest` 例子只需要 CPU。假如任务换成“修改一个 CUDA solver 并测试”，任务环境本身也要使用 GPU。

```text
模型推理 GPU：运行 Qwen，生成“执行 ./solver”的操作
                                ↓
任务环境 GPU：真正运行 ./solver，返回计算结果
```

训练模型参数还会使用训练侧资源。

Env Service 管的是任务环境资源。它需要防止环境错误地挤到模型推理或训练仍在使用的设备上。

在文档描述的部署中，环境由独立的 Docker 服务创建。它们的 GPU 使用不会自动计入 Ray 对 actor 的逻辑资源分配。因此，不能因为“Ray 已经分过 GPU”就认为新开的任务容器一定不会抢错设备。

### 显存够不够：必须在启动前算

假设一张 GPU 有 48 GiB 显存，预留一部分后，给任务登记 40 GiB 预算。每个任务预计需要常驻 18 GiB：

```text
两个任务：18 + 18 = 36 GiB，可以放下
三个任务：18 + 18 + 18 = 54 GiB，放不下
```

Gate A 应阻止第三个任务启动。还要考虑实际峰值和任务申报误差，不能把预计用量当成永远准确的保证。

暂停其中一个任务的模型请求，通常解决不了这个问题。它的 solver 进程可能仍在运行，已分配的显存也可能还在。

“暂时不调用模型”“不再进行 GPU 计算”和“释放显存”是不同的状态。

### 显存放得下，也不一定适合同时评分

原文记录的 `laps-accel-cuda` 场景有一个容易忽略的问题：某些检查观察的是整张 GPU 的活动。

假设：

```text
任务 A：实际没有正确使用 GPU
任务 B：正在同一张 GPU 上计算
检查程序：看见 GPU 很忙，误以为 A 使用了 GPU
```

如果这种检查影响评判，A 的结果就被 B 干扰了。对于依赖该检查的评分，测量期间需要没有其他任务的 GPU 计算。

所以要分别控制：

| 要控制的事情 | 解决什么问题 |
|---|---|
| 同时存在多少个环境、合计占多少显存 | 避免装不下而 OOM |
| 同时有多少任务真正执行 GPU 运算 | 控制计算竞争与相互干扰 |
| 评分期间是否有其他任务在用 GPU | 避免测量结果归错任务 |

原文所述任务的基础 reward 与正确性相关，speedup 是辅助信息。不能由这个例子推断所有 SciAccel 任务都直接按速度打分。

### Gate B：先缓一缓，再让 agent 执行下一条工具命令

Gate A 管“新容器能不能启动”。文档另外为 GPU unit 设计了 **Gate B**，控制已经启动的任务何时继续下一轮环境操作。

普通 agent 的顺序是：

```text
等待模型回复 → 收到工具调用 → 执行工具 → 再请求模型
```

提案将 Gate B 放在 SessionRouter 返回模型回复之前：

```text
模型已经生成回复 → Gate B 暂时扣住回复 → 放行 → agent 执行工具
```

这样就能推迟后续工具执行。它与“阻止下一次模型请求进入”不同：如果到下一次请求才拦，前一条工具命令早已执行了。

不过，等待时容器仍在，显存也不会自动释放。Gate B 不能代替 Gate A 的显存预算检查。

### 后台程序为什么让 Gate B 也不够用

假如模型执行：

```bash
nohup ./solver > solver.log 2>&1 &
```

末尾的 `&` 让程序转到后台执行。命令很快返回，但 solver 可能仍然占用 GPU。

这时 agent 可以去问模型，也可能被挂起；这两件事都不能证明 solver 已停止。需要查看真实的 GPU 进程和占用，不能只看 session 是否处于模型生成阶段。

另外，提案允许 Gate B 最多等待默认的 600 秒，超时后放行，以避免毁掉长时间运行的 episode。这个等待发生在模型请求中，也会消耗客户端的请求超时预算。

这说明 Gate B 是软节流。要保证评分不受其他计算污染，还需要额外落实干净的测量窗口。识别并处理受污染结果也是可考虑的方向，但这不是已经实现的功能。

## 7. EnvWorker 为什么还要持续上报状态、处理清理

### 申报用量和实际用量可能不同

任务启动时说“需要 18 GiB”，运行起来可能达到更高峰值。一个已经结束的任务，也可能留下后台进程。

因此，服务不能只有启动时的账本，还需要知道现在的实际情况。例如一份报告可以表示：

```text
这个 unit 有 2 个运行中的容器
任务申报显存总量是 36 GiB
实际观察到显存占用是 39 GiB
有一个 solver 进程仍在进行 GPU 计算
```

文档将这种定期报告叫“负载快照”。EnvWorker 提供本地观测，全局服务再结合等待队列等信息做决定。随着方案推进，调度可以利用实际负载，而不是只看容器个数。

### 任务结束，不代表资源已经释放

假设 agent 进程崩溃，它来不及关闭容器：

```text
agent 已退出
容器仍在
solver 仍在占 GPU
```

如果系统只从账本里删掉这个任务，就可能立刻把同一份资源发给新任务，造成重叠占用。

提案因此需要容器标签、租约和回收机制：

| 词 | 在这里是什么意思 |
|---|---|
| 容器标签 | 给容器贴上可查询的归属信息，便于找出某任务留下的环境 |
| slot | 允许一个任务进入的并发名额 |
| lease，租约 | 获准使用资源及其有效期等信息的记录 |
| TTL | 有效期限，帮助识别长期失联的占用 |

健康的长任务也可能运行很久，因此活动记录、有效期和续期规则必须合理设计。不能仅因一段时间没有模型请求就认为任务死了。

对于 GPU，归还需要经过“正在清理”和“核验已经空闲”。文档用 `RETURNING` 表示这个中间状态：

```text
环境使用中 → 正在归还（RETURNING）→ 确认资源已释放 → 空闲（FREE）
```

### 为什么不直接暂停容器，拿走它的显存

暂停计算通常不会释放程序已经申请的显存。

模型侧的 `torch_memory_saver` 可以管理模型进程中受它控制的内存，但环境里的 solver 是另一个进程，自己的 CUDA 内存通常不在它的管理范围内。

在原文讨论的部署和方案下，要回收这份资源，主要依靠等待任务结束，或终止并清理任务。把一个运行中的 GPU 程序连同状态搬到别处，不在当前落地范围内；这不表示所有系统永远都做不到 GPU 进程迁移。

## 8. SMG 和 SessionRouter 在哪：把模型这条路与工具这条路分开看

前面主要讲执行环境。现在回到“模型如何生成下一步操作”。

对于这里讨论的 Harbor session 型接入，一轮交互可以简化成：

```text
请求模型：
Agent → SessionRouter → SMG → vLLM → 返回模型回复

执行工具：
Agent / Harbor → 任务容器执行命令 → 返回命令输出

下一轮：
把命令输出加入上下文，再请求模型
```

这是两类操作的路径示意，省略了返回链路细节和训练控制组件。原生 token 型 agent 还可以直接请求 SMG，不一定经过 SessionRouter。

| 组件 | 用一句具体的话理解 |
|---|---|
| SessionRouter | “这次模型调用属于哪次做题？这个会话现在能继续吗？” |
| SMG | “这次模型请求可以交给哪个推理实例？” |
| vLLM | “在这个实例上执行模型计算，生成 token。” |
| EnvRouter | “新任务环境放在哪个 unit？资源够不够？” |
| EnvWorker | “我负责的这些环境现在是否正常，资源是否已释放？” |
| Harbor | “在任务环境里执行命令，然后运行评分流程。” |

SMG 在本地依赖中的全称是 Shepherd Model Gateway。一个推理实例不一定只用一张 GPU，也可能用多张卡共同运行模型。

### 为什么 SMG 不能只选最空闲的实例

PSRL 一边采集样本，一边训练和更新模型。不同推理实例可能忙闲不同，权重更新状态也不同。

假设：

```text
实例 A：正在同步权重，暂时不能接请求
实例 B：很空闲，但模型版本不符合这次请求的要求
实例 C：版本满足要求，当前可以接请求
```

这时应选 C。不能因为 B 最空闲就把请求交给它。

满足可用性、版本和训练侧准入等条件后，才进一步比较负载，或使用配置启用的缓存亲和策略。“亲和”可以理解成尽量让相关请求继续去原来的实例，以增加复用已有前缀缓存的机会，并不保证必然命中缓存。

训练侧的请求预留是样本和版本记账，不是预先分配一块物理显存。版本约束也不是要求一个 episode 永远使用同一版权重。

### SMG 为什么还要记录模型输出

PSRL 最后要训练模型，需要知道它实际生成了哪些 token，以及生成时的相关信息，不能只拿一段显示出来的文字猜。

SMG 的 TITO 记录保存模型调用的 token、生成概率相关信息和轮次边界。episode 结束后，PSRL 把这些记录与评分对应，构建训练数据。具体 token 与 mask 的解释见后面的延伸文档。

在启用相应路径时，SMG 还可以处理部分生成被中断后的续跑。保留已生成 token 并继续，不等于一定把原实例的 KV cache 搬到新实例；后者需要额外机制。

### 到底是谁决定暂停会话

PSRL 的 coordinator 汇集信息，相关 SessionScheduler 可以计算哪些会话需要暂停或继续；SessionRouter 执行对应的会话门控。这个 Python 调度逻辑不在 Rust SMG 内部，容量驱动的会话策略还需要相应配置启用。

现有 SessionRouter 的 `hang` 主要阻止后续模型请求进入，不会直接暂停已经运行的工具程序。第 6 节的 Gate B 则是提案中位于模型响应出口的额外控制点。

SessionRouter 用是否有在途模型请求推导 `generate/env` 状态。没有模型请求时标成 `env`，也可能只是轮间空隙；有模型请求时，后台 solver 仍可能运行。因此，这个状态不是实际 GPU 占用报告。

Env Service 借鉴的是“全局选择位置，本地执行工作”的分工方式。SMG 本身不会因此替它管理 Docker 容器或环境 GPU 租约。

## 9. 当前代码是什么样，新方案准备怎样接入

截至 2026-09-22 的检查，项目里有两条环境执行路径：

| 路径 | 当前怎样执行任务 | 需要理解的区别 |
|---|---|---|
| 旧 EnvWorker，主要对应文档所述 MLGym / AIRS-Bench 配方 | 自己创建容器、维持 shell、执行命令 | 已有执行组件，还没有精简成本文的新角色 |
| SciAccel 的 Harbor 路径 | AgentLoopWorker 内的专用线程运行 Harbor，使用进程内 semaphore | 已能执行 episode，但没有本文完整的统一环境服务 |

旧路径在所检查配方中使用 CPU 沙箱，GPU 路径尚未得到验证。本次搜索未找到提案中的 `EnvRouter` / `EnvUnitRegistry` 实现。原提案中的规划阶段测试通过记录，也不能视为整个服务已经接入。

提案的推进顺序可以理解成：

1. **先整理现有执行方式。** 用 EnvWorker 包装 Harbor 调用，修正共享并发限制，给容器增加可追踪标签。旧 shell 后端要在兼容性验证通过后才删除，例如要验证跨轮 shell 状态满足旧任务要求。
2. **再统一管理资源。** 登记 unit，接入 EnvRouter 和 Gate A，提供状态报告与失联回收。
3. **再支持 GPU 环境。** 落实正确设备映射，核验借出和归还，接入 Gate B，并测试后台 GPU 计算对评分的干扰。
4. **最后优化放置。** 利用实际负载选位置，必要时对失败尝试进行有上限的重新派发。重新开始一次尝试，不等于迁移正在运行的进程。

原文还用 L1/L2/L3 区分接入 Harbor 的深度：

| 层次 | 通俗理解 | 提案态度 |
|---|---|---|
| L1 | 在现有 Harbor 外面加资源申请，传入本次任务的容器配置 | 优先采用 |
| L2 | 替换 Harbor 的环境实现，自己更深入地管理环境 | 留待需要容器复用等能力时考虑 |
| L3 | 增加远程执行和文件传输，让 agent 与容器可以在不同节点 | 不属于当前落地范围 |

这两组编号表达不同事情：Phase 表示先后步骤，L1/L2/L3 表示改动 Harbor 的深度。

## 10. 接入之后能改善什么，哪些问题还要另外处理

对 PSRL 的主要价值，是让做题样本更稳定地产生：

| 问题 | 新方案提供的管理能力 |
|---|---|
| 两个进程各自限流，合计却超载 | 共享容量账本和启动前准入 |
| A 节点排长队，B 节点有空位 | 在派发任务时选择合适 unit |
| 环境误用推理 GPU | 明确设备归属并落实设备映射 |
| agent 退出后容器仍占资源 | 跟踪归属、清理遗留环境、核验归还 |
| 只知道容器数，不知道实际负载 | 周期报告进程和资源占用 |
| 评分受到其他 GPU 任务影响 | 提供观测与调度基础，进一步落实干净的评分窗口 |

它不直接让模型学会更好的解题方法，也不包治 OOM。模型 prompt 太长、训练激活占用太大、单个 solver 峰值超预算，仍需分别分析。

如果集群的 GPU 已全部分给训练和推理，还需要明确从哪里给环境留出设备。配置一个 EnvRouter 并不会产生新的显存。

两个实现细节初读时可以跳过，但实现时不能忽略：
