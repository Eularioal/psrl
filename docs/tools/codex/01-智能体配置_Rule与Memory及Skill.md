## 为什么需要它们

让 AI 帮忙做事时，除了“这次要做什么”，通常还得交代三类信息：团队有什么要求、之前做到哪里、这类事情通常怎么做。每次重新解释既费时间，也容易遗漏。

可以把 AI 想成刚加入团队的同事：给他一份工作规范、一份交接笔记，再给常见任务配一份操作手册。它们分别对应 Rule、Memory、Skill。这里按通用用途介绍，具体文件名和加载方式以所用产品为准。

## 三者分别做什么

| 概念 | 主要回答 | 适合保存什么 | 简单例子 |
|---|---|---|---|
| **Rule，规则** | 做事应遵守哪些要求？ | 团队约定、输出要求、操作边界 | “项目文档统一放在 `docs/`，新增文档要更新索引。” |
| **Memory，记忆** | 有哪些背景值得记住？ | 用户偏好、项目事实、历史决策、进度与经验 | “上次已完成安装，测试卡在缺少示例数据。” |
| **Skill，技能** | 这类任务应该怎样完成？ | 适用条件、执行步骤、检查方法、模板或脚本 | “整理技术文档：查资料、写解释、补例子、检查链接。” |

**Rule 的作用是减少反复纠正。** 比如每次都要求使用中文，不如把它写成长期约定。在 Codex 中，`AGENTS.md` 可以承载这类指令，工具按其发现与作用范围规则加载。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

**Memory 的作用是减少反复交接。** 它把过去工作中有用的信息保留下来，后续任务读取相关内容后，就能继续推进。记忆可能由产品自动整理，也可以是项目自行维护的笔记。保存只是第一步，还要有读取或检索机制，才能进入 AI 本次可用的信息中。Codex 的内置记忆有独立的开关和使用控制，不等于项目里的任意笔记文件都会自动生效。[官方说明](https://learn.chatgpt.com/docs/customization/memories)

**Skill 的作用是复用成熟做法。** 它通常围绕一种任务编写，例如审查代码、生成报告、处理表格。在 Codex 中，技能以 `SKILL.md` 为核心，可附带脚本、参考资料和模板。AI 先看到技能名称与简介，判断适用后再读详细步骤，也可以由用户点名使用。[官方说明](https://learn.chatgpt.com/docs/build-skills)

## 一个例子就能分清

假设你对 AI 说：“帮我写一份项目使用说明。”以下是教学示例，并非某次真实执行记录。

1. **Rule 提供要求**：“用中文写，文档放进 `docs/`，并更新索引。”它决定交付要满足哪些条件。
2. **Memory 提供背景**：“目标读者是新同事，安装步骤上次已经验证，但示例数据还没准备好。”AI 据此知道应面向谁，以及哪些信息需要补查。
3. **Skill 提供方法**：“阅读项目入口 → 核对安装命令 → 编写最小示例 → 检查链接。”AI 按这套方法组织工作。
4. **最终交付**：一份放在正确目录、适合新同事阅读的中文说明，其中明确交代示例数据的准备条件，并登记到索引。

若这次又验证了示例数据的获取方法，可将有用结论更新到记忆或项目文档中，供下次参考。是否自动保存，取决于工具功能和项目约定。

## 怎样选择放在哪里

- **希望以后都遵守的要求，写成 Rule。** 尽量短、清楚、能判断是否做到。
- **以后可能需要回忆的信息，写入 Memory。** 记录时间、适用条件和来源，过时后及时更新。
- **反复出现的一类任务，整理成 Skill。** 写清什么时候使用、需要什么输入、如何执行、最后检查什么。

同一主题可以同时涉及三者。例如，“报告必须包含数据来源”是规则，“上次报告用了哪份数据”是记忆，“如何读取数据并生成报告”是技能。

## 把清晰讲解写成长期规则

“回答详细、高质量、容易理解”表达了目标，还需要说明怎样组织答案，才能减少反复纠正。本工作区于 2026-11-19 将通用表达要求集中维护在个人 `AGENTS.md`，工作区规则引用它，并保留项目文档、实验与知识回顾的补充要求。下面解释规则的写法，完整执行要求以实际加载文件为准。

### 把质量要求变成具体行为

| 容易出现的阅读障碍 | 应写入规则的行为 |
|---|---|
| 结论和细节交叉，读完仍不知道在回答什么 | 开头先回答核心问题，后文沿初始状态、动作、变化和结果推进 |
| A、B 在不同段落代表不同任务 | 同一例子保持任务身份、变量、单位与计时起点一致，切换例子时明确说明 |
| 公式有定义，但不知道为什么这样算 | 先解释实际动作与重叠关系，再给公式、代入数字，并将结果对应到等待或完成时间 |
| 长篇文字描述并发、等待和资源变化，读者需要自己拼出过程 | 总览图建立关系，时间线或状态图解释关键变化，图后说明原因，并实际渲染检查 |
| 多个模块进展不同，却笼统说已经完成 | 分别说明正式接入、实验原型和待实现部分，并核对实际依据 |
| 发散只有名词和链接，正文又太跳跃 | 主线讲完整后，选择少量相关机制，说明它怎样帮助理解当前问题 |

这些要求配合发送前的可读性检查：核心问题是否已回答，角色与数字是否一致，因果是否缺了一步，关键关系是否需要图表，相关知识是否确实有帮助。智能体应据此直接修改答案，无需向用户逐项展示检查过程。

### 把配图要求写到执行步骤里

“尽量图文并茂”需要变成可检查的交付条件。本工作区要求每篇维护中的文档至少嵌入一张相关的彩色解释图，README 也包括在内。Logo、装饰封面与纯箭头流程不能单独满足要求。提纲阶段就确定图要回答的问题，较长机制与架构文档先用总览图建立关系，再在难点处配局部图。图放在对应段落，前文提出问题，后文解释怎样读、为什么发生这些变化，以及它对当前问题意味着什么。

| 当前要解释什么 | 选择什么图表 | 正文补充什么 |
|---|---|---|
| A、B 谁运行、谁排队，哪段时间重叠 | 同一时间轴的对照时间线 | 每个动作的条件，以及等待怎样影响最终完成时间 |
| 并发增加后吞吐和延迟怎样变化 | 标清横纵轴、单位和条件的曲线 | 变化的原因、优化目标，以及教学假设或实测依据 |
| 谁调用谁，资源归属怎样改变 | 流程图、时序图、状态图或布局图 | 箭头传递什么、状态何时改变、实现到了哪一步 |

交付前需要实际渲染并查看，确认中文、字号、箭头和坐标清楚，图文中的角色与数字一致。留档默认嵌入可直接显示的图片，保留生成脚本或可编辑源文件。实测图保留数据来源与条件，教学曲线明确标注假设。[全文档配图检查器](../../_static/img/document-figures/check.py)检查覆盖和图片路径，图意与可读性仍由实际查看来判断。

已有的[借卡时间线](../../_static/img/document-figures/explained-borrowing-timeline-2487ead.png)和 [Roofline 与合批曲线](../../_static/img/document-figures/explained-roofline-and-batching-1ddd7ab.png)分别演示时间关系与性能关系的表达方式。两张图服务各自正文的独立场景，数字不沿用下一节的教学例子。[图集入口](../../_static/img/literature-reviews/README.md)提供对应正文与生成方法。完整配图规范集中在工作区规则，仓库入口与 README 风格指南引用它，避免维护多套详细要求。

### 同一个例子怎样连接解释与拓展

下面是演示表达方法的教学假设：只有一张 GPU，任务 A 可以安全归还它并暂停 10 秒，之后还需要 5 秒 GPU。任务 B 从暂停开始时就已就绪，需要 40 秒 GPU。两者互斥使用设备，没有借还开销，也没有 GPU 工作结束后的其他任务。

若给 A 留着，GPU 先空闲 10 秒，A 再运行 5 秒，B 最后运行 40 秒，全部在第 55 秒结束。若让 B 先用，B 在第 40 秒结束，A 随后运行 5 秒，全部在第 45 秒结束。A 自己从第 15 秒完成变成第 45 秒完成，多等了 30 秒，但整批提前了 10 秒。

这个例子先讲清当前决策，再自然引出相关知识：单任务完成时间和整批完成时间是两个指标，优化目标决定怎样评价“任务变慢”。如果进一步讨论任务还有 CPU 后续工作，就明确新增这个条件，再解释后续依赖怎样改变整体结果。完整机制与条件集中在[共享调度专题](../../env-worker-deep-dive/knowledge/02-资源与调度/05-训推共享_vLLM余量与容量调度.md#用完整时间线比较保留与归还)，本篇只演示怎样让一个场景贯穿解释。

同样，讲 Roofline 时可以从“这段计算为什么在等数据”出发，解释带宽，再说明缓存和合批怎样改变搬运量，最后回到并发决策。每次选择当前问题需要的关联，而非展开所有系统知识。相关原理见[推理机制中的 prefill 与 decode](../../psrl/推理与训练/01-vLLM推理_计算瓶颈与KV缓存.md#11-prefill-与-decode-的根本差异)。

## 介绍时别混淆这些概念

**这是一种用途划分，不是三个绝对互斥的文件格式。** 记忆里也可能保存偏好，技能里也可能包含注意事项。判断重点是：这条内容主要在约束行为、保存背景，还是指导任务步骤。

**Skill 不等于给模型重新训练了一项能力。** 它主要提供可复用的指导和配套资源，实际执行仍依赖模型、工具和权限。Memory 也不等于完整聊天记录，更不保证其中的历史事实至今有效。

**Codex 的 Rules 专有功能与广义规则有区别。** 本文的 Rule 泛指工作约定，而 Codex 的 `.rules` 文件主要控制命令在沙箱外执行时是允许、询问还是禁止。普通文字要求与工具层面的权限控制要分开理解。[官方 Rules 说明](https://learn.chatgpt.com/docs/agent-configuration/rules)

**重要要求不要只寄希望于记忆。** 需要持续遵守的团队规范应明确写进规则文件或项目文档，并确认工具确实读取了它们。

## 延伸阅读

本文用于快速介绍三者的用途，不展开客户端内部实现，也不保证不同产品具有相同的自动加载行为。Codex 相关机制依据上文链接的官方文档核对于 2026-11-09，未测试当前客户端的内置记忆开关。

下面继续用 Codex 的 AGENTS.md 说明这些规则应放在哪里、哪些会话会加载，以及如何确认生效。


## AGENTS.md 的放置、范围与验证

`AGENTS.md` 用于保存长期工作约定，例如文档位置、测试方法和回答偏好。一个项目可以有共同规则，也可以在子目录补充局部规则。判断生效范围时，要看 Codex 实际读取的指令链。

### 从哪里读取规则

按 2026-11-19 核对的[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)，Codex 在启动时建立指令链，先读取个人规则，再读取项目规则：

| 位置 | 用途 | 读取方法 |
|---|---|---|
| `$CODEX_HOME/AGENTS.md` | 跨项目的个人偏好 | 同目录有非空 `AGENTS.override.md` 时优先读取后者 |
| 项目根目录至当前工作目录 | 项目及子目录约定 | 沿目录逐级读取，每个目录至多选一个指令文件 |
| 更深目录的规则 | 该范围内的具体要求 | 与上层冲突时采用更具体的要求 |

项目根目录通常由 Git 仓库识别；没有识别到项目根时，项目级搜索从当前目录进行。项目外层的普通父目录文件是否被带入，还取决于启动环境是否显式提供它。个人规则默认位于 `~/.codex`，也可以通过 `CODEX_HOME` 更换位置。

`AGENTS.override.md` 替代的是**同一目录**的普通 `AGENTS.md`。更深层规则与已加载上层规则一起组成指令链。

### 用一个目录例子理解优先级

```text
lw/
├── AGENTS.md                 工作区约定
└── psrl/                     Git 仓库根目录
    ├── AGENTS.md             PSRL 约定
    └── docs/
        └── AGENTS.md         文档专属约定（假设存在）
```

假设从 `psrl/docs/` 启动，项目搜索会覆盖 `psrl/` 和 `psrl/docs/`。例如上层要求“更新文档索引”，下层补充“源码链接使用相对路径”，两条共同生效。若两处对同一格式有冲突，则采用更靠近任务目录的要求。

`lw/AGENTS.md` 在 Git 根目录之外。当前对话的启动环境已显式提供工作区规则，因此本会话遵守这些规则；在另一个终端重新启动 Codex 时，应检查加载结果。这个例子中的 `docs/AGENTS.md` 仅用于教学。

### 这个工作区应该怎样放规则

- 所有项目都要遵守的个人偏好：放在 `$CODEX_HOME/AGENTS.md`。
- PSRL 的项目规则由[仓库 AGENTS.md](../../../AGENTS.md)提供入口，详细的工作区文档、开发与验证约定由它指向父层工作区规则。是否自动加载父层文件，仍按上面的搜索范围检查。
- 某个子目录才需要的细节：在该目录维护局部规则，避免复制整份上层文件。

本次现场检查确认，当前 `CODEX_HOME` 指向工作区的 `.codex` 目录，该处已有个人 `AGENTS.md`，没有同目录 override。因此通用回答规则在个人文件中维护，工作区文件引用它，不再复制整段表达偏好。新会话沿用这个 `CODEX_HOME` 时会读取该文件，换用其他个人配置目录时需核对相应文件。

规则应说明“怎样完成任务”，并保持足够短，方便理解与维护。默认项目文档读取上限为 32 KiB，可通过配置调整；冗长且重复的规则会挤占这部分空间。

### 怎样确认已经生效

修改规则后，在新会话中询问 Codex“本项目加载了哪些规则，请列出文件和关键约定”，并对照工作目录检查。实际加载信息比仅凭目录名推断更可靠。

本次会话已收到更新后的个人规则。已有其他会话是否收到文件更新，应另行确认，重新启动可让 Codex 按新文件建立指令链。文件存在、指令已加载和回答实际符合偏好，是三个需要分别核对的层次。本轮完成文件维护与本地链接检查，未批量启动会话测量回答质量。

会话名称、恢复入口与聊天存储属于另一组功能，见[会话管理](session-management/01-Codex会话_恢复命名与历史回看.md)。如果想进一步了解“规则、持久记忆、技能分别适合什么”，读[三者的区别](01-智能体配置_Rule与Memory及Skill.md)。
