## Codex 会话使用：恢复、命名、回看与图片

> **本节要点**：重新打开已有会话用 `codex resume`，回看当前问答用完整对话浏览。会话正文、名称索引、终端标签和输入历史是不同对象，图片必须在客户端或服务器可访问的位置。终端标签变成 `codex` 时，先核对标签标题，不直接认定聊天名称丢失。


最初整理日期：2026-09-10。早期命令核对版本为 CLI `0.154.0`，后续功能和诊断沿用各节自己的核对日期与版本边界。

### 恢复已有会话

#### 精确回到指定对话

先从会话列表取得目标 ID。下面的 `SESSION_ID` 代表该实际 ID。

重新连接服务器或打开新终端后执行：

```bash
codex resume SESSION_ID
```

使用和原会话相同的 `CODEX_HOME`；它决定本机从哪里读取会话存储。恢复依赖原会话记录仍可访问；只有会话 ID 而没有对应记录，不足以在另一台机器上恢复。

#### 从列表选择或恢复最近一次

在同一工作目录和相同 `CODEX_HOME` 下：

| 命令 | 用途 |
|---|---|
| `codex resume` | 打开历史会话选择器 |
| `codex resume --last` | 恢复最近一次会话，不一定是你想找的那次 |
| `codex resume --all` | 取消当前工作目录过滤，查找其他目录的会话 |

若使用图形界面或 IDE 插件，应从该界面的历史会话入口打开原对话。第三方界面的会话不保证与本地 CLI 共享存储。

#### 会话和文件的区别

恢复会话是继续已有对话上下文，不是回滚工作区文件。反之，新建对话也不会自动继承上一次的完整聊天记录 —— 这正是把知识落盘成文档的意义。

### 能否给会话改名

可以。在支持该命令的当前 Codex CLI 中，在对话输入框执行：

```text
/rename PSRL 参数服务器设计讨论
```

它修改当前会话标题。2026-11-16 已按[官方命令文档](https://learn.chatgpt.com/docs/developer-commands#rename-the-current-session-with-rename)核对；本次未改名。旧记录中的 CLI `0.154.0` 当时未查到公开命令，该结论已移至历史背景，日常使用按当前客户端帮助处理。

会话 ID 是稳定的定位标识，标题用于帮助识别。重要会话可以保留 ID，使用 `codex resume <SESSION_ID>` 精确恢复。日常改名通过正式命令完成，内部 SQLite 或索引格式由 Codex 自己维护。

|---|---|---|
| “提交代码相关”“工作现状总结” | 索引仍保存这些名称，数据库 `name` 和服务 `title` 却为空 | 名称记录不同步，不能据此认定会话正文丢失 |

| Science benchmark 汇总会话 | 索引包含原名称与 `/resume` 的交替记录，当前服务返回 `/resume` | 命令文字成为了名称，索引最新记录也不一定与当前服务一致 |

核查方法是按同一个 ID 对照索引的名称历史、数据库的 `name` 与 `title`、服务的名称与摘要，不按名称本身关联会话。当前数据库 `title` 保留首条请求，而服务返回的 `title` 对应简短名称，两个同名字段不能混用。这里只读观察，未确认内部写入调用链。

具体由自动命名、版本迁移、不同进程缓存还是其他写入触发，尚未定位，不能断言为某次升级造成。恢复应优先使用正式重命名接口并读回验证，保留原有人工名称，不直接批量修改运行中的数据库。上述诊断阶段没有修改会话名称、会话正文或 Codex 配置。

### 重新登录后终端标签只显示 codex

#### 三个名称与重连路径

本节按 VS Code 终端面板侧面的标签列表解释。这里的“重新登录”可能只是编辑器断线后重新连接，服务器上的 Codex 进程可以一直存活。下面是概念流程，重连分支是假设待核实的标题丢失路径，不是已经捕获的客户端事件。

```text
[1] 会话存储：聊天名称和正文
      ↓ Codex 读取会话
[2] Codex：按标题配置，输出终端标题控制序列
      ↓
[3] VS Code 标签：按配置显示应用标题或进程名
      ↑
[4] 重连：恢复进程与屏幕文字
      └─ 若应用标题没恢复或未重新发送，标签可能显示进程名 codex
```

图例：图里每个部分对应的实现与证据：

| 编号 | 实际职责 | 可核实位置与限制 |
|---|---|---|
| 1 | 保存聊天名称与正文 | 本机会话列表接口能读回原名称，未取得会话存储实现源码 |
| 2 | 选择终端标题内容 | `tui.terminal_title`，有效值用 `codex doctor --json` 检查，未取得匹配版本的 Codex Rust 源码 |
| 3 | 将标题用于终端标签 | VS Code 的 `terminal.integrated.tabs.title`，客户端有效值不能从当前服务器命令环境直接取得 |
| 4 | 重连并回放屏幕内容 | 本机 `ptyhost.log` 有重连与回放记录，未捕获客户端恢复标签的完整事件流 |

三个名称分别是：聊天名称，例如“排查 Bus error”，属于会话记录。应用发给终端的标题，是界面显示提示。进程名 `codex`，是正在运行的程序名称。三者可以不同。

标题控制序列是一串让终端执行特殊操作的字节。OSC，即操作系统命令序列，是终端历史沿用的命名，这里用于设置标题，并不是执行 shell 命令。应用可发送 `ESC ] 0 ; 标题 BEL`。其中 `ESC` 和 `BEL` 是控制字节，终端解析后更新标题，不把它们作为正文显示。因此恢复屏幕上的聊天文字，并不自动等于恢复先前发送过的标题事件。

VS Code 的 `${process}` 表示进程名，`${sequence}` 表示程序提供的标题。若标签模板只选择 `${process}`，即使 Codex 发送了聊天标题，标签也可以继续显示 `codex`。这些变量属于 VS Code 设置，不是 Bash 环境变量。[VS Code 标签外观说明](https://code.visualstudio.com/docs/terminal/appearance#tab-text)

#### 怎样确认和调整

在受影响的 Codex 对话输入框执行下面的命令，不是在 Bash 中执行：

```text
/title app-name thread-title
```

它要求本次会话的终端标题包含应用名与聊天名称。如果标签立即恢复，说明会话名可读，程序重新发送标题这条路径有效，问题集中在标题选择或重连恢复。如果没有变化，检查 VS Code 的用户、远程和工作区设置中，`terminal.integrated.tabs.title` 的有效值是否选择了 `${process}` 或被其他标题覆盖。

希望显示程序提供的标题时，VS Code 可配置：

```json
"terminal.integrated.tabs.title": "${sequence}"
```

它只改变显示来源，不会自动补发已经丢失的标题事件。也不要未经检查就覆盖整个设置文件。若希望以后新启动的 Codex 都包含会话名，可在现有 `[tui]` 表里添加：

```toml
terminal_title = ["app-name", "thread-title"]
```

显式 `/title` 参数是当前会话调整，永久设置可使用 `/title` 选择器确认保存，或修改个人配置。两者均不保证修复编辑器重连时的标题恢复缺陷。当前运行进程也未必立即重读配置文件。[OpenAI 标题命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli#configure-terminal-title-items-with-title)与[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

如果仍显示 `bash`，先确认 Codex 聊天确实仍在同一个终端运行。若已经退出回到 shell，显示 `bash` 可以是正常状态。若聊天还在，用 `Ctrl+,` 打开 VS Code 设置，搜索 `@id:terminal.integrated.tabs.title`，检查当前工作区有效值并按需要改为 `${sequence}`，再执行标题命令。这个设置属于编辑器客户端，当前服务器工具不能读取或直接修改其本地用户设置。如果仍不变，再检查这个终端是否设置了固定名称，或终端配置中的 `overrideName` 是否覆盖动态标题。不要把“仍显示 bash”单独当作某一种覆盖机制已查实的证据。

### 快速找到当前会话前几轮的问题与回答

适用场景：在终端里的 Codex CLI 中，想回看同一 session 的上一次、上上次提问，以及当时对应的完整回答。Session 就是一条持续的聊天，transcript 指这条聊天的对话记录。这与[恢复已有会话](#恢复已有会话)“重新打开另一条会话”不同，也不需要先修改[终端滚动文档](02-Codex终端_滚动与Tmux排查.md)中的 tmux 配置。

**先打开完整对话，再翻页或搜索问题关键词。** 可以先试 `Ctrl+T`。若按键没有打开记录，在 Codex 输入框提交 `/keymap`，查找 `Open the transcript overlay`，读取该动作实际绑定的按键。官方配置示例给出了 `open_transcript = "ctrl-t"`，但示例不等于所有版本和配置的默认值。[官方快捷键配置](https://learn.chatgpt.com/docs/config-file/config-basic#tui-keymap)

进入记录后，使用界面提示的翻页键浏览，通常为 `PageUp`、`PageDown`。如果不想穿过大量工具输出，在 `/keymap` 查找 `Find text in the full transcript`，按显示的快捷键搜索自己问题里独特的词。它对应 `global.find_transcript`，与输入框里的历史搜索是不同动作。关闭记录时使用底部显示的关闭键，也可在 `/keymap` 查找 `Close the transcript overlay`。

这里不把未经核对的按键写成“上一轮”“上上轮”的固定跳转键。长会话更适合以问题中的关键词定位，短会话直接翻页即可。若终端或编辑器截获了按键，`/keymap` 中的 `Inspect keypresses` 可检查 Codex 实际有没有收到它。

| 想做什么 | 入口 | 查看或操作的对象 |
|---|---|---|
| 阅读旧问题和对应回答 | 完整对话浏览，先试 `Ctrl+T`，或从 `/keymap` 核对 | 整条聊天记录 |
| 在问题或回答正文中定位关键词 | `/keymap` 中的 `Find text in the full transcript` | 完整对话中的文字 |
| 找回以前输入过的问题 | 输入框中的 `↑`、`↓`，或 `Ctrl+R` | 输入历史，不包含对应回答 |
| 编辑上一条问题并从那里分支 | 空输入框连续两次 `Esc` | 编辑及分支操作，不是单纯阅读 |
| 只复制最近一次完成的回答 | `/copy` 或 `Ctrl+O` | 最近完成的输出 |
| 在编辑器中检索整条聊天 | `/export session.md` | 导出的 Markdown 对话文件 |
| 重新打开以前的另一条聊天 | `codex resume` | 已保存的会话列表 |

输入历史、复制和双 `Esc` 的行为见 [官方 CLI 交互快捷键](https://learn.chatgpt.com/docs/cli/reference#interactive-shortcuts)。导出见 [官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)。斜杠命令输入在 Codex 对话输入框，`codex resume` 则在 shell 中执行。

**具体例子。** 假设一条聊天依次有“解释 EnvRouter”“比较 baseline”“解释 OOM”三轮问答，现在想回看中间那轮。

1. 打开完整对话浏览，启动全文搜索。
2. 搜索 `比较 baseline`，定位你当时发送的问题。只搜索 `baseline` 可能也命中多条回答，使用问题中更长的短语可以减少匹配。
3. 从该问题往下读，经过可能存在的进度和工具输出，找到对应回答。下一条用户提问通常是下一轮的边界，执行中追加的指令可能打断这种简单排列。
4. 读完关闭记录，返回当前输入位置。这条浏览路径不需要重新提交旧问题。

如果更习惯编辑器，可在会话空闲时输入下面的命令，将记录导出到一个尚未使用的文件名：

```text
/export session.md
```

打开导出的文件，在编辑器中按 `Ctrl+F` 搜索 `比较 baseline`，macOS 编辑器通常是 `Cmd+F`。定位问题后，下方就是同一份导出记录中的后续内容，可继续阅读对应回答。文件写到当前会话工作目录，具体路径以导出反馈为准。导出包含聊天内容，应放在自己的工作目录，不要顺手提交到公开仓库。

**核对边界。** 本节于 2026-10-20 核对，本机命令返回 `codex-cli 0.163.0`。本机安装包的界面文本中确认存在 `/keymap`、完整对话浏览、完整对话搜索、分页和按键检查动作。安装包未提供这些界面的源码，二进制字符串不能证明具体按键绑定和运行效果，因此本节不伪造源码行号，也不声称已在用户前台按键验证。官方页面用于核对公开行为，实际快捷键以当前客户端 `/keymap` 为准。本节是功能使用说明，没有额外运行模型请求或修改快捷键配置。

### 给 Codex 发送图片

**已有会话优先直接提供可访问的图片路径，启动新会话可以用 `-i` 附图。** 图片必须实际传入模型或由看图工具打开，仅在消息中出现文件名不等于已经读取图片。

- **当前会话读文件**：把截图放到当前工作区，再发送“请打开工作区里的 `error.png`，解释红框中的错误”。当前助手具备本地看图工具，会读取图片内容后回答。这里的文件名是示例，需要先准备自己的图片。
- **终端启动时附图**：在保存截图的目录运行下面的命令。`-i` 是 `--image` 的简写，后面的文字说明要检查什么。这会启动会话，不是向当前对话追加消息。

  ```bash
  codex -i error.png "解释截图中的报错，并指出应该先检查哪里"
  ```

- **交互输入框粘贴**：官方 CLI 支持粘贴图片，粘贴后确认出现图片附件再发送。快捷键与剪贴板是否可用取决于终端和系统，不应将普通文字粘贴成功当作图片附加成功。
- **VS Code 扩展**：按住 `Shift`，把图片拖入 Codex 的对话输入框，避免编辑器接管拖放。确认图片已附加，再补充问题并发送。

多张图片可使用 `codex --image before.png,after.png "比较修改前后的布局差异"`。两张文件都需事先存在，问题中的“前后”分别对应 `before.png` 与 `after.png`。常用格式包括 PNG、JPEG。

**远程服务器场景：** 如果截图在自己电脑上，而 Codex 在服务器运行，需要先通过远程编辑器的上传功能或文件传输工具将图片放到服务器工作区。电脑上的路径和剪贴板不会因为建立终端连接就自动成为服务器可读的文件。对已经上传的 `error.png`，发送路径与问题后，助手才能从服务器打开该图片。实际上传入口随客户端而异。

依据：[OpenAI 官方图片输入说明](https://learn.chatgpt.com/docs/image-inputs?surface=cli)。本机 `codex --help` 已确认 `-i, --image` 用于初始提示词附图。本节未实际操作用户的剪贴板、拖放或上传界面，也未发送额外模型请求。

## Fork 与多会话上下文汇总

> **核心结论**：`/fork` 从一个会话的分叉点创建新会话，继承此前可继续使用的历史上下文，此后分别追加消息。多个会话可以作为资料汇总到当前会话，当前 CLI 没有把几份完整历史自动合成一份的 `/merge` 命令。对话分叉、资料汇总和代码合并分别处理。

在 Codex 输入框执行 `/fork`，用于分叉当前会话。在 Bash 中执行 `codex fork SESSION_ID`，用于从指定的已保存会话分叉，`SESSION_ID` 要替换为实际 ID。两者都创建新的会话身份，原对话仍可继续使用。公开协议的 `thread/fork` 还支持用 `lastTurnId` 指定继承到哪一轮，此轮包含在内，之后的轮次不继承。客户端是否提供对应的历史位置选择，以实际界面为准。[官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli#fork-the-current-chat-with-fork)与[分叉接口](https://learn.chatgpt.com/docs/app-server)。

### 历史继承怎样落到存储与模型输入

从执行关系看，客户端请求分叉，后台确定来源与截止位置，建立新会话 ID，然后将新输入及后续结果归入新会话。模型继续执行时使用继承的有效上下文和当前新增输入。创建历史分支这个动作本身不要求模型重新生成旧回答。

“继承历史”描述逻辑结果，不要求把所有旧记录的字节复制一遍。本地保留的一份 `0.167.0` 分页记录，含有以下关系：

| 元信息 | 用途 |
|---|---|
| `forked_from_id` | 指明直接来源会话 |
| `history_base.thread_id` | 指明共同历史前缀的来源 |
| `history_base.end_ordinal_exclusive` 与 `end_byte_offset` | 固定继承到哪个事件位置和文件字节位置 |

因此可以保存“从 P 继承截至分叉点的前缀，加上 A 的新记录”这种关系。前缀截止位置固定，P 继续追加消息也不会让 A 自动继承这些新消息。这也解释了[数据库恢复](03-Codex故障_会话数据库与SIGBUS排查.md#再次出现-code-26状态库正常时只重建历史)为什么需要找齐父会话记录。本节没有取得当前版完整 Rust 源码，不将这份旧版记录的物理布局概括为所有模式、所有版本的唯一实现。

继承会话上下文也不等于复制模型参数、GPU 上的 KV cache 或操作系统进程。对长会话，还要区分磁盘中可回看的历史与下一次请求实际使用的上下文。Codex 支持压缩长对话，保留关键内容的摘要，因而“能回看全部旧消息”不保证每个旧 token 都原样进入后续模型请求。[官方上下文管理建议](https://learn.chatgpt.com/guides/best-practices)。

对话分开后，文件是否隔离取决于工作目录。A、B 若都在同一个 `psrl/` 目录操作，A 修改的文件会出现在 B 随后读取的文件状态中，B 的聊天历史却不会自动获得 A 的修改理由。这属于共享工作区，不能从 `/fork` 推导出代码已隔离。当前项目默认沿用 `psrl/`，确实需要同时保留不同代码状态时才另行使用 worktree。分叉也不承诺复制正在运行的训练、容器或终端进程状态。

### 把两条讨论的内容汇总到当前会话

继续上述场景，将正在对话的汇总会话称为 C。目标是让 C 同时使用 A 的 Roofline 结论与 B 的 GPU 配额结论。当前环境提供 `read_thread`，可按会话 ID 读取其他会话，并通过分页继续查阅。取回内容进入 C 作为可引用的资料，原 A、B 保持各自的会话身份。

| 对象 | 汇总到 C 时保留什么 |
|---|---|
| P 的共同背景 | 目标、约束与术语，去重后保留一次 |
| A 的 Roofline 讨论 | 并发与延迟的结论、实测条件、证据位置及未验证假设 |
| B 的 GPU 配额讨论 | 实现状态、资源边界、相关版本、证据与未完成事项 |
| C 的后续判断 | 对齐 A、B 的版本和假设后形成综合结论，明确仍冲突的部分 |

例如 A 的结论只对环境独占 GPU 成立，而 B 讨论的是与 vLLM 共享 GPU，C 不能直接把两者当作相同条件下的结论。汇总应先保留这项条件差异，再判断哪些结论能迁移，哪些需要重新验证。共同背景也不用从 A、B 各复制一次。

当前 `0.171.0` 的 CLI 帮助和生成的协议中，没有标准会话合并入口，`thread/fork` 的来源也是单个会话。底层协议虽提供原始 item 注入接口，这不等于已有自动去重、处理冲突和保持工具调用关系的合并功能。日常使用优先读取相关原文或摘要，不拼接 JSONL 或直接合并 SQLite 数据库。

历史正文、当前指令、工作目录中的代码状态和正在运行的任务，也不会因为一次资料汇总而全部合在一起。C 依据当前有效指令使用取回的资料，涉及实现现状时仍需核对当前源码，涉及实验结果时保留原版本与条件。

### 可直接使用的汇总请求

把下面的 A_ID、B_ID 替换成会话 ID，并写明希望形成的综合结论：

```text
读取会话 A_ID 中关于 Roofline 并发的讨论，
以及会话 B_ID 中关于 GPU 配额的讨论，汇总到当前会话。
保留共同背景、已验证结论、代码与实验版本、证据位置和未完成事项，
去掉重复内容，显式列出冲突与不同假设。
先围绕“怎样结合性能代价和资源预算作调度决定”形成工作摘要，
缺少依据时再读取相关原文，不修改或合并原会话数据库。
```

这种方式可以逐步吸收多个会话的知识，不要求一开始把所有日志塞进模型输入。需要精确细节时，沿会话 ID、原文位置和文档链接取回资料。若摘要要长期维护，优先整合到 `docs/` 已有主题正文，并在后续会话按需读取。摘要会压缩信息，不能把它宣称为几份原始历史的无损合并。

2026-11-23 核对本机 CLI 与后台均为 `0.171.0`，读取 `codex fork --help`，从该版本生成含实验字段的 App Server JSON Schema，并检查当前工具清单。生成的 `ThreadForkParams` 仅有一个来源 `threadId`，可选 `lastTurnId` 或 `beforeTurnId`，生成的客户端方法没有 `thread/merge`。另只读查看一份既有 `0.167.0` 分页会话的父历史引用，未创建新 fork、未合并用户会话、未调用模型生成来验证本说明。官方页面可能涵盖更新版本，以上本机字段与存储证据分别注明适用范围。

## 持续目标与结束条件

`/goal` 把“要完成什么、怎样算完成”保存为当前会话的持续目标，方便 Codex 根据每轮结果接着推进。它适合需要反复定位和验证的任务，例如修复一组失败测试。

### 它怎样持续推进

普通请求也可以包含读代码、修改和测试等多个步骤。持续目标额外保存目标状态：一轮处理结束后，目标仍活动且具备继续条件时，Codex 可以从已有结果继续工作，减少反复输入“继续”。这里“一轮”指一次助手处理过程，内部可以调用多次工具。

目标附着在当前会话上，运行仍受当前进程、工具权限和使用预算约束。暂停、预算耗尽、执行中断或外部条件缺失，都可能让推进停止。根据 2026-11-16 核对的[官方指南](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)，这项功能用于给已有执行过程设置持续目标。

### 用修复测试的例子理解

假设项目有 100 个测试，其中 12 个失败。可以在支持 Goals 的 Codex 输入框中提交：

```text
/goal 修复约定测试集的 100 个测试，使其全部通过。
保留现有公开接口，保留测试覆盖。
先复现失败，再按根因修复，最后运行完整约定测试集。
缺少外部服务时，记录已验证结果和所需条件。
```

这些数字是教学假设。推进过程可以是：

1. 运行测试，得到 12 个失败及对应日志。
2. 修复共同配置问题，剩余 3 个失败，继续分析这 3 个问题。
3. 修复后运行完整测试集，以 100 个全部通过作为完成依据。
4. 如果最后 3 个依赖暂不可用的服务，保留已完成修改并报告验证缺口，等待所需条件。

“100 个全部通过”给出结果，“测试输出”给出证据，“保留接口与覆盖”给出约束。这样每一步发现都能决定下一步工作，完成时也有明确终点。

### 常用操作

以下命令输入在 Codex 对话框中：

| 命令 | 用途 |
|---|---|
| `/goal <目标描述>` | 设置持续目标 |
| `/goal` | 查看当前目标 |
| `/goal pause` | 暂停 |
| `/goal resume` | 恢复 |
| `/goal clear` | 清除目标状态 |

清除目标后，已保存的代码和文档仍保留；文件恢复通过版本管理或备份完成。不同版本的界面和预算选项以当前帮助为准。

### 怎样写清楚结束条件

一个有效目标包含：预期结果、验证方式、允许修改的范围，以及需要保留的约束。比如“修复这 100 个测试”比“让项目更好”更容易判断完成。

若任务需要实验，还应注明资源、时间和重试预算，结论明确后结束。例如“确认一次真实容器 CUDA 调用能完成”只需要该调用及其输出证据，无需继续训练模型。

本次只核对命令和整理示例，未创建目标或运行测试。日常恢复会话见[会话管理入口](01-Codex会话_恢复命名与历史回看.md)；如果想进一步了解“目标状态和聊天记录怎样保存”，可从[修复地图](03-Codex故障_会话数据库与SIGBUS排查.md#codex-修复思路-map)继续阅读。

### TCodex 安装与共享已有会话

TCodex 是使用腾讯登录与网关的 Codex 启动器。此处保存下表所列固定版本的本地安装记录，安装参考用户提供的《TCodex与TClaude使用文档笔记.md》。安装包与启动脚本保存在工作区，不作为 PSRL 项目依赖发布。

**直接使用：**

```bash
tcodex login
tcodex resume --all
```

第一条命令在终端打印腾讯账号登录链接，需要使用者在浏览器完成认证。第二条打开历史会话选择器，`--all` 取消工作目录过滤。需要精确指定会话时，使用 `tcodex resume` 后接该会话的真实 ID，避免 `--last` 在多会话环境中选错。已在另一端运行的同一会话，应先结束那一端的任务再接续。

如果共享系统账号，优先在自己的终端通过 `TCODEX_AUTH_TOKEN` 提供个人凭据。可用 Bash 隐藏输入读取，无需把 Token 写进 shell 历史：

```bash
read -r -s -p 'TCodex API Token: ' TCODEX_AUTH_TOKEN
printf '\n'
export TCODEX_AUTH_TOKEN
tcodex resume --all
```

`TCODEX_AUTH_TOKEN` 只对这个 shell 和后续子进程生效。会话共享不等于登录身份共享，原版 Codex 的账号凭据不能替代腾讯认证。`tcodex login` 的腾讯状态使用启动器自己的用户级目录，不能仅凭 `CODEX_HOME` 相同推断腾讯登录态也存在那里。

**本地安装配置：**

| 项目 | 配置 |
|---|---|
| TCodex 包 | `@tencent/tcodex`，版本 `0.1.4` |
| 安装位置 | 工作区 `.local/share/tcodex/` |
| 启动脚本 | 工作区 `.local/bin/tcodex`，通过用户命令目录中的同名链接调用 |
| 会话目录 | 启动脚本固定 `CODEX_HOME` 为本工作区原有 `.codex` |
| 实际 Codex 程序 | `TCODEX_CODEX_PATH` 指向现有的 `0.163.0` 可执行文件 |
| 后台服务 | 转发给 Codex 时加入 `--no-daemon`，为 TCodex 使用独立运行进程 |
| 网关配置 | TCodex 在本次启动参数中注入腾讯提供方与本地网关地址 |

这样共享的是同一份配置及会话存储，不是复制一份历史，也不是只链接旧版 `sessions/` 目录。现有记录还使用 `state_5.sqlite` 和 `thread_history_1.sqlite`，只链接旧目录不足以覆盖这些会话。启动器注入的腾讯网关参数只影响本次启动，原有配置文件不需要改成腾讯地址。

例如，原来在 `codex` 中讨论过 EnvRouter 的会话，其 ID 在共享目录中保持不变。腾讯登录完成后，把同一个 ID 交给 `tcodex resume` 就能请求恢复这条会话，后续实际模型访问使用 TCodex 的网关。能读取旧记录与腾讯模型调用成功是两项不同的验证。

**版本检查：**

```bash
tcodex --version
tcodex -- -V
```

第一条显示 TCodex `0.1.4` 及包内标注的上游 `0.154.0`。第二条透传给实际执行的 Codex，输出 `codex-cli 0.163.0`。本地脚本使用 `TCODEX_CODEX_PATH` 覆盖包内默认运行时，所以两项版本不同是预期现象。升级 TCodex 的配套运行时不会自动改变脚本固定的路径，后续升级时需重新核对版本与会话兼容性。
