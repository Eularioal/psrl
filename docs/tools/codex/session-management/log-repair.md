### Results：文件头与独立副本验证

普通 SQLite 3 数据库的前 16 字节应是 `SQLite format 3` 加一个零字节。它是文件格式的识别标记，不是可有可无的日志文字。[SQLite 文件格式](https://www.sqlite.org/fileformat.html#the_database_header)与[错误码 26 说明](https://www.sqlite.org/rescode.html#notadb)分别定义文件头和 `SQLITE_NOTADB`。

本次读取到的文件大小为 339968 字节，前 16 字节的十六进制为 `0d000000010ff5000ff5000000000000`，不符合该标记。文件修改时间为本地时区 2026-11-09 20:49:45。该时间只说明文件元数据记录的修改时间，不能当作损坏首次发生时间或执行者证据。

检查步骤和实际结果：

1. 仅按普通文件读取源库，不对源库建立 SQLite 连接。读取前后 inode、文件大小与纳秒修改时间一致，但这不是多文件事务快照保证。
2. 把读出的字节写到本机临时目录内的新文件。
3. 用 Python 标准库 SQLite 以 `mode=ro&immutable=1` 打开这个固定副本，再执行 `PRAGMA quick_check`。
4. 副本返回 `file is not a database`。全过程未调用模型 API，检查后关闭连接并清理临时副本。

本次副本的 SHA-256 为 `dceaa58ce3e274facc8bade465e9568976b82cbc0032db28883fde3aa8f000e2`。这仅标识本次读到的字节，不证明共享存储后端每个副本都返回相同内容。

例如正常数据库即使保存了一条“远程接口返回 401”的日志，文件开头仍应保持 SQLite 格式。把错误内容作为数据库记录保存，不等于用那段文字替换数据库文件头。当前离线副本也无法识别，说明已有的异常字节足以重现问题，不需要当时发生新的模型接口故障。

### 已确认的近因与未确认的根因

近因是读到的文件不符合普通 SQLite 数据库格式，解析器无法把它当作数据库。这比笼统说“日志服务异常”更具体。

根因仍有多种待验证方向：应用或维护程序错误覆盖文件、活动连接与文件替换发生冲突、共享文件系统的锁或读写一致性问题等。搜索到的部分会话命令记录没有提供能锁定写坏操作的证据。没有系统调用审计或足够的前后快照，不能指定某个进程、操作者或存储组件负责。

昨天的 SIGBUS 证据针对 `logs_2.sqlite-shm` 映射，今天的格式错误针对 `logs_2.sqlite` 主文件。它们属于同一日志数据库文件组，但对象与时间不同，尚未证明“某一次删除操作同时导致两者”。复制后错误仍在，排除了必须依赖当前活跃连接或远程模型响应才能复现的解释，但不能区分这些字节最初由客户端写坏还是由共享存储返回异常。

处理重点应放在客户端日志库和存储方式。单纯切换模型或重新登录，没有修复已异常文件内容的机制。不要手工补回 16 字节文件头，这不能保证其余页面结构正确。以下修复使用新的日志位置，没有在活跃进程使用的旧路径上替换数据库。

### 日志维护仍探测旧路径

使用隔离 `CODEX_HOME` 和文件打开系统调用跟踪，确认同版客户端会同时打开配置指定的新日志库，以及 `CODEX_HOME/logs_2.sqlite` 旧文件。旧位置放入异常测试文件时会探测该文件，旧文件不存在时跳过这一访问。跟踪须覆盖 `open` 与 `openat`，只跟踪后者会遗漏本版本的数据库打开调用。

因此，改变 `log_dir` 解决了日志写入位置，但在旧位置保留异常数据库仍会触发维护错误。确认本机没有文件描述符或映射持有原异常文件，且没有 WAL、SHM 伴随文件后，把旧文件原子重命名到备份目录。文件内容和摘要完整保留，没有删除原始证据，没有替换健康的新库，也没有给共享路径加本机符号链接。

此处定位的是残留维护错误的来源，不是最初文件头为何损坏。没有取得该版本的对应 Rust 源码，因此证据限于实际文件访问和对照实验，不编造内部函数调用。
