## 恢复已有会话

### 精确回到指定对话

原始笔记记录的会话 ID：`01a08968-76ae-7171-8b90-fddf1a6be535`。

重新连接服务器或打开新终端后执行：

```bash
cd ${WORKSPACE_ROOT}
CODEX_HOME=${WORKSPACE_ROOT}/.codex codex resume 01a08968-76ae-7171-8b90-fddf1a6be535
```

这里显式指定该环境实际使用的 `CODEX_HOME`，避免新终端落到另一个存储目录。恢复依赖原会话记录仍可访问；只有会话 ID 而没有对应记录，不足以在另一台机器上恢复。

### 从列表选择或恢复最近一次

在同一工作目录和相同 `CODEX_HOME` 下：

| 命令 | 用途 |
|---|---|
| `codex resume` | 打开历史会话选择器 |
| `codex resume --last` | 恢复最近一次会话，不一定是你想找的那次 |
| `codex resume --all` | 取消当前工作目录过滤，查找其他目录的会话 |

若使用图形界面或 IDE 插件，应从该界面的历史会话入口打开原对话。第三方界面的会话不保证与本地 CLI 共享存储。

### 会话和文件的区别

恢复会话是继续已有对话上下文，不是回滚工作区文件。反之，新建对话也不会自动继承上一次的完整聊天记录 —— 这正是把知识落盘成文档的意义。

## 能否给会话改名

### 结论

以下公开 CLI 命令的结论仅适用于历史核对版本 `0.154.0`，不能推广到当前版本。2026-11-09 当前会话服务明确提供 `set_thread_title` 重命名工具，因此当前环境可以通过会话工具改名。本次没有调用它，也没有重新核实当前 CLI 的交互式改名命令。

历史检查中，Codex CLI `0.154.0` **没有**给已有 session 改名的公开命令，也没有 `/rename` 子命令。

本机帮助列出了 `resume`、`archive`、`delete`、`unarchive`、`fork` 等 session 管理命令，但没有 `rename`。官方文档说明 `codex resume` 用来返回已保存的聊天，同样未提及 CLI 中可修改会话名称。

### 当前的名称来自哪里

每条 session 记录同时有三个标识：

- **UUID**：不变，用于精确恢复会话。
- **`title`**：原始首条用户请求。
- **`name`**：Codex 自动生成的简短标题。

例如原始笔记那次 session 的自动名称是"阅读项目并总结结构及添加回顾规则"。`codex resume`、`archive` 等命令接受 UUID 或 name，因此该名称可用于引用会话；但 CLI 未提供把它改成自定义名称的入口。

### 实际建议

1. **用 UUID 恢复重要会话** —— 这是唯一稳定、明确的标识。

   ```bash
   codex resume <SESSION_UUID>
   ```

2. **用首条请求写清主题** —— Codex 会据此生成更容易辨认的自动标题。新建会话时第一句可写成"PSRL 参数服务器设计讨论"这类明确的说明。

3. **图形界面另说** —— 在 ChatGPT 桌面端、网页端或 IDE 扩展中使用 Codex 时，可查看会话列表的更多操作菜单，界面可能提供标题编辑。这不是本机 CLI 已验证的功能，也不应假定它与 CLI 的本地 session 记录互通。

### 不建议的做法

不要直接编辑 `.codex/session_index.jsonl` 或 `.codex/state_5.sqlite` 中的名称。它们是内部存储，运行中的 Codex 进程、缓存和数据库记录可能不一致；CLI 版本升级也可能改变格式。

### Results：名称混乱的只读核查

2026-11-09 核对本机 CLI `0.167.0`、当前会话服务 `list_threads`、本地 `session_index.jsonl` 和只读 SQLite 查询，发现两类问题：

| 例子 | 索引与当前名称 | 可以确认的结论 |
|---|---|---|
| “提交代码相关”“工作现状总结” | 索引仍保存这些名称，数据库 `name` 和服务 `title` 却为空 | 名称记录不同步，不能据此认定会话正文丢失 |
| GPU benchmark 研究会话 | 索引有原名称，随后追加“修复 session 名称混乱问题”，服务也返回新名称 | 此会话名称确实被覆盖，本次诊断尚未调用重命名工具 |
| Science benchmark 汇总会话 | 索引包含原名称与 `/resume` 的交替记录，当前服务返回 `/resume` | 命令文字成为了名称，索引最新记录也不一定与当前服务一致 |

例如，原主题仍是 GPU benchmark 研究、会话 ID 不变，但名称变成刚提出的问题，列表就会让人误以为打开了另一段会话。当前所查会话的 ID 与原始主题对应，未发现正文被互换的证据。这不等于已经逐条审计全部历史消息。

核查方法是按同一个 ID 对照索引的名称历史、数据库的 `name` 与 `title`、服务的名称与摘要，不按名称本身关联会话。当前数据库 `title` 保留首条请求，而服务返回的 `title` 对应简短名称，两个同名字段不能混用。这里只读观察，未确认内部写入调用链。

具体由自动命名、版本迁移、不同进程缓存还是其他写入触发，尚未定位，不能断言为某次升级造成。恢复应优先使用正式重命名接口并读回验证，保留原有人工名称，不直接批量修改运行中的数据库。上述诊断阶段没有修改会话名称、会话正文或 Codex 配置。

用户随后要求恢复原名，已备份名称索引和恢复前字段，按异常出现前的最后名称，通过 `set_thread_title` 恢复 25 个会话，包括“提交代码相关”“工作现状总结”等已有人工名称。服务列表、数据库 `name` 和索引最新记录逐项读回一致。此结果证明名称已恢复，尚未证明覆盖名称的触发原因已消除。会话正文与 Codex 配置未修改。

## 重新登录后终端标签只显示 codex

### 三个名称与重连路径

本节按 VS Code 终端面板侧面的标签列表解释。这里的“重新登录”可能只是编辑器断线后重新连接，服务器上的 Codex 进程可以一直存活。下面是概念流程，重连分支是假设待核实的标题丢失路径，不是已经捕获的客户端事件。

```text
[1] 会话存储：聊天名称和正文
      ↓ Codex 读取会话
[2] Codex：按标题配置，输出终端标题控制序列
      ↓
[3] VS Code 标签：按配置显示应用标题或进程名
      ↑
[4] 重连：恢复进程与屏幕文字
      └─ 若应用标题没恢复或未重新发送，标签可能显示进程名 codex
```

图例：图里每个部分对应的实现与证据：

| 编号 | 实际职责 | 可核实位置与限制 |
|---|---|---|
| 1 | 保存聊天名称与正文 | 本机会话列表接口能读回原名称，未取得会话存储实现源码 |
| 2 | 选择终端标题内容 | `tui.terminal_title`，有效值用 `codex doctor --json` 检查，未取得匹配版本的 Codex Rust 源码 |
| 3 | 将标题用于终端标签 | VS Code 的 `terminal.integrated.tabs.title`，客户端有效值不能从当前服务器命令环境直接取得 |
| 4 | 重连并回放屏幕内容 | 本机 `ptyhost.log` 有重连与回放记录，未捕获客户端恢复标签的完整事件流 |

三个名称分别是：聊天名称，例如“排查 Bus error”，属于会话记录。应用发给终端的标题，是界面显示提示。进程名 `codex`，是正在运行的程序名称。三者可以不同。

标题控制序列是一串让终端执行特殊操作的字节。OSC，即操作系统命令序列，是终端历史沿用的命名，这里用于设置标题，并不是执行 shell 命令。应用可发送 `ESC ] 0 ; 标题 BEL`。其中 `ESC` 和 `BEL` 是控制字节，终端解析后更新标题，不把它们作为正文显示。因此恢复屏幕上的聊天文字，并不自动等于恢复先前发送过的标题事件。

VS Code 的 `${process}` 表示进程名，`${sequence}` 表示程序提供的标题。若标签模板只选择 `${process}`，即使 Codex 发送了聊天标题，标签也可以继续显示 `codex`。这些变量属于 VS Code 设置，不是 Bash 环境变量。[VS Code 标签外观说明](https://code.visualstudio.com/docs/terminal/appearance#tab-text)

### 怎样确认和调整

在受影响的 Codex 对话输入框执行下面的命令，不是在 Bash 中执行：

```text
/title app-name thread-title
```

它要求本次会话的终端标题包含应用名与聊天名称。如果标签立即恢复，说明会话名可读，程序重新发送标题这条路径有效，问题集中在标题选择或重连恢复。如果没有变化，检查 VS Code 的用户、远程和工作区设置中，`terminal.integrated.tabs.title` 的有效值是否选择了 `${process}` 或被其他标题覆盖。

希望显示程序提供的标题时，VS Code 可配置：

```json
"terminal.integrated.tabs.title": "${sequence}"
```

它只改变显示来源，不会自动补发已经丢失的标题事件。也不要未经检查就覆盖整个设置文件。若希望以后新启动的 Codex 都包含会话名，可在现有 `[tui]` 表里添加：

```toml
terminal_title = ["app-name", "thread-title"]
```

显式 `/title` 参数是当前会话调整，永久设置可使用 `/title` 选择器确认保存，或修改个人配置。两者均不保证修复编辑器重连时的标题恢复缺陷。当前运行进程也未必立即重读配置文件。[OpenAI 标题命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli#configure-terminal-title-items-with-title)与[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

如果仍显示 `bash`，先确认 Codex 聊天确实仍在同一个终端运行。若已经退出回到 shell，显示 `bash` 可以是正常状态。若聊天还在，用 `Ctrl+,` 打开 VS Code 设置，搜索 `@id:terminal.integrated.tabs.title`，检查当前工作区有效值并按需要改为 `${sequence}`，再执行标题命令。这个设置属于编辑器客户端，当前服务器工具不能读取或直接修改其本地用户设置。如果仍不变，再检查这个终端是否设置了固定名称，或终端配置中的 `overrideName` 是否覆盖动态标题。不要把“仍显示 bash”单独当作某一种覆盖机制已查实的证据。

## 快速找到当前会话前几轮的问题与回答

适用场景：在终端里的 Codex CLI 中，想回看同一 session 的上一次、上上次提问，以及当时对应的完整回答。Session 就是一条持续的聊天，transcript 指这条聊天的对话记录。这与[恢复已有会话](#恢复已有会话)“重新打开另一条会话”不同，也不需要先修改[终端滚动文档](terminal-scrolling.md)中的 tmux 配置。

**先打开完整对话，再翻页或搜索问题关键词。** 可以先试 `Ctrl+T`。若按键没有打开记录，在 Codex 输入框提交 `/keymap`，查找 `Open the transcript overlay`，读取该动作实际绑定的按键。官方配置示例给出了 `open_transcript = "ctrl-t"`，但示例不等于所有版本和配置的默认值。[官方快捷键配置](https://learn.chatgpt.com/docs/config-file/config-basic#tui-keymap)

进入记录后，使用界面提示的翻页键浏览，通常为 `PageUp`、`PageDown`。如果不想穿过大量工具输出，在 `/keymap` 查找 `Find text in the full transcript`，按显示的快捷键搜索自己问题里独特的词。它对应 `global.find_transcript`，与输入框里的历史搜索是不同动作。关闭记录时使用底部显示的关闭键，也可在 `/keymap` 查找 `Close the transcript overlay`。

这里不把未经核对的按键写成“上一轮”“上上轮”的固定跳转键。长会话更适合以问题中的关键词定位，短会话直接翻页即可。若终端或编辑器截获了按键，`/keymap` 中的 `Inspect keypresses` 可检查 Codex 实际有没有收到它。

| 想做什么 | 入口 | 查看或操作的对象 |
|---|---|---|
| 阅读旧问题和对应回答 | 完整对话浏览，先试 `Ctrl+T`，或从 `/keymap` 核对 | 整条聊天记录 |
| 在问题或回答正文中定位关键词 | `/keymap` 中的 `Find text in the full transcript` | 完整对话中的文字 |
| 找回以前输入过的问题 | 输入框中的 `↑`、`↓`，或 `Ctrl+R` | 输入历史，不包含对应回答 |
| 编辑上一条问题并从那里分支 | 空输入框连续两次 `Esc` | 编辑及分支操作，不是单纯阅读 |
| 只复制最近一次完成的回答 | `/copy` 或 `Ctrl+O` | 最近完成的输出 |
| 在编辑器中检索整条聊天 | `/export session.md` | 导出的 Markdown 对话文件 |
| 重新打开以前的另一条聊天 | `codex resume` | 已保存的会话列表 |

输入历史、复制和双 `Esc` 的行为见 [官方 CLI 交互快捷键](https://learn.chatgpt.com/docs/cli/reference#interactive-shortcuts)。导出见 [官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)。斜杠命令输入在 Codex 对话输入框，`codex resume` 则在 shell 中执行。

**具体例子。** 假设一条聊天依次有“解释 EnvRouter”“比较 baseline”“解释 OOM”三轮问答，现在想回看中间那轮。

1. 打开完整对话浏览，启动全文搜索。
2. 搜索 `比较 baseline`，定位你当时发送的问题。只搜索 `baseline` 可能也命中多条回答，使用问题中更长的短语可以减少匹配。
3. 从该问题往下读，经过可能存在的进度和工具输出，找到对应回答。下一条用户提问通常是下一轮的边界，执行中追加的指令可能打断这种简单排列。
4. 读完关闭记录，返回当前输入位置。这条浏览路径不需要重新提交旧问题。

如果更习惯编辑器，可在会话空闲时输入下面的命令，将记录导出到一个尚未使用的文件名：

```text
/export session.md
```

打开导出的文件，在编辑器中按 `Ctrl+F` 搜索 `比较 baseline`，macOS 编辑器通常是 `Cmd+F`。定位问题后，下方就是同一份导出记录中的后续内容，可继续阅读对应回答。文件写到当前会话工作目录，具体路径以导出反馈为准。导出包含聊天内容，应放在自己的工作目录，不要顺手提交到公开仓库。

**核对边界。** 本节于 2026-10-20 核对，本机命令返回 `codex-cli 0.163.0`。本机安装包的界面文本中确认存在 `/keymap`、完整对话浏览、完整对话搜索、分页和按键检查动作。安装包未提供这些界面的源码，二进制字符串不能证明具体按键绑定和运行效果，因此本节不伪造源码行号，也不声称已在用户前台按键验证。官方页面用于核对公开行为，实际快捷键以当前客户端 `/keymap` 为准。本节是功能使用说明，没有额外运行模型请求或修改快捷键配置。

## 给 Codex 发送图片

**已有会话优先直接提供可访问的图片路径，启动新会话可以用 `-i` 附图。** 图片必须实际传入模型或由看图工具打开，仅在消息中出现文件名不等于已经读取图片。

- **当前会话读文件**：把截图放到当前工作区，再发送“请打开工作区里的 `error.png`，解释红框中的错误”。当前助手具备本地看图工具，会读取图片内容后回答。这里的文件名是示例，需要先准备自己的图片。
- **终端启动时附图**：在保存截图的目录运行下面的命令。`-i` 是 `--image` 的简写，后面的文字说明要检查什么。这会启动会话，不是向当前对话追加消息。

  ```bash
  codex -i error.png "解释截图中的报错，并指出应该先检查哪里"
  ```

- **交互输入框粘贴**：官方 CLI 支持粘贴图片，粘贴后确认出现图片附件再发送。快捷键与剪贴板是否可用取决于终端和系统，不应将普通文字粘贴成功当作图片附加成功。
- **VS Code 扩展**：按住 `Shift`，把图片拖入 Codex 的对话输入框，避免编辑器接管拖放。确认图片已附加，再补充问题并发送。

多张图片可使用 `codex --image before.png,after.png "比较修改前后的布局差异"`。两张文件都需事先存在，问题中的“前后”分别对应 `before.png` 与 `after.png`。常用格式包括 PNG、JPEG。

**远程服务器场景：** 如果截图在自己电脑上，而 Codex 在服务器运行，需要先通过远程编辑器的上传功能或文件传输工具将图片放到服务器工作区。电脑上的路径和剪贴板不会因为建立终端连接就自动成为服务器可读的文件。对已经上传的 `error.png`，发送路径与问题后，助手才能从服务器打开该图片。实际上传入口随客户端而异。

依据：[OpenAI 官方图片输入说明](https://learn.chatgpt.com/docs/image-inputs?surface=cli)。本机 `codex --help` 已确认 `-i, --image` 用于初始提示词附图。本节未实际操作用户的剪贴板、拖放或上传界面，也未发送额外模型请求。
