### 为什么数据库文件会引发内存错误

SQLite 是把数据保存在文件中的数据库。WAL 是预写日志，更新可先写入 `-wal` 文件，再合入主数据库。配套的 `-shm` 文件存放 WAL 索引等协调数据，程序可以通过 `mmap`，即内存映射，把文件区域当作内存访问。因此磁盘文件发生某些异常时，表现可能是进程收到内存访问类信号，而非普通的文件读取报错。

教学例子：进程先把一个 32768 字节文件映射进内存，读取第一个字节成功。假设文件随后被截断成 0 字节，原映射地址仍在，但文件已无法提供对应页面。再次读取相同地址时，Linux 可以发送 SIGBUS。默认处理会结束整个进程，而不只是结束那次数据库查询，所以终端会话会退出。

**删除目录项本身通常不足以导致 SIGBUS。** 正常本地文件系统会保留仍被打开或映射的文件内容。此次 `deleted` 是重要线索，不能单凭它认定有人手工删除文件，更不能把教学例子的“截断”写成本次已经查明的操作。仍需区分文件截断、清理重建时序、共享存储的映射与锁语义等原因。现有转储不足以识别执行者。

### 最小教学实验

下面只用 Linux Python 标准库，在子进程中操作自己的临时文件，不访问 Codex 数据，也不生成 core。示例模拟“映射后截断”，不是复现本次 FUSE 环境的具体根因。

```bash
python3 - <<'PY'
import subprocess
import sys

code = '''import mmap, os, resource, tempfile
resource.setrlimit(resource.RLIMIT_CORE, (0, 0))
with tempfile.TemporaryFile(dir="/tmp") as f:
    f.truncate(32768)
    view = mmap.mmap(f.fileno(), 32768)  # 对应图 2：建立文件映射。
    print("before:", view[0], flush=True)
    os.ftruncate(f.fileno(), 0)  # 教学假设，不是已查明的真实操作。
    print(view[0])  # 对应图 3：读取失去文件支撑的映射。
'''
p = subprocess.run(
    [sys.executable, "-c", code], stdout=subprocess.PIPE,
    stderr=subprocess.PIPE, universal_newlines=True, timeout=5,
)
print(p.stdout, end="")
print("child returncode:", p.returncode)
PY
```

本次已运行，输出 `before: 0` 和 `child returncode: -7`。Python 用负数表示子进程被信号终止，`-7` 即 SIGBUS。父进程正常结束。临时文件随子进程退出释放，未改动活动数据库。这验证了机制，不验证 Codex 中的触发来源。

### 处理建议与验证边界

不要在 Codex 仍运行时删除、截断或替换数据库及 `-wal`、`-shm` 文件。需要恢复或调整存储位置时，先保全数据并协调全部相关客户端停止，包括后台服务和其他机器上的使用者，再在副本上核验并迁移。

优先评估将诊断日志放到可靠的本机持久目录，避免这份日志库继续依赖尚未核实兼容性的共享挂载。OpenAI 官方提供 `log_dir` 配置方法，但若存在受管理的 `sqlite_home`，日志数据库位置可能仍由后者决定。迁移后必须检查实际打开文件的位置，再验证会话读取与继续保存。不能只修改配置便宣称故障已修复。
