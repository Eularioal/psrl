## 修复思路 Map：背景、证据与方法

下面是本次修复的排查思路图，不是 Codex 内部源码调用图。只概括[日志修复记录](log-repair.md)的实测，不新增验证结论。

```text
现象：会话退出，以及后续健康检查和日志告警
│
├─ 日志数据库：先恢复写入，再处理维护旧库的路径
│  ├─ 背景：SQLite 把结构化数据存进文件，文件格式损坏就无法读取
│  ├─ 证据：旧库复制到本地后仍报格式错误
│  ├─ 初步修复：备份旧库 → 本机新目录建库 → 重启使服务采用新设置
│  └─ 残留修复：跟踪实际打开文件 → 发现仍探测旧库 → 将旧库归档
│
├─ Shell 快照：区分命令本身与命令启动前的准备时间
│  ├─ 背景：Bash 启动会按启动方式读取配置，初始化脚本也占时间
│  ├─ 证据：非交互登录启动约 6.5 秒，重复加载较重的环境脚本
│  └─ 修复：重初始化限于交互终端 → 约 0.7 秒 → 检查真实快照生成
│
├─ 会话索引：区分聊天正文与检索目录
│  ├─ 背景：原始记录在文件里，索引用于快速找到它们
│  ├─ 证据：文件存在，但有 7 份没有对应索引
│  └─ 修复：备份原文件 → 官方恢复接口补索引 → 检查历史可读
│
└─ 配置警告：区分配置文本与实际生效的设置
   ├─ 背景：版本变化后，旧配置项可能已不被识别
   ├─ 证据：当前版本明确忽略 3 项配置
   └─ 修复：备份后移除无效项 → 重新检查
```

**最有代表性的例子是日志问题。** 改了日志目录以后，新库能正常写入，但维护错误仍出现。这意味着“写日志”和“维护历史日志”可能走不同路径。于是用系统调用跟踪观察进程究竟打开哪个文件，再做对照：旧路径有坏库时会打开它，旧文件不存在时跳过。由此才决定归档旧库，而不是再次重建正常的新库。这里的系统调用跟踪，就是观察程序向操作系统发出的打开文件等请求。本机未取得对应 Codex Rust 源码，不能进一步声称已核对内部函数。

方法可以记成五步：**按现象分组 → 找可验证的证据 → 小范围对照 → 备份后最小修改 → 用实际功能验收**。例如快照问题不仅看日志不再报错，还看真实快照是否生成。索引问题不仅看数量一致，还要读出历史内容。

需要分清三层结论：健康检查通过、实际功能恢复、最初根因彻底查明。前两层已有相应证据，但原库最初为何损坏仍未确定。迁到本机存储是减少共享存储变量，并不证明共享存储就是元凶。远程插件的登录要求及 MCP 连接关闭告警仍按[修复验收](log-repair.md#最终检查与未解决边界)标注边界。
