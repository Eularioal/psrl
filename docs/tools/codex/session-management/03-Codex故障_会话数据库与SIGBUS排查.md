### 修复思路 Map：背景、证据与方法

下面是本次修复的排查思路图，不是 Codex 内部源码调用图。只概括[日志修复记录](#codex-日志库修复从文件格式异常到健康检查通过)的实测，不新增验证结论。

```text
现象：会话退出，以及后续健康检查和日志告警
│
├─ 日志数据库：先恢复写入，再处理维护旧库的路径
│  ├─ 背景：SQLite 把结构化数据存进文件，文件格式损坏就无法读取
│  ├─ 证据：旧库复制到本地后仍报格式错误
│  ├─ 初步修复：备份旧库 → 本机新目录建库 → 重启使服务采用新设置
│  └─ 残留修复：跟踪实际打开文件 → 发现仍探测旧库 → 将旧库归档
│
├─ Shell 快照：区分命令本身与命令启动前的准备时间
│  ├─ 背景：Bash 启动会按启动方式读取配置，初始化脚本也占时间
│  ├─ 证据：非交互登录启动约 6.5 秒，重复加载较重的环境脚本
│  └─ 修复：重初始化限于交互终端 → 约 0.7 秒 → 检查真实快照生成
│
├─ 会话索引：区分聊天正文与检索目录
│  ├─ 背景：原始记录在文件里，索引用于快速找到它们
│  ├─ 证据：文件存在，但有 7 份没有对应索引
│  └─ 修复：备份原文件 → 官方恢复接口补索引 → 检查历史可读
│
└─ 配置警告：区分配置文本与实际生效的设置
   ├─ 背景：版本变化后，旧配置项可能已不被识别
   ├─ 证据：当前版本明确忽略 3 项配置
   └─ 修复：备份后移除无效项 → 重新检查
```

**最有代表性的例子是日志问题。** 改了日志目录以后，新库能正常写入，但维护错误仍出现。这意味着“写日志”和“维护历史日志”可能走不同路径。于是用系统调用跟踪观察进程究竟打开哪个文件，再做对照：旧路径有坏库时会打开它，旧文件不存在时跳过。由此才决定归档旧库，而不是再次重建正常的新库。这里的系统调用跟踪，就是观察程序向操作系统发出的打开文件等请求。本机未取得对应 Codex Rust 源码，不能进一步声称已核对内部函数。

方法可以记成五步：**按现象分组 → 找可验证的证据 → 小范围对照 → 备份后最小修改 → 用实际功能验收**。例如快照问题不仅看日志不再报错，还看真实快照是否生成。索引问题不仅看数量一致，还要读出历史内容。

需要分清三层结论：健康检查通过、实际功能恢复、最初根因彻底查明。前两层已有相应证据，但原库最初为何损坏仍未确定。迁到本机存储是减少共享存储变量，并不证明共享存储就是元凶。远程插件的登录要求及 MCP 连接关闭告警仍按[修复验收](#最终检查与未解决边界)标注边界。


## Codex 会话数据库恢复：原始记录还在，怎样恢复列表与历史

2026-11-09 的会话恢复已完成，用户确认名称和 resume 可用；随后状态库、历史库完整性检查通过，并生成了独立存档。恢复依靠保留下来的原始会话文件，数据库最初损坏的原因仍未确定。

本节保留 2026-11-09 的恢复记录和 2026-11-22 的再次修复。后者的前台 CLI 为 `0.171.0`，实际后台服务仍为 `0.167.0`，隔离重建使用后台同版二进制。

### 先理解三类存储

| 对象 | 保存什么 | 损坏后的现象 |
|---|---|---|
| `sessions/` 内的 JSONL 文件 | 原始会话事件，一行一条 JSON 记录 | 未成功保存的消息可能缺失 |
| 状态库 `state_5.sqlite` | 会话 ID、名称、原始文件路径等元数据 | 列表或恢复入口失败 |
| 历史库 `thread_history_1.sqlite` | 用于界面分页读取的历史 | 会话可列出，打开历史页仍失败 |

例如一条对话的 JSONL 文件完整，但状态索引损坏，列表就找不到它。取得正确 ID 和文件路径后，可以由 Codex 重新读取原始文件，重建可浏览的历史。日志数据库另有用途，见[日志库修复](#codex-日志库修复从文件格式异常到健康检查通过)。

### 再次出现 code 26：状态库正常时只重建历史

2026-11-22，两条旧会话恢复时返回 `failed to list thread history` 和 SQLite code 26。现场确认 `thread_history_1.sqlite` 的前 16 字节为 `0a0000004e024a000fd30fa60f790f4c`，不符合 SQLite 文件头格式。状态库的只读 `quick_check` 返回 `ok`，两份报错 JSONL 分别为 1769 行和 1049 行，逐行解析没有错误。**因此本次保留状态库和原始会话文件，只处理历史分页库。**

重建前还要找齐历史的来源。一条分支会话可以只记录共同前缀的引用，以及分支后新增的事件。下面的教学图解释为什么只复制报错文件可能不够。

本次先在隔离目录复制原始会话，并在线备份状态库。最初只复制两份报错文件，恢复返回 `missing source rollout`。补齐父会话和较早的来源记录后，同版后台的 `thread/resume` 成功，两条会话各通过 `thread/items/list` 读取 10 个条目，隔离状态库与历史库的 `integrity_check` 均为 `ok`。整个过程没有调用 `turn/start`，没有请求模型继续生成。

安装时发现，异常历史库没有本机文件描述符或内存映射使用者，也没有 WAL、SHM 伴随文件。将其原子重命名至私有备份后，现有后台连接仍记得先前的初始化状态，直接读取新空文件会报 `no such table: thread_turns`。本次在 SQLite 事务内初始化同版验证库的表结构和迁移记录，再导入已验证的历史投影，后台无需重启。**这只是本次满足上述条件的操作记录，不能把在线改库当作通用恢复命令。**有使用者、伴随文件或版本差异时，应沿用后文的停写与离线验证流程。

两项细节决定导入后能否继续正确读取：

- **沿用原始文件的字节位置。** 隔离 `resume` 会追加一条遥测事件。导入时确认原始记录 SHA-256 未变，所有已投影 turn 的结束位置均未超过原文件末尾，并将下一读取位置设回原始 EOF。EOF 是文件末尾，不能把隔离副本较长的偏移带回较短的原文件。
- **核对文件名与会话 ID。** 第二份遗留文件名包含原 ID 与分支 ID，状态索引和文件元信息仍使用原 ID。隔离恢复生成的投影归属于分支 ID。本次仅对这份已核对的记录保留两种 ID 的历史视图，使原恢复入口可读，不改文件名或原始正文。将副本直接改为只含原 ID 的文件名会触发谱系循环，不能用这种方式处理该遗留文件。

最终通过正在运行的后台服务，使用用户报错中的两个原会话 ID，各读取最近 3 个 turn，均有实际助手消息且返回后续分页游标。状态库和历史库完整性检查通过，两份原始 JSONL 的 SHA-256 与修复前一致，当前会话也已正常写入新库。turn 是历史界面的一轮交互记录，此处数量不是训练 step 或模型请求数。

用户随后确认这两条可以恢复，但反馈名称错乱、另有老会话无法恢复。上述首轮验证只覆盖两条历史，未覆盖全部老会话与名称一致性，不能作为整套会话存储修复完成的结论。继续核查发现：名称索引有 35 个已保存名称，而当前数据库的名称字段为空。107 份原始文件中，起初有 51 份文件名对应的 ID 没有状态索引。修复期间客户端又补建了少量索引，最终安装实际新增 50 条元数据，状态库共 107 条。

本轮按原始文件 ID、文件内元信息、状态索引和名称历史逐项核对，在完整会话快照上使用同版后台恢复，再将验证结果补入当前正常库。已有元数据路径、历史条目和正在增长的会话记录保留，新的投影位置停在快照原始文件末尾。结果如下：

| 验收对象 | 结果与边界 |
|---|---|
| 35 个已保存名称 | 从名称索引恢复，新启动的独立服务连接逐项读取 `thread.name`，35 项均匹配，历史页均非空 |
| 70 个普通会话文件 | 全部通过隔离 `thread/resume`，没有调用 `turn/start` 或请求模型生成 |
| 37 个子 agent 文件 | 25 个可直接恢复或在父会话先恢复后打开，另 12 个仍受当前版本的子 agent 生命周期限制，不能当作独立普通会话恢复 |
| 13 份只有元信息的文件 | 恢复成功但历史页为空，与源文件没有正文一致，包含在上面的文件总数中 |
| 状态库与历史库 | 完整性检查均为 `ok`，安装新增 548 条历史 turn 与 28546 条 item，保留现有行 |
| 原始会话记录 | 全部保留，安装前逐份确认与备份快照相同的文件前缀，活动会话允许继续追加 |

此处普通会话、子 agent 文件和仅有元信息的文件按用途或内容分类，最后一类与前两类有重叠，不能再相加。turn 和 item 是历史存储记录，不代表训练步数或模型请求数量。子 agent 的 12 项限制是恢复接口返回的生命周期错误，原始正文仍有备份，不能把它写成会话已丢失，也没有将子 agent 改成普通会话绕过限制。

逐行检查还发现，一个正在使用的长会话文件有 22 行无法单独解析为 JSON，而同版恢复接口仍能完成该会话的恢复。本轮保留这些原始字节，没有删除异常行或重写活动文件，未逐条验证这些行对历史完整性的影响。因此“恢复接口成功”仍不能扩展为“全部历史消息已无遗漏”。

**数据已修复，后台已完成重启与连接切换。** 现场后台 PID 同时持有当前 `state_5.sqlite`，以及 `db-backups/` 中已归档的异常状态库。正式改名接口因此出现调用成功、落库不一致与部分调用报错的混合结果。当前正常库中的名称已在事务内恢复，并经新连接验证。随后通过已获用户授权的后台重启释放旧连接。重启后的数据库、名称与打开文件检查结果见下段。

用户随后明确授权“重启一下”。已执行后台重启，旧 PID 4016759 已退出，新后台 PID 为 2016764，实际版本为 `0.171.0`。新后台打开当前会话数据库，未持有归档异常状态库。重启后状态库与历史库完整性检查通过，35 个已保存名称逐项匹配，历史表仍有原始故障会话的非空记录。重启会中断当时正在运行的任务和修复对话，此项影响已获用户授权。70 个普通会话的逐份恢复验证仍指重启前的隔离验证，没有把它改称新版后台重新执行的全量验证。

与此前故障相比，**恢复主线相同，直接故障机制有区别，最初损坏诱因仍未确定**。两次都先保全原始会话和异常数据库，再从会话记录重建可用的索引、历史与名称，最后让服务使用修复后的存储。

| 对比项 | 2026-11-09 至 11-10 | 2026-11-22 |
|---|---|---|
| 会话读取故障 | 状态库、历史库出现内部页结构异常 | 历史库文件头无法识别，恢复返回 code 26 |

例如服务先打开 A 库，随后磁盘上的正常路径改为 B 库，原有连接不会仅因路径变化就自动转用 B。本次看到旧后台同时持有当前库与归档异常库，重启使新服务重新打开当前库。这解释了修复后部分旧请求仍异常的现象，不解释 A 库最初为何损坏。首轮只验证两条会话的范围不足，也与最初损坏诱因分别记录。后台换用已安装的 `0.171.0`、完整性检查通过和名称恢复，均不足以证明最初诱因已经根除。

#### 为什么数据库文件会引发内存错误

SQLite 是把数据保存在文件中的数据库。WAL 是预写日志，更新可先写入 `-wal` 文件，再合入主数据库。配套的 `-shm` 文件存放 WAL 索引等协调数据，程序可以通过 `mmap`，即内存映射，把文件区域当作内存访问。因此磁盘文件发生某些异常时，表现可能是进程收到内存访问类信号，而非普通的文件读取报错。

教学例子：进程先把一个 32768 字节文件映射进内存，读取第一个字节成功。假设文件随后被截断成 0 字节，原映射地址仍在，但文件已无法提供对应页面。再次读取相同地址时，Linux 可以发送 SIGBUS。默认处理会结束整个进程，而不只是结束那次数据库查询，所以终端会话会退出。

**删除目录项本身通常不足以导致 SIGBUS。** 正常本地文件系统会保留仍被打开或映射的文件内容。此次 `deleted` 是重要线索，不能单凭它认定有人手工删除文件，更不能把教学例子的“截断”写成本次已经查明的操作。仍需区分文件截断、清理重建时序、共享存储的映射与锁语义等原因。现有转储不足以识别执行者。

#### 文件头怎样解释这次错误

正常 SQLite 数据库前 16 字节为 `SQLite format 3` 加零字节，这是解析文件的格式标记。本次旧文件前 16 字节为：

```text
0d000000010ff5000ff5000000000000
```

文件大小 339968 字节，独立只读副本也返回 SQLite code 26（`SQLITE_NOTADB`，文件无法识别为数据库）。因此，读到的文件格式足以重现错误。格式标记含义见 [SQLite 文件格式](https://www.sqlite.org/fileformat.html#the_database_header)和[错误码说明](https://www.sqlite.org/rescode.html#notadb)。

例如数据库正常保存一条“模型接口返回 401”的日志时，文件开头仍保持 SQLite 标记。日志内容中的远程错误，与数据库文件自身无法解析，是两个不同层次的问题。

旧文件的 SHA-256 为 `dceaa58ce3e274facc8bade465e9568976b82cbc0032db28883fde3aa8f000e2`，用于识别这份证据。原记录没有系统调用审计或足够前后快照，最初覆盖文件的进程、时间及存储行为尚未确定。

#### 日志维护仍探测旧路径

使用隔离 `CODEX_HOME` 和文件打开系统调用跟踪，发现同版客户端既打开配置指定的新库，也会探测 `CODEX_HOME/logs_2.sqlite` 旧位置。旧位置放异常文件时出现探测，旧文件不存在时跳过该访问。跟踪同时覆盖 `open` 与 `openat`，以免漏掉调用。

这解释了“新日志正常，维护仍失败”的现象：写入位置已更新，维护过程还接触旧异常文件。确认旧文件没有被本机进程持有、没有 WAL 和 SHM 伴随文件后，将其原子重命名到备份目录。原字节与摘要保留，健康新库继续使用。
