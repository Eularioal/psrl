## Codex 会话数据库恢复：原始记录还在，怎样恢复列表与历史

本页是 CLI `0.167.0` 的历史故障记录。2026-11-16 整理为最终状态与恢复方法，未重新操作活动数据库。

### 先理解三类存储

| 对象 | 保存什么 | 损坏后的现象 |
|---|---|---|
| `sessions/` 内的 JSONL 文件 | 原始会话事件，一行一条 JSON 记录 | 未成功保存的消息可能缺失 |
| 状态库 `state_5.sqlite` | 会话 ID、名称、原始文件路径等元数据 | 列表或恢复入口失败 |
| 历史库 `thread_history_1.sqlite` | 用于界面分页读取的历史 | 会话可列出，打开历史页仍失败 |

例如一条对话的 JSONL 文件完整，但状态索引损坏，列表就找不到它。取得正确 ID 和文件路径后，可以由 Codex 重新读取原始文件，重建可浏览的历史。日志数据库另有用途，见[日志库修复](#codex-日志库修复从文件格式异常到健康检查通过)。

### Results：恢复时报 bounded thread item page

当时恢复两个长会话报 `failed to load a bounded thread item page`，进一步返回 `database disk image is malformed`。只读检查发现历史库页面异常，状态库也报损坏，而两个原始 JSONL 文件逐行解析通过。

在隔离副本上，实际执行 `thread/resume` 后再读取 `thread/items/list`，两个会话各返回 10 条非空历史消息，重建的历史库通过完整性检查。这验证了“读取原始会话并重建历史”的恢复路径。

恢复先在副本验证，再协调使用同一存储的客户端停止写入后切换。保全范围包括数据库及 WAL、SHM 伴随文件：WAL 是预写日志，可能含尚未合入主文件的事务；SHM 用于协调读取。原损坏文件作为证据保留。

下面是只读诊断示例，每份数据库最多检查五秒，使用 Python 标准库；缺失文件不会被新建。

```bash
python - <<'PYCODE'
import os
import sqlite3
import time
from pathlib import Path

root = Path(os.environ.get("CODEX_HOME", str(Path.home() / ".codex")))
for name in ("state_5.sqlite", "thread_history_1.sqlite"):
    path = root / name
    try:
        with sqlite3.connect(path.resolve().as_uri() + "?mode=ro",
                             uri=True, timeout=2) as db:
            deadline = time.monotonic() + 5
            db.set_progress_handler(lambda: int(time.monotonic() > deadline), 1000)
            print(name, db.execute("PRAGMA quick_check(3)").fetchall())
    except sqlite3.Error as error:
        print(name, type(error).__name__, str(error))
```

### Bus error 导致会话退出

#### 为什么数据库文件会引发内存错误

SQLite 是把数据保存在文件中的数据库。WAL 是预写日志，更新可先写入 `-wal` 文件，再合入主数据库。配套的 `-shm` 文件存放 WAL 索引等协调数据，程序可以通过 `mmap`，即内存映射，把文件区域当作内存访问。因此磁盘文件发生某些异常时，表现可能是进程收到内存访问类信号，而非普通的文件读取报错。

教学例子：进程先把一个 32768 字节文件映射进内存，读取第一个字节成功。假设文件随后被截断成 0 字节，原映射地址仍在，但文件已无法提供对应页面。再次读取相同地址时，Linux 可以发送 SIGBUS。默认处理会结束整个进程，而不只是结束那次数据库查询，所以终端会话会退出。

**删除目录项本身通常不足以导致 SIGBUS。** 正常本地文件系统会保留仍被打开或映射的文件内容。此次 `deleted` 是重要线索，不能单凭它认定有人手工删除文件，更不能把教学例子的“截断”写成本次已经查明的操作。仍需区分文件截断、清理重建时序、共享存储的映射与锁语义等原因。现有转储不足以识别执行者。

#### 最小教学实验

下面只用 Linux Python 标准库，在子进程中操作自己的临时文件，不访问 Codex 数据，也不生成 core。示例模拟“映射后截断”，不是复现本次 FUSE 环境的具体根因。

```bash

import subprocess
import sys

code = '''import mmap, os, resource, tempfile
resource.setrlimit(resource.RLIMIT_CORE, (0, 0))
with tempfile.TemporaryFile(dir="/tmp") as f:
    f.truncate(32768)
    view = mmap.mmap(f.fileno(), 32768)  # 对应图 2：建立文件映射。
    print("before:", view[0], flush=True)
    os.ftruncate(f.fileno(), 0)  # 教学假设，不是已查明的真实操作。
    print(view[0])  # 对应图 3：读取失去文件支撑的映射。
'''
p = subprocess.run(
    [sys.executable, "-c", code], stdout=subprocess.PIPE,
    stderr=subprocess.PIPE, universal_newlines=True, timeout=5,
)
print(p.stdout, end="")
print("child returncode:", p.returncode)
```

#### 文件头怎样解释这次错误

正常 SQLite 数据库前 16 字节为 `SQLite format 3` 加零字节，这是解析文件的格式标记。本次旧文件前 16 字节为：

```text
0d000000010ff5000ff5000000000000
```

文件大小 339968 字节，独立只读副本也返回 SQLite code 26（`SQLITE_NOTADB`，文件无法识别为数据库）。因此，读到的文件格式足以重现错误。格式标记含义见 [SQLite 文件格式](https://www.sqlite.org/fileformat.html#the_database_header)和[错误码说明](https://www.sqlite.org/rescode.html#notadb)。

例如数据库正常保存一条“模型接口返回 401”的日志时，文件开头仍保持 SQLite 标记。日志内容中的远程错误，与数据库文件自身无法解析，是两个不同层次的问题。
