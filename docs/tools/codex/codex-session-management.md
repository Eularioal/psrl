## 一、恢复已有会话

### 精确回到指定对话

原始笔记记录的会话 ID：`01a08968-76ae-7171-8b90-fddf1a6be535`。

重新连接服务器或打开新终端后执行：

```bash
cd ${WORKSPACE_ROOT}
CODEX_HOME=${WORKSPACE_ROOT}/.codex codex resume 01a08968-76ae-7171-8b90-fddf1a6be535
```

这里显式指定该环境实际使用的 `CODEX_HOME`，避免新终端落到另一个存储目录。恢复依赖原会话记录仍可访问；只有会话 ID 而没有对应记录，不足以在另一台机器上恢复。

### 从列表选择或恢复最近一次

在同一工作目录和相同 `CODEX_HOME` 下：

| 命令 | 用途 |
|---|---|
| `codex resume` | 打开历史会话选择器 |
| `codex resume --last` | 恢复最近一次会话，不一定是你想找的那次 |
| `codex resume --all` | 取消当前工作目录过滤，查找其他目录的会话 |

若使用图形界面或 IDE 插件，应从该界面的历史会话入口打开原对话。第三方界面的会话不保证与本地 CLI 共享存储。

### 会话和文件的区别

恢复会话是继续已有对话上下文，不是回滚工作区文件。反之，新建对话也不会自动继承上一次的完整聊天记录 —— 这正是把知识落盘成文档的意义。

## 二、能否给会话改名

### 结论

Codex CLI `0.154.0` **没有**给已有 session 改名的公开命令，也没有 `/rename` 子命令。

本机帮助列出了 `resume`、`archive`、`delete`、`unarchive`、`fork` 等 session 管理命令，但没有 `rename`。官方文档说明 `codex resume` 用来返回已保存的聊天，同样未提及 CLI 中可修改会话名称。

### 当前的名称来自哪里

每条 session 记录同时有三个标识：

- **UUID**：不变，用于精确恢复会话。
- **`title`**：原始首条用户请求。
- **`name`**：Codex 自动生成的简短标题。

例如原始笔记那次 session 的自动名称是"阅读项目并总结结构及添加回顾规则"。`codex resume`、`archive` 等命令接受 UUID 或 name，因此该名称可用于引用会话；但 CLI 未提供把它改成自定义名称的入口。

### 实际建议

1. **用 UUID 恢复重要会话** —— 这是唯一稳定、明确的标识。

   ```bash
   codex resume <SESSION_UUID>
   ```

2. **用首条请求写清主题** —— Codex 会据此生成更容易辨认的自动标题。新建会话时第一句可写成"PSRL 参数服务器设计讨论"这类明确的说明。

3. **图形界面另说** —— 在 ChatGPT 桌面端、网页端或 IDE 扩展中使用 Codex 时，可查看会话列表的更多操作菜单，界面可能提供标题编辑。这不是本机 CLI 已验证的功能，也不应假定它与 CLI 的本地 session 记录互通。

### 不建议的做法

不要直接编辑 `.codex/session_index.jsonl` 或 `.codex/state_5.sqlite` 中的名称。它们是内部存储，运行中的 Codex 进程、缓存和数据库记录可能不一致；CLI 版本升级也可能改变格式。

## 三、`/goal`：让当前会话持续推进一个目标

核对日期：2026-10-13。以下命令依据 OpenAI 官方文档；当前会话能力依据实际提供的目标管理工具；示例为教学假设，未运行项目测试，也未创建目标。

一句话结论：`/goal` 为当前会话设置一个持续目标，让 Codex 反复执行、验证和调整，直到达到完成条件或遇到停止条件，减少用户反复发送“继续”的需要。

### 它和普通请求的区别

普通请求同样可以包含读代码、修改、测试等多个步骤。`/goal` 增加的是显式的目标状态和跨轮次续跑机制：一轮工作结束后，只要目标尚未达成、仍处于活动状态且未触及限制，Codex 就可以从已有结果继续推进。它适合下一步依赖前一步发现的任务，例如复杂故障排查、迁移和反复实验。[官方 Goals 指南](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

这里的“轮次”指一次助手处理过程；一次处理过程内部可以调用很多次工具。“持续目标”指目标附着在当前对话上，不能据此假定它自动适用于所有新会话。

### 具体例子：修复一组测试

假设某项目共有 100 个测试，初始 12 个失败。可以在 Codex 对话输入框中提交下面这条示例指令：

```text
/goal 修复当前项目的测试失败，使约定测试集的 100 个测试全部通过。
不得删除或跳过测试，不改变现有公开接口。
先复现失败，再按根因修复；最后运行完整的约定测试集验证。
如果因缺少凭据或外部服务无法验证，说明阻塞点及所需条件。
```

示例中的数字是教学假设，不是本工作区实测结果。多行文字共同组成目标描述。

1. 先运行测试，确认 12 个失败及错误日志，建立初始状态。
2. 假设发现一个共同的配置问题，修复后剩余 3 个失败。此时已有进展，但没有达到 100 个全部通过，目标仍未完成。
3. 根据剩余错误进一步检查代码，修复后运行约定的完整测试集。
4. 只有 100 个测试全部通过，同时没有违反“不得跳过测试、不得改变公开接口”等约束，才能把目标标记为完成。
5. 如果最后 3 个测试依赖不可用的外部服务，应报告已经验证的部分和阻塞条件，不能把“无法运行”当作“通过”。

在这个例子中，“全部通过”是结果，“测试输出”是证据，“不跳过测试”是约束；失败日志决定下一步调查方向。这些内容让持续推进有明确的结束依据。

### 常用命令

以下命令输入在支持 Goals 的 Codex 对话框中，不是 Bash 命令。

| 命令 | 用途 |
|---|---|
| `/goal <目标描述>` | 设置持续推进的目标 |
| `/goal` | 查看当前目标 |
| `/goal pause` | 暂停目标 |
| `/goal resume` | 恢复已暂停的目标 |
| `/goal clear` | 清除当前目标 |

这些命令由[官方使用说明](https://learn.chatgpt.com/use-cases/follow-goals)列出。清除目标不应理解成撤销已经落盘的代码修改；目标管理和文件版本管理是不同操作。

### 当前会话能确认的机制

当前会话提供了 `create_goal`、`get_goal`、`update_goal` 工具，分别用于创建目标、读取目标状态与用量、更新完成/暂停/阻塞状态。它们是助手使用的工具名称，用户通常直接使用 `/goal` 即可。

工具支持显式指定 token 预算。Token 是模型处理文本时使用的计量单位，不等于汉字数，也不是运行秒数。预算用来限制消耗，不是“花到这个数量必然完成”的保证；本次没有核实界面的预算参数语法，因此不提供猜测性的 `/goal` 参数写法。

当前工具一次只能维护一个未完成目标。预算停止和使用量限制由用户或系统控制，助手不能自行解除。询问 `/goal` 的含义不会构成创建目标的请求，本次只做说明和文档留档。

### 怎样写得有效，以及什么时候使用

目标描述应交代：要得到什么结果、怎样验证、哪些约束必须保持、可操作范围，以及遇到什么情况需要报告阻塞。例如“让项目更好”缺乏可检查的终点，而上面的测试目标有明确的验收标准。官方建议将目标限定为一项可持续推进且可验证的工作，避免放入互不相关的任务清单。[官方使用说明](https://learn.chatgpt.com/use-cases/follow-goals)

对于“解释一个概念”“改一个变量名”等边界清楚的小任务，普通请求已经足够。对于需要反复观察结果再决定下一步的工作，持续目标更有用。

`/goal` 不保证任务一定成功，也不会改变当前工具权限；仍可能因用户暂停、预算、执行中断或确实无法推进的阻塞而停止。目标保留也不等于本地进程关闭后仍有机器替它执行，不应将其当成自动提供离线算力的功能。

## 四、滚轮切换历史而无法阅读长回复

核对日期：2026-10-14。本节补充会话恢复时的显示问题，不改变前文各历史版本结论。

### 先看滚轮经过哪些环节

下面是概念路径，分支取决于终端模式和配置，不是本次已经捕获到的真实鼠标事件：

```text
[1] 鼠标向上滚动
       ↓
[2] 终端决定如何处理
       ├─ 普通回滚 → 移动终端显示位置，查看旧输出
       ├─ 备用屏幕中的按键转换 → 向上方向键 → [4] 应用切换输入历史
       └─ 鼠标事件 → [3] tmux → 复制模式回滚，或转发给 [4] 应用
```

图例：图里每个部分对应的源码位置与核对边界：

| 编号 | 职责 | 本地实现与证据 |
|---|---|---|
| 1 | 用户产生滚轮事件 | 远端工具不能直接读取用户实际鼠标事件 |
| 2 | 终端解释事件，管理显示历史 | 环境变量为 `TERM_PROGRAM=vscode`；未定位到用户前台终端的事件处理源码或设置 |
| 3 | tmux 管理多个终端窗口，处理或转发事件 | 本机 tmux 2.7；只读命令核对全局 `mouse off`、前缀 `C-b`，未找到本工作区对应源码 |
| 4 | Codex 显示回复、维护输入框 | 本机 Codex CLI 0.162.1 帮助确认 `--no-alt-screen`；安装包入口只是原生程序启动器，不是滚轮实现源码 |

**备用屏幕（alternate screen）**是终端提供给全屏应用的一块独立显示区域，方便应用重画界面并在退出时恢复原 shell 画面。它通常不提供普通终端那样的回滚历史。**回滚历史（scrollback）**则是终端保留的旧输出行。有些终端在备用屏幕中把滚轮转换为上下方向键；如果应用把方向键用于选择以前发过的问题，就会出现“滚轮切换输入历史”的现象。

这仍是候选原因。若实际切换的是整个窗口，还要检查指针是否放在 tmux 状态栏：本机绑定中 `WheelUpStatus` 是 `previous-window`，`WheelDownStatus` 是 `next-window`。这些绑定是否生效，还取决于鼠标事件是否传入 tmux，不能仅凭绑定存在就认定根因。

初次排查时，工具环境的 `TMUX_PANE` 指向后台隧道窗口 `wc_tunnel`，该窗口 `alternate=0`；其他多个窗格为 `alternate=1`。因此不能把工具环境当作用户正在阅读回复的前台，不能断言用户当前 Codex 必然处于备用屏幕，也不能归因为某次更新。初次排查没有修改全局 tmux 配置；随后用户明确要求修复，实际变更见第五节。

### 具体例子：同一次滚轮为何产生不同结果

教学假设：一条回复有 100 行，屏幕能显示 20 行，现在看到第 81–100 行。用户向上滚一格，假设这一格等于三行。

- 正常回滚：终端把显示起点从第 81 行移到第 78 行，看到第 78–97 行；输入框不变。
- 按键转换：终端发送向上方向键，应用输入框选中上一条问题；显示起点仍是第 81 行，所以长回复的前半部分依然看不到。
- tmux 复制模式：tmux 暂时让键盘控制保存的屏幕历史，可以向上翻页；退出复制模式后重新把输入交给应用。但已经丢弃或未保存的画面不能凭此恢复。

这里的“输入历史切换”本身不等于向模型发送了新请求，更不能据此推断模型上下文被删掉。终端显示历史、应用保存的会话记录、模型处理请求时使用的上下文，各自有不同的存储和管理方式。

### 立即阅读与后续恢复

1. **先尝试 Shift 加滚轮。** 一些终端用它绕过应用鼠标处理，但它不是所有终端都支持的通用修复，也不能补回未保存的历史。
2. **在实际使用的 tmux 窗口查看历史。** 按 `Ctrl+b`，松开，再按 `[`，进入复制模式；用方向键或 `PageUp` 翻阅。当前检查到的 emacs 按键模式可用 `Esc` 退出。前缀已自定义或不在 tmux 中时不适用。
3. **Codex 使用保留回滚的模式启动。** 等当前任务结束，正常退出 Codex，在原来的 shell 中运行：

   ```bash
   codex resume --no-alt-screen
   ```

   从选择器选回当前会话。`resume` 读取已有会话；`--no-alt-screen` 关闭备用屏幕。本机 `codex --help` 与 `codex resume --help` 均已确认该参数。如果明确知道会话 ID，可用 `codex resume <会话ID> --no-alt-screen`。不要盲用 `--last`，多会话时它可能选错。恢复时沿用原来的工作目录、`CODEX_HOME` 和远端连接参数。
4. **通过界面保存模式。** 当前官方文档提供 `/tui`：选择 `scrollback`，确认后重启生效。此斜杠命令输入在 Codex 对话框，不是在 shell；本次未在用户前台界面执行它。如果当前客户端不提供该命令，使用上面已由本机帮助确认的启动参数。[官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
5. **需要立刻在编辑器看全文时。** 官方文档提供 `/export session.md`，可在本轮结束后把完整对话导出成 Markdown，再用编辑器打开；本次未在前台验证该命令。[官方导出说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

如果 `--no-alt-screen` 后仍在 tmux 内无法用滚轮，可在实际发生问题的窗口按 `Ctrl+b`、松开、按 `:`，输入 `set-option mouse on`，回车；这是当前会话级设置，没有 `-g`。将指针放在正文区再试。鼠标事件仍可能被转发给应用，因此必要时先进入复制模式。用 `set-option -u mouse` 可撤销会话级覆盖，恢复继承全局设置。此为初次排查建议；第五节记录随后实际应用的全局默认值及滚轮绑定，无需重复执行本段建议。

### 为什么原来会切换问题

鼠标滚轮只是一个输入事件；“它应该滚哪里”由接收事件的软件决定。终端、tmux、窗格里的应用分别有自己的状态，可能给同一个动作分配不同含义。

修复前确定看到的是 `mouse off`。这意味着 tmux 没有通过该选项接管鼠标；终端可能自行滚动，也可能在备用屏幕中把滚轮转换为方向键。应用收到方向键后可能选择之前输入过的问题。另一个已确认的事实是原 `WheelUpPane` 默认规则在应用要求鼠标事件时会转发事件。因此单独设置 `mouse on` 仍不足以保证正文滚轮一定用于 tmux 历史。

“原始滚轮实际在哪一层被转换”属于推断，未抓取用户前台事件确认。修复的思路是明确规定这条路径：tmux 收到正文滚轮后，优先滚动 tmux 的历史。用户看到的问题因此可以在 tmux 输入处理层解决，无须修改聊天文本或模型会话。

### 复制模式是什么，为什么能看旧内容

tmux 是终端复用器：一个服务器维护多个会话，每个会话有窗口，窗口可以分成多个**窗格（pane）**，每个窗格运行自己的程序。程序输出先经过 tmux，tmux 维护屏幕内容及有限的历史行，再发送画面给连接的终端。

普通交互时，键盘主要用于操作窗格里的程序。**复制模式（copy mode）**是 tmux 自己提供的查看历史、移动光标、选择并复制文字的模式。名字包含“复制”，是因为它同时支持选中文本；本次只用到其中的历史浏览，不会自动把文字复制进剪贴板。

进入复制模式后，相当于把“当前阅读位置”从最新输出移向历史行。前台应用进程不会因此被暂停，但用户需要退出此模式才能回到通常的输入交互。tmux 2.7 在该模式下的画面也不应视为持续跟随最新输出的视图。

教学例子：假设历史里保存了 100 行、可见区能显示 20 行，初始显示第 81–100 行。

| 动作 | 模式 | 距最新位置的偏移 | 可见内容 |
|---|---|---|---|
| 尚未滚动 | 普通交互 | 0 行 | 第 81–100 行 |
| 向上滚一个事件 | 进入复制模式 | 5 行 | 第 76–95 行 |
| 再向上滚一个事件 | 保持复制模式 | 10 行 | 第 71–90 行 |
| 向下滚一个事件 | 保持复制模式 | 5 行 | 第 76–95 行 |
| 再向下滚一个事件 | 到底自动退出 | 0 行 | 第 81–100 行 |

数字为教学假设。配置中的 5 指每个 tmux 收到的滚轮事件移动 5 行；触控板或终端加速可能把一次手势转成多个事件，所以一次手势不保证恰好 5 行。

### 实际配置逐步解释

第一步，在 [第 3 行](tmux-scroll.conf#L3) 启用鼠标：

```tmux
set-option -g mouse on
```

`-g` 设置全局的会话默认值，未单独覆盖此选项的会话会继承它。本次修复影响当前 tmux 服务器的这些会话，不仅一个 Codex 窗口。

第二步，[第 4 行](tmux-scroll.conf#L4) 是核心规则，下面为原文：

```tmux
bind-key -n WheelUpPane if-shell -F -t = '#{pane_in_mode}' 'send-keys -M' 'copy-mode -e -t = ; send-keys -X -N 5 -t = scroll-up'
```

从左到右阅读：

- `bind-key -n WheelUpPane`：正文区域向上滚动就触发，不需要先按 `Ctrl+b`。`-n` 表示放在无需前缀的 root 键表。
- `if-shell -F`：这里依据 tmux 的格式变量判断条件，不启动 shell 执行一个外部判断命令。
- `-t =`：目标是鼠标事件所在窗格。这样鼠标停在哪个窗格，就针对那里处理。
- `#{pane_in_mode}`：窗格是否处于 tmux 的模式。值为 0 时走后面的假分支；非零走真分支。严格说这不专指复制模式，其他 tmux 模式也可能为非零；本次讨论普通状态与历史阅读状态。
- 假分支 `copy-mode -e -t =`：进入复制模式；`-e` 让向下滚回底部时自动退出。在本机 2.7 中，期间使用非滚动键可能关闭这种自动退出行为，此时仍可用退出键。
- 接着 `send-keys -X -N 5 -t = scroll-up`：给复制模式发送向上滚动命令，重复 5 次。`-X` 的意义非常关键：目标是 tmux 模式里的命令，不是向应用输入一串 `scroll-up` 文本。
- 真分支 `send-keys -M`：把当前鼠标事件交给目标窗格继续处理。在已经进入复制模式的这条路径里，是当前模式处理事件。不能脱离上下文说 `-M` 永远不会把事件传给应用；它本身就是鼠标转发选项。

第三步，[第 5 行](tmux-scroll.conf#L5) 配置向下滚动：在模式中继续处理鼠标事件；不在模式中则执行空动作。已经处于最新位置时，再向下滚也不会意外触发应用的“下一条历史输入”。

第四步，[第 6–9 行](tmux-scroll.conf#L6) 明确复制模式中的上下滚动。以 emacs 键表的向上规则为例，以下为原文：

```tmux
bind-key -T copy-mode WheelUpPane select-pane \; send-keys -X -N 5 scroll-up
```

`-T copy-mode` 指定历史模式使用的按键表；先 `select-pane` 选中鼠标所在窗格，再滚动 5 行。`\;` 用于在配置里连接这两个 tmux 命令。`copy-mode-vi` 是另一套偏向 vi 编辑器习惯的按键表；两套都配置以覆盖不同的 `mode-keys` 设置，本机当前采用 emacs。

第五步，[第 11–12 行](tmux-scroll.conf#L11) 删除 `WheelUpStatus` 和 `WheelDownStatus` 的绑定。正文事件以 `Pane` 结尾，状态栏事件以 `Status` 结尾；取消后，鼠标偶然落在状态栏也不会因为滚轮换到其他窗口。

相关命令语义已核对本机 tmux 2.7 手册 `/usr/share/man/man1/tmux.1.gz`。当前版本手册可延伸阅读 [tmux 手册](https://man.openbsd.org/tmux#MOUSE_SUPPORT)，但新版本新增选项不能反推本机 2.7 也支持。

```bash

```

脚本创建一个独立 tmux 服务器，读入 [配置快照](tmux-scroll.conf)，让小程序输出 150 行，再用**伪终端（PTY）**连接测试客户端。伪终端提供与真实终端相同类别的输入输出接口，脚本可以向它写入鼠标事件编码。这里使用 SGR 扩展鼠标编码格式，事件包含方向与屏幕坐标；例如 `ESC [ < 64 ; 10 ; 10 M` 表示坐标 `(10,10)` 处的一次向上滚轮事件。协议细节不影响配置原理。

本次实际输出：

```text

application_input=b''

```

`0:` 表示不在 tmux 模式中；`1:5` 表示进入模式且历史偏移为 5 行；`b''` 表示应用收到的输入字节为空。脚本还会再次进入复制模式，发送 Esc，验证主动退出。

保存实验时，首次把 Esc 等待时间设为 0.3 秒导致退出检查失败。检查发现本机 `escape-time=500`，即 tmux 等待 500 毫秒以区分单独 Esc 与以 Esc 开头的特殊键序列。将实验等待改为 0.8 秒后通过；没有改动用户的 `escape-time`。这不是滚轮修复失败，也不掩盖首次实验的时序问题。

整个实验只有固定几次事件、约 3 秒的预定等待，单次外部命令超时 5 秒，无重试循环。退出时只清理其独立服务器和客户端。已核实未留下测试 socket；没有重新启动用户会话。

### 生效范围、持久化与边界

这次修改文件 `${HOME}/.tmux.conf` 保存了以后启动时要读取的规则；另外把相同规则通过 `tmux source-file` 加载进当前服务器，所以现有会话可以马上使用，无须重启应用。二者作用不同：仅写文件不自动更新正在运行的服务器，仅在命令行临时设置则不保证下次启动还存在。

鼠标开关是全局会话默认值，按键绑定属于当前 tmux 服务器共享的键表。因此其他应用也会受到影响：正文滚轮优先用于 tmux 历史，原本依赖滚轮操作的编辑器或列表不再保证收到它。这是按用户希望“滚轮滚内容”的偏好实施的选择。

本次没有修改 Codex 启动参数、会话记录或模型上下文。tmux 滚动的是保存的屏幕历史，不是直接读取会话数据库；历史已被丢弃，或全屏应用只覆盖重画而没有留下完整历史时，此配置无法凭空恢复文字。需要完整会话时可参考第四节的回滚模式与导出建议。

验证证明了本机 tmux 2.7 的隔离测试路径，且重新读取了当前服务器生效的规则；用户实际前台终端是否已经恢复，仍以用户操作结果为准。

- 这三组终端没有出现在 tmux 窗格列表中。检查时 `tmux list-clients` 为空，不能把工具继承的 `TMUX` 环境变量当作用户当前界面正在 tmux 中的证据。

因此“给 `wc_tunnel` 设置会话级 mouse 和键表”虽然技术上能执行，但只会影响查看该 tmux 窗格时的鼠标操作，不能继承到 tunnel 服务创建的所有 VS Code 集成终端。

按用户给定的兜底授权，已重新将滚轮修复块写入 `${HOME}/.tmux.conf`，并只加载该块到运行中的 tmux 服务器；保留可能存在的其他配置内容。随后重新读取确认全局 `mouse on`、正文滚轮绑定生效，状态栏滚轮切换绑定已移除。本次没有新增针对特定会话的覆盖。

第五节的独立 tmux 实验是此前对相同规则的验证，不能写成这次前台端到端验证。本次仅核对恢复后的配置。对不经过 tmux 的 VS Code 终端，仍应检查该终端自身及应用的滚动行为，不宣称全局 tmux 设置能修复它。

## 七、快速找到当前会话前几轮的问题与回答

适用场景：在终端里的 Codex CLI 中，想回看同一 session 的上一次、上上次提问，以及当时对应的完整回答。Session 就是一条持续的聊天，transcript 指这条聊天的对话记录。这与第一节“重新打开另一条会话”不同，也不需要先修改第四至六节的 tmux 配置。

**先打开完整对话，再翻页或搜索问题关键词。** 可以先试 `Ctrl+T`。若按键没有打开记录，在 Codex 输入框提交 `/keymap`，查找 `Open the transcript overlay`，读取该动作实际绑定的按键。官方配置示例给出了 `open_transcript = "ctrl-t"`，但示例不等于所有版本和配置的默认值。[官方快捷键配置](https://learn.chatgpt.com/docs/config-file/config-basic#tui-keymap)

进入记录后，使用界面提示的翻页键浏览，通常为 `PageUp`、`PageDown`。如果不想穿过大量工具输出，在 `/keymap` 查找 `Find text in the full transcript`，按显示的快捷键搜索自己问题里独特的词。它对应 `global.find_transcript`，与输入框里的历史搜索是不同动作。关闭记录时使用底部显示的关闭键，也可在 `/keymap` 查找 `Close the transcript overlay`。

这里不把未经核对的按键写成“上一轮”“上上轮”的固定跳转键。长会话更适合以问题中的关键词定位，短会话直接翻页即可。若终端或编辑器截获了按键，`/keymap` 中的 `Inspect keypresses` 可检查 Codex 实际有没有收到它。

| 想做什么 | 入口 | 查看或操作的对象 |
|---|---|---|
| 阅读旧问题和对应回答 | 完整对话浏览，先试 `Ctrl+T`，或从 `/keymap` 核对 | 整条聊天记录 |
| 在问题或回答正文中定位关键词 | `/keymap` 中的 `Find text in the full transcript` | 完整对话中的文字 |
| 找回以前输入过的问题 | 输入框中的 `↑`、`↓`，或 `Ctrl+R` | 输入历史，不包含对应回答 |
| 编辑上一条问题并从那里分支 | 空输入框连续两次 `Esc` | 编辑及分支操作，不是单纯阅读 |
| 只复制最近一次完成的回答 | `/copy` 或 `Ctrl+O` | 最近完成的输出 |
| 在编辑器中检索整条聊天 | `/export session.md` | 导出的 Markdown 对话文件 |
| 重新打开以前的另一条聊天 | `codex resume` | 已保存的会话列表 |

输入历史、复制和双 `Esc` 的行为见 [官方 CLI 交互快捷键](https://learn.chatgpt.com/docs/cli/reference#interactive-shortcuts)。导出见 [官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)。斜杠命令输入在 Codex 对话输入框，`codex resume` 则在 shell 中执行。

**具体例子。** 假设一条聊天依次有“解释 EnvRouter”“比较 baseline”“解释 OOM”三轮问答，现在想回看中间那轮。

1. 打开完整对话浏览，启动全文搜索。
2. 搜索 `比较 baseline`，定位你当时发送的问题。只搜索 `baseline` 可能也命中多条回答，使用问题中更长的短语可以减少匹配。
3. 从该问题往下读，经过可能存在的进度和工具输出，找到对应回答。下一条用户提问通常是下一轮的边界，执行中追加的指令可能打断这种简单排列。
4. 读完关闭记录，返回当前输入位置。这条浏览路径不需要重新提交旧问题。

如果更习惯编辑器，可在会话空闲时输入下面的命令，将记录导出到一个尚未使用的文件名：

```text
/export session.md
```

打开导出的文件，在编辑器中按 `Ctrl+F` 搜索 `比较 baseline`，macOS 编辑器通常是 `Cmd+F`。定位问题后，下方就是同一份导出记录中的后续内容，可继续阅读对应回答。文件写到当前会话工作目录，具体路径以导出反馈为准。导出包含聊天内容，应放在自己的工作目录，不要顺手提交到公开仓库。

**核对边界。** 本节于 2026-10-20 核对，本机命令返回 `codex-cli 0.163.0`。本机安装包的界面文本中确认存在 `/keymap`、完整对话浏览、完整对话搜索、分页和按键检查动作。安装包未提供这些界面的源码，二进制字符串不能证明具体按键绑定和运行效果，因此本节不伪造源码行号，也不声称已在用户前台按键验证。官方页面用于核对公开行为，实际快捷键以当前客户端 `/keymap` 为准。本节是功能使用说明，没有额外运行模型请求或修改快捷键配置。
