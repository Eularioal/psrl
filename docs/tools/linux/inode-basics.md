# inode：文件名背后的文件身份与 Docker 写回阻塞

> **核心结论**：inode（索引节点）记录文件的身份和属性，目录把名字映射到 inode，文件内容则由文件系统保存。名字被删除不一定立刻释放文件，进程还打开它时仍可以读写。本次 Docker 的 `inode_wait_for_writeback` 表示等待文件节点的写回完成，不是 inode 数量用尽。

## 1. 从文件名到文件内容

当你打开 `a.txt` 时，操作系统不只是拿着字符串去寻找一块数据。文件系统先根据目录找到文件对象，再根据这个对象的属性和内容映射完成访问。

下面是**概念图**，说明真实文件系统的接口语义，不是某一版本内核的逐行调用图。编号对应后文的可运行实验。

```text
[1] 目录中的名字 a.txt ───┐
                         ├──→ [2] 同一个 inode I ───→ [3] 内容 hello\n
[1] 硬链接名字 b.txt ────┘       大小、权限、链接数等
                                      ↑
                            [4] 进程打开文件后持有的引用

[5] 删除名字：删除目录中的映射，减少硬链接数
    最后一个名字消失后，只要 [4] 还在，打开的文件仍可使用
    关闭最后的打开引用后，相关存储才具备回收条件
```

## 2. inode 保存什么，为什么要独立于文件名

inode 常译为“索引节点”。ext4 官方文档将它称为 Index Node，重点是它作为文件元信息与内容映射的索引角色，不必把它想成文件内容本身。

它通常记录文件类型、所有者、权限、大小、时间戳、硬链接数，以及定位文件内容所需的映射信息。目录项保存文件名与文件对象的关联，所以普通文件的 inode 不保存唯一的文件名。同一个文件可以同时有两个名字，也可以暂时没有目录名字但仍被进程打开。[inode 手册](https://man7.org/linux/man-pages/man7/inode.7.html)、[ext4 inode 文档](https://docs.kernel.org/filesystems/ext4/inodes.html)

| 信息 | 它回答的问题 |
|---|---|
| inode 编号 | 在这个文件系统内，这是哪个文件对象 |
| 类型、权限、所有者 | 是文件还是目录，谁可以读写 |
| 文件大小 | 内容的逻辑长度是多少字节 |
| 硬链接数 | 当前有几个目录名字直接指向它 |
| 内容映射 | 文件内容放在哪里，具体布局由文件系统决定 |

inode 编号只在所属文件系统内有意义。程序通常结合 `st_dev`（设备/文件系统标识）和 `st_ino`（inode 编号）比较文件身份，不能仅比较数字，更不能把删除后可能被复用的 inode 编号当作永久全局 ID。

这种分离直接解释几种常见操作：同一文件系统内重命名通常只改变目录名字，文件身份保持不变。硬链接增加另一个直接指向同一文件的名字，不复制内容。普通复制则创建另一个文件对象并复制内容，所以两个文件的内容相同也可以有不同 inode。[硬链接接口说明](https://man7.org/linux/man-pages/man2/link.2.html)

软链接不同：它是另一个文件对象，保存目标路径的引用信息。打开软链接时还要解析目标路径。目标名字消失后，软链接可能仍存在，却无法再找到原目标。硬链接的两个名字是平等入口，不存在必须保留的“原始名字”。

## 3. 一个六字节文件的完整变化

本次在节点本地临时目录做了真实文件操作，写入 `hello\n`，总计 6 字节。下面用 I 和 J 表示实际 inode，避免把一次运行的编号当成固定值。原始编号与结果保存在 [实验 JSON](inode-demo-results.json)。

| 步骤 | 目录中有什么 | inode 与链接数 | 内容与结果 |
|---|---|---|---|
| 创建 `a.txt` | `a.txt → I` | I 的链接数为 1 | I 内容为 `hello\n` |
| 给它创建硬链接 `b.txt` | `a.txt → I`，`b.txt → I` | I 的链接数为 2 | 两个名字读到同一份内容 |
| 复制为 `copy.txt` | 另外增加 `copy.txt → J` | J 与 I 不同，J 的链接数为 1 | 复制得到内容相同的独立文件 |
| 把 `a.txt` 改名为 `renamed.txt` | `renamed.txt → I`，`b.txt → I` | I 不变，链接数仍为 2 | 改名没有产生新文件对象 |
| 打开 I，再删除 `renamed.txt` | 只剩 `b.txt → I` | I 的链接数为 1 | 仍可通过 b 或打开的句柄访问 |
| 再删除 `b.txt` | I 的两个名字都不存在 | I 的链接数为 0 | 已打开的句柄仍能读出 `hello\n` |
| 关闭句柄 | 没有名字，也没有该打开引用 | 具备回收条件 | 实验随后清理自己的临时目录 |

“删除文件”更准确地说，首先是调用 unlink 去掉一个目录名字。最后一个名字消失时，如果仍有进程打开文件，文件内容不会立刻变得不可读。最后的打开引用关闭后，相关存储才可回收。[unlink 接口说明](https://man7.org/linux/man-pages/man2/unlink.2.html)

这解释了一个运维现象：你删除了某个大日志文件，但日志进程还持有打开的文件描述符，磁盘空间可能不会立刻下降。此时应核对打开引用和日志轮转方式，不能仅凭目录里看不到文件就认定空间已释放。这里解释的是接口机制，本次只使用六字节文件，没有创建大文件制造磁盘压力。

## 5. 磁盘容量与 inode 容量

文件系统需要同时管理内容存储空间和文件元信息。`df -h` 主要看空间容量，`df -i` 看文件系统报告的 inode 使用情况。不同文件系统的 inode 分配策略不同，不能把 ext4 的某种容量规划直接套用到 XFS 或 FUSE 文件系统。

**教学假设**：某文件系统还有 500 GiB 空间，但它当前能够提供的 100 万个 inode 都已使用。再创建一个只有 1 字节的小文件，也可能因无法分配新的 inode 而失败。反过来，只有几个巨大文件也能用光字节空间，但 inode 仍很充足。

所以“还有很多 GB”不等于“还能无限创建文件”。大量小文件、构建缓存和容器文件层尤其值得同时检查两个指标。零字节普通文件也需要元信息，不能因为没有内容就认为它不需要 inode。

## 6. 与本机 Docker 故障的关系

本机检查时 Docker 原数据路径所在文件系统空间使用率约 67%，inode 使用率约 3%。这不支持“当前 inode 用尽”的判断。

`inode_wait_for_writeback` 中的 writeback 是“写回”：内核准备释放或处理某个文件节点时，要等待相关写回工作结束。这与“还能否分配新 inode”是两个不同问题。就像停车场仍有空位，也不能保证某辆车的出场手续没有卡住，实际机制仍是具体文件节点的写回和锁等待。

本次故障还有 dockerd 的 `deactivate_super` 锁等待，涉及文件系统实例的清理。不能因为栈里出现 inode 就得出“删除小文件可修复”的结论，也不能把 inode 当作可以手动删除的一份配置文件。

故障证据与恢复尝试统一维护在 [集群指南第 19 节及后续恢复记录](../../psrl/psrl-run-guide/cluster-preflight.md#19-本机-docker-挂起原因排查2026-10-20)。本篇补充概念基础，不重复保存服务状态作为永久结论。

## 7. 运行实验与验证边界

从 PSRL 仓库根目录，在已激活项目环境后执行：

```bash
python docs/tools/linux/inode_demo.py
```

预期观察：`hard_link.a` 与 `hard_link.b` 的 inode 相同，链接数为 2。`copy` 的 inode 不同。`renamed` 保持原 inode。`no_names_but_open` 的 links 为 0、names_exist 为 false，但 read 仍为 `hello\n`。最后两个清理标记都为 true。

本次已实际执行，全部断言通过。操作仅涉及标准库创建的本地临时目录，结束时关闭文件并清理。它验证的是文件接口语义，不测物理磁盘写回时延、不证明磁盘块在 close 返回时已全部回收，也不复现 Docker 的内核阻塞。
