## 1. 先把整个过程连起来

这次问题涉及两套流程：应用保存信息的正常流程，以及文件映射访问失败后的退出流程。先用下图把它们串起来，再逐个解释。

这是概念图，不是 Codex 源码调用图。当前没有取得与运行版本匹配的 Codex Rust、SQLite 和 Linux 内核源码，不伪造函数或行号。它也不表示所有组件都在同一个线程顺序执行。

```text
[1] Codex 本地进程
    多个线程分别处理界面、请求、数据库等工作（职责示意）
        ↓ 数据库连接调用
[2] SQLite：嵌入进程内的数据库库
        ├── 主数据库 .sqlite：已经合并的数据页
        ├── -wal：新提交的数据页版本，随后可合入主库
        └── -shm：WAL 索引和协调信息
                    ↓ mmap：建立文件到虚拟地址的映射
[3] 线程访问映射地址
        ├── 正常：内核提供对应的文件页面，访问继续
        └── 异常分支：底层无法提供需要的页面
                    ↓
[4] 内核向故障线程递送 SIGBUS
                    ↓ 默认致命处理作用于进程
[5] 整个进程退出，可能生成 core 转储
                    ↓
[6] 外层终端或启动器报告 Bus error
```

图例：图里每个部分对应的源码位置。下表明确区分外部机制和本地教学代码，实验不实现 SQLite，也不模拟 Codex 的后台服务拓扑。

| 节点或箭头 | 职责与证据 | 本地对应 |
|---|---|---|
| 1、2 | 应用调用嵌入式数据库 | 本次无匹配源码，事故中的数据库线程证据见上述事故章节 |
| 2 → 3 | 将文件映射到进程地址空间 | 实验 [`child`](mmap-sigbus-demo.py#L14) 的 `mmap.mmap`，不是 SQLite 源码 |
| 3 正常路径 | 读取映射字节 | 实验 [`child`](mmap-sigbus-demo.py#L18) |
| 3 异常分支 | 教学中用截断撤去文件支撑 | 实验 [`os.ftruncate` 与后续读取](mmap-sigbus-demo.py#L27) |

## 2. 进程、线程与信号

**程序**是磁盘上的代码，**进程**是程序运行起来后的实例。启动一次程序，操作系统通常会为它建立进程，管理虚拟地址空间、打开的文件以及执行状态。

**线程**是进程内的一条执行线。一个应用可以同时有负责界面响应、网络请求和数据库工作的线程。各线程有自己的执行位置和栈，但通常共享进程的地址空间和打开文件表。线程不是隔离的安全容器。

教学假设：一个进程有三个线程，A 接收输入，B 等待网络，C 写数据库。C 遇到普通数据库错误时，程序可以把错误传回上层并继续运行。但如果 C 的内存访问触发致命 SIGBUS，默认行为是终止整个进程，A、B 也会停止。不能推断“坏的是日志，所以最多丢一条日志”。

**信号（signal）**是操作系统通知进程或线程发生事件的一种机制。例如按 Ctrl+C 通常发出 SIGINT，而非法内存访问可能触发 SIGSEGV 或 SIGBUS。SIGBUS 中 SIG 表示信号，BUS 的历史名称与总线访问错误有关，但今天看到它不等于主板或物理总线损坏。

| 提示 | 大致含义 | 不应直接推断 |
|---|---|---|
| 普通应用错误 | 函数返回错误，或语言运行时抛出异常 | 不一定结束进程 |
| SIGSEGV | 常见于未映射地址或权限不允许的访问 | 不等于内存容量耗尽 |
| SIGBUS | 包括文件映射无法提供页面、某些对齐错误等 | 不等于硬件总线损坏 |
| SIGKILL | 强制终止，可能由用户、管理程序或 OOM 机制发出 | 不一定是 OOM |

OOM 指内存不足。内核可能选择杀死进程来释放内存，但要凭内核日志或资源限制记录判断。上述表是常见含义，具体信号与错误细节也受平台影响。致命信号可以有专门处理机制，但捕获信号不等于数据库状态仍可安全使用。[Linux 信号手册](https://man7.org/linux/man-pages/man7/signal.7.html)

## 3. 虚拟内存与文件映射

程序看到的内存地址通常是**虚拟地址**，不是直接的内存条位置。操作系统结合处理器的地址转换机制，决定这个地址当前对应哪块物理内存、什么权限以及由什么内容支撑。

内存按**页**管理。教学假设一页为 4096 字节，那么 32768 字节就是八页。页大小并非所有平台都相同。地址范围已经登记为有效映射，也不意味着全部页面都已装入物理内存。

访问尚未准备好的页面时，会触发**缺页异常（page fault）**，让内核接手。名字虽然包含“异常”，但它常是正常机制：内核读入文件页或建立页表后，程序继续执行。只有无法完成所需访问时，才可能变成对程序可见的错误。

读取文件主要可以走两种接口：

| 接口 | 对程序的含义 | 文件后续变化的影响 |
|---|---|---|
| `read` | 把读到的字节复制到自己的缓冲区 | 文件随后缩短，已经复制出的普通字节仍然存在 |
| `mmap` | 建立一段地址与文件区域的对应关系，之后按地址读取 | 映射生命周期仍与底层文件对象有关 |

两者底层都可能使用内核的文件页缓存，不能理解成 `read` 完全不缓存、`mmap` 完全不需要磁盘。映射也不保证所有场景都更快，更不等于一开始就把整个文件读入内存。

教学例子：文件第一个字节是字符 `A`，其字节值是 65。先用 `read` 取得一个字节，同时建立 32 KiB 映射。此时两个接口都能得到 65。若把文件截断到零，先前复制出的 65 仍在，但重新读取映射第一个字节可能触发 SIGBUS，因为对应的文件页已在文件末尾之外。

这里用零长度避免“末尾半页”的特殊处理。不能把规则简化为“读到逻辑文件末尾后的任何一个字节都立即 SIGBUS”。[Linux mmap 手册](https://man7.org/linux/man-pages/man2/mmap.2.html)

## 4. SQLite 为什么有三个文件

SQLite 是**嵌入式数据库**：应用把数据库引擎作为库调用，数据库代码可以直接运行在应用进程内。它不要求像许多服务型数据库那样，先连到独立数据库服务器。SQLite 可以保存会话索引、名称、任务状态或诊断记录，具体用途由应用决定。

以下文件组合适用于 SQLite 的普通 WAL 模式，不是所有 SQLite 数据库都永远存在三个文件。

| 文件 | 作用 | 类比的边界 |
|---|---|---|
| `logs_2.sqlite` | 主数据库文件，保存已合入的数据库页 | 可以理解成主体账本 |
| `logs_2.sqlite-wal` | 预写日志，先记录新数据页版本与提交信息 | 是数据库恢复所需内容，不是可随意删除的调试文本 |
| `logs_2.sqlite-shm` | WAL 索引及协调信息，帮助连接找到页面版本 | 类似查找目录，但活跃使用时不能任意重建 |

WAL 全称 Write-Ahead Logging，中文是预写日志。之所以叫“预写”，是因为变化先写入日志，再于后续合入主数据库。一次操作可能改变多个数据库页，**事务**把它们组成一个整体，提交后应当作为整体对相应读者生效。这里不是逐条 SQL 文本简单追加。

教学假设：主库中某个状态是 10，现在要改为 11。

1. 写入者把包含新值的数据库页版本及提交信息写入 WAL。
2. 在满足相应同步配置要求后，事务提交。主库可能仍保存 10，但新读事务已经可以从 WAL 看到 11。
3. 已开始的读事务可能继续看到自己的旧快照 10。它不会因为另一连接提交就自动改变本次读取视图。
4. **检查点（checkpoint）**在条件允许时，把 WAL 中可合并的页写回主库。已有读者可能限制推进范围。

这样读者与一个写入者可以较好地并发，但普通 WAL 模式仍只有一个写入者，不能推断写线程越多吞吐越高。`-shm` 帮助定位 WAL 中的页面版本，避免每次从头扫描。完整性与断电持久性也要区分，后者还取决于同步设置和存储是否正确兑现承诺。

特别容易混淆的是“日志”一词：`logs_2.sqlite` 装的是应用诊断记录，而 `-wal` 是保护这份数据库更新的事务机制。即使不在意诊断文本，错误操作它的事务文件仍可能让运行中的程序出问题。[SQLite WAL 官方文档](https://www.sqlite.org/wal.html)

## 5. 删除、截断与同名重建

文件名只是目录里的一个名字。**inode（索引节点）**标识文件系统中的文件对象，并记录其属性。打开文件后，程序持有指向对象的引用，不需要每次读写都重新按文件名寻找。更多基础见 [inode 文档](inode-basics.md)。

| 操作 | 名字 | 原文件对象 | 已有打开引用或映射 |
|---|---|---|---|
| 删除名字 `unlink` | 该目录项消失 | 仍可能被进程持有 | 正常本地文件系统中通常仍可用 |
| 截断 `truncate` | 可以不变 | 同一个对象，长度改变 | 超出新长度的整页访问可能 SIGBUS |
| 删除后同名新建 | 相同名字再次出现 | 新对象，可能有不同 inode | 旧进程仍指向旧对象，不自动切换 |

教学例子：A 打开文件对象 I，名字叫 `state-shm`。B 删除这个名字，再新建同名文件 J。A 手里的映射仍指向 I，新进程 C 打开名字时得到 J。路径字符串相同，并不意味着大家访问同一个对象。这对数据库协调很重要。

所以 core 里看到 `(deleted)`，只能说明该映射对应的名字已被解除。可能来自程序正常清理、人工维护或其他操作。正常的删除本身通常不会撤去仍被引用对象的全部内容，不能跳过证据直接断定它就是 SIGBUS 的原因。[Linux unlink 手册](https://man7.org/linux/man-pages/man2/unlink.2.html)

## 6. 共享存储与共享内存的区别

**共享存储**让多台机器通过文件路径访问同一套数据。**共享内存**让相关进程看到同一片受协调的内存内容。名字里都有“共享”，但解决的问题不同。`MAP_SHARED` 也不提供对多步数据库更新的自动事务保护，程序仍需要锁和协调协议。

教学假设：机器 A、B 都能打开共享目录中的一个文件。A 更新某一页后，B 什么时候看见变化，B 是否仍使用本机缓存，以及 A 的锁能否阻止 B 的冲突写入，都依赖文件系统及其实现。能 `ls`、能创建文件，并不证明数据库依赖的所有语义都成立。

SQLite 的普通 WAL 协调要求使用数据库的进程位于同一主机，不能把它当作任意跨机器共享数据库方案。其他日志模式也仍然依赖可靠的锁。迁到本机存储减少跨主机协调问题，但不会自动修复已损坏的数据，也不能防止错误脚本截断文件。

**FUSE** 是 Filesystem in Userspace，意为用户态文件系统。它让一部分文件系统逻辑在用户进程中实现，而不全放在内核。FUSE 可以连接本地或远程存储，它不是 NFS 的别名，更不意味着所有 FUSE 实现都有相同缺陷。

本次实际观察到的挂载类型是 `fuse.dop-fuse`。只能据此确定所走的文件系统接口，不能仅凭类型证明锁错误或映射失效原因。还应区分 `xxx.sqlite-shm` 与系统目录 `/dev/shm`，它们不是同一个东西。前者位于数据库相关目录，名字中的 shm 不代表它一定存放在 `/dev/shm`。

## 7. 转储证据能证明什么

**core dump（核心转储）**保存进程崩溃时的状态，例如寄存器、线程和内存映射。**GDB** 是调试器，可读取这些状态，找出故障信号和访问地址。转储是否生成、保存多少数据受系统配置影响。

可以把定位过程理解为“出错门牌号”和“地址所属街区”的对照。假设映射范围是 `0x100000` 到 `0x108000`，右端不包含，那么故障地址 `0x100000` 就落在这块 32768 字节映射的起点。这些地址是教学数字。

真实事故中，两份转储都显示 SIGBUS，故障地址分别命中 `logs_2.sqlite-shm (deleted)` 映射起点。这个结论定位了访问对象，但没有回答谁删除或截断了文件、何时操作，也没有还原文件系统内部行为。没有解析出函数符号时，不能声称已定位具体源码行。

| 已确认 | 尚未确认 |
|---|---|
| 两份进程以 SIGBUS 结束 | 是否由同一操作触发 |
| 故障地址落在日志库 SHM 映射内 | 对象为何不能继续提供页面 |
| 转储标记对应文件已删除 | 删除者是谁，是否同时截断 |
| 现场挂载为 FUSE 类型 | 该实现是否存在相关缺陷 |

这也不直接证明主会话数据库或全部聊天记录都丢失。进程退出会丢失未保存的内存状态，已持久化记录是否完整则要单独验证。具体转储文件名和地址继续以事故章节为准，本教程不重复刷新其验证时间。

## 8. 跟着图读源码与运行实验

为了直接观察“删除不等于截断”，脚本用两个子进程依次运行两个分支。没有 GPU、SQLite 或模型服务依赖，只有 Python 标准库和 Linux。它是教学实验，不是 Codex 故障复现。

```text
[A] 父进程创建临时目录与 32 KiB 文件，首字节 A
    ↓ 启动一个子进程，等待它退出
[B] 子进程同时 read 一字节、mmap 文件
    ├── [C1] unlink：再读映射成功 → 正常退出
    └── [C2] truncate 到零：复制值还在 → 读映射 → SIGBUS 退出
    ↓ 父进程得到退出状态
[D] 打印结果，运行下一分支，最后清理临时目录
```

图例与“跟着图读源码”合在下表，按真实路径覆盖入口到清理。父子是两个进程，父进程等待期间子进程执行，不把它们伪装成同一线程。

| 步骤 | 图中编号 | 文件、行号、函数 | 输入、输出或状态变化 |
|---|---|---|---|
| 1 | A | [`main`](mmap-sigbus-demo.py#L33) | 创建临时目录和首字节为 65 的文件，扩展为 32768 字节 |
| 2 | A → B | [`subprocess.run`](mmap-sigbus-demo.py#L41) | 把路径和分支名传入子进程，父进程等待，每个分支最多五秒 |
| 3 | B | [入口分支](mmap-sigbus-demo.py#L56) 与 [`child`](mmap-sigbus-demo.py#L14) | 子进程禁用 core，避免教学实验产生大转储 |
| 4 | B | [`mmap` 与 `read`](mmap-sigbus-demo.py#L18) | 得到文件映射和独立字节副本 |
| 5a | C1 | [`os.unlink`](mmap-sigbus-demo.py#L23) | 删除名字，原打开对象仍可读，分支正常关闭映射及文件 |
| 5b | C2 | [`os.ftruncate`](mmap-sigbus-demo.py#L27) | 文件变为零长度，随后映射访问触发 SIGBUS，内核回收子进程资源 |
| 6 | D | [退出状态核对](mmap-sigbus-demo.py#L48) | 父进程报告结果，检查预期信号 |
| 7 | D | [`TemporaryDirectory` 作用域](mmap-sigbus-demo.py#L35) | 两个分支结束后父进程清理目录，信号退出不依赖子进程运行 Python 清理逻辑 |

从仓库根目录运行：

```bash
python3 docs/tools/linux/mmap-sigbus-demo.py
```

2026-11-09 在本机实际运行得到：

```text
Case: unlink.
Before: copied=65, mapped=65.
After unlink: mapped=65.
Return code: 0.
Case: truncate.
Before: copied=65, mapped=65.
After truncate: copied=65.
Reading the mapping now.
Return code: -7.
```

65 是字符 `A` 的字节值。Python 的子进程接口用负信号号表示被信号终止，因此本机 `-7` 表示 SIGBUS。Shell 常用另一套约定报告为 128 加信号号，本机可表现为 135，不能把两种接口的数字直接混淆。

实验不触碰 Codex 文件，不生成 core，父进程正常结束，临时文件已清理。验证了普通本地文件的两种机制，不验证 FUSE 实现、跨机器锁或这次事故的真正触发操作。

## 9. 排查与处理的顺序

先记录原始提示、发生时间和进程版本，再用转储确认信号与访问对象。随后检查对象对应的文件系统、打开引用和相关维护操作，区分“在哪里崩溃”和“为什么变成这样”。没有证据时，不直接归为内存不足、模型问题或硬盘坏了。

需要操作数据库文件时，先停止所有相关写入者，包括后台服务和其他主机使用者，保全主库与伴随文件，再在副本上核验。WAL 可能含已经提交但尚未合入主库的数据，只备份主库或随手删除 WAL 都可能遗漏变化。即使某个 SHM 索引理论上可重建，也不等于可以在仍有连接使用时删除。

调整存储位置是一项修复方案，读取副本和继续保存成功才是对应验证。解释机制、确认根因、完成修复、验证不会复发是不同阶段，不把教学实验成功当作生产修复成功。
